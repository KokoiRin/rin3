协程与结构化并发

suspend 说明函数可以挂起；CoroutineScope 则决定任务归谁所有、何时取消、失败怎样传播。

阅读约定

本章是基于 Kotlin 官方资料整理翻译的结构化精读，不是逐段完整翻译。保留项目阅读所需的核心概念、关键边界和代表性代码，暂缓与当前学习目标关系较弱的高级细节。

本章主线

读协程代码时，不只追踪“在哪个线程执行”，更要追踪 Job 的父子关系、作用域的生命周期和取消路径。

1. suspend 不等于后台线程

suspend fun loadProfile(id: UserId): Profile {
    delay(100) // 挂起当前协程，不阻塞承载它的线程
    return repository.get(id)
}

suspend 表示函数可以暂停并在之后恢复，只能从另一个挂起函数或协程中调用。它本身既不创建协程，也不自动把工作切到后台线程。

2. Scope 是任务所有权

class Presenter(private val scope: CoroutineScope) {
    fun refresh() = scope.launch {
        val profile = loadProfile(currentUserId)
        render(profile)
    }
}

这里最重要的问题是：谁创建 scope，谁在 Presenter 不再需要时取消它？结构化并发让子协程属于某个父作用域，父任务会等待子任务，取消和失败也沿结构传播。

工具含义典型读取方式
launch启动任务，返回 Job关心完成/取消，不直接返回业务值
async并发计算，返回 Deferred稍后用 await() 取得结果
withContext在指定上下文完成一段工作并返回结果用于明确切换 dispatcher
coroutineScope建立子任务作用域离开前等待所有子任务完成

3. 并发要有明确收益

suspend fun loadDashboard(): Dashboard = coroutineScope {
    val user = async { loadUser() }
    val cards = async { loadCards() }
    Dashboard(user.await(), cards.await())
}

只有两个操作彼此独立时，并发才成立。如果 loadCards 需要 user 的结果，就应顺序表达依赖。async 不是让代码“更协程化”的装饰。

4. Dispatcher 决定执行资源

Dispatchers.Default 面向 CPU 计算，Dispatchers.IO 面向 JVM 上的阻塞 I/O，主线程 dispatcher 用于 UI。许多挂起式网络或数据库 API 已经自己管理执行环境，不要在外面机械包一层 withContext(IO)。

5. 取消必须能到达任务

挂起函数通常会配合取消；长时间纯计算循环需要主动检查取消。清理资源放在 finally 中。捕获异常时不要误吞 CancellationException，否则生命周期已经结束的任务仍可能继续工作。

容易误用
  • 使用 GlobalScope 或自己创建永不取消的 Scope，任务失去所有者。
  • 把 launch 当作“发出去就不管”，异常只能在远处爆炸。
  • 在协程中调用阻塞 API，却误以为只要写了 suspend 就不会阻塞线程。
