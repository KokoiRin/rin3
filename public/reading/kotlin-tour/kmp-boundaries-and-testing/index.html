KMP 边界与测试

共享的是能跨平台成立的业务决策、状态与不变量；平台层提供平台能力和事实，测试也沿同一边界分层。

阅读约定

本章是基于 Kotlin 官方资料整理翻译的结构化精读，不是逐段完整翻译。保留项目阅读所需的核心概念、关键边界和代表性代码，暂缓与当前学习目标关系较弱的高级细节。

本章主线

迁移到 commonMain 的单位不是零散函数，而是一个业务闭环：决策、状态变化、规则与验证应尽量留在一起。

1. commonMain 应拥有业务决策

// commonMain
class RefreshPolicy {
    fun decide(cache: CacheState, network: NetworkState): RefreshDecision =
        when {
            cache.isFresh -> RefreshDecision.UseCache
            network.isAvailable -> RefreshDecision.Fetch
            else -> RefreshDecision.ShowOffline
        }
}

这段规则不依赖 Android 或 iOS，且它决定产品行为，适合放在 commonMain。共享层最有价值的部分不是“能编译过去的工具函数”，而是跨平台必须保持一致的决策、状态机和不变量。

2. 平台层提供能力与事实

// commonMain
interface NetworkStatus {
    fun isAvailable(): Boolean
}

// androidMain / iosMain 分别实现
class PlatformNetworkStatus : NetworkStatus {
    override fun isAvailable(): Boolean = platformCheck()
}

“网络是否可用”依赖平台 API，是平台事实；“离线时展示什么”是业务决策。接口让依赖方向保持为：共享业务规则依赖抽象，平台实现提供能力。

3. 接口还是 expect/actual

方式适合代价
公共接口 + 平台实现需要替换实现、注入测试替身，或能力本身是业务依赖需要在组合入口装配
expect/actual小而稳定、天然按平台存在的声明平台实现与声明在编译期绑定

不要为了使用 KMP 而给每个类都做 expect/actual。先问是否真的存在平台差异，再选择最小边界。

4. 测试沿生产边界放置

// commonTest
class RefreshPolicyTest {
    @Test
    fun freshCacheDoesNotRequestNetwork() {
        val decision = RefreshPolicy().decide(
            cache = CacheState(isFresh = true),
            network = NetworkState(isAvailable = true)
        )
        assertEquals(RefreshDecision.UseCache, decision)
    }
}

commonTest 用 kotlin.test 验证共享业务行为，并在配置的多个目标上运行。依赖 Android、JVM 或 iOS API 的行为放到对应平台测试源码集；不要用 JVM 测试假装已经验证 iOS 平台能力。

5. 用业务闭环判断迁移范围

  1. 找出谁做决定，而不只是找“纯函数”。
  2. 列出决定依赖的状态、输入事实和不变量。
  3. 把平台事实收敛为窄接口，留在平台实现。
  4. 把共享决策及其测试一起移入 commonMain/commonTest。
  5. 在各平台组合入口装配，并补平台特有验证。
容易误用
  • 只抽一个接口、移动几个函数，就宣称完成共享；状态和规则仍散落在平台层。
  • 把数据库、系统时间、权限状态等平台事实伪装成共享实现。
  • 只测工具函数，不测试用户可观察到的业务结果。
  • 为了追求最高共享率，牺牲清楚的平台边界。

最后的判断：共享率不是目标，一致的业务行为和清楚的变化边界才是目标。
