Kotlin 项目与 Gradle

先读懂构建脚本、模块、目标与源码集，再进入业务代码；目录位置本身就是一条编译规则。

阅读约定

本章是基于 Kotlin 官方资料整理翻译的结构化精读，不是逐段完整翻译。保留项目阅读所需的核心概念、关键边界和代表性代码，暂缓与当前学习目标关系较弱的高级细节。

本章主线

一个 Kotlin 文件能使用哪些 API、会编译到哪些平台，不只由代码决定，还由它所在的模块、源码集和依赖配置决定。

1. 先建立项目地图

真实项目的第一层语言不是 Kotlin 语法，而是构建结构。通常先找 settings.gradle.kts，确认项目包含哪些模块；再看各模块的 build.gradle.kts，确认插件、目标、源码集和依赖。

模块

独立构建和依赖的边界，例如应用、共享业务模块、基础库。

目标（target）

代码要编译到哪里，例如 JVM、Android、iOS 或 JS。

源码集（source set）

一组拥有相同目标、依赖与编译选项的源码。

依赖

决定当前源码集能看见哪些库和 API。

2. 读懂一段 KMP 构建脚本

kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies {
            implementation(libs.kotlinx.coroutines.core)
        }
        androidMain.dependencies {
            implementation(libs.androidx.lifecycle.runtime)
        }
        commonTest.dependencies {
            implementation(kotlin("test"))
        }
    }
}

这段配置可以按三个问题阅读：

  1. 编译到哪里？ Android、iPhone 真机和 iOS 模拟器。
  2. 什么代码共享？ commonMain 会编译到所有已声明目标。
  3. 能力从哪里来？ 协程是跨平台依赖；Android 生命周期库只属于 androidMain。
关键方向

平台源码集可以使用 commonMain 的声明；commonMain 不能反向使用平台源码集的声明。这个单向关系是理解 KMP 边界的起点。

3. 目录位置就是能力范围

commonMain 中的代码必须能在全部目标上成立，因此不能直接使用 java.io.File、Android Context 或 Apple Foundation 等单平台 API。平台能力应留在对应源码集，再通过接口或 expect/actual 接到共享代码。

中间源码集（例如 iosMain、appleMain）用于“只在一组平台之间共享”。先理解默认层级，不必一开始手工搭复杂的源码集树。

4. 不要把 Gradle 当作依赖清单

构建脚本同时表达架构：哪些模块允许互相引用、哪些能力可以跨平台、测试会在哪些目标运行。遇到某个符号“明明存在却引用不到”，先检查模块和源码集可见性，再怀疑 import。

容易误用
  • 看到新版本就盲目升级插件；Kotlin、Gradle、AGP 和 IDE 存在兼容关系。
  • 把平台库加到 commonMain，然后试图用条件分支绕过编译限制。
  • 为了“整洁”过早自定义源码集层级，增加理解和维护成本。
下周项目对照

不要另写玩具代码，直接在项目里取证

先搜索：settings.gradle.kts、build.gradle.kts、sourceSets、commonMain、implementation

  1. 选一个真实文件，用一句话写出它在业务流程中的职责。
  2. 圈出本章概念的一个真实用法，写清输入、输出与所有者。
  3. 沿调用方向再追一层，确认它的生命周期或依赖边界。
  4. 找一条对应测试；如果没有，写下最值得补的可观察行为。
读完自测

合上正文，回答这三个问题

  1. 本章最重要的边界是什么？
  2. 项目里哪个类型或文件最能体现这个边界？
  3. 如果把这个边界拿掉，最可能出现什么错误？
