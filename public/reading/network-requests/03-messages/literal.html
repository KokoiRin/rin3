阅读前的版本与适用范围校注（3 条）

原文“只有 POST、PUT、PATCH 请求有消息体”过于绝对。是否允许、有什么语义，需要按具体方法与规范判断；例如 OPTIONS 可以携带内容，而 GET 内容没有通用定义的语义，不应据此随意给 GET 加请求体。参见 RFC 9110，第 9.3 节。

authority 在这里是 URI 中定位服务器的组成部分，不是登录授权。HTTP/1.x 的普通源站请求常用路径加 Host，HTTP/2 则使用 :authority 等伪标头。

原文的“六条连接”是浏览器中常见的实现策略，不是 HTTP 的通用限制。HTTP/2 解决 HTTP 层的串行等待，仍可能受到 TCP 丢包造成的跨流阻塞。具体客户端的连接数和池配置，应查看所用网络库。

HTTP 消息是 HTTP 协议中服务器与客户端交换数据的机制。消息有两种：客户端发送的请求，用来触发服务器上的操作；以及响应，即服务器针对请求发送的答复。

开发者很少、甚至从不从零构造 HTTP 消息。浏览器、代理或 Web 服务器等应用，使用专门的软件可靠而高效地创建 HTTP 消息。消息的创建或转换方式，由浏览器中的 API、代理或服务器的配置文件，以及其他接口控制。

在 HTTP/2 之前的 HTTP 协议版本中，消息基于文本；熟悉格式之后，阅读和理解相对直接。在 HTTP/2 中，消息被包裹在二进制帧中，阅读起来稍难一些。不过，协议的底层语义相同，因此你可以基于 HTTP/1.x 消息的文本格式，学习 HTTP 消息的结构和含义，并将这种理解应用到 HTTP/2 及后续版本。

为方便阅读，本指南采用 HTTP/1.1 消息，并用 HTTP/1.1 格式解释 HTTP 消息的结构。最后一节会指出描述 HTTP/2 时可能需要了解的一些差异。

备注：例如，你可以在浏览器开发者工具的 Network 标签页中查看 HTTP 消息，也可以使用 curl 等命令行工具，将 HTTP 消息输出到控制台。

HTTP 消息的组成

为了理解 HTTP 消息如何工作，我们来查看 HTTP/1.1 消息并分析其结构。下图展示了 HTTP/1.1 消息的样子：

请求和响应具有相似的结构：

  1. 起始行是一行文本，描述 HTTP 版本，以及请求方法或请求结果。
  2. 一组可选的 HTTP 标头，包含描述消息的元数据。例如，资源请求可以列出允许的资源格式；响应则可以用标头指出实际返回的格式。
  3. 一个空行，表示消息的元数据已经结束。
  4. 一个可选的消息体，包含与消息关联的数据。这可能是请求中要发送给服务器的 POST 数据，也可能是响应中返回给客户端的某个资源。消息是否包含消息体，由起始行和 HTTP 标头决定。

HTTP 消息的起始行和标头，合称请求的头部（head）；其后承载内容的部分称为消息体（body）。

HTTP 请求

来看下面的 HTTP POST 请求示例：用户在网页上提交表单后，会发送这样的请求。

http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 49

name=FirstName+LastName&email=bsmth%40example.com

HTTP/1.x 请求中的起始行（上例中的 POST /users HTTP/1.1）称为“请求行”，由三部分组成：

http
<method> <request-target> <protocol>
<method>

HTTP 方法（也称为 HTTP 动词）是一组已定义词语中的一个，用来描述请求的含义和期望的结果。例如，GET 表示客户端希望接收一个资源；POST 表示客户端正在向服务器发送数据。

<request-target>

请求目标通常是绝对或相对 URL，其形式取决于请求的上下文。请求目标的格式由所使用的 HTTP 方法和请求上下文决定。下面的请求目标一节会更详细地介绍。

<protocol>

HTTP 版本定义消息其余部分的结构，并指示期望响应使用的版本。这里几乎总是 HTTP/1.1，因为 HTTP/0.9 和 HTTP/1.0 已经过时。在 HTTP/2 及更高版本中，消息不包含协议版本，因为版本在建立连接时已经确定。

请求目标

请求目标有几种表示方式，其中最常见的是“源站形式”（origin form）。下面列出各种目标形式及其使用场景：

  1. 在源站形式中，接收方将绝对路径与 Host 标头中的信息组合起来。路径后面可以附加查询字符串，提供额外信息，通常采用 key=value 格式。这种形式用于 GET、POST、HEAD 和 OPTIONS 方法：

    http
    GET /en-US/docs/Web/HTTP/Guides/Messages HTTP/1.1

  2. 绝对形式是一个包含 authority（授权信息部分）的完整 URL，连接代理时与 GET 一起使用：

    http
    GET https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages HTTP/1.1

  3. authority 形式是由冒号（:）分隔的 authority 与端口。它只在建立 HTTP 隧道时与 CONNECT 方法一起使用：

    http
    CONNECT developer.mozilla.org:443 HTTP/1.1

  4. 星号形式只与 OPTIONS 一起使用，用来表示整个服务器（*），而不是某个具名资源：

    http
    OPTIONS * HTTP/1.1

请求标头

标头是随请求发送的元数据，位于起始行之后、消息体之前。在上面的表单提交示例中，它们对应以下几行消息：

http
Host: example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 49

在 HTTP/1.x 中，每个标头都由一个不区分大小写的字符串、一个冒号（:）和一个值组成；值的格式取决于具体标头。整个标头，包括它的值，都位于同一行。在某些情况下，这一行可能很长，例如 Cookie 标头。

有些标头专门用于请求，另一些可以同时用于请求和响应，或者还可以归入更具体的类别：

  • 请求标头为请求提供额外的上下文，或者增加服务器应如何处理它的额外逻辑，例如条件请求。
  • 如果消息有消息体，请求会发送表示标头，描述消息数据的原始形式及其采用的编码。这样，接收方就知道如何重建资源，使其恢复到网络传输之前的形式。

请求体

请求体是请求中向服务器携带信息的部分。只有 PATCH、POST 和 PUT 请求有消息体。在表单提交示例中，下面这一部分就是消息体：

http
name=FirstName+LastName&email=bsmth%40example.com

表单提交请求的消息体包含少量以 key=value 键值对表示的信息，但请求体也可以包含服务器期望的其他类型的数据：

json
{
  "firstName": "Brian",
  "lastName": "Smith",
  "email": "bsmth@example.com",
  "more": "data"
}

或者包含由多个部分组成的数据：

http
--delimiter123
Content-Disposition: form-data; name="field1"

value1
--delimiter123
Content-Disposition: form-data; name="field2"; filename="example.txt"

Text file contents
--delimiter123--

HTTP 响应

响应是服务器为答复请求而发送回来的 HTTP 消息。响应让客户端知道请求的结果。下面是一个 HTTP/1.1 响应示例，用来答复创建了新用户的 POST 请求：

http
HTTP/1.1 201 Created
Content-Type: application/json
Location: http://example.com/users/123

{
  "message": "New user created",
  "user": {
    "id": 123,
    "firstName": "Example",
    "lastName": "Person",
    "email": "bsmth@example.com"
  }
}

响应中的起始行（上面的 HTTP/1.1 201 Created）称为“状态行”，由三部分组成：

http
<protocol> <status-code> <reason-phrase>
<protocol>

消息的 HTTP 版本。

<status-code>

数字形式的状态码，指出请求成功还是失败。常见状态码有 200、404 和 302。

<reason-phrase> 可选

状态码后面的可选文本，是对状态的简短文字描述，仅供参考，用来帮助人们理解请求结果。原因短语有时会放在括号里，例如“201 (Created)”，以表明它是可选的。

响应标头

响应标头是随响应发送的元数据。在 HTTP/1.x 中，每个标头都由一个不区分大小写的字符串、一个冒号（:）和一个值组成；值的格式取决于使用的标头。

与请求标头一样，响应中可以出现许多不同的标头，它们可以分为以下类别：

  • 响应标头提供关于消息的额外上下文，或者增加客户端应如何发起后续请求的额外逻辑。例如，Server 等标头包含服务器软件信息，而 Date 包含响应生成的时间。还有描述返回资源的信息，例如内容类型（Content-Type），或者应如何缓存它（Cache-Control）。
  • 如果消息有消息体，表示标头就会描述消息数据的形式及其采用的编码。例如，同一资源可以采用 XML 或 JSON 等特定媒体类型的格式，针对某种书面语言或地理区域进行本地化，并且／或者为传输进行压缩或其他编码。这样，接收方就知道如何重建资源，使其恢复到网络传输之前的形式。

响应体

发给客户端的大多数响应消息都包含响应体。请求成功时，响应体包含客户端通过 GET 请求索取的数据。如果客户端请求存在问题，响应体通常会描述失败原因，并提示这是永久性问题还是临时问题。

响应体可以是：

  • 单资源消息体，由 Content-Type 和 Content-Length 两个标头定义；也可以长度未知、采用分块编码，此时 Transfer-Encoding 被设置为 chunked。
  • 多资源消息体，包含多个部分，每个部分承载一项不同的信息。多部分消息体通常与 HTML 表单有关，但也可以用于回应范围请求。

如果响应的状态码已经足以答复请求，无需包含消息内容，例如 201 Created 或 204 No Content，就不会有消息体。

HTTP/2 消息

HTTP/1.x 使用基于文本的消息，阅读和构造都很直接，但这也带来一些缺点。可以使用 gzip 或其他压缩算法压缩消息体，却不能压缩标头。在客户端与服务器的交互中，标头往往相似或相同，却仍然在同一连接上的连续消息中反复出现。已经有许多非常高效的重复文本压缩方法，因此这里有大量节省带宽的机会未被利用。

HTTP/1.x 还有一个称为队头阻塞（head-of-line blocking，HOL blocking）的问题：客户端必须等到服务器响应，才能发送下一个请求。HTTP 流水线尝试绕过这一问题，但由于支持不佳且实现复杂，它很少被使用，也难以正确实现。要并发发送请求，就需要打开多个连接；而由于 TCP 慢启动，热连接（已经建立且繁忙的连接）比冷连接更高效。

在 HTTP/1.1 中，如果想并行发出两个请求，就必须打开两个连接：

这意味着浏览器能够同时下载和渲染的资源数量受到限制，通常上限为 6 个并行连接。

HTTP/2 允许通过单个 TCP 连接，同时处理多个请求和响应。具体方式是将消息封装为二进制帧，并通过连接上带编号的流（stream）发送请求和响应。数据帧与标头帧分开处理，使标头可以通过 HPACK 算法压缩。在同一个 TCP 连接上同时处理多个请求，称为多路复用。

请求不必依次完成：例如，流 9 不需要等待流 7 结束。多个流的数据通常在连接上交错传输，因此客户端可以同时接收流 9 和流 7。协议提供了为每个流或资源设置优先级的机制。通过不同流发送时，低优先级资源占用的带宽比高优先级资源少；如果存在应当优先处理的关键资源，也可以让这些资源实际上在同一连接上依次发送。

总体而言，虽然相较于 HTTP/1.x 增加了许多改进和抽象，开发者用于发起请求的 API 几乎不需要改变，就可以改用 HTTP/2。当浏览器与服务器都支持 HTTP/2 时，就会自动启用并使用它。

伪标头

HTTP/2 消息的一项显著变化是使用伪标头。HTTP/1.x 使用消息起始行，而 HTTP/2 使用以 : 开头的特殊伪标头字段。请求中的伪标头包括：

  • :method：HTTP 方法。
  • :scheme：目标 URI 的 scheme（协议方案）部分，通常为 HTTP(S)。
  • :authority：目标 URI 的 authority 部分。
  • :path：目标 URI 的路径和查询部分。

响应只有一个伪标头，即 :status，用于提供响应的状态码。

我们可以使用 nghttp 发起 HTTP/2 请求，获取 example.com，它会以更易读的形式输出请求。可以使用下面的命令，其中 -n 选项丢弃下载的数据，-v 表示详细输出，显示帧的接收与发送情况：

bash
nghttp -nv https://www.example.com

向下查看输出，可以看到每个发送和接收的帧所对应的时间：

[  0.123] <send|recv> <frame-type> <frame-details>

不必深入讨论输出的每个细节，但请留意格式为 [ 0.123] send HEADERS frame ... 的 HEADERS 帧。在发送标头之后，你会看到以下几行：

http
[  0.447] send HEADERS frame ...
          ...
          :method: GET
          :path: /
          :scheme: https
          :authority: www.example.com
          accept: */*
          accept-encoding: gzip, deflate
          user-agent: nghttp2/1.61.0

如果已经熟悉 HTTP/1.x，这些内容看起来应该很熟悉，本指南前面介绍的概念仍然适用。这是请求 example.com 的 GET 请求所对应的二进制帧，由 nghttp 转换为可读形式。继续向下查看命令输出，会在从服务器接收的某个流中看到 :status 伪标头：

http
[  0.433] recv (stream_id=13) :status: 200
[  0.433] recv (stream_id=13) content-encoding: gzip
[  0.433] recv (stream_id=13) age: 112721
[  0.433] recv (stream_id=13) cache-control: max-age=604800
[  0.433] recv (stream_id=13) content-type: text/html; charset=UTF-8
[  0.433] recv (stream_id=13) date: Fri, 13 Sep 2024 12:56:07 GMT
[  0.433] recv (stream_id=13) etag: "3147526947+gzip"
...

如果去掉消息中的时间和流 ID，内容应该会更加熟悉：

http
:status: 200
content-encoding: gzip
age: 112721

进一步探讨消息帧、流 ID 以及连接管理超出了本指南的范围。不过，为了理解和调试 HTTP/2 消息，本文提供的知识和工具应当已经能让你做好准备。

结论

本指南概述了 HTTP 消息的组成，并用 HTTP/1.1 格式进行说明。我们还探讨了 HTTP/2 消息分帧：它在 HTTP/1.x 语法和底层传输协议之间引入了一层，但没有从根本上改变 HTTP 的语义。HTTP/2 通过支持请求多路复用，解决 HTTP/1.x 中存在的队头阻塞问题。

HTTP/2 仍然存在一个问题：虽然协议层面的队头阻塞得到解决，但 TCP 内部（传输层）的队头阻塞仍会造成性能瓶颈。HTTP/3 用构建在 UDP 之上的 QUIC 协议代替 TCP，解决这一限制。这个变化提高了性能，缩短连接建立时间，并增强了网络状况恶化或不可靠时的稳定性。HTTP/3 保留了相同的 HTTP 核心语义，因此请求方法、状态码和标头等特性，在三个主要 HTTP 版本中保持一致。

如果理解了 HTTP/1.1 的语义，就已经具备理解 HTTP/2 和 HTTP/3 的坚实基础。主要区别在于这些语义在传输层上如何实现。通过本指南的示例和概念，现在你应该能够使用 HTTP，理解消息的含义，以及应用如何通过 HTTP 发送和接收数据。
