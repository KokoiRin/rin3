HTTP/1.x 的连接管理

Connection management in HTTP/1.x · Mozilla Contributors

编者导读 · 不属于原文

为什么请求完了还保留连接，复用连接为什么能更快？

本篇聚焦 HTTP/1.x。持久连接、流水线和 HTTP/2 多路复用是三件不同的事；理解这个区别，比记住某个连接数更重要。

阅读前的版本与适用范围校注（3 条）

TLS/1.0、域名分片和流水线的段落包含历史背景。不要把 TLS/1.0 当作当前配置建议；不要仅凭本文就给项目增加多个域名或强制连接数。HTTP/2、HTTP/3 的连接行为应结合后面的版本篇理解。

幂等指同一请求重复执行，其预期服务器效果与执行一次相同，并不保证每次响应内容相同。故障后能否自动重试，还要判断方法语义、请求体能否重放，以及服务端是否已经执行。参见 RFC 9110，第 9.2.2 节。

HTTP/1.1 的 Keep-Alive / Connection 标头与 TCP keepalive 不是同一层的机制。HTTP/2 多路复用也不是简单打开 HTTP/1.1 流水线。

连接管理是 HTTP 中的重要主题：建立和维护连接，会显著影响网站与 Web 应用的性能。HTTP/1.x 有几种模型：短连接、持久连接和 HTTP 流水线。

HTTP 主要依靠 TCP 作为传输协议，在客户端与服务器之间提供连接。HTTP 早期只使用一种模型处理这些连接：短连接。每次需要发送请求时创建一条新连接，收到答复后就关闭。

这个模型天生存在性能限制：每次建立 TCP 连接都要消耗资源，客户端与服务器还要先交换若干条消息。发送请求时，网络延迟和带宽都会影响性能。现代网页通常需要十几个甚至更多请求，才能取得所需内容，因此这种早期模型的效率不高。

HTTP/1.1 中出现了两种更新的模型。持久连接模型在连续请求之间保持连接打开，减少建立新连接所需的时间。HTTP 流水线模型更进一步，无需等待答复就连续发送多个请求，从而减少网络中的大量延迟。

备注：HTTP/2 增加了其他连接管理模型。

这里的连接管理针对两个相邻节点之间的一段连接，也就是逐跳，而非端到端。客户端到第一个代理所用的模型，可以与代理到目标服务器，或代理到另一代理所用的模型不同。Connection、Keep-Alive 等连接管理标头都是逐跳标头，中间节点可以修改其值。

一个相关主题是 HTTP 连接升级：将 HTTP/1.1 连接升级为不同的协议，例如 TLS/1.0、WebSocket，甚至明文 HTTP/2。关于这种协议升级机制，其他文档有更详细的介绍。

短连接

HTTP 最初的模型，也是 HTTP/1.0 的默认模型，是短连接。每个 HTTP 请求都在自己的连接上完成；这意味着每次 HTTP 请求之前都会发生 TCP 握手，而且这些操作按顺序进行。

TCP 握手本身就需要时间。而且 TCP 连接会逐渐适应负载，持续使用、已经预热的连接更高效。短连接每次都从新的冷连接开始，无法利用这个特性，因此性能不如最佳状态。

这是 HTTP/1.0 使用的默认模型：没有 Connection 标头，或其值被设为 close 时，就使用这种模型。在 HTTP/1.1 中，只有发送值为 close 的 Connection 标头时，才会使用这种模型。

备注：除非要与不支持持久连接的非常老旧的系统打交道，否则没有充分理由使用这种模型。

持久连接

短连接的主要开销来自两处：建立连接要花时间，TCP 连接也要使用一段时间、成为热连接后，性能才会改善。为缓解这些问题，HTTP/1.1 出现之前就已经有了持久连接，也叫 keep-alive 连接。

持久连接会保持打开一段时间，供多个请求复用。这样既省去了新的 TCP 握手，也能利用 TCP 持续传输时的性能优势。不过，它不会永久保持打开：空闲一段时间后，连接会关闭。服务器可以用 Keep-Alive 标头指定应保持连接的最短时间。

持久连接也有缺点：即使空闲，它们仍然消耗服务器资源；在高负载下，还可能遭受 DoS 攻击。这时，使用一空闲就关闭的非持久连接，可能获得更好的性能。

HTTP/1.0 连接默认不是持久连接。将 Connection 设置为 close 以外的值，通常是 retry-after，就会使它们成为持久连接。

在 HTTP/1.1 中，持久连接是默认行为，不再需要这个标头。不过，为了防备需要回退到 HTTP/1.0 的情况，仍经常会添加它。

HTTP 流水线

备注：现代浏览器默认不启用 HTTP 流水线：

  • 有缺陷的代理仍然很常见，它们会导致奇怪且不稳定的行为，Web 开发者难以预见，也不容易诊断。
  • 流水线不容易正确实现。资源大小、实际的 RTT 和有效带宽，都会直接影响它能带来多大改善。如果不了解这些条件，重要消息可能反而排在不重要的消息后面；而且页面布局过程中，哪些消息“重要”也会变化。因此，多数情况下，流水线只能带来有限的改进。
  • 流水线会受到队头阻塞的影响。

由于这些原因，流水线已经被 HTTP/2 使用的更好算法——多路复用——取代。

默认情况下，HTTP 请求按顺序发出。只有收到当前请求的响应后，才发送下一个请求。由于受到网络延迟和带宽限制的影响，下一个请求可能过很久才会被服务器看到。

流水线是在同一条持久连接上连续发送请求、而不等待答复的过程。这样可以避免连接等待造成的延迟。理论上，如果能将两个 HTTP 请求装进同一个 TCP 消息，也能提高性能。尽管 HTTP 请求的体积需求不断增加，典型的 MSS（最大报文段大小）仍足够容纳若干个简单请求。

并非所有 HTTP 请求都适合流水线。只有幂等方法，也就是 GET、HEAD、OPTIONS、TRACE、PUT 和 DELETE，才能安全重放。这样，发生故障后，就可以重新发送流水线中的请求。

如今，每个符合 HTTP/1.1 的代理和服务器都应该支持流水线，但实际上很多实现存在限制；这是现代浏览器都不默认启用它的重要原因。

域名分片

备注：除非有非常具体且迫切的需求，否则不要使用这种已经不推荐的技术，应改用 HTTP/2。在 HTTP/2 中，域名分片不再有用：HTTP/2 连接能够很好地处理没有优先级的并行请求。域名分片甚至会损害性能。大多数 HTTP/2 实现使用称为连接合并（connection coalescing）的技术，来抵消可能存在的域名分片。

HTTP/1.x 连接会将请求串行化，即使没有顺序要求，如果可用带宽不够大，也无法达到最优。为解决这个问题，浏览器向每个域名打开多个连接，并行发送请求。默认数量曾经是 2～3 个，现在更常见的是 6 个并行连接。尝试超过这个数量，有触发服务器端 DoS 防护的风险。

如果服务器希望网站或应用响应更快，可以促使浏览器建立更多连接。例如，不将所有资源都放在同一个域名（比如 www.example.com）下，而是分散到 www1.example.com、www2.example.com、www3.example.com 等多个域名。这些域名都解析到同一台服务器，但 Web 浏览器会为每个域名打开 6 个连接。在这个例子中，连接数就增加到 18 个。这种技术称为域名分片。

结论

改善连接管理，可以显著提高 HTTP 性能。对于 HTTP/1.1 或 HTTP/1.0，使用持久连接——至少在连接空闲之前保持它——能带来最佳性能。不过，流水线的失利促使人们设计更优秀的连接管理模型，这些模型已经被纳入 HTTP/2。
