HTTPS 除了加密，还怎样确认对面真的是目标服务器？

先抓住加密、完整性和身份认证这三件事。TLS 层的客户端证书认证，与业务接口里的登录 token 不是同一个概念。

阅读前的版本与适用范围校注（2 条）

原文把密码套件概括为包含密钥协商、认证、加密等算法，这对理解早期版本有帮助，但 TLS 1.3 已把认证和密钥交换机制与密码套件分离。握手中的密钥也不是简单在网络上传送一把裸密钥。参见 RFC 8446，第 1.2 节。

混合内容、自动升级请求、HSTS 预加载等段落描述的是浏览器行为。原生 Android 网络库是否采用类似策略，需要分别确认，不能假设与浏览器一致。证书校验失败时，关闭校验并不能解决身份可信的问题。

传输层安全（Transport Layer Security，TLS）是一种协议，用来让客户端在不可信的网络上安全地与服务器通信。它最常见的用途，是保护 Web 上的 HTTP 连接；这样得到的协议就是 HTTPS。

TLS 从三个方面保护网络连接：

  • 加密：客户端与服务器交换的数据在传输过程中经过加密，因此攻击者无法读取。
  • 完整性：数据在双方之间传输时，攻击者不能偷偷修改内容而不被发现。
  • 身份认证：双方都能向对方证明，自己确实是所声称的实体。在 Web 上，通常由服务器向客户端证明身份；客户端一般不向服务器证明身份。

特别是，HTTPS 可以防御中间人（MITM）攻击。在这种攻击中，攻击者插入用户浏览器与其连接的服务器之间，读取并修改双方交换的流量。

浏览器认为，通过 HTTPS 提供的页面构成安全上下文。许多功能强大的 Web API，只能由运行在安全上下文中的代码使用。

所有网站都应通过 HTTPS 提供全部页面和子资源，并实施服务器身份认证。

TLS 握手

客户端通过 TLS 连接服务器时，会先进行握手，确定协议所需的安全参数：

  • 客户端与服务器就使用哪个 TLS 版本达成一致。当前 TLS 版本为 1.3（RFC 8446），也是使用最广泛的版本。一些网站仍在使用 TLS 1.2，而 TLS 1.1 和 1.0 已经不应继续使用。
  • 客户端与服务器就要使用的密码套件达成一致；它定义双方用于密钥协商、身份认证、加密和消息认证的算法。
  • 双方可以相互认证。客户端向服务器证明身份，称为客户端认证；除了特定应用，Web 上很少使用。相反，服务器向客户端证明身份，是 Web 安全的基础。
  • 客户端与服务器就用于加密和解密消息的秘密密钥达成一致。

握手之后，客户端与服务器使用秘密密钥加密和解密所有消息，包括 HTTP 标头与消息体。

配置 TLS

选择正确的 TLS 服务器配置，会显著影响连接的安全性。特别是，它决定使用的 TLS 版本和密码算法。如果需要配置自己的服务器，可以参考 Mozilla 的 TLS 推荐配置等资源。

Mozilla 还提供了 TLS 配置生成器，可以为许多不同的 Web 服务器生成配置文件。

服务器身份认证

网站要支持服务器身份认证，就必须有数字证书。证书中包含与网站私钥配对的公钥，以及相应的数字签名。它把密钥与网站域名绑定起来，让浏览器能确认自己确实连接到了“https://example.com”这样的网站。

Let's Encrypt 是一家广泛使用的非营利证书颁发机构，提供免费的 TLS 证书。

现代网站托管服务会默认或通过配置选项，为你提供 HTTPS 支持。在这种情况下，托管服务很可能会代你管理证书并配置服务器。

混合内容

网站不仅应当对主文档使用 HTTPS，也应当对加载的所有子资源使用 HTTPS，例如脚本、样式表、图片和字体。如果网站通过 HTTPS 加载主文档，却通过 HTTP 加载其中任何子资源，就称为混合内容。

例如，从 https://example.org 提供的文档如果包含以下内容，就会构成混合内容：

html
<img src="http://example.org/my-image.png" />

混合内容中的子资源得不到 HTTPS 保护。攻击者不仅可能读取它们，还可能修改它们，进而破坏整个页面的完整性。例如，攻击者可以改写脚本，让它执行有害操作。图片等资源虽然危险程度较低，也可能被改动，用来迷惑或误导用户。

因此，浏览器不允许安全页面加载不安全的子资源。它们会根据子资源的类型，将加载请求升级为 HTTPS，或者彻底阻止请求。

如果无法修改代码，使其从 HTTPS URL 加载资源，例如 HTML 已经归档，那么服务器可以设置包含 upgrade-insecure-requests 指令的内容安全策略，浏览器就会自动将这些请求升级为 HTTPS。

更多细节请参阅混合内容。

升级 HTTP 连接

即使网站只通过 HTTPS 提供服务，用户仍可能通过 HTTP 请求它，例如在地址栏中输入 http://example.org。为了让网站在这种情况下也能正常工作，应监听 HTTP 请求，并使用 301 Moved Permanently 响应，重定向到 HTTPS 版本。

不过，这给了攻击者拦截最初交互、阻止升级到 HTTPS 的机会。这有时称为 SSL 剥离攻击；SSL 是 TLS 的前身。

为降低这种风险，服务器还应发送 Strict-Transport-Security 响应标头，也就是 HSTS。它要求客户端使用 HTTPS。之后即使用户输入 HTTP URL，浏览器也会直接通过 HTTPS 连接。

使用 HSTS 后，除浏览器第一次尝试连接网站之外，可以防止 SSL 剥离攻击。由于 HSTS 会过期，浏览器中的 HSTS 记录过期后的第一次连接也属于例外。为了在首次连接或 HSTS 记录过期时仍保护网站，Chrome 维护了一份称为 HSTS 预加载列表的域名清单。如果域名在清单中，Chrome 就始终将 HTTP 请求升级为 HTTPS，效果相当于服务器已经发送过 HSTS 标头。Safari 和 Firefox 也有类似行为，它们使用从 Chrome 清单衍生的列表。
