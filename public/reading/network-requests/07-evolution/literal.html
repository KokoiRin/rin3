HTTP 的演进

Evolution of HTTP · Mozilla Contributors

编者导读 · 不属于原文

HTTP/2 和 HTTP/3 到底改变了什么，又保留了什么？

把前面学到的连接和消息放回历史中看：HTTP/1.1 复用连接，HTTP/2 多路复用，HTTP/3 改用 QUIC。首次阅读可以略读历史 API 扩展，重点看三个版本的连接与传输差异。

阅读前的版本与适用范围校注（3 条）

本文中的网站使用比例对应原文标注的 2022 年等历史时点，不代表今天的采用率。SSL、DNT、旧扩展的出现史也不是今天的配置清单。

原文说 QUIC 针对每条流独立进行丢包检测与重传，是概念化表述。更准确地说，丢包检测在 QUIC 传输机制中完成；各流独立、有序地交付数据，某条流的缺失数据不必阻止其他流的数据交付。不同流仍共享连接的拥塞控制等资源。参见 RFC 9000，第 2 节。

HTTP/3 定义于 RFC 9114。不能把正文中 HTTP/3 的“下一个版本”或概览篇的“QUIC 试验”理解为尚未标准化。

HTTP（超文本传输协议）是万维网的底层协议。Tim Berners-Lee 及其团队在 1989～1991 年间开发了它。此后，HTTP 经历了许多变化，在保持简单性的同时塑造了灵活性。继续阅读，了解 HTTP 如何从一种为半可信实验室环境交换文件而设计的协议，演变为承载高分辨率和三维图像、视频的现代互联网复杂体系。

万维网的发明

1989 年，Tim Berners-Lee 在 CERN 工作期间，撰写了一份提案，希望在互联网上构建超文本系统。它最初名为 Mesh，后来在 1990 年实现时改名为 World Wide Web（万维网）。它建立在已有的 TCP 和 IP 协议之上，由四个基本部分组成：

  • 一种表示超文本文档的文本格式，即超文本标记语言（HTML）。
  • 一种交换这些文档的协议，即超文本传输协议（HTTP）。
  • 一个用于显示和编辑这些文档的客户端，即第一款 Web 浏览器 WorldWideWeb。
  • 一个提供文档访问的服务器，即早期版本的 httpd。

这四个基本部分在 1990 年底完成。到 1991 年初，第一批位于 CERN 之外的服务器已经开始运行。1991 年 8 月 6 日，Tim Berners-Lee 在公开的 alt.hypertext 新闻组中发帖。如今，这被视为万维网作为公共项目的正式起点。

早期使用的 HTTP 协议非常简单。它后来被称为 HTTP/0.9，有时也叫单行协议。

HTTP/0.9：单行协议

HTTP 最初的版本没有版本号；后来为了与后续版本区别，才称为 0.9。HTTP/0.9 极其简单：请求只有一行，以唯一可用的方法 GET 开头，后跟资源路径。它不包含完整 URL，因为一旦已经连接到服务器，就不再需要协议、服务器和端口信息。

http
GET /my-page.html

响应也极其简单：只包含文件本身。

html
<html>
  A text-only web page
</html>

与后续版本不同，它没有 HTTP 标头。这意味着只能传输 HTML 文件。也没有状态码或错误码。如果出现问题，就生成一个专门的 HTML 文件，在其中包含供人阅读的问题描述。

HTTP/1.0：建立可扩展性

HTTP/0.9 的能力非常有限，但浏览器和服务器很快让它变得更通用：

  • 每个请求都会发送版本信息，在 GET 行末尾追加 HTTP/1.0。
  • 响应开头也会发送一行状态码，让浏览器本身识别请求成功还是失败，并相应调整行为，例如以某种特定方式更新或使用本地缓存。
  • 请求与响应都引入了 HTTP 标头的概念。这样就能传输元数据，协议因此变得非常灵活且可扩展。
  • 借助 Content-Type 标头，可以传输纯 HTML 文件之外的文档。

这时，典型的请求和响应如下所示：

http
GET /my-page.html HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)

HTTP/1.0 200 OK
Date: Tue, 15 Nov 1994 08:12:31 GMT
Server: CERN/3.0 libwww/2.17
Content-Type: text/html

<HTML>
A page with an image
  <IMG SRC="/my-image.gif">
</HTML>

随后建立第二条连接，并发出获取图片的请求，及其对应响应：

http
GET /my-image.gif HTTP/1.0
User-Agent: NCSA_Mosaic/2.0 (Windows 3.1)

HTTP/1.0 200 OK
Date: Tue, 15 Nov 1994 08:12:32 GMT
Server: CERN/3.0 libwww/2.17
Content-Type: text/gif

(image content)

在 1991～1995 年间，这些功能通过“试试看”的方式引入。服务器与浏览器增加一项功能，再观察它是否得到采用。互操作问题很常见。为了处理这些问题，一份描述通行做法的信息性文档于 1996 年 11 月发布，即 RFC 1945，它定义了 HTTP/1.0。

HTTP/1.1：标准化的协议

与此同时，正式的标准化工作也在进行，与 HTTP/1.0 的各种不同实现并行发展。HTTP 第一个标准化版本 HTTP/1.1 于 1997 年初发布，距离 HTTP/1.0 仅几个月。

HTTP/1.1 澄清了歧义，并引入了许多改进：

  • 连接可以复用，从而节省时间。为了显示同一初始文档中嵌入的资源，不再需要反复建立连接。
  • 增加了流水线，允许在第一个响应尚未完整传输完毕时，发送第二个请求，从而降低通信延迟。
  • 支持分块响应。
  • 引入更多缓存控制机制。
  • 引入内容协商，包括语言、编码和类型。客户端与服务器可以协商交换哪种内容。
  • 借助 Host 标头，同一个 IP 地址可以托管不同域名，从而允许多个服务共同部署。

建立 TCP 连接是客户端与服务器交互中开销较大的环节，而 TCP 慢启动意味着长时间使用的连接比新建连接更快。HTTP/1.1 允许多个请求和响应复用一条 TCP 连接，避免每个请求都新建连接。不过，客户端仍需等一个资源下载完成后，才能请求下一个资源，即队头阻塞。为了绕过这个问题，大多数浏览器允许每个网站或源最多建立六条 TCP 连接。有了六条并行连接，浏览器就能在 HTTP/1.1 模型下同时获取多个资源，显著提高性能。

HTTP/1.1 最初于 1997 年 1 月以 RFC 2068 发布。

二十余年的发展

HTTP 的可扩展性，让创建新标头和新方法很容易。虽然 HTTP/1.1 在 HTTP/2 发布前经历了两轮完善，分别是 1999 年 6 月发布的 RFC 2616，以及 2014 年 6 月发布的 RFC 7230～RFC 7235，但它在超过十五年的时间里一直非常稳定。2022 年，HTTP/1.1 又通过 RFC 9110 更新。不只是 HTTP/1.1，整个 HTTP 都经过修订，如今拆分为以下文档：适用于所有 HTTP 版本的语义（RFC 9110）和缓存（RFC 9111），以及 HTTP/1.1（RFC 9112）、HTTP/2（RFC 9113）和 HTTP/3（RFC 9114）。此外，规范终于取得互联网标准（STD 97）的地位，而此前一直是提议标准或草案标准。

用 HTTP 进行安全传输

HTTP 最大的一次变化发生在 1994 年底。计算机服务公司 Netscape Communications 不再仅通过基本的 TCP/IP 协议栈发送 HTTP，而是在其上增加了加密传输层 SSL。SSL 1.0 从未公开发布，但 SSL 2.0 及其后继者 SSL 3.0，通过加密客户端与服务器之间交换的消息并保证其真实性，让电子商务网站成为可能。SSL 最终经过标准化，演变为 TLS。

同一时期，对加密传输层的需求也变得明确。Web 不再是以学术用途为主的网络，而成为广告商、普通个人与犯罪分子竞相获取尽可能多私人数据的丛林。随着基于 HTTP 的应用越来越强大，需要访问通讯录、电子邮件和用户位置等私人信息，TLS 的必要性也超出了电子商务场景。

用 HTTP 构建复杂应用

Tim Berners-Lee 最初并没有将 HTTP 设想为只读媒介。他希望创建一种允许人们远程添加和移动文档的 Web，类似分布式文件系统。大约在 1996 年，HTTP 得到扩展，支持创作，并产生了名为 WebDAV 的标准。它随后发展出面向特定用途的应用，例如处理通讯录条目的 CardDAV，以及处理日历的 CalDAV。但所有这些 *DAV 扩展都有一个缺点：只有服务器实现它们之后，才能使用。

2000 年，出现了一种新的 HTTP 使用模式：表述性状态转移，也就是 REST。这类 API 不基于新的 HTTP 方法，而是依靠基本 HTTP/1.1 方法访问特定 URI。这使任何 Web 应用都能够通过 API 获取和修改数据，而无需更新浏览器或服务器。所有必要信息都嵌入网站通过标准 HTTP/1.1 提供的文件中。REST 模型的缺点是，每个网站都定义自己的非标准 RESTful API，并完全控制它；这与客户端和服务器可以互操作的 *DAV 扩展不同。RESTful API 在 2010 年代变得非常普遍。

自 2005 年起，网页可以使用更多 API。其中一些 API 为特定目的扩展了 HTTP 协议：

  • 服务器发送事件，让服务器能够不时向浏览器推送消息。
  • WebSocket，一种可以通过升级现有 HTTP 连接来建立的新协议。

放宽 Web 安全模型的限制

HTTP 独立于称为同源策略的 Web 安全模型。事实上，当前 Web 安全模型是在 HTTP 创建之后才发展起来的！多年来，人们发现，在一定条件下解除这项策略的部分限制很有用。服务器使用一组新的 HTTP 标头，告诉客户端何时以及在多大程度上解除限制。这些标头定义在跨源资源共享（CORS）和内容安全策略（CSP）等规范中。

除了这些大型扩展，还增加了许多其他标头，其中一些仅用于试验。值得注意的有控制隐私的 Do Not Track（DNT）标头、X-Frame-Options 和 Upgrade-Insecure-Requests，此外还有很多。

HTTP/2：追求更高性能的协议

多年来，网页变得更加复杂，有些本身就已经是应用。页面展示更多视觉媒体，增加交互的脚本在数量和体积上也不断增长。更多数据通过大幅增加的 HTTP 请求传输，为 HTTP/1.1 连接带来更多复杂性和开销。为此，Google 在 2010 年代初实现了试验性协议 SPDY。这种在客户端与服务器之间交换数据的替代方式，引起了浏览器和服务器开发者的兴趣。SPDY 改善了响应速度，并解决重复数据传输的问题，成为 HTTP/2 协议的基础。

HTTP/2 与 HTTP/1.1 有以下区别：

  • 它是二进制协议，而不是文本协议，无法直接手工阅读和创建。尽管有这个障碍，它也使更好的优化技术得以实现。
  • 它是支持多路复用的协议，可以在同一连接上并行发出请求，消除 HTTP/1.x 的限制。
  • 它压缩标头。由于一组请求的标头往往相似，这可以消除重复内容和传输开销。

HTTP/2 于 2015 年 5 月正式标准化，使用率在 2022 年 1 月达到峰值，占全部网站的 46.9%，见这份统计。高流量网站采用得最快，希望借此节省数据传输开销和相应预算。

采用速度如此之快，可能是因为 HTTP/2 不要求修改网站和应用。只需要较新的服务器与较新的浏览器通信，就能使用。推动采用所需涉及的群体有限；随着旧版浏览器与服务器更新，使用率自然增长，Web 开发者不需要投入大量工作。

HTTP/2 之后的演进

HTTP 的可扩展性仍然被用来增加新功能。特别值得一提的，是 2016 年出现的这些 HTTP 协议扩展：

  • 对 Alt-Svc 的支持，让某个资源的标识与位置可以分离，意味着能够采用更智能的 CDN 缓存机制。
  • 客户端提示（client hints）的引入，让浏览器或客户端能够主动向服务器传达需求和硬件约束信息。
  • Cookie 标头中引入的安全相关前缀，有助于确保安全 Cookie 不被修改。

HTTP/3：基于 QUIC 的 HTTP

HTTP 的下一个主要版本 HTTP/3，与此前版本保持相同的语义，但在传输层使用 QUIC，而不是 TCP。截至 2022 年 10 月，26% 的网站正在使用 HTTP/3。

QUIC 的设计目标是大幅降低 HTTP 连接的延迟。它与 HTTP/2 一样支持多路复用，但 HTTP/2 运行在单条 TCP 连接上，因此 TCP 层处理的丢包检测和重传会阻塞所有流。QUIC 在 UDP 上运行多个流，并针对每个流独立实现丢包检测和重传，因此发生错误时，只有数据位于该数据包中的流会被阻塞。

HTTP/3 定义于 RFC 9114，并已获得多数主流浏览器的支持，包括 Chromium 及其 Chrome、Edge 等变体，以及 Firefox。
