HTTP 缓存保存与某个请求关联的响应，并在后续请求中复用已经存储的响应。

可复用性有几个优点。首先，因为不需要把请求发送到源服务器，客户端与缓存越接近，响应就越快。最典型的例子，是浏览器自己为浏览器请求存储缓存。

另外，响应可复用时，源服务器就不需要处理请求：不用解析和路由请求，不用根据 Cookie 恢复会话，不用查询数据库获取结果，也不用通过模板引擎渲染。这降低了服务器的负载。

缓存的正确运行，对系统健康至关重要。

缓存的类型

在 HTTP 缓存规范中，缓存主要分为两类：私有缓存和共享缓存。

私有缓存

私有缓存与某个特定客户端绑定，典型例子是浏览器缓存。由于存储的响应不会与其他客户端共享，私有缓存可以保存针对该用户的个性化响应。

另一方面，如果将个性化内容存储在私有缓存以外的缓存中，其他用户就可能获取这些内容，从而造成意外的信息泄露。

如果响应包含个性化内容，而你只希望将它存储在私有缓存中，就必须指定 private 指令。

http
Cache-Control: private

个性化内容通常由 Cookie 控制，但存在 Cookie 并不总意味着内容是私有的，因此仅有 Cookie 不会让响应自动成为私有响应。

共享缓存

共享缓存位于客户端与服务器之间，可以存储能够在用户之间共享的响应。共享缓存还可以进一步分为代理缓存和受管理的缓存。

代理缓存

除了访问控制功能，一些代理还实现了缓存，以减少流出网络的流量。服务开发者通常不管理它们，因此必须通过合适的 HTTP 标头等方式进行控制。不过，过去一些过时的代理缓存实现，例如不能正确理解 HTTP 缓存标准的实现，经常给开发者造成问题。

下面这样的大杂烩标头，试图绕过那些“老旧且不再更新的代理缓存”实现；它们无法理解当前 HTTP 缓存规范中的 no-store 等指令。

http
Cache-Control: no-store, no-cache, max-age=0, must-revalidate, proxy-revalidate

然而，近年来 HTTPS 越来越普及，客户端与服务器之间的通信经过加密，在很多情况下，路径中的代理缓存只能通过隧道转发响应，无法充当缓存。在这种场景下，就不必担心那些连响应内容都看不到的过时代理缓存实现。

另一方面，如果某个 TLS 桥接代理在 PC 上安装由组织管理的 CA（证书颁发机构）签发的证书，以中间人的方式解密全部通信，并进行访问控制等操作，那么它就可以查看响应内容并缓存。不过，近年来 CT（证书透明度）已经广泛使用，一些浏览器只接受带有 SCT（签名证书时间戳）的证书，因此这种方法需要应用企业策略。在这种受控环境中，不必担心代理缓存“过时且不再更新”。

受管理的缓存

受管理的缓存由服务开发者明确部署，用来减轻源服务器负载，并高效分发内容。例如反向代理、CDN，以及与 Cache API 配合使用的 service worker。

受管理缓存的特性因所部署的产品而异。大多数情况下，可以通过 Cache-Control 标头，以及自己的配置文件或控制台来控制缓存行为。

例如，HTTP 缓存规范基本上没有定义显式删除缓存的方法，但使用受管理的缓存时，可以随时通过控制台操作、API 调用、重启等方式删除存储的响应。这让更主动的缓存策略成为可能。

也可以不遵循标准 HTTP 缓存规范的协议，改为显式操作。例如，可以指定下面的设置，让私有缓存和代理缓存不参与缓存，同时使用自己的策略，只在受管理的缓存中存储内容。

http
Cache-Control: no-store

例如，Varnish Cache 使用 VCL（Varnish 配置语言，一种 DSL）逻辑处理缓存存储；service worker 与 Cache API 配合，则允许你使用 JavaScript 创建这种逻辑。

这意味着，如果受管理的缓存有意忽略 no-store 指令，没有必要认为它“不符合”标准。你应当避免使用大杂烩标头，仔细阅读所用受管理缓存机制的文档，并确保按它提供的方式正确控制缓存。

请注意，一些 CDN 提供仅对自身生效的专用标头，例如 Surrogate-Control。目前，正在推进定义 CDN-Cache-Control 标头的工作，以便将其标准化。

启发式缓存

HTTP 的设计倾向于尽可能缓存。因此，即使没有给出 Cache-Control，只要满足某些条件，响应仍会被存储和复用。这称为启发式缓存。

例如，看看下面的响应。它最后一次更新是在一年前。

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
Last-Modified: Tue, 22 Feb 2021 22:22:22 GMT

<!doctype html>
…

按经验推断，整整一年都没有更新的内容，在之后的一段时间内也不会更新。因此，客户端会存储这个响应，尽管没有 max-age，并在一段时间内复用。复用多久由实现决定，但规范建议大约为存储时已有时长的 10%，本例中为 0.1 年。

启发式缓存是在 Cache-Control 支持广泛普及之前采用的变通方法。原则上，所有响应都应显式指定 Cache-Control 标头。

根据 age 判断新鲜与陈旧

存储的 HTTP 响应有两种状态：新鲜（fresh）和陈旧（stale）。新鲜通常表示响应仍然有效，可以复用；陈旧表示缓存的响应已经过期。

判断响应何时新鲜、何时陈旧的标准是 age。在 HTTP 中，age 是自响应生成以来经过的时间。这与其他缓存机制中的 TTL 类似。

看下面的响应示例，604800 秒等于一周：

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
Cache-Control: max-age=604800

<!doctype html>
…

保存该响应的缓存，会计算自响应生成以来经过的时间，并将结果作为响应的 age。

对于这个响应，max-age 的含义如下：

  • 如果响应的 age 小于一周，响应就是新鲜的。
  • 如果响应的 age 大于一周，响应就是陈旧的。

只要存储的响应仍然新鲜，就会用它来满足客户端请求。

响应存储在共享缓存中时，可以将响应的 age 告诉客户端。接着上面的例子，如果共享缓存已经保存响应一天，它就会向后续客户端请求发送下面的响应。

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
Cache-Control: max-age=604800
Age: 86400

<!doctype html>
…

收到这个响应的客户端，会认为它在剩余的 518400 秒内仍然新鲜；这个值是响应的 max-age 与 Age 之差。

Expires 与 max-age

在 HTTP/1.0 中，新鲜度曾通过 Expires 标头指定。

Expires 标头使用明确的时间点来指定缓存的有效期，而不是指定一段经过的时间。

http
Expires: Tue, 28 Feb 2022 22:22:22 GMT

不过，这种时间格式难以解析，曾发现许多实现错误，而且有人可以故意调整系统时钟来制造问题。因此，HTTP/1.1 的 Cache-Control 采用了用来指定经过时长的 max-age。

如果同时提供 Expires 和 Cache-Control: max-age，规范规定优先使用 max-age。因此，在 HTTP/1.1 已经广泛使用的今天，没有必要再提供 Expires。

Vary

响应之间的区分，基本上依据各自的 URL：

不过，即使 URL 相同，响应内容也不一定相同。特别是在进行内容协商时，服务器响应可能取决于请求标头 Accept、Accept-Language 和 Accept-Encoding 的值。

例如，针对带有 Accept-Language: en 标头的请求返回并缓存了英文内容后，就不应该再将它用于带有 Accept-Language: ja 请求标头的请求。这时，可以将 Accept-Language 加入 Vary 标头的值，让响应按语言分别缓存。

http
Vary: Accept-Language

这样，缓存就以响应 URL 与 Accept-Language 请求标头的组合作为键，而不再只使用响应 URL。

此外，如果根据用户代理优化内容，例如实现响应式设计，你可能会想将 User-Agent 加入 Vary 标头的值。但 User-Agent 请求标头通常存在非常多的变化，会显著降低缓存被复用的机会。因此，如果可能，应考虑通过特性检测改变行为，而不是依据 User-Agent 请求标头。

对于使用 Cookie、希望防止别人复用缓存中个性化内容的应用，应指定 Cache-Control: private，而不是在 Vary 中指定 Cookie。

验证

陈旧响应不会立即被丢弃。HTTP 提供一种机制，可以通过询问源服务器，将陈旧响应重新变成新鲜响应。这称为验证（validation），有时也称为重新验证（revalidation）。

验证通过包含 If-Modified-Since 或 If-None-Match 请求标头的条件请求完成。

If-Modified-Since

下面的响应生成于 22:22:22，max-age 为 1 小时，因此可以知道，在 23:22:22 之前它都是新鲜的。

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT
Cache-Control: max-age=3600

<!doctype html>
…

到 23:22:22 时，响应变成陈旧状态，缓存不能再直接复用。所以下面的请求展示了客户端如何发送带有 If-Modified-Since 请求标头的请求，询问服务器在指定时间之后是否发生过变化。

http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
If-Modified-Since: Tue, 22 Feb 2022 22:00:00 GMT

如果内容自指定时间以来没有变化，服务器就会返回 304 Not Modified。

由于响应仅表示“没有变化”，所以没有响应体，只有状态码，传输体积非常小。

http
HTTP/1.1 304 Not Modified
Content-Type: text/html
Date: Tue, 22 Feb 2022 23:22:22 GMT
Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT
Cache-Control: max-age=3600

客户端收到这个响应后，就将存储的陈旧响应重新变为新鲜状态，并可以在接下来的一小时内复用它。

服务器可以从操作系统的文件系统中获取修改时间，对于提供静态文件的情况，这相对容易。不过也存在一些问题，例如时间格式复杂、难以解析，以及分布式服务器难以同步文件更新时间。

为解决这些问题，ETag 响应标头被标准化，作为一种替代方案。

ETag 与 If-None-Match

ETag 响应标头的值是服务器生成的任意值。规范不限制服务器必须如何生成它，因此服务器可以自由选择方式，例如消息体内容的哈希值，或者版本号。

例如，如果 ETag 标头采用哈希值，且 index.html 资源的哈希值为 33a64df5，响应就如下所示：

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
ETag: "33a64df5"
Cache-Control: max-age=3600

<!doctype html>
…

如果响应已经陈旧，客户端就取出缓存响应的 ETag 响应标头值，放入 If-None-Match 请求标头，询问服务器资源是否修改过：

http
GET /index.html HTTP/1.1
Host: example.com
Accept: text/html
If-None-Match: "33a64df5"

如果服务器为所请求资源确定的 ETag 标头值，与请求中的 If-None-Match 值相同，就会返回 304 Not Modified。

但如果服务器认为所请求资源现在应该具有不同的 ETag 值，就会返回 200 OK 和资源的最新版本。

备注：RFC 9110 建议，服务器在可能的情况下，应为 200 响应同时发送 ETag 和 Last-Modified。缓存重新验证时，如果同时出现 If-Modified-Since 和 If-None-Match，则优先使用 If-None-Match 进行验证。如果只考虑缓存，你可能觉得 Last-Modified 没有必要。但 Last-Modified 不只对缓存有用：它是标准 HTTP 标头，内容管理系统（CMS）用它显示最后修改时间，爬虫用它调整抓取频率，此外还有其他用途。因此，从整个 HTTP 生态考虑，同时提供 ETag 和 Last-Modified 更好。

强制重新验证

如果不希望直接复用响应，而是希望总能从服务器获取最新内容，可以使用 no-cache 指令强制验证。

像下面这样，在响应中同时加入 Cache-Control: no-cache、Last-Modified 和 ETag，客户端就会在所请求资源已更新时收到 200 OK 响应；否则，如果资源未更新，就会收到 304 Not Modified 响应。

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Date: Tue, 22 Feb 2022 22:22:22 GMT
Last-Modified: Tue, 22 Feb 2022 22:00:00 GMT
ETag: "deadbeef"
Cache-Control: no-cache

<!doctype html>
…

备注：no-cache 指令及 max-age=0, must-revalidate 等等效设置，不保证在历史记录导航时重新验证，例如点击后退按钮。如果使用前进／后退缓存（bfcache），浏览器会直接恢复页面快照，不进行重新验证。即使没有使用 bfcache，浏览器也可能不经重新验证就提供缓存响应。规范允许这种行为，因为历史记录导航通常被视为恢复历史会话的快照，而不是针对之前访问的页面发起新请求。

经常有人说，max-age=0 与 must-revalidate 的组合，与 no-cache 含义相同。

http
Cache-Control: max-age=0, must-revalidate

max-age=0 表示响应立即变为陈旧状态；must-revalidate 表示一旦陈旧，未经重新验证就不得复用。因此，两者结合起来，语义看上去与 no-cache 相同。

然而，max-age=0 的这种用法，是许多 HTTP/1.1 之前的实现无法处理 no-cache 指令所留下的历史痕迹；为了应对这个限制，当时使用 max-age=0 作为变通方案。

现在，符合 HTTP/1.1 的服务器已广泛部署，没有理由继续使用 max-age=0 与 must-revalidate 的组合；应直接使用 no-cache。

不要缓存

no-cache 指令不会阻止响应被存储，它阻止的是未经重新验证就复用响应。

如果不希望响应存储在任何缓存中，请使用 no-store。

http
Cache-Control: no-store

不过，一般而言，实践中的“不要缓存”要求，通常对应以下情况：

  • 出于隐私原因，不希望指定客户端以外的任何人存储响应。
  • 希望始终提供最新信息。
  • 不知道过时的实现会产生什么行为。

在这些情况下，no-store 不一定是最合适的指令。

下面几节会更详细地讨论这些情况。

不要与其他人共享

如果包含个性化内容的响应，意外地对使用同一缓存的其他用户可见，就会出问题。

此时，使用 private 指令，就能让个性化响应只存储在指定客户端中，不泄露给缓存的其他用户。

http
Cache-Control: private

每次都提供最新内容

no-store 指令阻止响应被存储，但不会删除同一 URL 下已经存储的任何响应。

换句话说，如果某个 URL 已经存储了旧响应，返回 no-store 并不会阻止这个旧响应被复用。

不过，no-cache 指令会强制客户端在复用任何存储的响应之前，先发送验证请求。

http
Cache-Control: no-cache

如果服务器不支持条件请求，可以用 200 OK 强制客户端每次都访问服务器，始终获取最新响应。

应对过时的实现

为了绕过忽略 no-store 的过时实现，你可能会看到下面这样的大杂烩标头。

http
Cache-Control: no-store, no-cache, max-age=0, must-revalidate, proxy-revalidate

建议使用 no-cache 作为应对此类过时实现的替代方式。从一开始就提供 no-cache 也没有问题，因为服务器始终会收到请求。

如果担心的是共享缓存，还可以加入 private，确保不会发生意外缓存：

http
Cache-Control: no-cache, private

使用 no-store 会失去什么

你可能认为，添加 no-store 是退出缓存的正确方式。

不过，不建议随意广泛使用 no-store，因为这样会失去 HTTP 和浏览器提供的许多优势，包括浏览器的前进／后退缓存。

因此，为了享受 Web 平台完整功能带来的好处，应优先组合使用 no-cache 和 private。

重新加载与强制重新加载

不仅响应，请求也可以执行验证。

重新加载和强制重新加载，是由浏览器端发起验证的常见例子。

重新加载

为了恢复损坏的窗口显示，或者更新到资源的最新版本，浏览器向用户提供重新加载功能。

浏览器重新加载时发送的 HTTP 请求，简化后如下：

http
GET / HTTP/1.1
Host: example.com
Cache-Control: max-age=0
If-None-Match: "deadbeef"
If-Modified-Since: Tue, 22 Feb 2022 20:20:20 GMT

Chrome、Edge 和 Firefox 的请求与上面非常相似；Safari 的请求会略有不同。

请求中的 max-age=0 指令指定“复用 age 小于或等于 0 的响应”，因此实际上不会复用中间存储的响应。

于是，请求通过 If-None-Match 和 If-Modified-Since 进行验证。

Fetch 标准也定义了这种行为。可以在 JavaScript 中调用 fetch()，并将缓存模式设为 no-cache 来重现。注意，这里正确的模式不是 reload：

js
// Note: "reload" is not the right mode for a normal reload; "no-cache" is
fetch("/", { cache: "no-cache" });

强制重新加载

浏览器出于向后兼容的原因，在重新加载时使用 max-age=0，因为许多 HTTP/1.1 之前的过时实现无法理解 no-cache。不过，如今在这个场景中使用 no-cache 已经没有问题；强制重新加载则是绕过缓存响应的另一种方式。

浏览器强制重新加载时，HTTP 请求如下：

http
GET / HTTP/1.1
Host: example.com
Pragma: no-cache
Cache-Control: no-cache

Chrome、Edge 和 Firefox 的请求与上面非常相似；Safari 的请求会略有不同。

由于这不是带有 no-cache 的条件请求，所以可以确定，会从源服务器得到 200 OK。

Fetch 标准也定义了这种行为。可以在 JavaScript 中调用 fetch()，并将缓存模式设为 reload 来重现。注意，不是 force-reload：

js
// Note: "reload" — rather than "no-cache" — is the right mode for a "force reload"
fetch("/", { cache: "reload" });

避免重新验证

对于永不改变的内容，应使用缓存破坏（cache busting）技术，也就是在请求 URL 中包含版本号、哈希值等，并设置很长的 max-age。

然而，用户重新加载时，即使服务器知道内容不可变，仍会发送重新验证请求。

为了防止这种情况，可以使用 immutable 指令，明确表示内容不会改变，所以无需重新验证。

http
Cache-Control: max-age=31536000, immutable

这样可以避免重新加载时发生不必要的重新验证。

注意，Chrome 已经改变了实现：它没有通过实现这个指令来处理，而是在重新加载时，不对子资源进行重新验证。

删除存储的响应

对于设置了很长 max-age、已经存储在中间服务器上的响应，没有办法将它们删除。

假设来自 https://example.com/ 的以下响应已被存储。

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Cache-Control: max-age=31536000

<!doctype html>
…

你可能希望在服务器上判定该响应过期后覆盖它，但响应一旦被存储，服务器就无能为力，因为缓存会让后续请求不再到达服务器。

规范提到的一种方法，是使用 POST 这样的不安全方法，向同一个 URL 发送请求，但对许多客户端来说，这很难做到。

Clear-Site-Data: cache 标头及其指令值可用于清除浏览器缓存，但对中间缓存没有作用。否则，除非用户手动执行重新加载、强制重新加载或清除历史记录，响应会一直保留在浏览器缓存中，直到 max-age 过期。

缓存减少了对服务器的访问，也意味着服务器失去了对这个 URL 的控制。如果服务器不希望失去控制，例如某个资源经常更新，就应添加 no-cache，让服务器始终能够收到请求，并发送预期的响应。

请求合并

共享缓存主要位于源服务器之前，目的是减少到达源服务器的流量。

因此，如果多个相同请求同时到达共享缓存，中间缓存会代表自己向源站转发一个请求，再将结果复用于所有客户端。这称为请求合并（request collapse）。

请求合并发生在请求同时到达时，所以即使响应中给出了 max-age=0 或 no-cache，响应仍然会被复用。

常见缓存模式

Cache-Control 规范中有许多指令，全部理解可能很困难。但大多数网站的需求，用少数几种模式组合就能覆盖。

本节介绍设计缓存时的常见模式。

默认设置

如前所述，缓存的默认行为，也就是响应没有 Cache-Control 时的行为，并不简单等于“不缓存”，而是按照所谓的“启发式缓存”隐式缓存。

为避免启发式缓存，最好为所有响应显式提供默认的 Cache-Control 标头。

为确保默认情况下始终传输资源的最新版本，通常会让默认的 Cache-Control 值包含 no-cache：

http
Cache-Control: no-cache

此外，如果服务使用 Cookie 或其他登录方式，内容针对每个用户进行个性化处理，还必须提供 private，防止与其他用户共享：

http
Cache-Control: no-cache, private

缓存破坏（Cache Busting）

最适合缓存的资源，是内容永远不变的静态文件。对于内容会变化的资源，一种常见的最佳实践是在每次内容变化时改变 URL，让每个 URL 对应的资源能够缓存更久。

例如，考虑下面的 HTML：

html
<script src="bundle.js"></script>
<link rel="stylesheet" href="build.css" />
<body>
  hello
</body>

在现代 Web 开发中，JavaScript 和 CSS 资源会随着开发不断更新。如果客户端使用的 JavaScript 与 CSS 版本不同步，显示就会出问题。

所以，上面的 HTML 使得使用 max-age 缓存 bundle.js 和 build.css 很困难。

因此，可以通过带有可变部分的 URL 提供 JavaScript 和 CSS，这部分基于版本号或哈希值生成。下面展示几种方式。

# version in filename
bundle.v123.js

# version in query
bundle.js?v=123

# hash in filename
bundle.YsAIAAAA-QG4G6kCMAMBAAAAAAAoK.js

# hash in query
bundle.js?v=YsAIAAAA-QG4G6kCMAMBAAAAAAAoK

因为缓存根据 URL 区分资源，所以资源更新时，只要 URL 发生变化，就不会再次复用旧缓存。

html
<script src="bundle.v123.js"></script>
<link rel="stylesheet" href="build.v123.css" />
<body>
  hello
</body>

采用这种设计，JavaScript 和 CSS 资源都可以缓存很长时间。那么，max-age 应设多长？QPACK 规范提供了一个答案。

QPACK 是压缩 HTTP 标头字段的标准，其中定义了包含常用字段值的表。

下面列出一些常用的缓存标头值。

36 cache-control max-age=0
37 cache-control max-age=604800
38 cache-control max-age=2592000
39 cache-control no-cache
40 cache-control no-store
41 cache-control public, max-age=31536000

如果选择其中一个带编号的选项，通过 HTTP/3 传输时，就可以将值压缩为 1 字节。

编号 37、38 和 41 分别对应一周、一个月和一年。

因为缓存保存新条目时会移除旧条目，即使 max-age 被设置为一周，存储的响应在一周后仍然存在的概率也没有那么高。因此，实践中选择哪一个，差别并不大。

注意，编号 41 的 max-age 最长，为一年，但同时带有 public。

public 的作用是，即使存在 Authorization 标头，也允许存储响应。

备注：只有在设置了 Authorization 标头、却仍需要存储响应时，才应使用 public 指令。其他情况下不需要，因为只要给出 max-age，响应就会存储在共享缓存中。

因此，如果响应通过基本身份认证进行个性化处理，public 的存在可能带来问题。如果担心这一点，可以选择第二长的值 38，即一个月。

http
# response for bundle.v123.js

# If you never personalize responses via Authorization
Cache-Control: public, max-age=31536000

# If you can't be certain
Cache-Control: max-age=2592000

验证

不要忘记设置 Last-Modified 和 ETag 标头，这样重新加载时就不必重新传输资源。对于预先构建好的静态文件，生成这些标头很容易。

这里的 ETag 值可以是文件的哈希值。

http
# response for bundle.v123.js
Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT
ETag: "YsAIAAAA-QG4G6kCMAMBAAAAAAAoK"

此外，还可以加入 immutable，防止重新加载时进行验证。

组合后的结果如下。

http
# bundle.v123.js
HTTP/1.1 200 OK
Content-Type: text/javascript
Content-Length: 1024
Cache-Control: public, max-age=31536000, immutable
Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT
ETag: "YsAIAAAA-QG4G6kCMAMBAAAAAAAoK"

缓存破坏通过在内容变化时改变 URL，让响应能够长时间缓存。这种技术可以用于图片等所有子资源。

备注：评估 immutable 与 QPACK 的配合使用时，如果担心 immutable 会改变 QPACK 提供的预定义值，可以考虑将 Cache-Control 的值拆成两行，让 immutable 部分单独编码。不过，这取决于具体 QPACK 实现采用的编码算法。

http
Cache-Control: public, max-age=31536000
Cache-Control: immutable

主资源

与子资源不同，主资源不能以相同方式给 URL 添加版本等信息，因此无法使用缓存破坏技术。

如果下面的 HTML 本身被存储，即使服务器端更新了内容，也无法显示最新版本。

html
<script src="bundle.v123.js"></script>
<link rel="stylesheet" href="build.v123.css" />
<body>
  hello
</body>

这种情况下，no-cache 比 no-store 更合适，因为我们不想存储 HTML，而只想让它始终保持最新。

此外，添加 Last-Modified 和 ETag 可以让客户端发送条件请求；如果 HTML 没有更新，就能返回 304 Not Modified：

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Cache-Control: no-cache
Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT
ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE"

这种设置适合非个性化 HTML，但如果响应通过 Cookie 实现个性化，例如登录之后的响应，不要忘记同时指定 private：

http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
Cache-Control: no-cache, private
Last-Modified: Tue, 22 Feb 2022 20:20:20 GMT
ETag: "AAPuIbAOdvAGEETbgAAAAAAABAAE"
Set-Cookie: __Host-SID=AHNtAyt3fvJrUL5g5tnGwER; Secure; Path=/; HttpOnly

同样的设置也适用于 favicon.ico、manifest.json、.well-known，以及无法通过缓存破坏改变 URL 的 API 端点。

大多数 Web 内容，都可以用上面介绍的两种模式的组合覆盖。

进一步了解受管理的缓存

使用前面介绍的方法，子资源可以通过缓存破坏长时间缓存，但主资源，通常是 HTML 文档，不可以。

缓存主资源很困难，因为仅使用 HTTP 缓存规范中的标准指令，在服务器更新内容时，没有办法主动删除缓存内容。

不过，部署 CDN 或 service worker 等受管理的缓存后，就可以做到。

例如，如果某个 CDN 允许通过 API 或控制台清除缓存，就可以采用更积极的缓存策略：存储主资源，仅在服务器发生更新时，显式清除相关缓存。

如果 service worker 能在服务器发生更新时删除 Cache API 中的内容，它也可以实现同样的效果。

更多信息请参阅所用 CDN 的文档，以及 service worker 文档。
