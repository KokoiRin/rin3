HTTP 是用来获取 HTML 文档等资源的协议，也是 Web 上数据交换的基础。它采用客户端—服务器模式：请求由内容的接收方发起，通常就是 Web 浏览器。一份完整的文档，通常由文字、布局指令、图片、视频、脚本等资源共同组成。

客户端与服务器通过交换一条条独立的消息进行通信，而不是交换连续的数据流。客户端发送的消息称为请求，服务器作为答复发送的消息称为响应。

HTTP 设计于 20 世纪 90 年代初，是一种随时间不断演进的可扩展协议。它是应用层协议，通过 TCP 或经 TLS 加密的 TCP 连接传输，不过理论上也可以使用任何可靠的传输协议。由于具备可扩展性，HTTP 不仅用来获取超文本文档，也用来获取图片和视频，或者向服务器提交内容，例如 HTML 表单的结果。HTTP 还可以获取文档的一部分，按需更新网页。

基于 HTTP 的系统由哪些部分组成

HTTP 是客户端—服务器协议：请求由一个实体——用户代理（user-agent），或者代表它的代理服务器——发出。用户代理大多是 Web 浏览器，但也可以是其他任何工具，例如抓取 Web 内容、填充并维护搜索引擎索引的机器人。

每个请求都会发给服务器，由服务器处理并返回答复，这个答复称为响应。客户端和服务器之间还有许多中间实体，统称为代理。它们承担不同的工作，例如充当网关或缓存。

实际网络中，浏览器与处理请求的服务器之间还经过路由器、调制解调器等更多设备。Web 采用分层设计，这些设备的工作被隐藏在网络层和传输层中，HTTP 则位于更上方的应用层。底层对排查网络问题很重要，但介绍 HTTP 时，通常不需要涉及它们。

客户端：用户代理

用户代理是代表用户执行操作的任何工具。这个角色主要由 Web 浏览器承担，也可以由工程师和 Web 开发者用来调试应用的程序承担。

浏览器始终是发起请求的一方。服务器从来不是请求发起方，尽管多年来已经增加了一些机制，用来模拟服务器主动发起的消息。

为了显示网页，浏览器首先发出请求，获取代表该页面的 HTML 文档。随后，它解析文件，再发出额外请求，获取执行脚本、显示页面所需的布局信息（CSS），以及页面包含的子资源（通常是图片和视频）。浏览器将这些资源组合起来，呈现完整文档，也就是网页。浏览器执行的脚本还可以在后续阶段获取更多资源，浏览器也会相应更新网页。

网页是超文本文档。这意味着显示内容中的一部分是链接，激活它们——通常是点击鼠标——就能获取新网页，让用户指挥自己的用户代理在 Web 上浏览。浏览器将这些指令转换为 HTTP 请求，再解释 HTTP 响应，向用户呈现清楚的反馈。

Web 服务器

通信通道的另一端是服务器，负责按客户端的请求提供文档。它在逻辑上像一台机器，实际却可能是一组共同分担负载的服务器，也就是负载均衡；也可能由缓存、数据库服务器、电商服务器等其他软件，按需生成全部或部分文档。

服务器不一定对应一台独立机器；同一台机器也可以托管多个服务器软件实例。借助 HTTP/1.1 和 Host 标头，它们甚至可以共享同一个 IP 地址。

代理

Web 浏览器与服务器之间，有许多计算机和设备负责转发 HTTP 消息。由于 Web 协议栈是分层的，其中大多数设备工作在传输层、网络层或物理层，对 HTTP 层来说是透明的，但可能显著影响性能。工作在应用层的设备通常称为代理。代理可以是透明的，原样转发收到的请求；也可以是不透明的，在将请求转交给服务器之前做某种修改。代理可以执行许多功能：

  • 缓存（可以是公共缓存，也可以是浏览器缓存这样的私有缓存）
  • 过滤（例如病毒扫描或家长控制）
  • 负载均衡（让多台服务器分别处理不同请求）
  • 身份认证（控制对不同资源的访问）
  • 日志记录（保存历史信息）

HTTP 的基本特性

HTTP 是简单的

HTTP 总体上被设计为人类可读，即使 HTTP/2 将 HTTP 消息封装为帧，增加了一些复杂性。人可以阅读并理解 HTTP 消息，这让开发者更容易测试，也降低了初学者面对的复杂程度。

HTTP 是可扩展的

HTTP/1.0 引入的 HTTP 标头，让这个协议很容易扩展和试验。客户端与服务器甚至只需就某个新标头的语义达成约定，就能引入新功能。

HTTP 无状态，但并非不能建立会话

HTTP 本身无状态：同一连接上连续发生的两个请求，彼此没有关联。这会给需要连贯交互的功能带来问题，例如电商购物车。不过，HTTP Cookie 可以在无状态的 HTTP 之上支持有状态的会话。利用可扩展的标头，把 Cookie 加入请求流程，就能让各次请求通过会话共享同一份上下文或状态。

HTTP 与连接

连接由传输层控制，因此从根本上说不属于 HTTP 的范围。HTTP 不要求底层传输协议基于连接，只要求它可靠，即不丢失消息，或者至少在发生这种情况时报告错误。互联网中最常见的两种传输协议里，TCP 是可靠的，UDP 则不是。因此，HTTP 依赖面向连接的 TCP 标准。

交换一对 HTTP 请求和响应之前，客户端与服务器需要先建立 TCP 连接；这个过程需要若干次往返。HTTP/1.0 默认让每对请求和响应使用单独的 TCP 连接。多个请求密集连续发送时，这样做不如共享一条连接高效。

为缓解这个缺点，HTTP/1.1 引入了流水线（事实证明很难实现）和持久连接：通过 Connection 标头，可以对底层 TCP 连接进行部分控制。HTTP/2 又进一步，在单个连接上对消息进行多路复用，帮助连接保持活跃，提高效率。

为设计更适合 HTTP 的传输协议，相关试验正在进行。例如，Google 正在试验 QUIC，它建立在 UDP 之上，提供更可靠、更高效的传输协议。

HTTP 可以控制什么

随着时间推移，HTTP 的可扩展性让 Web 获得了更多控制能力和功能。缓存和身份认证在 HTTP 早期就已经得到处理；相比之下，放宽同源限制的能力直到 2010 年代才加入。

下面列出了一些可通过 HTTP 控制的常见功能：

  • 缓存：HTTP 可以控制文档如何缓存。服务器可以告诉代理和客户端缓存什么、缓存多久；客户端可以告诉中间的缓存代理忽略已经存储的文档。
  • 放宽同源限制：为防止窥探和其他隐私侵犯，Web 浏览器严格隔离不同网站。只有同源页面才能访问某个网页的全部信息。虽然这种约束会给服务器带来负担，但 HTTP 标头可以让服务器端放宽这种严格隔离，允许一份文档组合来自不同域的信息；有时这样做甚至出于安全方面的原因。
  • 身份认证：有些页面受到保护，只允许特定用户访问。HTTP 可以提供基本身份认证，例如使用 WWW-Authenticate 等标头，或者通过 HTTP Cookie 设置特定会话。
  • 代理与隧道：服务器或客户端经常位于内网，对其他计算机隐藏真实 IP 地址。HTTP 请求于是通过代理跨越这一网络边界。并非所有代理都是 HTTP 代理，例如 SOCKS 协议工作在更低的层次。这些代理也可以处理 FTP 等其他协议。
  • 会话：使用 HTTP Cookie 可以将请求与服务器上的状态联系起来。这样，尽管基本的 HTTP 是无状态协议，仍然能够建立会话。这不仅对电商购物车有用，也适用于任何允许用户配置输出内容的网站。

HTTP 的流程

客户端希望与服务器通信时，无论对方是最终服务器还是中间代理，都会执行以下步骤：

  1. 打开 TCP 连接，用来发送一个或多个请求并接收答复。客户端可以新建连接、复用现有连接，也可以向服务器建立多条 TCP 连接。

  2. 发送 HTTP 消息：HTTP/2 之前的 HTTP 消息是人类可读的。HTTP/2 将这些消息封装为帧，使它们无法直接阅读，但原理保持不变。例如：

    http
    GET / HTTP/1.1
Host: developer.mozilla.org
Accept-Language: fr

  3. 读取服务器发送的响应，例如：

    http
    HTTP/1.1 200 OK
Date: Sat, 09 Oct 2010 14:28:02 GMT
Server: Apache
Last-Modified: Tue, 01 Dec 2009 20:18:22 GMT
ETag: "51142bc1-7449-479b075b2891b"
Accept-Ranges: bytes
Content-Length: 29769
Content-Type: text/html

<!doctype html>… (here come the 29769 bytes of the requested web page)

  4. 关闭连接，或者复用连接发送后续请求。

启用 HTTP 流水线后，不必等第一个响应完整接收完毕，就能接着发送其他请求。但现有网络里，新旧软件共存，让流水线很难正确实现。HTTP/2 改用基于帧、更健壮的请求多路复用机制，取代流水线。

HTTP 消息

HTTP/1.1 及更早版本的消息是人类可读的。HTTP/2 则把消息放入称为帧的二进制结构，以支持标头压缩、多路复用等优化。虽然它可能只传输原始 HTTP 消息的一部分，但消息语义不变，客户端会在逻辑上重建原来的 HTTP/1.1 请求。因此，先用 HTTP/1.1 的格式理解消息，也有助于理解 HTTP/2。

HTTP 消息分为请求和响应两种，各自有自己的格式。

请求

HTTP 请求示例：

请求由以下元素组成：

  • HTTP 方法，通常是 GET、POST 这样的动词，或者 OPTIONS、HEAD 这样的名词，用来定义客户端想执行的操作。通常，客户端希望获取资源（使用 GET），或者提交 HTML 表单中的值（使用 POST）；其他情况下可能需要执行更多操作。
  • 要获取的资源路径。它相当于从资源 URL 中去掉上下文里已经明确的部分，例如协议（http://）、域名（这里是 developer.mozilla.org）和 TCP 端口（这里是 80）。
  • HTTP 协议版本。
  • 可选的标头，向服务器传递额外信息。
  • 对于 POST 等某些方法，还会有消息体，与响应中的消息体类似，包含要发送的资源。

基于 HTTP 的 API

最常用的基于 HTTP 的 API 是 Fetch API，可以用它从 JavaScript 发起 HTTP 请求。Fetch API 取代了 XMLHttpRequest API。

另一个 API 是服务器发送事件（server-sent events），这是一种单向服务，让服务器以 HTTP 为传输机制向客户端发送事件。客户端通过 EventSource 接口打开连接，并建立事件处理器。客户端浏览器自动把 HTTP 流上到达的消息转换为相应的 Event 对象。如果已知事件的 type，就把对象交给为该事件注册的处理器；如果没有建立对应类型的事件处理器，就交给 onmessage 事件处理器。

结论

HTTP 是一种易用、可扩展的协议。客户端—服务器结构，加上可以添加标头的能力，让 HTTP 能随着 Web 能力的扩展而发展。

虽然 HTTP/2 为提高性能，把 HTTP 消息嵌入帧中，增加了一些复杂性，但消息的基本结构自 HTTP/1.0 以来一直保持不变。会话流程仍然很简单，可以用 HTTP 网络监视器检查和调试。
