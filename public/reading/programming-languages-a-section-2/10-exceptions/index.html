没有可返回的答案时，让谁来决定怎么办

前面 zip3 遇到长度不一致会写 raise BadTriple。那不是一份普通结果，也不是把列表当空列表返回：它表示正常计算到此中断，交给外层决定怎样处理。这一篇把这条路径讲完整。

先从已经熟悉的“求最大值”开始。非空列表有整数答案，空列表则没有；以下函数让调用者同时传入一个异常值，用于指定空列表时应报告哪种失败。

largest 是 5，recovered 是 42。第二个结果不是数学上说“空列表的最大值为42”，而是调用者明确选择了这个替代结果。上周的 option 把“没有答案”放进返回值；异常则让程序离开当前正常求值路径，去找处理它的外层位置。

声明一个异常，与抛出一个异常，是两件事

exception MyUndesirableCondition 引入一个新的异常种类。名字按惯例首字母大写，它作为值的类型是 exn。仅仅声明它，或者把它传给 maxlist，都不会自动发生失败；执行到 raise 才会抛出。

因此开头的非空调用很正常：虽然带着一个异常值进入函数，但它走不到空列表分支，从未执行 raise ex。这也解释了 maxlist 的类型 int list * exn -> int：正常返回时结果是整数，异常离开时并没有返回另一个类型的普通结果。

标准库的 hd 也采用相同思路。下面重写为 my_hd，避免覆盖已有名字；输入非空列表时返回头部，空列表时抛出已经存在的 List.Empty。

first 是 12。raise List.Empty 没有给空列表制造一个任意头部值，所以整个函数仍可以对不同元素类型的列表工作。raise 可以出现在本来需要某种类型结果的位置，因为它不会正常返回到那个位置。

这与“函数返回一个异常值”不同。若函数正常返回 List.Empty，结果类型就是 exn，接收它的调用者仍会继续按普通值处理；若执行 raise List.Empty，当前求值就沿异常路径离开。前者是数据，后者改变了控制接下来往哪里走。只看代码里出现一个异常名字，不能判断它已经被抛出。

异常也可以携带说明失败的数据

handle 保护的是一段表达式

一般形式是 e1 handle p => e2。先计算 e1；若它正常得到值，那就是整个表达式的结果，处理分支不会执行。只有 e1 抛出的异常匹配 p，才改为计算 e2。

因此继续使用开头的定义，maxlist ([3,4,5],MyUndesirableCondition) handle MyUndesirableCondition => 42 仍然得到 5。处理器并非无条件替换答案。若处理分支返回字符串，而正常路径返回整数，整个表达式会类型错误：两条可能正常结束的路径必须给出同类结果。

处理范围要看表达式的边界，而不是看两行代码离得近不近。需要保护较长计算时，用括号明确范围；异常会越过中途还没完成的正常工作，直到遇到涵盖该次求值、且模式匹配的处理器。

例如下面先在内层尝试处理另一种异常。它没有匹配实际抛出的 MyUndesirableCondition，所以原异常继续向外传播，最终由外层处理，结果为 42。

如果连外层也没有合适处理器，异常就继续离开这段计算。maxlist ([],MyUndesirableCondition) 单独求值就是预期运行异常：它不会让左侧的 val 成功得到一个整数。与之不同，语法或类型错误发生在求值前，不能用普通的 handle 把一段无法通过检查的代码“救回来”。

传播可以穿过普通函数调用，而不要求每一层都手动检查。继续使用前面的 my_hd，下面的正常任务是把第一天阅读量乘以2；空列表却会使 my_hd 抛出异常，所以外层等待的乘法也不会完成。

doubled 是24，emptyFallback 是0。处理器放在整个调用外面，仍能接住内部 my_hd 的失败；它没有让内部乘法先拿到0再继续算，而是放弃那条尚未完成的正常路径，直接用处理分支的0作为整个表达式结果。若希望采用另一种恢复策略，就应在相应的表达式边界明确写出来。

还有一个范围容易混淆：如果处理分支 e2 自己又抛出异常，这个新异常不会回头再由同一层 handle 的其他分支处理，而是继续向外找处理器。处理器负责保护前面的 e1，不是把自己的处理过程无限包起来。

异常名字也遵循绑定的作用域：在局部 let 中声明的名字，只能在相应范围内按名字使用。实践中应把声明放在需要共同抛出、匹配它的代码都能看见的位置；处理载荷得到的变量则只在那个处理分支中有效。

现在可以回看 zip3：长度不一致时，它终止的是那次正常拼接，先前等待的 :: 不会继续拼出一份伪结果。接下来我们会从另一个角度观察这些“等待的工作”：当递归正常返回时，调用者还剩多少事没做？
