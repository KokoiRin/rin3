一条模式，能不能同时拆开好几层

前一篇说明了模式为什么能帮助类型检查。现在把它用于真正的数据任务：如果三份列表分别记录阅读量、是否完成、文章标题，怎样把同一位置的数据拼成一条记录？我们希望输入 ([12,18],[true,false],["A","B"])，输出 [(12,true,"A"),(18,false,"B")]。

列表里有头尾，头部还可能是元组；为每一层再写一个 case，很快就会把简单任务写成很多层。嵌套模式把数据的多层形状直接写出来：外层匹配成功后，再检查里面的模式。 先从最小的结构看起，再回到这个拼接任务。

列表的长度条件，藏在模式末尾

下面的函数接收整数列表。有至少三项时，返回前三项与剩余列表；不足三项则返回 NONE。

enough 是 SOME (12,18,10,[7])，tooShort 是 NONE。最外层的 :: 拆出第一项，内层的 :: 继续拆第二、第三项；最后的变量 rest 可以接收任意剩余列表，包括 []。所以这个形状要求“至少三项”。

如果末尾写成 a::(b::(c::[]))，它就要求第三项后面必须立刻结束，含义变成“恰好三项”。括号经常能省略，因为 :: 向右结合；刚开始阅读时保留括号，更容易看清谁的尾部里面还有一层结构。

另一个常见形状是 (a,b,c)::rest。它先要求非空列表，再要求头部是三项元组；a、b、c 对应头部的三项，rest 则对应后面的整个列表。它并没有要求列表恰好只有一个元素。

zip3：三份列表一起前进

现在回到开头的任务。原课函数名 zip3 表示像拉上拉链一样，把三个位置对应的元素合成一组三项元组。以下代码可以完整运行；BadTriple 是长度不一致时使用的失败标记，异常的传播和处理会在第10篇展开。

combined 得到开头所需的两个元组。第一条模式要求三个列表同时为空，表示三份数据刚好一起处理完。第二条模式要求三个列表同时非空，绑定三个头与三个尾，先把头部组成一项，再递归处理三份尾部。

剩下的情况就是有的列表已经空了、有的仍然非空。第三条 _ 接住这些形状并报告失败；它不是把比较短的列表悄悄截断。例如 zip3 ([12],[true,false],["A"]) 是预期运行异常 BadTriple，不会返回一份“凑合能用”的配对结果。三个列表内部各自仍需同类元素，但三个列表彼此可以采用不同元素类型。

把正确输入带入第二条分支，可以看到六个名字各有明确去处：hd1=12、hd2=true、hd3="A"，三个尾部分别是 [18]、[false]、["B"]。下一次同时取到18、false、B，第三次输入才是 ([],[],[])。这时交回 []，先接回第二个元组，再接回第一个元组，所以位置次序没有颠倒。

若改用三次嵌套 case，当然也能检查这些情况，但第一份为空以后还要继续查第二、第三份，第一份非空以后也有另一组检查。嵌套模式把同样的检查整理成我们真正关心的三种整体形状，让“同时为空、同时非空、长度不一致”直接出现在代码结构中。

unzip3：把同一行的三部分分开积回

相反的任务是把三项元组列表拆成三份列表。输入上面的 combined，应当取回 ([12,18],[true,false],["A","B"])。

第二条模式一次拆开“非空列表”和“头部元组”这两层。递归先把后面的一行拆成 ([18],[false],["B"])；val (l1,l2,l3) 再把返回的三份列表取出来，分别在前面接回 12、true、"A"。这里返回的是三份完整列表，不是三项头部值。

这里的两种元组尤其值得分清：输入列表的每一个元素是“一行三项数据”，返回值则是“三份各自完整的列表”。它们看起来都有括号和逗号，职责却不同。unzip3 [] 必须返回 ([],[],[]) 而不能只返回 []，因为调用者接下来始终期待取到三份列表；终止分支与递归分支必须遵守同一个结果结构。

看两项，却只向前走一项

如果要判断阅读量有没有下降，就要比较相邻两天。原课 nondecreasing 判断的是“不递减”：后一项可以等于前一项，也可以更大。

staysUp 是 true，falls 是 false。空列表和单元素列表没有相邻下降，因此都返回真。第三个分支拿到前两项，先比较它们，再用 neck::rest 继续检查；保留 neck 很关键，因为下一次还要比较第二项与第三项。若直接递归 rest，就会漏掉这对相邻元素。

_ 仍会匹配那个值，只是不为它取名字。单元素分支只关心“恰好一项”，用不到具体整数，所以不必引入一个随后不用的变量。andalso 也沿用上周的短路规则：第一次下降已经足够得到假，不再检查后面的尾部。

原课用长度函数再次强调这个区别。下面只数有多少个元素，不读取头部的内容，所以对整数列表和其他元素类型的列表都能工作。

days 是3。这里仍然检查了“非空”这层结构，只是头部无需命名；尾部则确实需要绑定给 rest，以便继续数下去。

把两个结果并排匹配

嵌套模式不只用于列表。原课还把两个整数先变成正、负、零三个标签，再一起判断乘积符号；这样无需真的计算乘积。

结果依次是 P、N、Z。最后的 _ 在这里剩下的确实只有正负异号两种情况，但它也会接住一切未被前面列出的形状。若漏写了某种本应单独处理的情况，编译器无法靠“不完整匹配”提醒你。

因此也可以把末尾明确写成 (N,P) => N | (P,N) => N。两种写法能有相同结果，区别在于把多少检查责任留给自己。下一篇会把这些例子背后的匹配规则精确列出来，也会解释分支为什么必须按顺序读。
