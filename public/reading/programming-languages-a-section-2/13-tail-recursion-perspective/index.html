省下调用栈之后，还要看它反复做了什么

上一篇已经能把部分结果放进累加器。这一篇回答最后一个实际问题：看见递归时，什么时候值得改成尾递归，什么时候保留直接的写法更清楚？先比较两段都能正确反转列表的程序，再回到本周的表达式计算器。

下面是原课的两个版本。输入 [12,18,10]，它们都会得到 [10,18,12]；差别藏在每一步怎样接出结果。

rev1 先把尾部反过来，再把头部放到结果末尾。@ 是列表拼接，两边都需要是列表，所以这里写 [x]，而不是裸元素 x。:: 的含义不同，它在一个已有列表前面接一个元素，不能直接拿来表示“在末尾补一个元素”。

rev1 的慢，主要不只是等待返回

最内层先得到 [10]。上一层做 [10] @ [18]，再上一层做 [10,18] @ [12]。按上周 append 的结构，拼接要沿着左边列表走一遍，并重建它的前缀，才能接上右边列表。

在长度为3的输入上 @ 左侧长度 需要沿左侧走多少项
[] @ [10] 0 0
[10] @ [18] 1 1
[10,18] @ [12] 2 2

若输入长度为 n，这些左侧长度累计是 0+1+...+(n-1)，等于 n*(n-1)/2。因此总工作量按 n 的平方增长，是二次时间；除了返回时等待拼接的栈，它还反复走过已经构建出的列表。

rev2 每一步只有 x::acc，接入一个头部即可，不需要遍历已经建好的累加器。它处理 n 项的工作量随 n 成正比，是线性时间，同时递归调用处于尾位置。这是两个不同的改进：每一步做多少工作，和同时保留多少调用帧，要分别判断。

“二次”和“线性”是在说明输入变大时的增长趋势，不是在保证某次运行精确花几毫秒。在忽略固定开销的比较中，元素数翻倍，线性工作大约翻倍，二次工作的主要部分则大约变为四倍。小列表上这点差别可能不明显，长列表上反复遍历左侧前缀就会越来越突出；这也是原课程强调不要只盯着是否尾递归的原因。

比较项目 rev1 rev2
总时间随输入长度增长 二次 线性
递归调用链所需栈空间 线性 常量级
返回的新列表 长度为 n 长度为 n

最后一行提醒我们，“常量级栈”不等于“整个程序常量空间”。两种版本都要产生一份有 n 个元素的结果；尾调用优化没有把输出列表消掉。阶乘和求和的两种版本则原本就都只需线性次数的算术操作，改成尾递归主要解决的是调用链增长，并不是同样的二次变线性。

次序不能为了省事悄悄改掉

上一篇的 x::acc 会把已处理前缀反过来。这适合反转任务；如果任务本来要保留原顺序，就必须安排最后的次序恢复，而不是返回反过来的答案。

例如下面只是展示“先反着收集，再反回去”的两阶段安排，继续使用本篇已定义的 rev2。输入 [12,18,10]，输出仍是 [12,18,10]。

两遍线性遍历合起来仍然是线性时间，但多做的一遍和额外构建的列表也有真实成本。这个例子不是建议把原样列表都复制两遍，而是帮助识别累加器改写中的顺序问题：计算结果的要求，应当先于对某种代码形状的偏好。

树还有另一边，必须有人记着

回到本周计算器。下面给出完整定义，输入 Add (Constant 12,Multiply (Constant 3,Constant 4))，应当输出24。

在加法节点，既要得到左子树结果，也要得到右子树结果，然后才能相加。无论先算哪一边，都必须有人保存“另一边还没处理，以及最后要做加法”这份工作。源代码中的两个 eval 调用都嵌在加法操作里，因此都不是当前 eval 的尾调用。

直接的递归调用栈恰好能保存这些信息。树越深，尚未完成的祖先节点就可能越多；常见的深度优先处理，其调用栈会随树的高度增长。它不一定随整棵树的节点数同样增长，但对一条很偏的树，高度本身也可能很大。

例如一个表达式可以在根节点下面展开很多较浅的加法、乘法分支，也可以写成一长串 Negate (Negate (...))。两种输入都可能有很多节点，但从根到最深叶子的路径不同，等待链的长度也不同。说“递归处理树需要保存进度”，指的是这条尚未完成的访问路径，不是要求同时把所有节点都放成调用帧。

技术上可以换一种程序表示，把待处理节点与操作放进显式列表或其他数据结构，再用尾调用处理它们。那是把工作记录搬到了别处，不是把所有等待都消灭了。这一阶段无需为了让每个调用都“尾递归”，先引入一套更难读的控制结构。

用需要解决的问题来决定改写

原课程提醒，不要刚学尾递归，就把所有自然的递归都改得复杂。小输入上的阶乘，直接版本很容易验证；树的结构递归也常常最贴近数据。可读、正确、便于检查，本身就是值得保留的性质。

真正评估时，先看答案和数据顺序是否正确，再看每层有没有重复遍历、重复调用，最后看调用栈增长是否会成为实际限制。长列表求和可以考虑累加器；反转中的逐层 @ 应优先看时间成本；表达式树则要接受它确实有未完成的分支需要保存。

尾位置规则已经在第11篇列出：沿函数体、分支结果和 let 主体向里找，参数计算与绑定右边仍有后续工作。把这个规则与本篇的成本分析连起来，才能判断一次改写到底省下了什么，而不只是看程序有没有一个名叫 acc 的参数。
