Android 应用通常使用 Gradle 构建系统。在深入了解如何配置构建之前，我们先介绍构建背后的概念，帮助你看清整个系统。

什么是构建？

构建系统会把源代码转换成可执行的应用。构建通常需要多个工具，分别负责分析、编译、链接，以及打包应用或库。Gradle 通过任务来组织和运行这些命令。

任务（Task）封装了把输入转换为输出的命令。插件（Plugin）定义任务及其配置。将插件应用到构建中，就会注册它提供的任务，并通过任务的输入和输出把它们连接起来。例如，在构建文件中应用 Android Gradle Plugin（AGP），就会注册构建 APK 或 Android 库所需的全部任务。java-library 插件可以把 Java 源代码构建成 JAR。Kotlin 和其他语言也有类似的插件。另外一些插件则用于扩展已有插件，例如，protobuf 插件会为 AGP、java-library 等插件添加 protobuf 支持。

Gradle 倾向于“约定优于配置”，因此插件通常会提供合理的默认值。你也可以使用声明式的领域特定语言（Domain-Specific Language，DSL）进一步配置构建。DSL 让你描述要构建什么，而把如何构建的逻辑交给插件。这些配置分布在项目及其子项目的多个构建文件中。

任务输入可以是文件、目录，也可以是以 Java 类型表示的其他信息，例如整数、字符串或自定义类。输出则只能是文件或目录，因为它们必须写入磁盘。把一个任务的输出连接到另一个任务的输入，就建立了任务之间的关联，使前一个任务必须先于后一个任务运行。

虽然 Gradle 允许你在构建文件中编写任意代码和声明任务，但这样会让工具更难理解构建，也会增加维护难度。例如，插件中的代码可以编写测试，而构建文件中的代码不具备同样的测试方式。因此，应把构建逻辑和任务声明限制在插件中——插件可以由你或其他人定义——再在构建文件中声明如何使用这些逻辑。

运行 Gradle 构建时会发生什么？

Gradle 构建分为三个阶段。每个阶段会执行构建文件中不同部分的代码。

  • 初始化（Initialization）：确定哪些项目和子项目参与构建，并准备包含构建文件及所应用插件的类路径。这个阶段围绕 Settings 文件展开，你会在其中声明要构建的项目，以及获取插件和库的位置。
  • 配置（Configuration）：为各项目注册任务，并执行构建文件，应用用户声明的构建配置。需要理解的是，配置代码无法访问执行阶段才会生成的数据或文件。
  • 执行（Execution）：实际完成应用的“构建”。配置阶段的结果是一张任务的有向无环图（DAG），表示用户请求的全部构建步骤，也就是命令行指定的任务，或构建文件指定的默认任务。这张图反映任务之间的关系：关系可以在任务声明中明确指定，也可以来自输入和输出。如果某个任务的输入是另一个任务的输出，它就必须在后者之后运行。执行阶段按照图中的顺序运行需要更新的任务；如果任务的输入自上次执行以来没有变化，Gradle 会跳过它。

更多信息请参阅 Gradle 的构建生命周期。

配置 DSL

Gradle 使用领域特定语言（DSL）配置构建。这种声明式写法侧重于描述数据，而不是编写逐步执行的命令式指令。构建文件可以用 Kotlin 或 Groovy 编写，不过我们强烈建议使用 Kotlin。

DSL 通过定义一种小型语言，以更自然的方式表达数据，让领域专家和程序员都更容易参与项目。Gradle 插件可以扩展 DSL，以便配置自身任务所需的数据。

例如，构建中 Android 部分的配置可能如下所示：

Kotlin

android {
    namespace = "com.example.app"
    compileSdk {
        version = release(36) {
            minorApiLevel = 1
        }
    }
    // ...

    defaultConfig {
        applicationId = "com.example.app"
        minSdk {
            version = release(23)
        }
        targetSdk {
            version = release(36)
        }
        // ...
    }
}

Groovy

android {
    namespace = 'com.example.app'
    compileSdk {
        version = release(36) {
            minorApiLevel = 1
        }
    }
    // ...

    defaultConfig {
        applicationId = 'com.example.app'
        minSdk {
            version = release(23)
        }
        targetSdk {
            version = release(36)
        }
        // ...
    }
}

在底层，这段 DSL 代码类似于：

fun Project.android(configure: ApplicationExtension.() -> Unit) {
    ...
}

interface ApplicationExtension {
    var namespace: String?

    fun compileSdk(configure: CompileSdkSpec.() -> Unit) {
        ...
    }

    val defaultConfig: DefaultConfig

    fun defaultConfig(configure: DefaultConfig.() -> Unit) {
        ...
    }
}

DSL 中的每个代码块，都对应一个接收 lambda 进行配置的函数，以及一个用于访问该配置的同名属性。这样，构建文件中的代码读起来就更像一份数据说明。

注意：如果你想了解 Kotlin 如何实现这种写法，请参阅类型安全构建器。关于 DSL 的一般原理，可阅读 Martin Fowler 和 Rebecca Parsons 所著的 Domain Specific Languages。

外部依赖

Maven 构建系统引入了一套依赖描述、存储和管理机制。库保存在仓库中，仓库可以是服务器或目录，同时保存库的版本、对其他库的依赖等元数据。你需要指定要搜索的仓库和所需依赖的版本，构建系统会在构建期间下载它们。

Maven 产物通过组名（公司、开发者等）、产物名（库名）和产物版本来标识，通常写成 group:artifact:version。

这种方式大幅改善了构建管理。你经常会听到“Maven 仓库”这个说法，但这里真正指的是产物的打包和发布方式。这套仓库与元数据机制被多个构建系统复用，其中也包括 Gradle；Gradle 还可以向这些仓库发布产物。公共仓库方便所有人共享使用，公司内部仓库则让内部依赖留在公司内部。

你也可以把项目模块化，拆成多个子项目，也就是 Android Studio 中所说的“模块”。子项目也可以作为依赖使用。每个子项目会生成输出，例如 JAR，供其他子项目或顶层项目消费。这既有助于隔离需要重新构建的部分、改善构建耗时，也有助于分开应用中不同部分的职责。

关于如何声明依赖，我们会在添加构建依赖项中进一步介绍。

构建变体

创建 Android 应用时，通常需要构建多个变体。不同变体可以包含不同的代码，也可以采用不同的构建选项；它们由构建类型和产品变种组合而成。

构建类型（Build Type）用于改变所声明的构建选项。默认情况下，AGP 会建立 release 和 debug 两种构建类型。你可以调整它们，也可以增加更多类型，例如用于预发布环境或内部测试。

Debug 构建不会对应用进行压缩或混淆，从而加快构建并保留原有符号。它还会把应用标记为“可调试”，使用通用的调试密钥签名，并允许访问设备上已安装应用的文件。因此，你可以在运行应用时查看文件和数据库中保存的数据。

Release 构建会优化应用，使用你的发布密钥签名，并保护已安装应用的文件。

通过产品变种（Product Flavor），你可以改变应用所包含的源码和依赖变体。例如，为应用创建 demo 和 full，或者 free 和 paid 两种产品变种。公共源码写在 main 源集目录中，需要覆盖或补充的内容则放在以产品变种命名的源集中。

AGP 会为构建类型与产品变种的每一种组合创建变体。如果没有定义产品变种，变体就以构建类型命名。如果二者都定义了，变体名称就是 <flavor><Buildtype>。例如，构建类型为 release、debug，产品变种为 demo、full 时，AGP 会创建以下变体：

  • demoRelease
  • demoDebug
  • fullRelease
  • fullDebug
