分离 API 与实现

标准 Java 插件与 Java Library 插件的关键区别在于，后者引入了向使用方暴露 API 的概念。库是一种供其他组件使用的 Java 组件。这在多项目构建中十分常见，而只要涉及外部依赖，也会遇到这种情况。

该插件提供了两个可用于声明依赖的配置：api 和 implementation。api 配置应用于声明通过库 API 导出的依赖，而 implementation 配置应用于声明组件内部使用的依赖。

build.gradle.kts
dependencies {
    api("org.apache.httpcomponents:httpclient:4.5.7")
    implementation("org.apache.commons:commons-lang3:3.5")
}
build.gradle
dependencies {
    api 'org.apache.httpcomponents:httpclient:4.5.7'
    implementation 'org.apache.commons:commons-lang3:3.5'
}

声明在 api 配置中的依赖会传递地暴露给库的使用方，因此会出现在使用方的编译类路径上。相反，声明在 implementation 配置中的依赖不会暴露给使用方，也就不会泄露到使用方的编译类路径中。这会带来以下好处：

  • 依赖不再泄露到使用方的编译类路径中，因此你不会意外依赖某个传递依赖

  • 类路径规模缩小，编译更快

  • 实现依赖发生变化时，重新编译的次数更少：使用方无需重新编译

  • 发布时的依赖关系更清晰：与新的 maven-publish 插件配合使用时，Java 库生成的 POM 文件会准确区分“编译依赖该库的代码时需要什么”和“在运行时使用该库需要什么”。换句话说，不要混淆编译库本身所需的依赖与编译依赖该库的代码所需的依赖。

Gradle 7.0 已移除 compile 和 runtime 配置。如何迁移到 implementation 和 api 配置，请参阅升级指南。

如果构建使用的是带有 POM 元数据的已发布模块，Java 插件和 Java Library 插件都会通过 POM 中的作用域来遵循 API 与实现的分离规则。也就是说，编译类路径只包含 Maven compile 作用域的依赖，而运行时类路径还会加入 Maven runtime 作用域的依赖。

对于使用 Maven 发布的模块，这种分离通常不会生效，因为定义项目的 POM 会直接作为元数据发布。在这些模块中，compile 作用域既包含编译项目所需的依赖（即实现依赖），也包含编译依赖该已发布库的代码时所需的依赖（即 API 依赖）。对于大多数已发布的库，这意味着所有依赖都属于 compile 作用域。如果现有库存在这类问题，可以考虑使用组件元数据规则在构建中修正不正确的元数据。不过，如上所述，如果库使用 Gradle 发布，生成的 POM 文件只会将 api 依赖放入 compile 作用域，其余 implementation 依赖则放入 runtime 作用域。

如果构建使用的模块带有 Ivy 元数据，并且所有模块都遵循特定结构，那么你或许可以按这里介绍的方式启用 API 与实现的分离。

识别 API 依赖与实现依赖

本节将通过一些简单的经验规则，帮助你识别代码中的 API 依赖与实现依赖。第一条规则是：

  • 尽可能优先使用 implementation 配置，而不是 api

这样可以将依赖排除在使用方的编译类路径之外。此外，如果任何实现类型意外泄露到公开 API 中，使用方会立即编译失败。

那么，什么时候应该使用 api 配置？如果某个依赖至少包含一种暴露在库二进制接口中的类型，它就是 API 依赖。库的二进制接口通常称为 ABI（Application Binary Interface，应用程序二进制接口）。这类类型包括但不限于：

  • 用于父类或接口的类型

  • 用于公开方法参数的类型，包括泛型参数类型（这里的公开指对编译器可见，即 Java 中的 public、protected 和包私有成员）

  • 用于公开字段的类型

  • 公开的注解类型

相比之下，只在以下位置使用的类型与 ABI 无关，因此应声明为 implementation 依赖：

  • 仅在方法体中使用的类型

  • 仅在私有成员中使用的类型

  • 仅出现在内部使用的类中的类型（Gradle 目前不支持声明哪些包属于公开 API）

下面的类使用了两个第三方库，其中一个暴露在该类的公开 API 中，另一个只在内部使用。仅凭 import 语句无法判断两者的区别，因此需要查看字段、构造函数和方法：

示例：区分 API 与实现

src/main/java/org/gradle/HttpClientWrapper.java
// The following types can appear anywhere in the code
// but say nothing about API or implementation usage
import org.apache.commons.httpclient.*;
import org.apache.commons.httpclient.methods.*;
import org.apache.commons.lang3.exception.ExceptionUtils;
import java.io.IOException;
import java.io.UnsupportedEncodingException;

public class HttpClientWrapper {

    private final HttpClient client; // private member: implementation details

    // HttpClient is used as a parameter of a public method
    // so "leaks" into the public API of this component
    public HttpClientWrapper(HttpClient client) {
        this.client = client;
    }

    // public methods belongs to your API
    public byte[] doRawGet(String url) {
        GetMethod method = new GetMethod(url);
        try {
            int statusCode = doGet(method);
            return method.getResponseBody();

        } catch (Exception e) {
            ExceptionUtils.rethrow(e); // this dependency is internal only
        } finally {
            method.releaseConnection();
        }
        return null;
    }

    // GetMethod is used in a private method, so doesn't belong to the API
    private int doGet(GetMethod method) throws Exception {
        int statusCode = client.executeMethod(method);
        if (statusCode != HttpStatus.SC_OK) {
            System.err.println("Method failed: " + method.getStatusLine());
        }
        return statusCode;
    }
}

HttpClientWrapper 的公开构造函数使用 HttpClient 作为参数，因此该类型暴露给了使用方，属于 API。请注意，HttpGet 和 HttpEntity 用在一个私有方法的签名中，因此它们不会使 HttpClient 成为 API 依赖。

另一方面，来自 commons-lang 库的 ExceptionUtils 类型只用在方法体中，而不在方法签名中，因此它是实现依赖。

因此可以推断，httpclient 是 API 依赖，而 commons-lang 是实现依赖。这个结论对应以下构建脚本声明：

build.gradle.kts
dependencies {
    api("commons-httpclient:commons-httpclient:3.1")
    implementation("org.apache.commons:commons-lang3:3.5")
}
build.gradle
dependencies {
    api 'commons-httpclient:commons-httpclient:3.1'
    implementation 'org.apache.commons:commons-lang3:3.5'
}
