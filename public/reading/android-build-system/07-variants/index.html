本页介绍如何通过配置构建变体，在同一个项目中创建应用的不同版本，以及如何正确管理依赖和签名配置。

每个构建变体（Build Variant）都代表一种可以构建出的应用版本。例如，你可能希望提供一个内容受限的免费版本，以及一个内容更丰富的付费版本。也可以根据 API 级别或其他设备差异，构建面向不同设备的版本。

构建变体是 Gradle 按照特定规则，将构建类型与产品变种中的设置、代码和资源组合起来的结果。你并不直接配置构建变体，而是配置组成它们的构建类型和产品变种。

例如，demo 产品变种（Product Flavor）可以指定某些功能和设备要求，包括自定义源码、资源和最低 API 级别；debug 构建类型（Build Type）则应用不同的构建与打包设置，包括调试选项和签名密钥。两者组合成应用的 demoDebug 版本，其中包含 demo 产品变种、debug 构建类型和 main/ 源集中的配置与资源。

配置构建类型

你可以在模块级 build.gradle.kts 文件的 android 块中创建和配置构建类型。创建新模块时，Android Studio 会自动创建 Debug 和 Release 构建类型。虽然 Debug 构建类型没有显示在构建配置文件中，但 Android Studio 会为它配置 debuggable true。这样，你就可以在安全的 Android 设备上调试应用，并使用通用的调试密钥库配置应用签名。

如果想增加或修改某些设置，可以在配置中加入 Debug 构建类型。下面的示例为 Debug 构建类型指定了 applicationIdSuffix，并配置了一个以 Debug 设置为初始值的 staging 构建类型：

Kotlin

android {
    defaultConfig {
        manifestPlaceholders["hostName"] = "www.example.com"
        ...
    }
    buildTypes {
        getByName("release") {
            isMinifyEnabled = true
            proguardFiles(getDefaultProguardFile("proguard-android.txt"), "proguard-rules.pro")
        }

        getByName("debug") {
            applicationIdSuffix = ".debug"
            isDebuggable = true
        }

        /**
         * The `initWith` property lets you copy configurations from other build types,
         * then configure only the settings you want to change. This one copies the debug build
         * type, and then changes the manifest placeholder and application ID.
         */
        create("staging") {
            initWith(getByName("debug"))
            manifestPlaceholders["hostName"] = "internal.example.com"
            applicationIdSuffix = ".debugStaging"
        }
    }
}

Groovy

android {
    defaultConfig {
        manifestPlaceholders = [hostName:"www.example.com"]
        ...
    }
    buildTypes {
        release {
            minifyEnabled true
            proguardFiles getDefaultProguardFile('proguard-android.txt'), 'proguard-rules.pro'
        }

        debug {
            applicationIdSuffix ".debug"
            debuggable true
        }

        /**
         * The `initWith` property lets you copy configurations from other build types,
         * then configure only the settings you want to change. This one copies the debug build
         * type, and then changes the manifest placeholder and application ID.
         */
        staging {
            initWith debug
            manifestPlaceholders = [hostName:"internal.example.com"]
            applicationIdSuffix ".debugStaging"
        }
    }
}

注意：修改构建配置文件后，Android Studio 会要求你将项目与新配置同步。点击修改后出现的通知栏中的 Sync Now，或者点击工具栏中的 Sync Project即可同步。如果 Android Studio 发现配置错误，Messages 窗口会显示问题说明。

关于构建类型可以配置的全部属性，请参阅 BuildType 参考文档。

配置产品变种

创建产品变种与创建构建类型类似。在构建配置的 productFlavors 块中添加产品变种，并加入所需设置即可。产品变种支持与 defaultConfig 相同的属性，因为 defaultConfig 实际上也属于 ProductFlavor 类。因此，你可以在 defaultConfig 中提供所有产品变种的基础配置，再由每个变种修改其中任意默认值，例如 applicationId。关于应用 ID，请参阅设置应用 ID。

注意：你仍然需要使用 main/ 清单文件中的 package 属性指定软件包名称。源码中引用 R 类，或者解析以相对名称注册的 Activity、Service 时，也必须使用这个包名。这样，你就可以通过 applicationId 为每个产品变种指定唯一的打包和分发标识，而不必修改源码。

所有产品变种都必须属于某个有名称的变种维度（Flavor Dimension），即一组产品变种。你必须为所有变种指定维度，否则会出现以下构建错误。


  Error: All flavors must now belong to a named flavor dimension.
  The flavor 'flavor_name' is not assigned to a flavor dimension.

如果某个模块只指定了一个变种维度，Android Gradle 插件会自动把该模块的全部产品变种分配到这个维度。

提示：插件会尝试把应用的变体与本地库依赖的变体匹配起来。感知变体的依赖匹配依赖变种维度的名称，因此命名时需要慎重。合理命名能让你更好地控制：应用的每个版本会匹配本地依赖中的哪些代码和资源。

下面的代码示例创建了名为 version 的变种维度，并添加 demo 和 full 两个产品变种。它们分别提供自己的 applicationIdSuffix 和 versionNameSuffix：

Kotlin

android {
    ...
    defaultConfig {...}
    buildTypes {
        getByName("debug"){...}
        getByName("release"){...}
    }
    // Specifies one flavor dimension.
    flavorDimensions += "version"
    productFlavors {
        create("demo") {
            // Assigns this product flavor to the "version" flavor dimension.
            // If you are using only one dimension, this property is optional,
            // and the plugin automatically assigns all the module's flavors to
            // that dimension.
            dimension = "version"
            applicationIdSuffix = ".demo"
            versionNameSuffix = "-demo"
        }
        create("full") {
            dimension = "version"
            applicationIdSuffix = ".full"
            versionNameSuffix = "-full"
        }
    }
}

Groovy

android {
    ...
    defaultConfig {...}
    buildTypes {
        debug{...}
        release{...}
    }
    // Specifies one flavor dimension.
    flavorDimensions "version"
    productFlavors {
        demo {
            // Assigns this product flavor to the "version" flavor dimension.
            // If you are using only one dimension, this property is optional,
            // and the plugin automatically assigns all the module's flavors to
            // that dimension.
            dimension "version"
            applicationIdSuffix ".demo"
            versionNameSuffix "-demo"
        }
        full {
            dimension "version"
            applicationIdSuffix ".full"
            versionNameSuffix "-full"
        }
    }
}

注意：如果你的旧应用创建于 2021 年 8 月之前，并通过 APK 在 Google Play 分发，那么要使用 Google Play 的多 APK 支持，需要让所有变体使用相同的 applicationId，并为各变体分配不同的 versionCode。如果要把不同变体作为独立应用发布到 Google Play，则需要为每个变体分配不同的 applicationId。

创建并配置产品变种后，点击通知栏中的 Sync Now。同步完成后，Gradle 会根据构建类型和产品变种自动创建构建变体，并按照 <product-flavor><Build-Type> 命名。例如，如果创建了 demo 和 full 产品变种，同时保留默认的 debug 和 release 构建类型，Gradle 会创建以下变体：

  • demoDebug
  • demoRelease
  • fullDebug
  • fullRelease

要选择构建并运行的变体，请进入 Build > Select Build Variant，然后从菜单中选择。要为各变体定制功能和资源，需要按本页说明创建和管理源集。

修改构建变体的应用 ID

构建应用的 APK 或 AAB 时，构建工具会使用 build.gradle.kts 中 defaultConfig 块定义的应用 ID 标识应用，如下例所示。如果想让应用的不同版本分别出现在 Google Play 商店中，例如免费版 free 和专业版 pro，就需要创建不同的构建变体，并为它们分配不同的应用 ID。

在这种情况下，将各构建变体分别定义为产品变种。在 productFlavors 块的每个变种中，可以重新定义 applicationId 属性，也可以使用 applicationIdSuffix 为默认应用 ID 追加一段内容，如下所示：

Kotlin

android {
    defaultConfig {
        applicationId = "com.example.myapp"
    }
    productFlavors {
        create("free") {
            applicationIdSuffix = ".free"
        }
        create("pro") {
            applicationIdSuffix = ".pro"
        }
    }
}

Groovy

android {
    defaultConfig {
        applicationId "com.example.myapp"
    }
    productFlavors {
        free {
            applicationIdSuffix ".free"
        }
        pro {
            applicationIdSuffix ".pro"
        }
    }
}

这样，free 产品变种的应用 ID 就是 com.example.myapp.free。

你也可以根据构建类型，通过 applicationIdSuffix 追加一段内容，如下所示：

Kotlin

android {
    ...
    buildTypes {
        getByName("debug") {
            applicationIdSuffix = ".debug"
        }
    }
}

Groovy

android {
    ...
    buildTypes {
        debug {
            applicationIdSuffix ".debug"
        }
    }
}

Gradle 会在产品变种之后应用构建类型配置，因此 free debug 构建变体的应用 ID 是 com.example.myapp.free.debug。如果希望在同一设备上同时安装 Debug 和 Release 版本，这种做法就很有用，因为两个应用不能使用相同的应用 ID。

如果你的旧应用创建于 2021 年 8 月之前，通过 APK 在 Google Play 分发，而且希望在同一商店条目下提供多个 APK，分别面向不同设备配置，例如不同 API 级别，那么各构建变体必须使用相同的应用 ID，同时为每个 APK 分配不同的 versionCode。更多信息请参阅多 APK 支持。使用 AAB 发布不受此影响，因为默认情况下只使用一个产物、一个版本代码和一个应用 ID。

提示：如果需要在清单文件中引用应用 ID，可以在任意清单属性中使用 ${applicationId} 占位符。构建时，Gradle 会将它替换成实际应用 ID。更多信息请参阅向清单注入构建变量。

通过变种维度组合多个产品变种

有时，你可能需要组合多个产品变种的配置。例如，为 full 和 demo 分别创建基于 API 级别的不同配置。Android Gradle 插件允许你创建多组产品变种，每组对应一个变种维度。

构建应用时，Gradle 会从每个已定义的维度中各取一个产品变种，再结合一种构建类型，形成最终的构建变体。属于同一维度的产品变种不会相互组合。

下面的代码示例使用 flavorDimensions 属性创建 mode 维度，将 full、demo 分成一组；同时创建 api 维度，将按 API 级别区分的产品变种配置分成一组：

Kotlin

android {
  ...
  buildTypes {
    getByName("debug") {...}
    getByName("release") {...}
  }

  // Specifies the flavor dimensions you want to use. The order in which you
  // list the dimensions determines their priority, from highest to lowest,
  // when Gradle merges variant sources and configurations. You must assign
  // each product flavor you configure to one of the flavor dimensions.
  flavorDimensions += listOf("api", "mode")

  productFlavors {
    create("demo") {
      // Assigns this product flavor to the "mode" flavor dimension.
      dimension = "mode"
      ...
    }

    create("full") {
      dimension = "mode"
      ...
    }

    // Configurations in the "api" product flavors override those in "mode"
    // flavors and the defaultConfig block. Gradle determines the priority
    // between flavor dimensions based on the order in which they appear next
    // to the flavorDimensions property, with the first dimension having a higher
    // priority than the second, and so on.
    create("minApi24") {
      dimension = "api"
      minSdk = 24
      // To ensure the target device receives the version of the app with
      // the highest compatible API level, assign version codes in increasing
      // value with API level.
      versionCode = 30000 + (android.defaultConfig.versionCode ?: 0)
      versionNameSuffix = "-minApi24"
      ...
    }

    create("minApi23") {
      dimension = "api"
      minSdk = 23
      versionCode = 20000  + (android.defaultConfig.versionCode ?: 0)
      versionNameSuffix = "-minApi23"
      ...
    }

    create("minApi21") {
      dimension = "api"
      minSdk = 21
      versionCode = 10000  + (android.defaultConfig.versionCode ?: 0)
      versionNameSuffix = "-minApi21"
      ...
    }
  }
}
...

Groovy

android {
  ...
  buildTypes {
    debug {...}
    release {...}
  }

  // Specifies the flavor dimensions you want to use. The order in which you
  // list the dimensions determines their priority, from highest to lowest,
  // when Gradle merges variant sources and configurations. You must assign
  // each product flavor you configure to one of the flavor dimensions.
  flavorDimensions "api", "mode"

  productFlavors {
    demo {
      // Assigns this product flavor to the "mode" flavor dimension.
      dimension "mode"
      ...
    }

    full {
      dimension "mode"
      ...
    }

    // Configurations in the "api" product flavors override those in "mode"
    // flavors and the defaultConfig block. Gradle determines the priority
    // between flavor dimensions based on the order in which they appear next
    // to the flavorDimensions property, with the first dimension having a higher
    // priority than the second, and so on.
    minApi24 {
      dimension "api"
      minSdkVersion 24
      // To ensure the target device receives the version of the app with
      // the highest compatible API level, assign version codes in increasing
      // value with API level.

      versionCode 30000 + android.defaultConfig.versionCode
      versionNameSuffix "-minApi24"
      ...
    }

    minApi23 {
      dimension "api"
      minSdkVersion 23
      versionCode 20000  + android.defaultConfig.versionCode
      versionNameSuffix "-minApi23"
      ...
    }

    minApi21 {
      dimension "api"
      minSdkVersion 21
      versionCode 10000  + android.defaultConfig.versionCode
      versionNameSuffix "-minApi21"
      ...
    }
  }
}
...

Gradle 创建的构建变体数量，等于每个变种维度的产品变种数量与构建类型数量的乘积。为变体或相应产物命名时，优先级较高的维度中的产品变种排在前面，然后是优先级较低的维度，最后是构建类型。

以前面的配置为例，Gradle 会创建共 12 个构建变体，命名方式如下：

  • 构建变体：[minApi24, minApi23, minApi21][Demo, Full][Debug, Release]
  • 对应 APK：app-[minApi24, minApi23, minApi21]-[demo, full]-[debug, release].apk
    • 例如：
    构建变体：minApi24DemoDebug
    对应 APK：app-minApi24-demo-debug.apk

除了为单个产品变种和构建变体创建源集目录之外，也可以为产品变种的每种组合创建源集目录。例如，在 src/demoMinApi24/java/ 目录中添加 Java 源码，Gradle 只会在构建同时包含这两个产品变种的变体时使用它们。

为产品变种组合创建的源集，优先级高于单个产品变种的源集。关于源集及 Gradle 如何合并资源，请参阅创建源集。

过滤变体

Gradle 会为已配置的产品变种与构建类型的每一种可能组合创建构建变体。但其中某些变体可能不需要，或者对当前项目没有意义。可以在模块级 build.gradle.kts 文件中创建变体过滤器，移除这些构建变体配置。

以前一节的构建配置为例，假设应用的 Demo 版本只打算支持 API 23 及以上。可以使用 variantFilter 块，过滤掉同时包含 minApi21 和 demo 产品变种的全部变体配置：

Kotlin

android {
  ...
  buildTypes {...}

  flavorDimensions += listOf("api", "mode")
  productFlavors {
    create("demo") {...}
    create("full") {...}
    create("minApi24") {...}
    create("minApi23") {...}
    create("minApi21") {...}
  }
}

androidComponents {
    beforeVariants { variantBuilder ->
        // To check for a certain build type, use variantBuilder.buildType == "<buildType>"
        if (variantBuilder.productFlavors.containsAll(listOf("api" to "minApi21", "mode" to "demo"))) {
            // Gradle ignores any variants that satisfy the conditions above.
            variantBuilder.enable = false
        }
    }
}
...

Groovy

android {
  ...
  buildTypes {...}

  flavorDimensions "api", "mode"
  productFlavors {
    demo {...}
    full {...}
    minApi24 {...}
    minApi23 {...}
    minApi21 {...}
  }

  variantFilter { variant ->
      def names = variant.flavors*.name
      // To check for a certain build type, use variant.buildType.name == "<buildType>"
      if (names.contains("minApi21") && names.contains("demo")) {
          // Gradle ignores any variants that satisfy the conditions above.
          setIgnore(true)
      }
  }
}
...

将变体过滤器加入构建配置，并点击通知栏中的 Sync Now 后，Gradle 就会忽略满足指定条件的构建变体。之后从菜单栏进入 Build > Select Build Variant，或者点击工具窗口栏中的 Build Variants时，这些变体就不会再出现在菜单中。

创建源集

默认情况下，Android Studio 会创建 main/ 源集及相关目录，用来保存所有构建变体共享的内容。你也可以创建新的源集，精确控制 Gradle 针对特定构建类型、产品变种、产品变种组合（使用变种维度时）和构建变体，编译和打包哪些文件。

例如，在 main/ 源集中定义基础功能，再使用产品变种源集为不同客户更换应用品牌；或者只给采用 Debug 构建类型的变体加入特殊权限和日志功能。

Gradle 期望源集中的文件和目录按特定结构组织，与 main/ 源集类似。例如，专用于 debug 构建类型的 Kotlin 或 Java 类文件，应放在 src/debug/kotlin/ 或 src/debug/java/ 目录中。

Android Gradle 插件提供了一个实用的 Gradle 任务，可以显示各个构建类型、产品变种和构建变体应该如何组织文件。例如，下面的任务输出片段描述了 Gradle 期望在什么位置找到 debug 构建类型的特定文件：

要查看这份输出，请按以下步骤操作：

  1. 点击工具窗口栏中的 Gradle。

  2. 进入 MyApplication > Tasks > android，双击 sourceSets。

    要显示 Tasks 文件夹，必须允许 Gradle 在同步时建立任务列表。操作步骤如下：

    1. 进入 File > Settings > Experimental；在 macOS 上则进入 Android Studio > Settings > Experimental。
    2. 取消选中 Do not build Gradle task list during Gradle sync。
  3. Gradle 执行任务后，会打开 Run 窗口显示输出。

注意：任务输出还会显示应该如何组织用于运行应用测试的源集文件，例如 test/ 和 androidTest/ 测试源集。

创建新的构建变体时，Android Studio 不会自动为你创建源集目录，但会提供几种辅助方式。例如，要为 debug 构建类型只创建 java/ 目录：

  1. 打开 Project 窗格，并从窗格顶部菜单选择 Project 视图。
  2. 进入 MyProject/app/src/。
  3. 右键点击 src 目录，选择 New > Directory。
  4. 在 Gradle Source Sets 下的菜单中选择 full/java。
  5. 按 Enter。

Android Studio 会为 Debug 构建类型创建源集目录，再在其中创建 java/ 目录。另一种方式是：为项目中的特定构建变体添加新文件时，让 Android Studio 自动创建相应目录。

例如，要为 debug 构建类型创建一个 values XML 文件：

  1. 在 Project 窗格中，右键点击 src 目录，选择 New > XML > Values XML File。
  2. 输入 XML 文件名，或者保留默认名称。
  3. 从 Target Source Set 旁的菜单中选择 debug。
  4. 点击 Finish。

由于指定了 debug 构建类型作为目标源集，Android Studio 会在创建 XML 文件时自动建立所需目录。生成的目录结构如图 1 所示。

图 1。为 debug 构建类型新建的源集目录。

当前参与构建的源集，其图标会显示绿色标记。debug 源集后面带有 [main]，表示它会与 main 源集合并。

使用相同方法，也可以为产品变种创建目录，例如 src/demo/；或者为构建变体创建目录，例如 src/demoDebug/。还可以创建面向特定变体的测试源集，例如 src/androidTestDemoDebug/。更多信息请参阅测试源集。

修改默认源集配置

如果源码没有按照上一节创建源集中所说的默认文件结构组织，可以使用 sourceSets 块，修改 Gradle 为源集各个组成部分收集文件时搜索的位置。

sourceSets 块必须位于 android 块中。你不必移动源文件，只需向 Gradle 提供各组成部分所在的路径；路径相对于模块级 build.gradle.kts 文件。关于哪些组成部分可以配置，以及是否可以映射到多个文件或目录，请参阅 Android Gradle 插件 API 参考文档。

下面的代码示例将 app/other/ 目录中的源码映射到 main 源集的部分组成中，并修改 androidTest 源集的根目录：

Kotlin

android {
  ...
  // Encapsulates configurations for the main source set.
  sourceSets.getByName("main") {
    // Changes the directory for Java sources. The default directory is
    // 'src/main/java'.
    java.setSrcDirs(listOf("other/java"))

    // If you list multiple directories, Gradle uses all of them to collect
    // sources. Because Gradle gives these directories equal priority, if
    // you define the same resource in more than one directory, you receive an
    // error when merging resources. The default directory is 'src/main/res'.
    res.setSrcDirs(listOf("other/res1", "other/res2"))

    // Note: Avoid specifying a directory that is a parent to one
    // or more other directories you specify. For example, avoid the following:
    // res.srcDirs = ['other/res1', 'other/res1/layouts', 'other/res1/strings']
    // Specify either only the root 'other/res1' directory or only the
    // nested 'other/res1/layouts' and 'other/res1/strings' directories.

    // For each source set, you can specify only one Android manifest.
    // By default, Android Studio creates a manifest for your main source
    // set in the src/main/ directory.
    manifest.srcFile("other/AndroidManifest.xml")
    ...
  }

  // Create additional blocks to configure other source sets.
  sourceSets.getByName("androidTest") {
      // If all the files for a source set are located under a single root
      // directory, you can specify that directory using the setRoot property.
      // When gathering sources for the source set, Gradle looks only in locations
      // relative to the root directory you specify. For example, after applying the
      // configuration below for the androidTest source set, Gradle looks for Java
      // sources only in the src/tests/java/ directory.
      setRoot("src/tests")
      ...
  }
}
...

Groovy

注意，一个源目录只能属于一个源集。例如，不能让 test 和 androidTest 共用同一份测试源码。因为 Android Studio 会为每个源集创建独立的 IntelliJ 模块，而不同源集之间不能有重复的内容根目录。

使用源集构建

源集目录可以保存只希望打包进特定配置的代码和资源。例如，构建由 demo 产品变种与 debug 构建类型组合而成的 demoDebug 变体时，Gradle 会按以下优先级查找目录：

  1. src/demoDebug/（构建变体源集）
  2. src/debug/（构建类型源集）
  3. src/demo/（产品变种源集）
  4. src/main/（主源集）

为产品变种组合创建的源集必须覆盖全部变种维度。例如，构建变体源集必须是构建类型与全部变种维度的组合。不支持合并覆盖了多个、但没有覆盖全部变种维度的组合目录中的代码和资源。

如果组合多个产品变种，它们之间的优先级由所属维度决定。使用 android.flavorDimensions 属性列出维度时，产品变种按维度声明顺序确定优先级，前面的维度高于后面的维度。此外，为产品变种组合创建的源集，优先级高于单个产品变种的源集。

Gradle 合并代码和资源时，会根据这一顺序确定源集优先级。demoDebug/ 目录通常包含该变体专用的文件；如果 demoDebug/ 和 debug/ 都定义了同一个文件，Gradle 会使用 demoDebug/ 中的文件。同样，构建类型和产品变种源集中的文件，优先于 main/ 中的同名文件。应用下面这些构建规则时，Gradle 会考虑这一优先级：

  • kotlin/ 或 java/ 目录中的全部源码会一起编译，生成同一份输出。

    注意：对于某个构建变体，如果 Gradle 在两个或更多源集目录中发现同一个 Kotlin 或 Java 类的定义，就会报构建错误。例如，构建 Debug 应用时，不能同时定义 src/debug/Utility.kt 和 src/main/Utility.kt，因为 Gradle 会读取这两个目录，从而报出 duplicate class 错误。如果希望不同构建类型使用不同版本的 Utility.kt，需要在各构建类型中分别定义它，而不要把它放进 main/ 源集。

  • 多个清单会合并成一份清单，优先级与前面示例列表的顺序一致。例如，构建类型中的清单设置会覆盖产品变种中的对应设置。更多信息请参阅清单合并。
  • values/ 目录中的文件会合并。如果存在同名文件，例如两份 strings.xml，则按前面列表中的相同顺序确定优先级。例如，构建类型源集文件中定义的值，会覆盖产品变种文件中的同名值。
  • res/ 和 asset/ 目录中的资源会一起打包。如果两个或更多源集定义了同名资源，则按前面列表中的相同顺序确定优先级。
  • 构建应用时，Gradle 会把库模块依赖中包含的资源和清单设为最低优先级。

声明依赖

要为某个构建变体或测试源集配置依赖，可以把变体或测试源集的名称加在 Implementation 关键字前面，如下例所示：

Kotlin

dependencies {
    // Adds the local "mylibrary" module as a dependency to the "free" flavor.
    "freeImplementation"(project(":mylibrary"))

    // Adds a remote binary dependency only for local tests.
    testImplementation("junit:junit:4.12")

    // Adds a remote binary dependency only for the instrumented test APK.
    androidTestImplementation("com.android.support.test.espresso:espresso-core:3.6.1")
}

Groovy

dependencies {
    // Adds the local "mylibrary" module as a dependency to the "free" flavor.
    freeImplementation project(":mylibrary")

    // Adds a remote binary dependency only for local tests.
    testImplementation 'junit:junit:4.12'

    // Adds a remote binary dependency only for the instrumented test APK.
    androidTestImplementation 'com.android.support.test.espresso:espresso-core:3.6.1'
}

有关配置依赖的更多信息，请参阅添加构建依赖项。

使用感知变体的依赖管理

Android Gradle 插件 3.0.0 及以上版本提供了一种依赖机制，可以在消费库时自动匹配变体。例如，应用的 debug 变体会自动使用库的 debug 变体。使用产品变种时也一样：应用的 freeDebug 变体会使用库的 freeDebug 变体。

当无法直接匹配时，需要按照下一节说明提供匹配回退项，才能让插件正确匹配变体。

例如，假设应用配置了名为 staging 的构建类型，但某个库依赖没有这种类型。插件尝试构建应用的 staging 版本时，就无法确定应该使用哪个库版本，并会显示类似下面的错误：


Error:Failed to resolve: Could not resolve project :mylibrary.
Required by:
    project :app

解决变体匹配相关的构建错误

插件提供了相应的 DSL 元素，用来控制：当应用与依赖之间无法直接匹配变体时，Gradle 应如何处理。

下面列出感知变体的依赖匹配中可能出现的问题，以及使用 DSL 属性解决的方法：

  • 应用包含某种构建类型，但库依赖没有。

    例如，应用包含 staging 构建类型，而依赖只包含 debug 和 release。

    反过来，如果库依赖包含应用没有的构建类型，则不会产生问题，因为插件不会向依赖请求那种构建类型。

    使用 matchingFallbacks 为给定构建类型指定可替代的匹配项，如下所示：

    Kotlin

    // In the app's build.gradle.kts file.
android {
    buildTypes {
        getByName("debug") {}
        getByName("release") {}
        create("staging") {
            // Specifies a sorted list of fallback build types that the
            // plugin can try to use when a dependency does not include a
            // "staging" build type. You may specify as many fallbacks as you
            // like, and the plugin selects the first build type that's
            // available in the dependency.
            matchingFallbacks += listOf("debug", "qa", "release")
        }
    }
}

    Groovy

    // In the app's build.gradle file.
android {
    buildTypes {
        debug {}
        release {}
        staging {
            // Specifies a sorted list of fallback build types that the
            // plugin can try to use when a dependency does not include a
            // "staging" build type. You may specify as many fallbacks as you
            // like, and the plugin selects the first build type that's
            // available in the dependency.
            matchingFallbacks = ['debug', 'qa', 'release']
        }
    }
}

  • 应用和库依赖具有同一个变种维度，但应用包含的某个产品变种在库中不存在。

    例如，应用及其库依赖都有 tier 维度。但应用的 tier 维度包含 free 和 paid，某个依赖的同一维度却只包含 demo 和 paid。

    对于应用和库共有的某个变种维度，如果库包含应用没有的产品变种，则不会产生问题，因为插件不会向依赖请求那个产品变种。

    使用 matchingFallbacks 为应用的 free 产品变种指定可替代的匹配项，如下所示：

    Kotlin

    // In the app's build.gradle.kts file.
android {
    defaultConfig{
    // Don't configure matchingFallbacks in the defaultConfig block.
    // Instead, specify fallbacks for a given product flavor in the
    // productFlavors block, as shown below.
  }
    flavorDimensions += "tier"
    productFlavors {
        create("paid") {
            dimension = "tier"
            // Because the dependency already includes a "paid" flavor in its
            // "tier" dimension, you don't need to provide a list of fallbacks
            // for the "paid" flavor.
        }
        create("free") {
            dimension = "tier"
            // Specifies a sorted list of fallback flavors that the plugin
            // can try to use when a dependency's matching dimension does
            // not include a "free" flavor. Specify as many
            // fallbacks as you like; the plugin selects the first flavor
            // that's available in the dependency's "tier" dimension.
            matchingFallbacks += listOf("demo", "trial")
        }
    }
}

    Groovy

    // In the app's build.gradle file.
android {
    defaultConfig{
    // Don't configure matchingFallbacks in the defaultConfig block.
    // Instead, specify fallbacks for a given product flavor in the
    // productFlavors block, as shown below.
  }
    flavorDimensions 'tier'
    productFlavors {
        paid {
            dimension 'tier'
            // Because the dependency already includes a "paid" flavor in its
            // "tier" dimension, you don't need to provide a list of fallbacks
            // for the "paid" flavor.
        }
        free {
            dimension 'tier'
            // Specifies a sorted list of fallback flavors that the plugin
            // can try to use when a dependency's matching dimension does
            // not include a "free" flavor. Specify as many
            // fallbacks as you like; the plugin selects the first flavor
            // that's available in the dependency's "tier" dimension.
            matchingFallbacks = ['demo', 'trial']
        }
    }
}

  • 库依赖包含应用没有的某个变种维度。

    例如，库依赖包含 minApi 维度中的产品变种，而应用只在 tier 维度中定义了产品变种。构建应用的 freeDebug 版本时，插件就无法确定应使用依赖的 minApi23Debug 还是 minApi18Debug 版本。

    反过来，如果应用包含库依赖没有的变种维度，则不会产生问题，因为插件只会匹配依赖中存在的维度。例如，如果依赖没有 ABI 维度，应用的 freeX86Debug 版本就会使用依赖的 freeDebug 版本。

    在 defaultConfig 块中使用 missingDimensionStrategy，为每个缺失维度指定插件默认选择的产品变种，如下例所示。也可以在 productFlavors 块中覆盖这些选择，让每个产品变种针对缺失维度采用不同的匹配策略。

    Kotlin

    // In the app's build.gradle.kts file.
android {
    defaultConfig{
    // Specifies a sorted list of flavors that the plugin can try to use from
    // a given dimension. This tells the plugin to select the "minApi18" flavor
    // when encountering a dependency that includes a "minApi" dimension.
    // You can include additional flavor names to provide a
    // sorted list of fallbacks for the dimension.
    missingDimensionStrategy("minApi", "minApi18", "minApi23")
    // Specify a missingDimensionStrategy property for each
    // dimension that exists in a local dependency but not in your app.
    missingDimensionStrategy("abi", "x86", "arm64")
    }
    flavorDimensions += "tier"
    productFlavors {
        create("free") {
            dimension = "tier"
            // You can override the default selection at the product flavor
            // level by configuring another missingDimensionStrategy property
            // for the "minApi" dimension.
            missingDimensionStrategy("minApi", "minApi23", "minApi18")
        }
        create("paid") {}
    }
}

    Groovy

    // In the app's build.gradle file.
android {
    defaultConfig{
    // Specifies a sorted list of flavors that the plugin can try to use from
    // a given dimension. This tells the plugin to select the "minApi18" flavor
    // when encountering a dependency that includes a "minApi" dimension.
    // You can include additional flavor names to provide a
    // sorted list of fallbacks for the dimension.
    missingDimensionStrategy 'minApi', 'minApi18', 'minApi23'
    // Specify a missingDimensionStrategy property for each
    // dimension that exists in a local dependency but not in your app.
    missingDimensionStrategy 'abi', 'x86', 'arm64'
    }
    flavorDimensions 'tier'
    productFlavors {
        free {
            dimension 'tier'
            // You can override the default selection at the product flavor
            // level by configuring another missingDimensionStrategy property
            // for the 'minApi' dimension.
            missingDimensionStrategy 'minApi', 'minApi23', 'minApi18'
        }
        paid {}
    }
}

更多信息请参阅 Android Gradle 插件 DSL 参考文档中的 matchingFallbacks 和 missingDimensionStrategy。

配置签名设置

除非为 Release 构建明确指定签名配置，否则 Gradle 不会为它的 APK 或 AAB 签名。如果还没有签名密钥，请使用 Android Studio 生成上传密钥和密钥库。

要通过 Gradle 构建配置，手动配置 Release 构建类型的签名：

  1. 创建密钥库。密钥库（Keystore）是保存一组私钥的二进制文件，必须存放在安全的地方。
  2. 创建私钥。私钥（Private Key）用于为待分发的应用签名，绝不能随应用一起提供，也不能向未获授权的第三方披露。

  3. 把签名配置加入模块级 build.gradle.kts 文件：

    Kotlin

    ...
android {
    ...
    defaultConfig {...}
    signingConfigs {
        create("release") {
            storeFile = file("myreleasekey.keystore")
            storePassword = "password"
            keyAlias = "MyReleaseKey"
            keyPassword = "password"
        }
    }
    buildTypes {
        getByName("release") {
            ...
            signingConfig = signingConfigs.getByName("release")
        }
    }
}

    Groovy

    ...
android {
    ...
    defaultConfig {...}
    signingConfigs {
        release {
            storeFile file("myreleasekey.keystore")
            storePassword "password"
            keyAlias "MyReleaseKey"
            keyPassword "password"
        }
    }
    buildTypes {
        release {
            ...
            signingConfig signingConfigs.release
        }
    }
}

注意：把发布密钥和密钥库的密码直接写进构建文件并不安全。应配置为从环境变量读取密码，或者让构建过程提示输入密码。

要从环境变量读取这些密码：

Kotlin

storePassword = System.getenv("KSTOREPWD")
keyPassword = System.getenv("KEYPWD")

Groovy

storePassword System.getenv("KSTOREPWD")
keyPassword System.getenv("KEYPWD")

另一种方式是从本地 properties 文件加载密钥库。出于安全考虑，不要把这个文件加入源码版本控制，而应由每位开发者在本地配置。更多信息请参阅从构建文件中移除签名信息。

完成这些步骤后，就可以分发应用，并将其发布到 Google Play。

警告：请将密钥库和私钥保存在安全位置，并确保有可靠的备份。如果使用 Play App Signing，却丢失了上传密钥，可以通过 Play Console 申请重置。如果未使用 Play App Signing 发布应用——这种情况适用于 2021 年 8 月之前创建的应用——并且丢失了应用签名密钥，就无法再发布任何更新，因为同一个应用的所有版本必须始终用同一把密钥签名。

为 Wear OS 应用签名

发布 Wear OS 应用时，手表 APK 及可选的手机 APK 必须使用同一把密钥签名。有关 Wear OS 应用的打包与签名，请参阅打包和分发 Wear 应用。
