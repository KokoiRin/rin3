构建，到底在变换什么？

同一条构建里，有工程配置，有工具转换，也有最后交付给设备或发布平台的产物。

本页是独立导读，不属于官方文档译文。每条工具关系均附官方说明。

先拿住两个问题

面对一个陌生工程，先问：这次要构建谁？它的输入从哪里来？Settings 把项目加入构建；模块脚本应用插件、声明依赖并配置变体；插件把这些信息组织成任务。命令行请求的任务，再沿依赖关系拉起需要的工作。

然后问：现在看到的是源码、编译中间结果，还是最终交付物？我们用 :app → :camera-editor → :camera-core 三个模块贯穿阅读。这个例子用来帮你对应概念，不代表公司工程的具体配置。

Android 中，代码与资源会走不同的处理链

下面是输入、工具和输出的概念图，不是精确的 Gradle 任务图。实际步骤会交叉：例如资源处理会生成编译代码需要的符号，代码生成也会增加后续编译的输入。

代码这一侧

Kotlin / Java 源码
也包括被纳入编译的生成源码↓ Kotlin / Java 编译器JVM 字节码
例如 .class、JAR 中的类↓ D8，或启用优化时的 R8DEX
供 Android Runtime 使用的代码格式

资源与清单这一侧

Android 资源
应用与依赖提供的 Manifest↓ AAPT2 编译 / 链接资源；Manifest 合并编译后的资源与资源表
合并后的 Manifest↓ 与代码、原生库等一起进入打包形成应用包所需的其他内容
具体内容取决于工程配置
最后还要看交付格式。

APK 是设备可以安装的应用包。AAB 是发布格式，Google Play 等工具再根据它生成适合设备的 APK。签名与优化也取决于构建配置；不能只看到 release 名称就认定已经配置完成。

官方工具说明：D8 的输入与 DEX 输出 · AAPT2 的 Compile / Link · Manifest 合并 · R8 中文阅读版。AAPT2 链接生成的中间 APK 本身不包含 DEX，也未签名，不能把它当作完整可安装应用。

用“在哪一段失败”来组织排查

依赖解析失败：工具还没拿到合适的输入

先看请求的坐标、仓库、版本和变体，再查 dependencies / dependencyInsight。不要把“找不到库”直接当成 Kotlin 源码错误。继续读依赖报告。

生成或编译失败：源码到编译结果这段有问题

区分处理器是否配置、目标是否正确、生成任务有没有产生文件、生成源码是否参与编译。KSP 任务成功，不等于公司宿主已能发现服务。继续读KSP和KMP compilation。

Debug 正常、Release 异常：先比较实际配置

比较依赖、源集、优化与签名等差异；如果证据指向 R8，再检查动态入口与保留规则。仅凭类找不到的异常，不能判断究竟是没有生成、没有打包、被裁剪，还是注册发现链路未接通。继续读构建变体和R8。

这一组怎么学

先把关系看懂，再回到一个真实工程观察。第一轮按首页的路线读，每阶段只抓一个可核对的问题：哪个文件决定模块、哪个依赖对消费者可见、正在构建哪个变体、哪个任务生成代码、缓存省掉哪一层工作、哪些源集进入哪个目标。

第二轮再带着配置或日志回查长文。你已经学过的并行、关键路径和 Task 输入输出，可以直接用于解释这里的现象。完成材料阅读不自动等于能独立排障；以后我们用一个真实问题，把文件、任务、产物和证据连起来就够了，不需要现在另造一整套构建平台。
