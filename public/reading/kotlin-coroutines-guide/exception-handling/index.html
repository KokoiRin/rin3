协程异常处理

协程取消后，会在可取消的挂起点抛出 CancellationException。协程机制把这看作正常取消。本章接着看两个问题：如果取消过程中又抛出别的异常，会怎样？如果同一父任务下有多个子任务抛出异常，最终会报告哪一个？

异常传播

先看没有父协程的任务，也就是根协程。用 launch 启动它时，未处理的异常会自动传播，类似 Java 的 Thread.uncaughtExceptionHandler 处理未捕获异常。用 async 或 produce 启动它时，调用方需要分别通过 await 或 receive 取得结果，此时也会得到异常。produce 和 receive 的用法见《通道》。

下面用 GlobalScope 创建根协程，演示这一区别。

编者注

根协程是没有父协程的协程。先记住这个条件，后面读到“子协程出错会通知父任务”时，就能看出两段代码为何表现不同。

GlobalScope 是需要谨慎使用的 API，可能带来不易察觉的问题。为整个应用创建根协程是它少数合理用途之一。使用时需显式声明 @OptIn(DelicateCoroutinesApi::class)。

import kotlinx.coroutines.*

//sampleStart
@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
    val job = GlobalScope.launch { // 用 launch 创建的根协程
        println("Throwing exception from launch")
        throw IndexOutOfBoundsException() // 异常将由 Thread.defaultUncaughtExceptionHandler 打印到控制台
    }
    job.join()
    println("Joined failed job")
    val deferred = GlobalScope.async { // 用 async 创建的根协程
        println("Throwing exception from async")
        throw ArithmeticException() // 这里没有输出；调用方要通过 await 取得结果或异常
    }
    try {
        deferred.await()
        println("Unreached")
    } catch (e: ArithmeticException) {
        println("Caught ArithmeticException")
    }
}
//sampleEnd

查看完整代码。

开启调试时，程序会产生以下输出。

Throwing exception from launch
Exception in thread "DefaultDispatcher-worker-1 @coroutine#2" java.lang.IndexOutOfBoundsException
Joined failed job
Throwing exception from async
Caught ArithmeticException

CoroutineExceptionHandler

根协程遇到未捕获异常时，默认会把它打印到控制台。想统一记录或显示根协程及其子任务最终未处理的错误，可以在根协程的上下文中安装 CoroutineExceptionHandler。它类似 Thread.uncaughtExceptionHandler。处理器运行时，出错的协程已经结束，此处可记录日志、显示错误、终止或重启应用，已经无法让它从失败处继续执行。

只有未通过其他方式处理的异常才会交给 CoroutineExceptionHandler。普通子协程，即在另一个 Job 的上下文中建立的协程，会将异常处理交给父协程，逐级传到根。因此，装在这些子协程上的处理器不会用于处理该错误。async 总是将异常保存在结果 Deferred 中，装在 async 上的处理器同样没有效果。

直接受监督作用域管理的协程不会将失败传给父任务，是这项规则的例外，详见「监督」。

import kotlinx.coroutines.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    val job = GlobalScope.launch(handler) { // 在 GlobalScope 中运行的根协程
        throw AssertionError()
    }
    val deferred = GlobalScope.async(handler) { // 同样是根协程，这次用 async 启动
        throw ArithmeticException() // 这里没有输出；调用方要通过 deferred.await() 取得结果或异常
    }
    joinAll(job, deferred)
//sampleEnd    
}

查看完整代码。

输出如下。

CoroutineExceptionHandler got java.lang.AssertionError

取消与异常

协程内部用 CancellationException 表示取消，异常处理器忽略这类异常。需要调试时可以在 catch 块中取得其他信息。用 Job.cancel 取消一个协程会使它终止，但不会因此取消它的父任务。

import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val job = launch {
        val child = launch {
            try {
                delay(Long.MAX_VALUE)
            } finally {
                println("Child is cancelled")
            }
        }
        yield()
        println("Cancelling child")
        child.cancel()
        child.join()
        yield()
        println("Parent is not cancelled")
    }
    job.join()
//sampleEnd    
}

查看完整代码。

输出如下。

Cancelling child
Child is cancelled
Parent is not cancelled

在普通父子关系中，子协程遇到 CancellationException 以外的异常时，会携带这个异常取消父协程。这种行为不可覆盖，以保证结构化并发中的层级关系稳定。普通子协程上的 CoroutineExceptionHandler 不会接管它。

这些例子把处理器装在用 GlobalScope 创建的协程上。若装在 main 的 runBlocking 作用域中的普通子协程上，子协程因异常结束时，主协程仍然会被取消。 [1]

一个子任务失败后，父协程会先等所有子任务结束。等其余子任务也完成收尾，父协程才处理最初的异常。留意下面日志中几行消息出现的顺序。

import kotlinx.coroutines.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    val job = GlobalScope.launch(handler) {
        launch { // 第一个子任务
            try {
                delay(Long.MAX_VALUE)
            } finally {
                withContext(NonCancellable) {
                    println("Children are cancelled, but exception is not handled until all children terminate")
                    delay(100)
                    println("The first child finished its non cancellable block")
                }
            }
        }
        launch { // 第二个子任务
            delay(10)
            println("Second child throws an exception")
            throw ArithmeticException()
        }
    }
    job.join()
//sampleEnd 
}

查看完整代码。

输出如下。

Second child throws an exception
Children are cancelled, but exception is not handled until all children terminate
The first child finished its non cancellable block
CoroutineExceptionHandler got java.lang.ArithmeticException

汇总多个异常

如果多个子任务先后失败，通常以第一个异常为主。随后出现的异常会附在第一个异常的 suppressed 列表里，所以查看主异常时也能找到它们。

import kotlinx.coroutines.*
import java.io.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, exception ->
        println("CoroutineExceptionHandler got $exception with suppressed ${exception.suppressed.contentToString()}")
    }
    val job = GlobalScope.launch(handler) {
        launch {
            try {
                delay(Long.MAX_VALUE) // 另一个子任务因 IOException 失败时，这个任务会被取消
            } finally {
                throw ArithmeticException() // 第二个异常
            }
        }
        launch {
            delay(100)
            throw IOException() // 第一个异常
        }
        delay(Long.MAX_VALUE)
    }
    job.join()  
}

查看完整代码。

输出如下。

CoroutineExceptionHandler got java.io.IOException with suppressed [java.lang.ArithmeticException]

原文注明，这种机制目前只能在 Java 1.7 及以上版本使用，JS 和 Native 上的限制是暂时的，计划今后解除。

取消异常是透明的，默认会解包，让原始异常出现在处理器中。

import kotlinx.coroutines.*
import java.io.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception ->
        println("CoroutineExceptionHandler got $exception")
    }
    val job = GlobalScope.launch(handler) {
        val innerJob = launch { // 这一串嵌套协程都会被取消
            launch {
                launch {
                    throw IOException() // 最初的异常
                }
            }
        }
        try {
            innerJob.join()
        } catch (e: CancellationException) {
            println("Rethrowing CancellationException with original cause")
            throw e // 这里重新抛出取消异常，处理器收到的仍是最初的 IOException  
        }
    }
    job.join()
//sampleEnd    
}

查看完整代码。

输出如下。

Rethrowing CancellationException with original cause
CoroutineExceptionHandler got java.io.IOException

监督

在普通任务树中，失败会影响父任务，取消又会向下传给其他任务，作用由此遍及层级。下面看需要单向传播的场景。

例如，UI 组件的作用域有自己的 Job。一个界面子任务失败时，未必需要取消整个组件；但组件被销毁、其 Job 被取消时，就应取消所有子任务，因为它们的结果已没有用途。

再如，服务器进程派生多个子任务，需要监督其执行、追踪故障并只重启那些失败的任务。

监督任务

在需要单向传递取消的地方，可以使用 SupervisorJob。子任务失败或被取消时，其他直接子任务可以继续运行；如果取消 SupervisorJob 本身，它管理的子任务仍都会被取消。

import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val supervisor = SupervisorJob()
    with(CoroutineScope(coroutineContext + supervisor)) {
        // 启动第一个子任务；仅本例忽略它的异常，实际应用应处理异常
        val firstChild = launch(CoroutineExceptionHandler { _, _ ->  }) {
            println("The first child is failing")
            throw AssertionError("The first child is cancelled")
        }
        // 启动第二个子任务
        val secondChild = launch {
            firstChild.join()
            // 第一个子任务被取消不会导致第二个子任务也被取消
            println("The first child is cancelled: ${firstChild.isCancelled}, but the second one is still active")
            try {
                delay(Long.MAX_VALUE)
            } finally {
                // 取消监督者时，取消请求会向下传播
                println("The second child is cancelled because the supervisor was cancelled")
            }
        }
        // 等第一个子任务失败并结束
        firstChild.join()
        println("Cancelling the supervisor")
        supervisor.cancel()
        secondChild.join()
    }
//sampleEnd
}

查看完整代码。

输出如下。

The first child is failing
The first child is cancelled: true, but the second one is still active
Cancelling the supervisor
The second child is cancelled because the supervisor was cancelled

监督作用域

可以用 supervisorScope 替代 coroutineScope 来组织局部并发。取消在这里单向传播：只有作用域自身失败或被取消时，才取消所有子任务。与 coroutineScope 相同，它要等所有子任务完成才会结束。

import kotlin.coroutines.*
import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    try {
        supervisorScope {
            val child = launch {
                try {
                    println("The child is sleeping")
                    delay(Long.MAX_VALUE)
                } finally {
                    println("The child is cancelled")
                }
            }
            // 调用 yield，让子协程有机会运行并打印 
            yield()
            println("Throwing an exception from the scope")
            throw AssertionError()
        }
    } catch(e: AssertionError) {
        println("Caught an assertion error")
    }
//sampleEnd
}

查看完整代码。

输出如下。

The child is sleeping
Throwing an exception from the scope
The child is cancelled
Caught an assertion error

受监督协程中的异常

普通任务和监督任务在异常处理上还有一项重要区别。由于直接子任务的失败不传播给监督者，每个子任务需按自身的异常处理机制处理异常。直接在 supervisorScope 内 launch 的协程可以像根协程一样使用其上下文中安装的 CoroutineExceptionHandler，详见前面的处理器一节。 [1]

import kotlin.coroutines.*
import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    supervisorScope {
        val child = launch(handler) {
            println("The child throws an exception")
            throw AssertionError()
        }
        println("The scope is completing")
    }
    println("The scope is completed")
//sampleEnd
}

查看完整代码。

输出如下。

The scope is completing
The child throws an exception
CoroutineExceptionHandler got java.lang.AssertionError
The scope is completed

编者自测

日志中，子协程开始在 finally 中清理时，为什么父协程的异常处理器还没有报告最初的错误？

查看答案

父协程要先等所有子任务结束。其他子任务收到取消后可能还要清理资源，等它们完成，处理器才收到导致失败的异常。
