协程怎样处理异常

一个子任务失败后，先发生取消、清理还是错误报告？对照普通任务树与监督作用域，跟踪同一个异常。

协程用 CancellationException 表示正常取消。接下来看看两种更复杂的情况：清理时又出错，以及多个子协程先后出错。

异常向哪里传播

先看没有父任务的根协程。根 launch 会报告未捕获异常，类似 JVM 线程的未捕获异常处理器。根 async 把失败保存在 Deferred 中，调用 await 时可见；produce 则可以通过通道的接收操作向消费者交付失败。 receive

下面特意在 GlobalScope 中创建根协程，比较两种构建器。

GlobalScope 属于需要显式选择加入的 API。只有任务确实与整个应用同寿命等少数情况才适合使用，示例通过 @OptIn(DelicateCoroutinesApi::class) 表明这一点。

import kotlinx.coroutines.*

//sampleStart
@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
    val job = GlobalScope.launch { // root coroutine with launch
        println("Throwing exception from launch")
        throw IndexOutOfBoundsException() // Will be printed to the console by Thread.defaultUncaughtExceptionHandler
    }
    job.join()
    println("Joined failed job")
    val deferred = GlobalScope.async { // root coroutine with async
        println("Throwing exception from async")
        throw ArithmeticException() // Nothing is printed, relying on user to call await
    }
    try {
        deferred.await()
        println("Unreached")
    } catch (e: ArithmeticException) {
        println("Caught ArithmeticException")
    }
}
//sampleEnd

查看完整示例。

开启协程调试后，可以看到下面的输出。 debug

Throwing exception from launch
Exception in thread "DefaultDispatcher-worker-1 @coroutine#2" java.lang.IndexOutOfBoundsException
Joined failed job
Throwing exception from async
Caught ArithmeticException

未捕获异常的最后处理处

可以在根协程的上下文里安装 CoroutineExceptionHandler，统一记录从任务树传来的未捕获异常。它的角色类似 Thread.uncaughtExceptionHandler。运行到这里，协程已经失败，通常只能写日志、显示错误，或让应用终止或重启。

处理器只接收尚未由其他途径处理的异常。普通子协程把失败交给父协程，逐层传至根，因此装在普通子协程上的处理器不会接管失败。async 会把异常保存在 Deferred 中，装在 async 上的处理器也不起这个作用。 Job

直接由监督作用域管理的子任务具有不同的传播规则，下文会展开。 Supervision

import kotlinx.coroutines.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    val job = GlobalScope.launch(handler) { // root coroutine, running in GlobalScope
        throw AssertionError()
    }
    val deferred = GlobalScope.async(handler) { // also root, but async instead of launch
        throw ArithmeticException() // Nothing will be printed, relying on user to call deferred.await()
    }
    joinAll(job, deferred)
//sampleEnd    
}

查看完整示例。

一次运行的输出如下。

CoroutineExceptionHandler got java.lang.AssertionError

取消与异常如何相遇

Job.cancel 请求取消时，协程内部用 CancellationException 传达信号。未捕获异常处理器通常忽略它，必要时可以在 catch 中取得调试线索。单独取消一个子任务不会取消父任务。

import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val job = launch {
        val child = launch {
            try {
                delay(Long.MAX_VALUE)
            } finally {
                println("Child is cancelled")
            }
        }
        yield()
        println("Cancelling child")
        child.cancel()
        child.join()
        yield()
        println("Parent is not cancelled")
    }
    job.join()
//sampleEnd    
}

查看完整示例。

一次运行的输出如下。

Cancelling child
Child is cancelled
Parent is not cancelled

在普通父子关系中，如果子协程抛出 CancellationException 以外的异常，它会让父协程随之失败。这条规则保证同一项工作一起收尾，在子协程里安装处理器也改变不了它。 structured concurrency · CoroutineExceptionHandler

示例把处理器安装在 GlobalScope 创建的根协程上。如果把它安装到 runBlocking 的普通子任务，子任务失败仍会取消外层 runBlocking。 CoroutineExceptionHandler

父协程要等所有子任务结束，才会处理最初的异常。观察下面例子中清理日志与处理器日志的顺序。

import kotlinx.coroutines.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    val job = GlobalScope.launch(handler) {
        launch { // the first child
            try {
                delay(Long.MAX_VALUE)
            } finally {
                withContext(NonCancellable) {
                    println("Children are cancelled, but exception is not handled until all children terminate")
                    delay(100)
                    println("The first child finished its non cancellable block")
                }
            }
        }
        launch { // the second child
            delay(10)
            println("Second child throws an exception")
            throw ArithmeticException()
        }
    }
    job.join()
//sampleEnd 
}

查看完整示例。

一次运行的输出如下。

Second child throws an exception
Children are cancelled, but exception is not handled until all children terminate
The first child finished its non cancellable block
CoroutineExceptionHandler got java.lang.ArithmeticException

多个异常如何汇总

一般是第一个失败决定最终报告的异常。此后出现的其他异常，会以 suppressed 异常附在第一个异常上，便于一起排查。

import kotlinx.coroutines.*
import java.io.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
    val handler = CoroutineExceptionHandler { _, exception ->
        println("CoroutineExceptionHandler got $exception with suppressed ${exception.suppressed.contentToString()}")
    }
    val job = GlobalScope.launch(handler) {
        launch {
            try {
                delay(Long.MAX_VALUE) // it gets cancelled when another sibling fails with IOException
            } finally {
                throw ArithmeticException() // the second exception
            }
        }
        launch {
            delay(100)
            throw IOException() // the first exception
        }
        delay(Long.MAX_VALUE)
    }
    job.join()  
}

查看完整示例。

一次运行的输出如下。

CoroutineExceptionHandler got java.io.IOException with suppressed [java.lang.ArithmeticException]

原文注明该示例的 suppressed 异常聚合机制适用于 Java 1.7 及以上，JS 和 Native 的支持情况需按目标平台核对。

取消异常在传播中具有透明性。观察嵌套任务被取消后，最外层处理器最后拿到的原始失败。

import kotlinx.coroutines.*
import java.io.*

@OptIn(DelicateCoroutinesApi::class)
fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception ->
        println("CoroutineExceptionHandler got $exception")
    }
    val job = GlobalScope.launch(handler) {
        val innerJob = launch { // all this stack of coroutines will get cancelled
            launch {
                launch {
                    throw IOException() // the original exception
                }
            }
        }
        try {
            innerJob.join()
        } catch (e: CancellationException) {
            println("Rethrowing CancellationException with original cause")
            throw e // cancellation exception is rethrown, yet the original IOException gets to the handler  
        }
    }
    job.join()
//sampleEnd    
}

查看完整示例。

一次运行的输出如下。

Rethrowing CancellationException with original cause
CoroutineExceptionHandler got java.io.IOException

监督子任务

普通任务树里，子任务失败会向上影响父任务，父任务取消又会向下传播。有时需要把这两个方向分开处理。

例如一个页面同时加载几个区域，其中一个失败时，其余区域仍可以显示。页面关闭后，所有子任务都应停止，因为它们的结果已经没有接收者。

服务端也可能需要分别观察各个任务，只重启失败的那个。

使用 SupervisorJob

SupervisorJob 像普通 Job 一样管理子任务，但一个直接子任务的失败或取消不会传给监督者和兄弟任务。看下面的例子，分别观察子任务失败与监督者取消的结果。

import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val supervisor = SupervisorJob()
    with(CoroutineScope(coroutineContext + supervisor)) {
        // launch the first child -- its exception is ignored for this example (don't do this in practice!)
        val firstChild = launch(CoroutineExceptionHandler { _, _ ->  }) {
            println("The first child is failing")
            throw AssertionError("The first child is cancelled")
        }
        // launch the second child
        val secondChild = launch {
            firstChild.join()
            // Cancellation of the first child is not propagated to the second child
            println("The first child is cancelled: ${firstChild.isCancelled}, but the second one is still active")
            try {
                delay(Long.MAX_VALUE)
            } finally {
                // But cancellation of the supervisor is propagated
                println("The second child is cancelled because the supervisor was cancelled")
            }
        }
        // wait until the first child fails & completes
        firstChild.join()
        println("Cancelling the supervisor")
        supervisor.cancel()
        secondChild.join()
    }
//sampleEnd
}

查看完整示例。

一次运行的输出如下。

The first child is failing
The first child is cancelled: true, but the second one is still active
Cancelling the supervisor
The second child is cancelled because the supervisor was cancelled

使用 supervisorScope

supervisorScope 把同样的行为限制在一个代码块里。直接子任务各自失败，作用域自身失败或被取消时则会取消所有子任务。和 coroutineScope 一样，它会等子任务结束才返回。

import kotlin.coroutines.*
import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    try {
        supervisorScope {
            val child = launch {
                try {
                    println("The child is sleeping")
                    delay(Long.MAX_VALUE)
                } finally {
                    println("The child is cancelled")
                }
            }
            // Give our child a chance to execute and print using yield 
            yield()
            println("Throwing an exception from the scope")
            throw AssertionError()
        }
    } catch(e: AssertionError) {
        println("Caught an assertion error")
    }
//sampleEnd
}

查看完整示例。

一次运行的输出如下。

The child is sleeping
Throwing an exception from the scope
The child is cancelled
Caught an assertion error

谁负责监督下的异常

监督者隔开了子任务的失败，所以每个直接子任务都需要自己的异常处理方式。直接在 supervisorScope 中 launch 的协程可以像根 launch 一样，使用上下文中的 CoroutineExceptionHandler 报告未处理的异常。

import kotlin.coroutines.*
import kotlinx.coroutines.*

fun main() = runBlocking {
//sampleStart
    val handler = CoroutineExceptionHandler { _, exception -> 
        println("CoroutineExceptionHandler got $exception") 
    }
    supervisorScope {
        val child = launch(handler) {
            println("The child throws an exception")
            throw AssertionError()
        }
        println("The scope is completing")
    }
    println("The scope is completed")
//sampleEnd
}

查看完整示例。

一次运行的输出如下。

The scope is completing
The child throws an exception
CoroutineExceptionHandler got java.lang.AssertionError
The scope is completed

读完试一题

在普通 coroutineScope 的子 async 里抛出异常，一直不调 await，能让它的兄弟任务继续吗？

展开参考答案

不能。异常虽也记录在 Deferred 里，子任务的非取消异常仍会使普通父作用域失败，进而取消兄弟任务。监督作用域才会隔离直接子任务的失败。
