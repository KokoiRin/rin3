Dispatchers.Default 可以把协程安排到多条线程上并行执行。如果这些协程读写同一份会变化的数据，就要协调它们的访问。下面的做法一部分也适用于普通多线程程序，另一部分利用了协程本身的特点。

问题

例子启动 100 个协程，每个协程把同一个动作重复 1,000 次。程序还会记录全部动作完成所用的时间，后面几种解法都用它来比较。

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

从最简单的操作开始：在多线程的 Dispatchers.Default 上递增一个共享的可变计数器。

编者注

counter++ 要先读出旧值，再把加一后的结果写回去。两个工作者若都读到 7，就可能都写回 8。代码执行了两次加一，计数器却只增加了一次。

import kotlinx.coroutines.*
import kotlin.system.*    

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
var counter = 0

fun main() = runBlocking {
    withContext(Dispatchers.Default) {
        massiveRun {
            counter++
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

如果每次加一都生效，最后应该得到 Counter = 100000。这里有 100 个协程从多条线程同时修改同一个变量，中间没有协调，运行时几乎不会稳定地得到这个数。

volatile 无法解决这个问题

一种常见误解是把变量声明为 volatile 就能解决并发访问问题。下面试一次。

import kotlinx.coroutines.*
import kotlin.system.*

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
@Volatile // Kotlin 用注解声明 volatile 
var counter = 0

fun main() = runBlocking {
    withContext(Dispatchers.Default) {
        massiveRun {
            counter++
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

加上 volatile 之后，程序更慢，结果也仍然有时小于 100000。volatile 保证对变量的每次读、每次写分别是原子的。一次自增却包括读出旧值、加一、写回新值，这几步合在一起没有原子性保证。

线程安全的数据结构

一种同时适用于线程和协程的通用方案是使用线程安全的数据结构，让它为共享状态上所需的操作提供同步，例如提供可线性化的原子操作。简单计数器可用 AtomicInteger，它提供原子的 incrementAndGet 操作。

import kotlinx.coroutines.*
import java.util.concurrent.atomic.*
import kotlin.system.*

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
val counter = AtomicInteger()

fun main() = runBlocking {
    withContext(Dispatchers.Default) {
        massiveRun {
            counter.incrementAndGet()
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

在这个特定问题中，这是速度最快的解法。它适用于计数器、集合、队列等标准数据结构及其基本操作。如果状态更复杂，或需要的复合操作缺少现成线程安全实现，就很难直接推广。

细粒度的线程封闭

线程封闭是将对某份共享状态的所有访问限制在一条线程上。典型例子是 UI 应用：所有界面状态都归单一的事件分发线程或应用线程处理。在协程中可以使用单线程上下文实现。

import kotlinx.coroutines.*
import kotlin.system.*

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
val counterContext = newSingleThreadContext("CounterContext")
var counter = 0

fun main() = runBlocking {
    withContext(Dispatchers.Default) {
        massiveRun {
            // 把每次自增都切换到单线程上下文执行
            withContext(counterContext) {
                counter++
            }
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

慢在哪里？每加一次，withContext(counterContext) 都要把执行从 Dispatchers.Default 切到那条专用线程。这个例子为每次加一都付出了切换上下文的代价。

粗粒度的线程封闭

实际中通常将整段更新状态的业务逻辑限制在单一线程上。下例从一开始就在单线程上下文中运行每个协程。

import kotlinx.coroutines.*
import kotlin.system.*

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
val counterContext = newSingleThreadContext("CounterContext")
var counter = 0

fun main() = runBlocking {
    // 把整段工作限制在同一个单线程上下文里
    withContext(counterContext) {
        massiveRun {
            counter++
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

新写法运行快得多，也能得到正确结果。

互斥

还可以约定，同一时间只允许一个执行者修改共享状态。受保护的这段代码叫临界区。阻塞代码常用 synchronized 或 ReentrantLock；协程可以用 Mutex，进入前 lock，离开时 unlock。Mutex.lock() 在等锁时会挂起协程，让线程继续做别的工作。

使用扩展函数 withLock 可以方便地表达先 mutex.lock()、在 try 中执行操作、最后在 finally 中 mutex.unlock() 的模式。

import kotlinx.coroutines.*
import kotlinx.coroutines.sync.*
import kotlin.system.*

suspend fun massiveRun(action: suspend () -> Unit) {
    val n = 100  // 要启动的协程数量
    val k = 1000 // 每个协程重复执行操作的次数
    val time = measureTimeMillis {
        coroutineScope { // 协程所属的作用域 
            repeat(n) {
                launch {
                    repeat(k) { action() }
                }
            }
        }
    }
    println("Completed ${n * k} actions in $time ms")    
}

//sampleStart
val mutex = Mutex()
var counter = 0

fun main() = runBlocking {
    withContext(Dispatchers.Default) {
        massiveRun {
            // 用锁保护每一次自增
            mutex.withLock {
                counter++
            }
        }
    }
    println("Counter = $counter")
}
//sampleEnd

查看完整代码。

这个例子每次递增都要加锁，因此有细粒度加锁的开销。当共享状态需要定期修改，又没有天然归属的线程时，互斥是合适的选择。

编者自测

给 counter 加上 volatile，为什么 counter++ 仍可能漏计？

查看答案

一次自增要先读再写。两个协程可能读到同一个旧值，各加一后写回同一个新值。volatile 对单次读写的保证，无法把这一整串操作合成一次。
