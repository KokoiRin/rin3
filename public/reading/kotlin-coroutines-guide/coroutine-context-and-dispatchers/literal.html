协程总是在某个上下文中执行。Kotlin 标准库用 CoroutineContext 类型的值表示这个上下文。

协程上下文是一组元素。其中最主要的是前面介绍过的 Job，以及本节讨论的调度器。

调度器与线程

上下文包含协程调度器 CoroutineDispatcher，它决定协程用哪条或哪些线程执行。它可以将执行限制在一条特定线程上，调度到线程池，也可以允许协程不受特定线程的约束。

launch、async 等构建器都接受可选的 CoroutineContext 参数，可以借此为新协程显式指定调度器及其他上下文元素。

试运行下面的示例。

import kotlinx.coroutines.*

//sampleStart
fun main() = runBlocking<Unit> {
    launch { // 继承父协程的上下文，本例的父协程是 main 中的 runBlocking
        println("main runBlocking      : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(Dispatchers.Unconfined) { // 不限定恢复线程，此处从主线程开始执行
        println("Unconfined            : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(Dispatchers.Default) { // 交由默认调度器执行 
        println("Default               : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(newSingleThreadContext("MyOwnThread")) { // 会拥有一条新的专用线程
        println("newSingleThreadContext: I'm working in thread ${Thread.currentThread().name}")
    }
}
//sampleEnd

可以在这里查看完整代码。

输出如下，顺序可能不同。

Unconfined            : I'm working in thread main
Default               : I'm working in thread DefaultDispatcher-worker-1
newSingleThreadContext: I'm working in thread MyOwnThread
main runBlocking      : I'm working in thread main

不带参数地使用 launch 时，会继承启动它的 CoroutineScope 的上下文，因而也继承其调度器。本例继承主线程上运行的 main 中的 runBlocking 协程的上下文。

Dispatchers.Unconfined 是一种特殊调度器。它看起来也在主线程上运行，但机制不同，下文会解释。

如果作用域未显式指定其他调度器，就使用默认调度器 Dispatchers.Default，它在共享的后台线程池上工作。

newSingleThreadContext 为协程创建一条新线程。专用线程是昂贵的资源。实际应用要么在不再需要时用 close 释放，要么保存到顶层变量中供整个应用复用。

不限定线程的调度器与限定线程的调度器

Dispatchers.Unconfined 从调用者线程开始执行协程，直到第一次真正挂起。挂起后，恢复在哪条线程完全取决于刚调用的挂起函数。它适用于几乎不占用 CPU 时间、也不更新限定在特定线程上的共享数据（例如 UI）的协程。

通常会默认继承外部 CoroutineScope 的调度器。特别是，runBlocking 的默认调度器限制在调用线程上。因此继承它的协程也限制在这条线程上，按可预期的先进先出顺序调度。

import kotlinx.coroutines.*

//sampleStart
fun main() = runBlocking<Unit> {
    launch(Dispatchers.Unconfined) { // 不限定恢复线程，此处从主线程开始执行
        println("Unconfined      : I'm working in thread ${Thread.currentThread().name}")
        delay(500)
        println("Unconfined      : After delay in thread ${Thread.currentThread().name}")
    }
    launch { // 继承父协程的上下文，本例的父协程是 main 中的 runBlocking
        println("main runBlocking: I'm working in thread ${Thread.currentThread().name}")
        delay(1000)
        println("main runBlocking: After delay in thread ${Thread.currentThread().name}")
    }
}
//sampleEnd

可以在这里查看完整代码。

输出如下。

Unconfined      : I'm working in thread main
main runBlocking: I'm working in thread main
Unconfined      : After delay in thread kotlinx.coroutines.DefaultExecutor
main runBlocking: After delay in thread main

所以，继承 runBlocking 上下文的协程仍在主线程中继续执行，而不限定线程的协程则在 delay 使用的默认执行器线程中恢复。

不限定线程的调度器属于高级机制。在某些特殊情形中，协程必须立即执行一项操作，把它排队留待以后执行没有必要或会产生副作用，此时才可能有用。普通代码中不宜使用。

调试协程与线程

协程可以在一条线程上挂起，在另一条线程上恢复。即便调度器只使用一条线程，缺乏专用工具时，也可能很难弄清协程在何时何处执行了什么。

使用 IDEA 调试

Kotlin 插件中的协程调试器简化了 IntelliJ IDEA 的协程调试。

调试功能适用于 kotlinx-coroutines-core 1.3.8 及以上版本。

Debug 工具窗口包含 Coroutines 标签页。其中既有正在运行的协程，也有已挂起的协程，并按照各自使用的调度器分组。

协程调试器支持以下操作。

  • 检查每个协程的状态。

  • 查看运行中或已挂起协程的局部变量及捕获变量。

  • 查看协程完整的创建栈和内部调用栈。栈中包含带有变量值的各个调用帧，包括普通调试中可能丢失的帧。

  • 取得含有所有协程状态与堆栈的完整报告。在 Coroutines 标签页中右键，选择 Get Coroutines Dump。

设置断点，以调试模式运行应用，即可开始调试。

在配套教程中可进一步了解如何调试协程。

通过日志调试

不使用协程调试器时，另一种调试多线程应用的方法是让每条日志都记录线程名，常见日志框架均支持。使用协程时，只有线程名提供的线索有限，kotlinx.coroutines 因而提供了额外的调试功能。

为 JVM 加上 -Dkotlinx.coroutines.debug 选项后，运行以下代码。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

//sampleStart
fun main() = runBlocking<Unit> {
    val a = async {
        log("I'm computing a piece of the answer")
        6
    }
    val b = async {
        log("I'm computing another piece of the answer")
        7
    }
    log("The answer is ${a.await() * b.await()}")
}
//sampleEnd

可以在这里查看完整代码。

这里共有三个协程：runBlocking 中的主协程（#1），以及分别计算 a（#2）和 b（#3）两个 Deferred 值的协程。它们都在 runBlocking 的上下文中执行，限定在主线程上。输出如下。

[main @coroutine#2] I'm computing a piece of the answer
[main @coroutine#3] I'm computing another piece of the answer
[main @coroutine#1] The answer is 42

log 函数用方括号打印线程名。可以看到主线程名后附有当前执行的协程编号。开启调试模式后，每个新建协程会依次获得一个编号。

用 -ea 选项启动 JVM 时也会开启调试模式。有关调试功能的详情见 DEBUG_PROPERTY_NAME 属性的文档。

在线程间切换

用 JVM 选项 -Dkotlinx.coroutines.debug 运行以下代码，详见调试说明。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

fun main() {
    newSingleThreadContext("Ctx1").use { ctx1 ->
        newSingleThreadContext("Ctx2").use { ctx2 ->
            runBlocking(ctx1) {
                log("Started in ctx1")
                withContext(ctx2) {
                    log("Working in ctx2")
                }
                log("Back to ctx1")
            }
        }
    }
}

可以在这里查看完整代码。

此示例演示了两种新的用法。

第一种是为 runBlocking 指定上下文。第二种是调用 withContext；它可能挂起当前协程，在与原上下文不同的新上下文中执行。如果指定了另一个 CoroutineDispatcher，会发生额外调度：代码块被安排到新调度器执行，结束后再回到原调度器。

因此，上述代码的输出如下。

[Ctx1 @coroutine#1] Started in ctx1
[Ctx2 @coroutine#1] Working in ctx2
[Ctx1 @coroutine#1] Back to ctx1

示例使用 Kotlin 标准库的 use 函数，在不再需要时正确释放由 newSingleThreadContext 创建的线程资源。

上下文中的 Job

协程的 Job 是其上下文的一部分，可以用 coroutineContext[Job] 取得它。

}

调试模式下的输出类似如下。

协程的子任务

在另一协程的 CoroutineScope 中启动协程时，会通过 CoroutineScope.coroutineContext 继承外层上下文。新协程的 Job 成为父 Job 的子任务。取消父协程时，其所有后代也会递归地被取消。

不过，可以显式用以下两种方式改变这层父子关系。

  1. 启动协程时显式使用其他作用域，例如 GlobalScope.launch，新任务就不会从调用处的父作用域取得 Job。

  2. 将另一个 Job 作为新协程的上下文参数传入，会覆盖原先父作用域中的 Job，如下例所示。

这两种情况下，新协程都脱离了调用处所在的作用域，独立运行。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    // 启动一个协程处理传入的请求
    val request = launch {
        // 它还会启动两个子任务
        launch(Job()) { 
            println("job1: I run in my own Job and execute independently!")
            delay(1000)
            println("job1: I am not affected by cancellation of the request")
        }
        // 另一个则继承父协程的上下文
        launch {
            delay(100)
            println("job2: I am a child of the request coroutine")
            delay(1000)
            println("job2: I will not execute this line if my parent request is cancelled")
        }
    }
    delay(500)
    request.cancel() // 取消这一次请求的处理
    println("main: Who has survived request cancellation?")
    delay(1000) // 让主协程等一秒，再观察结果
//sampleEnd
}

可以在这里查看完整代码。

输出如下。

job1: I run in my own Job and execute independently!
job2: I am a child of the request coroutine
main: Who has survived request cancellation?
job1: I am not affected by cancellation of the request

父协程的责任

父协程总会等待其全部子协程完成。无须显式记录它启动的所有子任务，也不必在末尾显式调用 Job.join 来等待它们。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    // 启动一个协程处理传入的请求
    val request = launch {
        repeat(3) { i -> // 启动几个子任务
            launch  {
                delay((i + 1) * 200L) // 延迟依次为 200、400、600 毫秒
                println("Coroutine $i is done")
            }
        }
        println("request: I'm done and I don't explicitly join my children that are still active")
    }
    request.join() // 等本次请求及其所有子任务完成
    println("Now processing of the request is complete")
//sampleEnd
}

可以在这里查看完整代码。

输出如下。

request: I'm done and I don't explicitly join my children that are still active
Coroutine 0 is done
Coroutine 1 is done
Coroutine 2 is done
Now processing of the request is complete

为协程命名以便调试

自动编号有助于将同一协程频繁产生的日志串起来。如果协程与特定请求或后台任务有关，为调试显式命名会更好。CoroutineName 上下文元素和线程名的用途相似。调试模式开启时，它会出现在执行该协程的线程名中。

以下例子演示这种用法。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

fun main() = runBlocking(CoroutineName("main")) {
//sampleStart
    log("Started main coroutine")
    // 在后台启动两项有返回值的计算
    val v1 = async(CoroutineName("v1coroutine")) {
        delay(500)
        log("Computing v1")
        6
    }
    val v2 = async(CoroutineName("v2coroutine")) {
        delay(1000)
        log("Computing v2")
        7
    }
    log("The answer for v1 * v2 = ${v1.await() * v2.await()}")
//sampleEnd    
}

可以在这里查看完整代码。

传入 JVM 选项 -Dkotlinx.coroutines.debug，输出类似如下。

[main @main#1] Started main coroutine
[main @v1coroutine#2] Computing v1
[main @v2coroutine#3] Computing v2
[main @main#1] The answer for v1 * v2 = 42

组合上下文元素

用 + 运算符可以为协程上下文组合多个元素。例如，可以在启动时同时显式指定调度器和名称。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    launch(Dispatchers.Default + CoroutineName("test")) {
        println("I'm working in thread ${Thread.currentThread().name}")
    }
//sampleEnd    
}

可以在这里查看完整代码。

使用 JVM 选项 -Dkotlinx.coroutines.debug 后，输出如下。

I'm working in thread DefaultDispatcher-worker-1 @test#2

协程作用域

把上下文、父子关系和 Job 联系起来考虑。假设应用中有一个具有生命周期的对象，它本身不是协程。例如，Android 应用中的 Activity 启动协程获取或更新数据、执行动画等。Activity 销毁时必须取消这些协程，以免内存泄漏。可以手动管理上下文与 Job 来关联生命周期，但 kotlinx.coroutines 已将这套管理封装成 CoroutineScope。它也是前文各个扩展构建器所用的作用域。

创建一个与 Activity 生命周期相连的 CoroutineScope 实例来管理这些协程。可以用 CoroutineScope() 或 MainScope() 工厂函数。前者建立通用作用域，后者适合 UI 应用，默认调度器是 Dispatchers.Main。

class Activity {
    private val mainScope = MainScope()
    
    fun destroy() {
        mainScope.cancel()
    }
    // 下文继续……

现在可以通过 mainScope 在 Activity 的作用域中启动协程。演示中启动十个协程，各自等待不同的时长。

    // Activity 类后续的代码
    fun doSomething() {
        // 为演示启动十个协程，它们各自运行的时长不同
        repeat(10) { i ->
            mainScope.launch {
                delay((i + 1) * 200L) // 延迟依次为 200 毫秒、400 毫秒……
                println("Coroutine $i is done")
            }
        }
    }
} // Activity 类定义结束

main 函数先创建 Activity，再调用 doSomething，500 毫秒后销毁 Activity。这将取消由 doSomething 启动的协程；可以看到，销毁后即使再等一段时间也没有更多消息打印。

import kotlinx.coroutines.*

class Activity {
    private val mainScope = CoroutineScope(Dispatchers.Default) // 演示时使用 Dispatchers.Default
    
    fun destroy() {
        mainScope.cancel()
    }

    fun doSomething() {
        // 为演示启动十个协程，它们各自运行的时长不同
        repeat(10) { i ->
            mainScope.launch {
                delay((i + 1) * 200L) // 延迟依次为 200 毫秒、400 毫秒……
                println("Coroutine $i is done")
            }
        }
    }
} // Activity 类定义结束

fun main() = runBlocking<Unit> {
//sampleStart
    val activity = Activity()
    activity.doSomething() // 运行测试函数
    println("Launched coroutines")
    delay(500L) // 等待半秒
    println("Destroying activity!")
    activity.destroy() // 取消所有协程
    delay(1000) // 观察它们确实已经停止运行
//sampleEnd    
}

可以在这里查看完整代码。

输出如下。

Launched coroutines
Coroutine 0 is done
Coroutine 1 is done
Destroying activity!

只有前两个协程打印了消息，Activity.destroy() 中的一次 mainScope.cancel() 取消了其余协程。

对具有生命周期的实体，Android 提供官方协程作用域支持。详见相应文档。

线程局部数据

有时需要将线程局部数据传入协程，或在协程之间传递。由于协程不绑定特定线程，手动处理通常要写许多重复代码。

ThreadLocal 的 asContextElement 扩展函数会创建一个上下文元素，保存指定的 ThreadLocal 值，并在协程每次切换上下文时恢复该值。

以下是一个例子。

import kotlinx.coroutines.*

val threadLocal = ThreadLocal<String?>() // 声明线程局部变量

fun main() = runBlocking<Unit> {
//sampleStart
    threadLocal.set("main")
    println("Pre-main, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
    val job = launch(Dispatchers.Default + threadLocal.asContextElement(value = "launch")) {
        println("Launch start, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
        yield()
        println("After yield, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
    }
    job.join()
    println("Post-main, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
//sampleEnd    
}

可以在这里查看完整代码。

本例使用 Dispatchers.Default 在后台线程池启动一个协程。即使它在不同的池线程上执行，仍能读到 threadLocal.asContextElement(value = "launch") 指定的线程局部值。开启调试后的输出如下。

Pre-main, current thread: Thread[main @coroutine#1,5,main], thread local value: 'main'
Launch start, current thread: Thread[DefaultDispatcher-worker-1 @coroutine#2,5,main], thread local value: 'launch'
After yield, current thread: Thread[DefaultDispatcher-worker-2 @coroutine#2,5,main], thread local value: 'launch'
Post-main, current thread: Thread[main @coroutine#1,5,main], thread local value: 'main'

若忘记安装相应的上下文元素，当协程换线程时读到的 ThreadLocal 值可能出乎预期。建议使用 ensurePresent，在用法有误时尽早报错。

ThreadLocal 得到直接支持，可以和 kotlinx.coroutines 的各种原语配合。但它有一个限制：直接写入线程局部变量后，新值不会传回协程的调用者，因为上下文元素无法跟踪对 ThreadLocal 的每次访问。下次挂起再恢复时，这个更新值也会丢失。需要更新时使用 withContext，详见 asContextElement。

也可以把值放在可变对象中，例如 class Counter(var i: Int)，再将这个对象保存为线程局部变量。这时若存在并发修改，对对象内部字段的同步完全由使用者负责。

若需要与日志 MDC、事务上下文或其他内部依靠线程局部变量传递数据的库集成，请参考应实现的 ThreadContextElement 接口文档。
