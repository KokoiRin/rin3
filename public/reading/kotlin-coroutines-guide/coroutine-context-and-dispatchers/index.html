协程上下文与调度器

一段代码启动于主线程，挂起后还会回来吗？同时看线程名、协程名和父 Job，就能分清执行位置与任务归属。

每个协程执行时都有一份上下文，类型是 Kotlin 标准库定义的 CoroutineContext。

上下文由多个元素组成。Job 记录任务的生命周期；调度器决定协程的代码在哪里执行。

调度器怎样选择线程

上下文里的 CoroutineDispatcher 可以把执行限制在指定线程，分配给线程池，或者让协程按恢复它的代码所在线程继续运行。

launch 和 async 都接受可选的 CoroutineContext 参数，可以一次指定调度器及其他上下文元素。

运行例子，对照每次 launch 的参数和打印的线程名。

import kotlinx.coroutines.*

//sampleStart
fun main() = runBlocking<Unit> {
    launch { // context of the parent, main runBlocking coroutine
        println("main runBlocking      : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(Dispatchers.Unconfined) { // not confined -- will work with main thread
        println("Unconfined            : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(Dispatchers.Default) { // will get dispatched to DefaultDispatcher 
        println("Default               : I'm working in thread ${Thread.currentThread().name}")
    }
    launch(newSingleThreadContext("MyOwnThread")) { // will get its own new thread
        println("newSingleThreadContext: I'm working in thread ${Thread.currentThread().name}")
    }
}
//sampleEnd

查看完整示例。

你可能看到如下输出，行的顺序也可能不同。

Unconfined            : I'm working in thread main
Default               : I'm working in thread DefaultDispatcher-worker-1
newSingleThreadContext: I'm working in thread MyOwnThread
main runBlocking      : I'm working in thread main

不带参数的 launch 继承启动它的 CoroutineScope 的调度器。这个例子外层是主线程中的 runBlocking，因此子协程也在主线程执行。

Dispatchers.Unconfined 启动时看起来也在主线程。它在挂起后如何恢复，和继承主线程的情况不同。

如果作用域里没有指定调度器，这些构建器会使用 Dispatchers.Default，在共享后台线程池执行任务。

newSingleThreadContext 会创建一条专用线程，成本较高。实际应用可以长期复用它，并在不再需要时调用 close 释放资源。

挂起后会回到哪个线程

Dispatchers.Unconfined 从调用者线程开始执行。第一次真正挂起后，它在哪个线程恢复，取决于相应挂起函数的恢复机制。这种方式只适合很少消耗 CPU、也不用碰线程专属数据（例如 UI）的任务。

普通情况下，子协程继承外层作用域的调度器。runBlocking 的默认事件循环位于调用线程，在本例中，继承它的子任务会留在该线程按队列调度。 CoroutineScope

import kotlinx.coroutines.*

//sampleStart
fun main() = runBlocking<Unit> {
    launch(Dispatchers.Unconfined) { // not confined -- will work with main thread
        println("Unconfined      : I'm working in thread ${Thread.currentThread().name}")
        delay(500)
        println("Unconfined      : After delay in thread ${Thread.currentThread().name}")
    }
    launch { // context of the parent, main runBlocking coroutine
        println("main runBlocking: I'm working in thread ${Thread.currentThread().name}")
        delay(1000)
        println("main runBlocking: After delay in thread ${Thread.currentThread().name}")
    }
}
//sampleEnd

查看完整示例。

一次运行的输出如下。

Unconfined      : I'm working in thread main
main runBlocking: I'm working in thread main
Unconfined      : After delay in thread kotlinx.coroutines.DefaultExecutor
main runBlocking: After delay in thread main

看两次打印之间的 delay。继承 runBlocking 调度器的协程回来后仍在主线程，Unconfined 协程则在负责恢复这次延时的默认执行器线程上继续。

只有在确实需要立即执行、额外排队会产生副作用等特殊场合，才考虑 Unconfined。一般业务代码更适合使用有明确执行约束的调度器。

同时观察协程和线程

同一个协程可以在一条线程挂起，在另一条线程恢复。即使只有一条线程，只看线程栈也很难还原多个协程分别走到了哪里。

在 IDEA 中观察协程

IntelliJ IDEA 的 Kotlin 插件提供协程调试器。

官方说明该调试功能支持 kotlinx-coroutines-core 1.3.8 及以上版本。

打开 Debug 工具窗口里的 Coroutines 标签。运行中与挂起的协程都会列出，并按调度器分组。

暂停在断点时，可以检查以下内容。

  • 查看每个协程当前的状态。

  • 查看运行中或已挂起协程的局部变量，以及闭包捕获的变量。

  • 查看创建协程的位置和协程内部的调用栈，其中可以保留普通线程栈调试时已经看不到的调用帧和变量信息。

  • 在 Coroutines 标签内右键选择 Get Coroutines Dump，可取得包含各协程状态和调用栈的报告。

在关心的行打断点，然后以 Debug 模式启动程序。

后面的 IDEA 实操教程会带你逐步观察。 tutorial

从日志追踪协程

许多日志框架能打印线程名。同一线程会运行多个协程，为了把几行日志串回同一个任务，还需要协程标识。kotlinx.coroutines 提供了相应的调试模式。

启动 JVM 时加入 -Dkotlinx.coroutines.debug，再运行下面的代码。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

//sampleStart
fun main() = runBlocking<Unit> {
    val a = async {
        log("I'm computing a piece of the answer")
        6
    }
    val b = async {
        log("I'm computing another piece of the answer")
        7
    }
    log("The answer is ${a.await() * b.await()}")
}
//sampleEnd

查看完整示例。

runBlocking 是第 1 个协程，计算 a 和 b 的分别是第 2、3 个。三者都继承同一个事件循环，执行线程都是 main。

[main @coroutine#2] I'm computing a piece of the answer
[main @coroutine#3] I'm computing another piece of the answer
[main @coroutine#1] The answer is 42

log 用方括号打印线程名。调试模式会把当前协程的标识附在线程名后面，创建的协程依次获得编号。

使用 JVM 的 -ea 参数开启断言时，默认的自动调试模式也会启用。细节见 DEBUG_PROPERTY_NAME 的文档。

观察一次上下文切换

加上 -Dkotlinx.coroutines.debug，运行下面的例子。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

fun main() {
    newSingleThreadContext("Ctx1").use { ctx1 ->
        newSingleThreadContext("Ctx2").use { ctx2 ->
            runBlocking(ctx1) {
                log("Started in ctx1")
                withContext(ctx2) {
                    log("Working in ctx2")
                }
                log("Back to ctx1")
            }
        }
    }
}

查看完整示例。

留心两处指定执行位置的代码。

runBlocking 可以直接接受指定的上下文。withContext 则在目标上下文执行一个块，再把结果带回调用处。目标调度器与当前调度器不同时，进入和返回都需要调度。 CoroutineDispatcher

看日志中的线程名如何变化，再回到起点。

[Ctx1 @coroutine#1] Started in ctx1
[Ctx2 @coroutine#1] Working in ctx2
[Ctx1 @coroutine#1] Back to ctx1

newSingleThreadContext 创建的线程由 use 块管理，作用域用完后会释放。

从上下文取得 Job

写 coroutineContext[Job] 即可取得上下文中的任务句柄，观察它的状态。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    println("My job is ${coroutineContext[Job]}")
//sampleEnd    
}

查看完整示例。

开启调试后，你会看到类似的状态信息。 debug mode

My job is "coroutine#1":BlockingCoroutine{Active}@6d311334

在有 Job 的协程作用域里，isActive 可直接读取当前任务是否仍然活跃。 CoroutineScope

子协程继承什么

在父协程的作用域里启动子协程时，它继承上下文里的执行配置，并得到一个与父 Job 相连的新 Job。取消父任务时，会递归取消子孙任务。 CoroutineScope · CoroutineScope.coroutineContext

下面两种写法会改变这层关系，读代码时尤其要留意。

  1. 显式在另一个作用域里启动，例如 GlobalScope.launch，新任务归那个作用域管理。

  2. 启动时显式传入另一个 Job，会替换原本用于建立父子关系的 Job。

这两种写法都能使新任务脱离原调用位置对应的任务树。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    // launch a coroutine to process some kind of incoming request
    val request = launch {
        // it spawns two other jobs
        launch(Job()) { 
            println("job1: I run in my own Job and execute independently!")
            delay(1000)
            println("job1: I am not affected by cancellation of the request")
        }
        // and the other inherits the parent context
        launch {
            delay(100)
            println("job2: I am a child of the request coroutine")
            delay(1000)
            println("job2: I will not execute this line if my parent request is cancelled")
        }
    }
    delay(500)
    request.cancel() // cancel processing of the request
    println("main: Who has survived request cancellation?")
    delay(1000) // delay the main thread for a second to see what happens
//sampleEnd
}

查看完整示例。

一次运行的输出如下。

job1: I run in my own Job and execute independently!
job2: I am a child of the request coroutine
main: Who has survived request cancellation?
job1: I am not affected by cancellation of the request

父协程何时才能结束

父协程要等所有子任务结束后才算完成。为这项保证，无须自己保存每个句柄，也无须在末尾为每个任务补一个 Job.join。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    // launch a coroutine to process some kind of incoming request
    val request = launch {
        repeat(3) { i -> // launch a few children jobs
            launch  {
                delay((i + 1) * 200L) // variable delay 200ms, 400ms, 600ms
                println("Coroutine $i is done")
            }
        }
        println("request: I'm done and I don't explicitly join my children that are still active")
    }
    request.join() // wait for completion of the request, including all its children
    println("Now processing of the request is complete")
//sampleEnd
}

查看完整示例。

一次运行的输出如下。

request: I'm done and I don't explicitly join my children that are still active
Coroutine 0 is done
Coroutine 1 is done
Coroutine 2 is done
Now processing of the request is complete

给协程起名

自动编号适合把日志归到同一个任务。若要判断某个请求或某项后台工作走到了哪一步，可以添加 CoroutineName。开启调试后，这个名字也会出现在执行协程时的线程名里。 debugging mode

例子给两个计算任务分别命名，再观察日志。

import kotlinx.coroutines.*

fun log(msg: String) = println("[${Thread.currentThread().name}] $msg")

fun main() = runBlocking(CoroutineName("main")) {
//sampleStart
    log("Started main coroutine")
    // run two background value computations
    val v1 = async(CoroutineName("v1coroutine")) {
        delay(500)
        log("Computing v1")
        6
    }
    val v2 = async(CoroutineName("v2coroutine")) {
        delay(1000)
        log("Computing v2")
        7
    }
    log("The answer for v1 * v2 = ${v1.await() * v2.await()}")
//sampleEnd    
}

查看完整示例。

使用 -Dkotlinx.coroutines.debug 后，输出大致如下。

[main @main#1] Started main coroutine
[main @v1coroutine#2] Computing v1
[main @v2coroutine#3] Computing v2
[main @main#1] The answer for v1 * v2 = 42

组合多个上下文元素

可以用 + 合并上下文元素。例如启动协程时同时指定调度器和 CoroutineName。

import kotlinx.coroutines.*

fun main() = runBlocking<Unit> {
//sampleStart
    launch(Dispatchers.Default + CoroutineName("test")) {
        println("I'm working in thread ${Thread.currentThread().name}")
    }
//sampleEnd    
}

查看完整示例。

开启 -Dkotlinx.coroutines.debug 后，可同时看见线程和任务名。

I'm working in thread DefaultDispatcher-worker-1 @test#2

让协程跟随对象的生命周期

假设一个 Android Activity 启动了加载数据、更新界面和播放动画等任务。页面销毁后，这些任务应一起取消，以免继续占用页面资源。CoroutineScope 把它们的上下文和 Job 组织起来，也是 launch 等构建器的接收者。

可以创建与页面同寿命的作用域。CoroutineScope() 接受自定义上下文；MainScope() 适合 UI，默认使用 Dispatchers.Main。

class Activity {
    private val mainScope = MainScope()
    
    fun destroy() {
        mainScope.cancel()
    }
    // to be continued ...

用页面的 mainScope 启动十个子协程，让它们分别等待不同的时间。

    // class Activity continues
    fun doSomething() {
        // launch ten coroutines for a demo, each working for a different time
        repeat(10) { i ->
            mainScope.launch {
                delay((i + 1) * 200L) // variable delay 200ms, 400ms, ... etc
                println("Coroutine $i is done")
            }
        }
    }
} // class Activity ends

主函数创建页面，调用 doSomething，再在 500 毫秒后销毁页面。之后即使多等一会儿，也不会看到余下任务继续打印。

import kotlinx.coroutines.*

class Activity {
    private val mainScope = CoroutineScope(Dispatchers.Default) // use Default for test purposes
    
    fun destroy() {
        mainScope.cancel()
    }

    fun doSomething() {
        // launch ten coroutines for a demo, each working for a different time
        repeat(10) { i ->
            mainScope.launch {
                delay((i + 1) * 200L) // variable delay 200ms, 400ms, ... etc
                println("Coroutine $i is done")
            }
        }
    }
} // class Activity ends

fun main() = runBlocking<Unit> {
//sampleStart
    val activity = Activity()
    activity.doSomething() // run test function
    println("Launched coroutines")
    delay(500L) // delay for half a second
    println("Destroying activity!")
    activity.destroy() // cancels all coroutines
    delay(1000) // visually confirm that they don't work
//sampleEnd    
}

查看完整示例。

一次运行的输出如下。

Launched coroutines
Coroutine 0 is done
Coroutine 1 is done
Destroying activity!

在这次运行中，只有前两个任务来得及打印。Activity.destroy() 里一次 mainScope.cancel() 就取消了其余任务。

Android 为有生命周期的组件提供了现成的协程作用域，相关用法见 Android 官方资料。 the corresponding documentation

在线程间传递 ThreadLocal

有的库把数据存在当前线程的 ThreadLocal 中。协程可能在另一条线程恢复，手动维护这份数据很容易遗漏。

ThreadLocal.asContextElement 会把指定值放入上下文元素。协程每次切换或恢复上下文时，它负责为当前执行线程恢复相应的值。

用下面的例子观察这个值的变化。

import kotlinx.coroutines.*

val threadLocal = ThreadLocal<String?>() // declare thread-local variable

fun main() = runBlocking<Unit> {
//sampleStart
    threadLocal.set("main")
    println("Pre-main, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
    val job = launch(Dispatchers.Default + threadLocal.asContextElement(value = "launch")) {
        println("Launch start, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
        yield()
        println("After yield, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
    }
    job.join()
    println("Post-main, current thread: ${Thread.currentThread()}, thread local value: '${threadLocal.get()}'")
//sampleEnd    
}

查看完整示例。

虽然子协程运行在 Dispatchers.Default 的后台线程池里，但通过 threadLocal.asContextElement(value = "launch") 指定的值会随它恢复。开启调试后可以同时核对线程名和变量值。 debug

Pre-main, current thread: Thread[main @coroutine#1,5,main], thread local value: 'main'
Launch start, current thread: Thread[DefaultDispatcher-worker-1 @coroutine#2,5,main], thread local value: 'launch'
After yield, current thread: Thread[DefaultDispatcher-worker-2 @coroutine#2,5,main], thread local value: 'launch'
Post-main, current thread: Thread[main @coroutine#1,5,main], thread local value: 'main'

漏装这个元素时，换线程可能会读到意外的值。可以用 ensurePresent 尽早发现调用方式有误。

上下文元素保存的是设置时的值，无法跟踪每次对 ThreadLocal 的写入。协程里直接修改后的新值不会自动传回调用者，挂起再恢复也可能丢失。要切换值，可以用 withContext 安装新的 asContextElement。

也可以让 ThreadLocal 持有一个可变对象，例如 class Counter(var i: Int)。此时多个协程若同时修改对象内的字段，要自行保证同步。

对接日志 MDC、事务上下文或其他依赖线程局部变量的库时，可以参考 ThreadContextElement 的接口约定。

读完试一题

把普通子任务的调度器改成 Dispatchers.Default，页面作用域取消时，它还会随父任务取消吗？

展开参考答案

会。只换调度器改变的是执行位置，子 Job 仍在原任务树中。显式换用别的作用域或另一个 Job 才会改动这种归属。
