Flow：连续到来的值

下载进度会从 0 走到 100。用同一条数据管道比较重新生产、广播事件和保存当前状态三种行为。

挂起函数适合表达一次调用拿到一个结果。搜索建议、下载进度、聊天消息都会陆续到来，适合用 Flow 表达一串随时间产生的值。

把流的生产、转换与收集接起来，就能逐步加载数据、响应事件，或实现订阅式接口。

一条管道中有三个角色。

  • 发射方负责产生并发出值。

  • 中间操作符按需出现，接收上游的值，加工后返回一条新流。

  • 收集方接收值并使用它。

在下面的例子中，找出谁生产数字、谁改变数字、谁打印结果。

import kotlinx.coroutines.flow.*

//sampleStart
suspend fun main() {
    // The emitter produces values
    flowOf(0x4B, 0x6F, 0x74, 0x6C, 0x69, 0x6E)
        // The intermediate operator consumes values,
        // applies an operation, and returns another flow
        .map { value -> value.toChar() }
        // The collector consumes the transformed values
        .collect { updatedValue ->
            println("Say '$updatedValue'!")
        }
}
//sampleEnd

值从上游流向下游。一个中间操作符先收集上游的值，再将处理后的结果交给下游。上下游是相对位置，同一个操作符两头都连着别人。

从「谁触发生产」看，Flow 可分两类。

  • 冷流在被收集时才开始工作，每个收集者都会独立运行一次上游。

  • 热流让多个订阅者观察同一个来源，生产者与某一个订阅者的生命周期可以分开。

单元测试可使用 Turbine 收集 Flow，并断言它发出了哪些值、是否结束或失败。 Turbine library

冷流

冷流和序列一样，会把真正的工作推迟到有人需要结果时。 sequences

只构造冷流不会运行它的代码块。每新增一个收集者，这段代码就从头运行一次。

创建冷流

用 flow() 描述生产过程，在块内用 emit() 把值交给收集者。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
fun main() {
    // Creates a flow
    val pageFlow = flow {
        for (page in 1..3) {
            println("Loading page $page...")

            // Emits each page as it is loaded
            emit("Page $page")
        }
    }
    println("Creating a cold flow doesn't run it!")
}
//sampleEnd

调用 flow() 得到 Flow<T> 时，手里只有「怎样生产这些值」的定义。第一次收集才真正执行块内代码。 collect it

对于已经准备好的数据，还有更短的创建方式。

  • flowOf() 根据给定的一组值创建流。

  • asFlow() 把整数区间等可迭代对象转换为流。 .asFlow()

看下面的例子。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun main() {
    // Creates a flow from provided values
    val predefinedPageFlow = flowOf("Page 1", "Page 2", "Page 3")
    // Creates a flow from a range
    val generatedPageFlow = (1..3).asFlow()
}

收集冷流

collect() 触发上游执行。传入的 lambda 每次收到一个新值就运行一次。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
suspend fun main() {
    withContext(Dispatchers.Default) {
        val pageFlow = flow {
            for (page in 1..3) {
                println("Loading page $page...")
                emit("Page $page")
            }
        }
        // Collects the flow with a lambda that receives each emitted page
        pageFlow.collect { page ->
            println("Processing $page...")
            delay(100.milliseconds)
            println("Done processing $page.")
        }
    }
}
//sampleEnd

同一条冷流被 collect() 两次，就会独立运行两遍。试着从输出中分辨哪几行属于同一轮。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
suspend fun main() {
    val pageFlow = flow {
        // Reads the name of the current coroutine
        val coroutineName = currentCoroutineContext()[CoroutineName]?.name

        println("Starting emissions in $coroutineName")
        for (page in 1..3) {
            println("Loading page $page in $coroutineName")
            emit("Page $page")
        }
        println("Done emitting in $coroutineName")
    }

    withContext(Dispatchers.Default) {
        // Launches a collector that processes each page slowly
        launch(CoroutineName("a slow coroutine")) {
            pageFlow.collect {
                println("Processing $it slowly")
                delay(100.milliseconds)
                println("Done processing $it slowly")
            }
        }

        // Launches a collector that processes each page quickly
        launch(CoroutineName("a fast coroutine")) {
            pageFlow.collect {
                println("Processing $it quickly")
                delay(10.milliseconds)
                println("Done processing $it quickly")
            }
        }
    }
}
//sampleEnd

例子用 CoroutineName 标记两个收集协程，这样就能看出是哪一位收集者触发了哪一轮生产。 debugging

在中间转换数据

中间操作符把上游变成一条新的下游流。一般的中间转换是冷的：即使上游是热流，这段转换也要等下游被收集后才开始处理。

kotlinx.coroutines 提供了许多转换和筛选操作。若现成的操作不够用，也可以自己封装。 wide range of intermediate flow operators

下面实现简化版 map：收集每个上游值，转换后再发给下游。 .map()

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
// A simplified custom implementation of the default .map() operator
fun <T, R> Flow<T>.myMap(transform: suspend (value: T) -> R): Flow<R> = flow {
    // Collects values from the upstream flow
    this@myMap.collect { value ->
        // Transforms each collected value and emits the result
        emit(transform(value))
    }
}

suspend fun main() {
    // Creates a flow, applies the custom map operator, and collects the transformed values
    flowOf(1, 2, 3).myMap { 2 * it }.collect {
        println("Collecting $it")
    }
}
//sampleEnd

在 flow 块中调用挂起函数

flow() 块允许调用一般的挂起函数，例如等待下一项数据。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
suspend fun loadPage(): Int {
    delay(100)
    return 3
}

suspend fun main() {
    flow {
        emit(loadPage())
    }.collect {
        println(it)
        // 3
    }
}
//sampleEnd

它要求 emit() 发生在这个块相同的协程上下文中。另起协程，或在 withContext() 切换到另一上下文后直接 emit，都会违反这项约束。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
suspend fun main() {
    // This fails with an exception!
    flow {
        // Changes the coroutine context with withContext()
        withContext(Dispatchers.IO) {
            emit('a')
        }
    }.collect { 
        println("This never prints")
    }
}
//sampleEnd

这是 flow() 构建器的约定。

想换一个上下文运行上游，用 flowOn()。 change it with the .flowOn() operator

想从多个协程并发发送值，用 channelFlow()。

用 flowOn() 移动上游

默认情况下，冷流在收集者的上下文中运行。

flowOn() 改变它前面的上游上下文，下游仍在调用方的上下文中执行。沿着管道寻找 flowOn 的位置，就能判断它影响哪部分代码。 .flowOn()

下面用日志对照发射与收集的位置。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
suspend fun main() {
    withContext(Dispatchers.Default + CoroutineName("downstream")) {
        flow {
            val coroutineName = currentCoroutineContext()[CoroutineName]?.name

            // Emits in the coroutine context applied with .flowOn()
            println("Emitting '1' in $coroutineName")
            // Emitting '1' in upstream
            emit(1)

        // Changes the coroutine context of the upstream flow
        }.flowOn(Dispatchers.IO + CoroutineName("upstream"))
            .collect {
            val coroutineName = currentCoroutineContext()[CoroutineName]?.name

            // Collects in the caller's coroutine context
            println("Collecting '$it' in $coroutineName")
            // Collecting '1' in downstream
        }
    }
}
//sampleEnd

Flow 中的异常

发射端和收集端都可能抛异常。

若没有处理，收集过程中的异常最终会从 collect() 调用处抛出。同步交付一个值时，下游的失败也可能从上游的 emit() 返回。

可以用 try/catch 观察这种传播过程。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

class MyFlowException(message: String) : Exception(message)

//sampleStart
suspend fun main() {
    val myFlow = flow {
        try {
            // The emit() function calls the lambda passed to collect()
            emit('a')
        } catch (e: MyFlowException) {
            println("Collector threw $e")

            // Rethrows the downstream exception
            throw e
        }
    }
    // Wraps flow collection in try-catch
    try {
        myFlow.collect {
            // Throws an exception from the collect() lambda
            throw MyFlowException("Can't process '$it'!")
        }
    } catch (e: MyFlowException) {
        println("Flow collection failed with $e")
        // Rethrows the exception to the caller
        throw e
    }
}
//sampleEnd

例子里的收集者刚收到值就失败，于是 flow 块在调用 emit 的地方接到了下游异常。

在构建器里捕获这种异常时，应重新抛出，保留异常透明性，让调用 collect() 的一方有机会处理它。

用 catch() 处理上游失败

如果希望异常到达收集者前已经得到处理，可以在流上添加 catch()。 .catch()

它可以处理自己上游的异常，例如用 emit() 发送一个可用的替代值。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

//sampleStart
suspend fun main() {
    flow {
        emit("a")
        emit("b")

        // Throws an exception from the upstream flow
        throw UnsupportedOperationException(
            "I am tired of listing letters"
        )
    }.catch { upstreamException ->
        println("Upstream completed with $upstreamException!")

        // Emits a fallback value downstream
        emit("Upstream terminated with an exception!")
    }.collect {
        println("Got '$it'")
    }
}
//sampleEnd

例子先发出几个正常值，再抛异常。catch() 随后发出字符串 Upstream terminated with an exception!，下游可以收到这最后一个值。

只处理预期且可恢复的异常，对意外失败应继续抛出。

下面让同一条流报告数据加载的进度与结果。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
sealed interface LoadingState {
    sealed interface Terminal: LoadingState
    object Started: LoadingState
    data class Percentage(val percents: Int): LoadingState
    object Failed: Terminal
    object Done: Terminal
}

fun loadBlob(url: String) = flow {
    emit(LoadingState.Started)

    val failureChancePerStep = 1 - java.lang.Math.pow(0.99, 10.0)

    repeat(10) { step ->
        if (Random.nextDouble() < failureChancePerStep)
            throw IOException("Failed to load!")
        emit(LoadingState.Percentage((step + 1) * 10))
        delay(10.milliseconds)
    }
    emit(LoadingState.Done)
}.catch { e ->
    println("Loading data failed with $e")
    if (e is IOException) {
        // Handles an expected exception
        emit(LoadingState.Failed)
    } else {
        // Rethrows unexpected exceptions, so the collect() fails with them
        throw e
    }
}

suspend fun main() {
    loadBlob("https://example.com/").collect {
        println("Got '$it'")
    }
}
//sampleEnd

对预期的加载失败，catch() 发出表示失败的替代状态；其余异常重新抛出，由调用 collect() 的一方决定怎么处理。

catch() 看不到它下游的收集者所抛的异常。如果 collect 的 lambda 出错，可在 collect() 调用外包一层 try/catch。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

suspend fun main() {
    val myFlow = flow {
        for (char in listOf('a', 'o', '5', 'c')) {
            try {
                emit(char)
            } catch (e: IllegalArgumentException) {
                println("Collector doesn't support character '$char': $e")

                // Rethrows the downstream exception
                throw e
            }
        }
    }.catch { e ->
        // Doesn't run because the exception happens downstream
        println("Upstream threw an exception: $e")
    }

    try {
        myFlow.collect {
            require(!it.isDigit()) { "Digits are not allowed!" }
        }
    } catch (e: IllegalArgumentException) {
        // Handles the exception from the collect() lambda
        println("Flow collection failed with $e")
    }
}

如果想让逐项处理中的失败由 catch() 接管，把这段处理移到它前面的 onEach()。 .onEach()

onEach() 先处理值，再把值交给下游。它若失败，后面的 catch() 可以处理，随后这一轮流结束，原序列不会从下一项继续。

看下面的例子。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

suspend fun main() {
    flowOf('a', 'o', '5', 'c')
        // Runs before each value is emitted downstream
        .onEach {
            require(!it.isDigit()) { "Digits are not allowed!" }
            println("Got '$it'")
        }
        .catch { e ->
            println("Caught an exception: $e")
        }
        .collect()
}

当 require() 检查到 5 并失败时，onEach() 位于 catch() 上游，因此异常会被它捕获。

失败后重新收集

网络短暂断开等故障可能恢复。retry() 可以在失败后让上游重新开始。 .retry()

retry() 的判断函数查看异常，返回 true 才重试，并受次数上限约束。retry(3) 表示首次失败后最多再试三次。

判断返回 false 时，停止重试并继续抛出异常。

retryWhen() 还可以查看尝试次数，并在重试前向下游发出状态。 .retryWhen()

下面的例子只对 IOException 进行重试，最多三次。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.Duration.Companion.seconds

//sampleStart
sealed interface LoadingState {
    sealed interface Terminal: LoadingState
    object Started: LoadingState
    data class Percentage(val percents: Int): LoadingState
    object Failed: Terminal
    object Done: Terminal
}

fun loadBlob(url: String) = flow {
    emit(LoadingState.Started)

    val failureChancePerStep = 1 - java.lang.Math.pow(0.99, 10.0)

    repeat(10) { step ->
        if (Random.nextDouble() < failureChancePerStep)
            throw IOException("Failed to load!")
        emit(LoadingState.Percentage((step + 1) * 10))
        delay(10.milliseconds)
    }
    emit(LoadingState.Done)
}.retry(3) { e ->
    if (e is IOException) {
        // This is an expected error
        // Waits for one second before retrying
        delay(1.seconds)
        true
    } else {
        // Stops retrying and rethrows unexpected exceptions
        false
    }
}

suspend fun main() {
    loadBlob("https://example.org/").collect {
        println("Got $it")
    }
}
//sampleEnd

停止收集

当请求超时或结果已用不上，就可以停止收集。

冷流的这次收集归调用 collect() 的协程管理。取消这个协程，它驱动的收集过程以及相应上游工作也会停止。

可以通过收集协程的 Job 调用 cancel()。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
val myFlow = flow {
    var i = 0
    try {
        while (true) {
            println("Emitting $i")
            emit(i)
            println("Emitted $i")
            ++i
            delay(10.milliseconds)
        }
    } catch (e: Throwable) {
        println("Upstream finished with $e")
        throw e
    }
}

suspend fun main() {
    coroutineScope {
        val job = launch {
            try {
                myFlow.collect {
                    println("Processing $it")
                    delay(5.milliseconds)
                }
            } catch (e: Throwable) {
                println("Collection finished with $e")
                throw e
            }
        }
        delay(100.milliseconds)

        // Cancels the coroutine that collects the flow
        job.cancel()
    }
}
//sampleEnd

也可以只结束这次上游收集：在收集逻辑中抛出专用的 CancellationException，并在本次操作边界处理它，使外层协程能继续工作。

take() 利用类似机制取够就停。例如 take(3) 只向下游交付前三个值。 .take()

下面给出 take 的简化实现。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
// Defines a simplified version of the default .take() operator
fun <T> Flow<T>.myTake(count: Int): Flow<T> = flow {
    require(count > 0)
    val cancellationException = CancellationException()
    var elementsRemaining = count
    try {
        this@myTake.collect {
            emit(it)
            --elementsRemaining
            if (elementsRemaining == 0) {
                // Cancels the upstream flow after the requested number of values
                throw cancellationException
            }
        }
    } catch (e: Throwable) {
        if (e === cancellationException) {
            // Handles the CancellationException used to cancel the upstream flow
            // Completes the flow after the set number of values in .myTake()
        } else {
            // Rethrows unexpected exceptions
            throw e
        }
    }
}

suspend fun main() {
    (0..1000).asFlow().myTake(3).collect {
        println("Got $it")
    }
}
//sampleEnd

myTake() 逐个发出值，达到目标数量后用取消异常终止上游。观察异常在哪里被处理，就能区分「截断流」和「取消整个协程」。

用 channelFlow() 并发生产

如果只有一个协程发射，flow() 简洁高效。要同时从多个来源加载并逐步交付结果，则可选用 channelFlow()。

channelFlow() 创建的仍是冷流，但内部用通道接收多个协程的值。生产端改用 send()。

下面的简化版 merge 启动两个收集协程，各自把收到的值送进同一条下游流。 .merge()

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
// Defines a simplified version of the default .merge() operator
fun <T> Flow<T>.myMerge(other: Flow<T>): Flow<T> = channelFlow {
    // CoroutineScope and SendChannel are available as receivers here
    // Launches a coroutine that collects the receiver flow
    launch {
        // Collects the receiver flow
        this@myMerge.collect {
            send(it)
        }
    }
    launch {
        // Launches a coroutine that collects the other flow
        other.collect {
            // Calls SendChannel.send
            send(it)
        }
    }
}

suspend fun main() {
    val flow1 = (0..3).asFlow().onEach { delay(20.milliseconds) }
    val flow2 = (6..9).asFlow().onEach { delay(50.milliseconds) }
    flow1.myMerge(flow2).collect { println(it) }
}
//sampleEnd

channelFlow() 默认有缓冲区，生产者可以先于收集者发送一批值；默认容量通常为 64。满了以后，send() 会挂起，等收集者腾出空位。

用 buffer() 调整容量。例如 buffer(12) 最多可预存十二个值；buffer(0) 表示没有缓冲，每次交付都需要有接收者接手。 .buffer()

看下面的例子。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.random.*
import java.io.IOException
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
suspend fun main() {
    val oneHundredNumbers = channelFlow {
        repeat(100) {
            println("Sending $it")
            send(it)
        }
    }

    // Uses the default buffer capacity
    oneHundredNumbers.collect {
        println("Processing $it")
        delay(10.milliseconds)
    }
  
    // Removes the buffer so sending and processing interleave from the start
    oneHundredNumbers.buffer(0).collect {
        println("Processing $it")
        delay(10.milliseconds)
    }
}
//sampleEnd

例子分别收集使用默认容量的 oneHundredNumbers，以及经 buffer(0) 配置的同一条流。

使用默认缓冲时，开始会连续看到 Sending，缓冲区满后，发送和 Processing 日志才逐渐交错。

改成 buffer(0) 后，每次发送都得等接收方接手，交错会更早出现。

热流

热流让多个订阅者接入同一个来源，每加入一个人无需重新运行一次生产逻辑。是否在没有订阅者时继续生产，取决于生产者和共享策略。

热流的收集者也称为订阅者。

聊天消息、用户操作、界面状态等更新，往往需要多个组件同时观察，适合用热流共享。

Kotlin 提供两种常见热流。

  • SharedFlow 把事件广播给多个订阅者，适合消息和通知。

  • StateFlow 是始终保存当前值的特殊 SharedFlow，适合表示随时间变化的状态。

创建 SharedFlow

SharedFlow 用于把陆续产生的值交给订阅者。

使用 MutableSharedFlow() 创建可写的共享流。

如果把 MutableSharedFlow 直接公开，外部拿到它也可以向里面发值。

将可写流存在私有属性里，用 asSharedFlow() 向外暴露只读视图。内部仍然用 emit() 发出新值。 backing property · .asSharedFlow()

data class Message(
    val senderId: Int,
    val time: Instant,
    val text: String,
)

class Chatroom {

订阅者仍调用 collect() 来接收值。

可以配置重放缓存，为后来加入的订阅者保留若干条最近的事件。

在 MutableSharedFlow() 上用 replay 参数设置重放数量。

// Sets the number of already emitted messages new subscribers receive on subscription

        // Replays the set amount of last emitted messages to new subscribers

    )

    val messages: SharedFlow<Message>
        get() = _messages.asSharedFlow()

    suspend fun sendMessageToEveryone(message: Message) {
        // Emits the message to subscribers of the messages flow 
        _messages.emit(message)
    }
}

热流的订阅不会自然结束，不再需要时要停止收集。 cancel the collecting coroutines

SharedFlow 本身没有 close 或 cancel 操作。取消某个收集者只会停止这份订阅；要停止新数据的来源，需要管理生产者的协程或作用域。

在聊天室例子里，当前在线的订阅者接收新消息，后来加入的人也能收到缓存中最近的消息。

import kotlinx.coroutines.flow.*

suspend fun main() {

例子用 CoroutineStart.UNDISPATCHED 让每个收集协程立即执行到第一次挂起。

创建 StateFlow

StateFlow 总有一个当前值。新订阅者一来就能取得当前状态，之后继续观察更新；消费较慢时可能跳过中间状态。

下载进度、UI 状态或对象的当前状态，都适合这样表达。

创建 MutableStateFlow() 时传入初始值。

// Creates a MutableStateFlow with LoadingState.Started as the initial value
val result = MutableStateFlow<LoadingState>(LoadingState.Started)

读写 value 属性即可取得或替换当前状态。

fun loadBlob(url: String): StateFlow<LoadingState> {
    val result = MutableStateFlow<LoadingState>(LoadingState.Started)

    DownloadManager.startLoading(
        url,
        onPercentageLoaded = { percentage ->
            // Replaces the current state with the latest progress
            result.value = LoadingState.Percentage(percentage)
        },
        onCompletion = {
            // Replaces the current state with the completion state
            result.value = LoadingState.Done
        },
        onFailure = {
            // Replaces the current state with the failure state
            result.value = LoadingState.Failed
        }
    )
}

单次设置 value 是线程安全的，但「先读旧值，再根据旧值写回」是复合操作。如果新值依赖旧值，应使用 update()。

MutableStateFlow 也提供写接口。即使把同一个实例声明为只读类型返回，外部代码仍可能尝试转回可写类型。

用 asStateFlow() 公开只读视图，可以把更新权限保留在类内部。 .asStateFlow()

fun loadBlob(url: String): StateFlow<LoadingState> {
    val result = MutableStateFlow<LoadingState>(LoadingState.Started)

    DownloadManager.startLoading(
        url,
        onPercentageLoaded = { percentage ->
            result.value = LoadingState.Percentage(percentage)
        },
        onCompletion = {
            result.value = LoadingState.Done
        },
        onFailure = {
            result.value = LoadingState.Failed
        }
    )

    // Exposes the loading state as a read-only StateFlow
    return result.asStateFlow()
}

下面把一个基于回调的加载 API 转换成可以观察的进度状态。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.*
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.Duration.Companion.seconds
import kotlin.io.encoding.*
import java.io.IOException
import kotlin.random.Random

//sampleStart
sealed interface LoadingState {
    sealed interface Terminal: LoadingState
    object Started: LoadingState
    data class Percentage(val percents: Int): LoadingState
    object Failed: Terminal
    object Done: Terminal
}

fun loadBlob(url: String): StateFlow<LoadingState> {
    // Creates a mutable StateFlow with the initial loading state
    val result = MutableStateFlow<LoadingState>(LoadingState.Started)
    DownloadManager.startLoading(
        url,
        onPercentageLoaded = { percentage ->
            // Replaces the current state with the latest progress
            result.value = LoadingState.Percentage(percentage)
        },
        onCompletion = {
            // Replaces the current state with the completion state
            result.value = LoadingState.Done
        },
        onFailure = {
            // Replaces the current state with the failure state
            result.value = LoadingState.Failed
        }
    )
    // Exposes the loading state as a read-only StateFlow
    return result.asStateFlow()
}

// Defines a callback-based API that downloads data asynchronously
object DownloadManager {
    // Starts loading the url asynchronously
    fun startLoading(
        url: String,
        onPercentageLoaded: (Int) -> Unit,
        onCompletion: () -> Unit,
        onFailure: (Throwable) -> Unit
    ) {
        // Uses GlobalScope for illustrative purposes only,
        // to keep this example self-contained
        GlobalScope.launch {
            val failureChancePerStep = 1 - java.lang.Math.pow(0.99, 10.0)

            repeat(10) { step ->
                if (Random.nextDouble() < failureChancePerStep) {
                    onFailure(IOException("Failed to load!"))
                    return@launch
                }
                onPercentageLoaded((step + 1) * 10)
                delay(10.milliseconds)
            }
            onCompletion()
        }
    }
}

suspend fun main() {
    loadBlob("https://example.com/").onEach { state ->
        when (state) {
            is LoadingState.Started -> {
                // Waits for progress updates
            }
            is LoadingState.Percentage ->
                println("Loaded ${state.percents}...")
            is LoadingState.Failed ->
                println("Loading failed.")
            is LoadingState.Done ->
                println("Finished loading!")
        }
    }.takeWhile { it !is LoadingState.Terminal }.collect()
}
//sampleEnd

为缩短示例，模拟加载使用了 GlobalScope。实际应用可把 CoroutineScope 传入 startLoading()，让调用方在不再需要时取消工作。

StateFlow 不会自行完成。这个例子用 takeWhile() 在加载进入终态时停止本次收集。

新值和当前值按相等性比较后确实不同，StateFlow 才会通知订阅者。

如果把可变对象放进去后原地修改，对象引用指向的仍是同一个值，收集者可能收不到更新。

需要根据旧状态计算新状态时，用 update() 原子地替换。多个协程同时修改同一个 MutableStateFlow 时，这一点尤为重要。 .update()

只需要并发更新而无须持续观察时，可以采用 Kotlin 的 AtomicInt 或 AtomicReference 等原子类型。

下面用一个 StateFlow 表示点赞总数，每一次点击都基于当前计数计算新值。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.*
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.Duration.Companion.seconds
import kotlin.io.encoding.*
import java.io.IOException
import kotlin.random.Random

//sampleStart
class Post(val id: Long) {
    // Stores the current number of likes as a StateFlow
    private val _numberOfLikes = MutableStateFlow<Int>(
        // Sets the initial number of likes
        0
    )

    // Exposes a read-only StateFlow with the current number of likes
    val numberOfLikes: StateFlow<Int>
        get() = _numberOfLikes.asStateFlow()


    // Adds a like
    fun like() {
        // Increments the number of likes atomically for concurrent and multithreaded calls
        _numberOfLikes.update { it + 1 }
    }
}

suspend fun drawUpdatedNumberOfLikes(likes: Int) {
    // Displays the latest number of likes
    println("${Clock.System.now()}: the number of likes is $likes")
}

suspend fun main() {
    withContext(Dispatchers.Default) {
        val post = Post(15)
        val notifyingJob = launch {
            post.numberOfLikes.collect {
                drawUpdatedNumberOfLikes(it)
            }
        }
        // Simulates users who like the post
        coroutineScope {
            repeat(10) {
                launch {
                    delay(Random.nextInt(100).milliseconds)
                    post.like()
                }
            }
        }
        // Cancels collection after all simulated users finish
        notifyingJob.cancelAndJoin()
    }
}
//sampleEnd

多个协程同时调用 like() 时，update() 会原子增加计数，避免两次点赞互相覆盖。

让当前状态包含全部历史

有时新订阅者想立即看到「截至目前的完整结果」。

例如新加入聊天室时，先显示已有消息，再随着新消息到来更新整个聊天记录。

可以把这样的累计结果建模为 StateFlow。

让 StateFlow<List<Message>> 的值代表整份历史。若要表达单条消息事件，则可以使用 SharedFlow<Message>。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.*

import kotlin.time.Duration.Companion.seconds

}

                    userId,

messageHistory 保存已有消息列表。每条新消息到来时，update() 基于旧列表创建新列表，原子地更新状态。

通过复制整个集合来保持不可变，数据越多开销越大。实验性的 kotlinx.collections.immutable 库提供持久化集合，可以更高效地共享已有结构。 Experimental

新订阅者先收到当前完整历史，随后随着状态改变，收到反映新历史的列表。

把冷流转换成热流

如果多位收集者只需要同一份上游结果，可以共享一次收集，避免每个人都重新执行生产逻辑。

简化版 shareIn() 示范了原理：只收集一次冷流，把值转发给 MutableSharedFlow，对外提供只读视图。

import kotlinx.coroutines.flow.*
import kotlinx.coroutines.*

fun <T> Flow<T>.simpleShareIn(scope: CoroutineScope): SharedFlow<T> {
    val sharedFlow = MutableSharedFlow<T>()
    scope.launch {
        this@simpleShareIn.collect {
            sharedFlow.emit(it)
        }
    }
    return sharedFlow.asSharedFlow()
}

suspend fun main() { 
    
}

simpleShareIn() 会在传入的作用域启动一个协程。取消该作用域，就能停止对上游的收集。 cancel the scope

上游异常会让共享协程失败。在共享之前放置 catch() 或 retry()，能让故障在进入共享边界前得到处理。 handle upstream exceptions

内置 shareIn() 封装了这套做法，也让你选择开始、停止和重放的策略。 .shareIn()

调用 shareIn() 时，要确定以下参数。

  • 哪个 CoroutineScope 负责运行共享的上游收集。

  • 用哪种 SharingStarted 策略控制启停。例如 Eagerly 会立即开始，无须等订阅者出现。 SharingStarted.Eagerly

  • 可选的 replay，决定为新订阅者保留几个已发出的值。

shareIn() 在指定作用域中只收集一次上游，再将这次收集的值广播给订阅者。

下面的例子共享序列化后的聊天消息。

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.*
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.Duration.Companion.seconds
import kotlin.io.encoding.*
import java.io.IOException
import kotlin.random.Random

//sampleStart
data class Message(
    val senderId: Int,
    val time: Instant,
    val text: String,
)

class Chatroom {
    // Stores the message flow
    private val _messages = MutableSharedFlow<Message>()

    // Exposes a read-only SharedFlow with emitted messages
    // New subscribers don't receive already emitted messages
    val messages: SharedFlow<Message>
        get() = _messages.asSharedFlow()
  
    // Sends a message to all subscribers of the messages flow
    suspend fun sendMessageToEveryone(message: Message) {
        _messages.emit(message)
    }
}

suspend fun main() {
    val nUsers = 3
    val chatroom = Chatroom()
    withContext(Dispatchers.Default) {
        // Creates a child scope of the currently running coroutine
        val derivedFlowsScope = CoroutineScope(
            currentCoroutineContext() + Job(currentCoroutineContext()[Job])
        )
        // Shares serialized messages between subscribers
        val serializedMessages: SharedFlow<String> =
            chatroom
                .messages
                .map {
                    // Serializes each message once for the shared flow
                    "senderId: ${it.senderId}, time: ${it.time}, text: " +
                        Base64.Default.encode(it.text.encodeToByteArray())
                }
                .shareIn(
                    // Starts the sharing coroutine in this scope.
                    // The upstream flow, including .map(), runs in that coroutine
                    derivedFlowsScope,

                    // Starts collecting the upstream flow immediately,
                    // before the first subscriber appears
                    SharingStarted.Eagerly,

                    // Doesn't replay previous serialized messages to new subscribers
                    replay = 0,
                )

        // Starts a message reader for each user
        val messageReaders = List(nUsers) { userId ->
            launch(start = CoroutineStart.UNDISPATCHED) {
                serializedMessages.collect { serializedMessage ->
                    println("User $userId observes the message $serializedMessage")
                }
            }
        }
        // Sends a greeting from each user
        repeat(nUsers) { userId ->
            chatroom.sendMessageToEveryone(
                Message(
                    userId,
                    Clock.System.now(),
                    "Hello from $userId!"
                )
            )
        }
        // Delays to make sure users have enough time to receive updates
        delay(100.milliseconds)
        // Cancels readers because SharedFlow collection doesn't finish by itself
        messageReaders.forEach { it.cancel() }
        // Cancels the scope that runs the derived hot flow
        derivedFlowsScope.cancel()
    }
}
//sampleEnd

map() 产生一条冷流，用来序列化每条消息。若每个人单独收集，这个转换会重复执行。shareIn() 把转换结果共享后，一条消息只需序列化一次。 .map()

因为选择 SharingStarted.Eagerly，调用 shareIn() 时就会开始收集 chatroom.messages。

类似地，可以用 stateIn() 把冷流共享为 StateFlow。 .stateIn()

这里展示的 stateIn() 重载还要传入初始值，以满足 StateFlow 随时可读的约定。

看下面的例子。

val lastUpdateFlow: StateFlow<Instant?> =
    chatroom
        .messageHistory
        .map { currentHistory -> currentHistory.lastOrNull()?.time }
        .stateIn(
            // Starts the sharing coroutine in this scope
            // The upstream flow, including .map(), runs in that coroutine
            derivedFlowsScope,

            // Starts collecting when the first subscriber appears
            // and stops when the last subscriber disappears
            SharingStarted.WhileSubscribed(),
            // Sets the initial state before the first upstream emission
            null,
        )

停止热流的上游

取消一位订阅者，一般不会直接停止整个热流。

这次取消只结束对应的收集协程。其他订阅者和生产者仍可能继续运行。

热流对象没有单独的取消方法。要停止生产，需要取消负责生产的任务或作用域。

shareIn() 和 stateIn() 由共享协程收集上游。取消它所属的作用域会结束这项工作。

用 SharingStarted.WhileSubscribed() 则可以在没有订阅者时按策略自动停止收集上游。

下面专门取消传给 stateIn() 的作用域，观察派生状态是否还会更新。

import kotlinx.coroutines.flow.*
import kotlin.time.*
import kotlin.time.Duration.Companion.milliseconds
import kotlin.time.Duration.Companion.seconds
import kotlin.io.encoding.*
import java.io.IOException
import kotlin.random.Random

data class Message(
    val senderId: Int,
    val time: Instant,
    val text: String,
)

class Chatroom {
    // Stores the message history
    private val _messageHistory = MutableStateFlow<List<Message>>(emptyList())

    // Exposes a read-only StateFlow with the current message history
    val messageHistory: StateFlow<List<Message>>
        get() = _messageHistory.asStateFlow()

    // Sends a message to all subscribers of the messageHistory flow
    suspend fun sendMessageToEveryone(message: Message) {
        _messageHistory.update {
            it + message

//sampleStart
suspend fun main() {
    val chatroom = Chatroom()
    withContext(Dispatchers.Default) {
        // Creates a child scope of the currently running coroutine
        val derivedFlowsScope = CoroutineScope(
            currentCoroutineContext() + Job(currentCoroutineContext()[Job])
        )
        val totalMessages = chatroom.messageHistory
            .map { currentHistory ->
                currentHistory.size
            }.onEach {
                println("There are currently $it messages")
            }.stateIn(
                // Starts the sharing coroutine in this scope
                derivedFlowsScope
            )
        // Updates messageHistory
        chatroom.sendMessageToEveryone(
            Message(0, Clock.System.now(), "We are shutting down soon!")
        )
        delay(100.milliseconds)
        // Cancels the scope that runs the derived hot flow
        derivedFlowsScope.cancel()
        // Updates messageHistory, but totalMessages no longer receives the update
        chatroom.sendMessageToEveryone(
            Message(0, Clock.System.now(), "We have shut down.")
        )
        println("Last collected history size: ${totalMessages.value}")
        println("Actual history size: ${chatroom.messageHistory.value.size}")
    }
}
//sampleEnd

调用 derivedFlowsScope.cancel() 后，totalMessages 停止收集 messageHistory。

发送新消息的协程仍在，因此 messageHistory 继续增长。此时 totalMessages.value 保留停收时的数值，chatroom.messageHistory.value.size 才反映最新消息数。

热流中的异常由谁处理

冷流中未被 catch() 等操作符处理的异常，会传到调用 collect() 的一方。 cold flows

在热流中，生产者的异常不会作为一个事件自动传给订阅者。生产逻辑出错，在生产协程中处理；订阅者自己的收集逻辑出错，则在收集协程中处理。

shareIn()、stateIn() 启动共享协程来收集上游。上游抛出的未处理异常会终止这个共享协程。

import kotlinx.coroutines.flow.*
import kotlinx.coroutines.*

//sampleStart
suspend fun main() {
    withContext(Dispatchers.Default) {
        launch {
            flow<Int> {
                error("An upstream failure")
            }.stateIn(
                this@launch
            )
        }
    }
}
//sampleEnd

若希望失败后重新开始，把 retry() 放在 shareIn() 或 stateIn() 之前。 restart upstream collection

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*
import kotlin.time.Duration.Companion.milliseconds

//sampleStart
suspend fun main() {
    coroutineScope {
        launch {
            var currentAttempt = 0

            val stateFlow = flow {
                delay(10.milliseconds)

                if (currentAttempt++ < 5) {
                    println("An error happened!")
                    error("An upstream failure")
                } else {
                    println("Success.")
                    emit(10)
                }
            }
                // Restarts the upstream flow after recoverable failures
                .retry(retries = 5)
                .stateIn(
                    // Starts the sharing coroutine in this scope
                    this@launch
                )

            stateFlow.collect {
                println("Observed $it")

                // Cancels collection and the sharing coroutine
                this@launch.cancel()
            }
        }
    }
}
//sampleEnd

例子中的上游连续失败五次才发出值。retry() 位于 stateIn() 前面，因而能先处理这些失败，维持后续尝试。

收到 10 后，收集协程取消自己。本例中它也是共享协程的父任务，因此子任务随之停止。
