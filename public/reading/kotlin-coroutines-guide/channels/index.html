两个协程之间只交付一个结果，可以用 Deferred。要陆续交付一串值，可以用通道 Channel。

发送与接收

把 Channel 想成协程之间的队列。对于 BlockingQueue，put 或 take 可能阻塞线程；通道提供的 send 和 receive 可以只挂起正在等待的协程。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking {
//sampleStart
    val channel = Channel<Int>()
    launch {
        // this might be heavy CPU-consuming computation or async logic, 
        // we'll just send five squares
        for (x in 1..5) channel.send(x * x)
    }
    // here we print five received integers:
    repeat(5) { println(channel.receive()) }
    println("Done!")
//sampleEnd
}

关闭通道与遍历元素

发送方可以关闭通道，表示后面没有新元素。接收方可以用普通 for 循环依次接收。

可以把 close 想成排在已有元素后面的结束标记。接收方先读完关闭前发来的元素，随后自然退出循环。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking {
//sampleStart
    val channel = Channel<Int>()
    launch {
        for (x in 1..5) channel.send(x * x)
        channel.close() // we're done sending
    }
    // here we print received values using `for` loop (until the channel is closed)
    for (y in channel) println(y)
    println("Done!")
//sampleEnd
}

编写生产者

经常会有一个协程负责生成一串值，另一个协程消费它们。可以把通道作为参数传给生产者，但从调用方看，更自然的形式是调用一个函数，从返回值里接收结果。

produce 会启动生产者协程，返回接收端。单一消费者可以用 consumeEach 替代 for 循环。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

//sampleStart
fun CoroutineScope.produceSquares(): ReceiveChannel<Int> = produce {
    for (x in 1..5) send(x * x)
}

fun main() = runBlocking {
    val squares = produceSquares()
    squares.consumeEach { println(it) }
    println("Done!")
//sampleEnd
}

查看完整示例。

把处理步骤串成管道

管道的第一站持续生成值，甚至可以一直生成下去。

fun CoroutineScope.produceNumbers() = produce<Int> {
    var x = 1
    while (true) send(x++) // infinite stream of integers starting from 1
}

后续协程接收上游值，处理后再交给下一站。这里的处理只有一步，把数字平方。

fun CoroutineScope.square(numbers: ReceiveChannel<Int>): ReceiveChannel<Int> = produce {
    for (x in numbers) send(x * x)
}

主程序把各站连接起来，启动整条管道。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking {
//sampleStart
    val numbers = produceNumbers() // produces integers from 1 and on
    val squares = square(numbers) // squares integers
    repeat(5) {
        println(squares.receive()) // print first five
    }
    println("Done!") // we are done
    coroutineContext.cancelChildren() // cancel children coroutines
//sampleEnd
}

fun CoroutineScope.produceNumbers() = produce<Int> {
    var x = 1
    while (true) send(x++) // infinite stream of integers starting from 1
}

fun CoroutineScope.square(numbers: ReceiveChannel<Int>): ReceiveChannel<Int> = produce {
    for (x in numbers) send(x * x)
}

查看完整示例。

创建协程的函数都写成 CoroutineScope 的扩展。这样管道归调用作用域管理，作用域结束时就能收拢工作。 structured concurrency

用管道筛选素数

先从一条无限的整数流开始，看看连续增加过滤步骤会发生什么。

fun CoroutineScope.numbersFrom(start: Int) = produce<Int> {
    var x = start
    while (true) send(x++) // infinite stream of integers from start
}

每一层过滤器接收上游数字，去掉给定素数的所有倍数，把余下的传下去。

fun CoroutineScope.filter(numbers: ReceiveChannel<Int>, prime: Int) = produce<Int> {
    for (x in numbers) if (x % prime != 0) send(x)
}

从 2 开始取数。当前通道送来的第一个数是新的素数，接着为它启动一层过滤器，再从新的出口取数。

numbersFrom(2) -> filter(2) -> filter(3) -> filter(5) -> filter(7) ...

下面在主线程上打印前十个素数。所有阶段都是 runBlocking 的后代，因此无需逐个保存句柄。取够十个数后，调用 cancelChildren 停止余下的生产和过滤。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking {
//sampleStart
    var cur = numbersFrom(2)
    repeat(10) {
        val prime = cur.receive()
        println(prime)
        cur = filter(cur, prime)
    }
    coroutineContext.cancelChildren() // cancel all children to let main finish
//sampleEnd    
}

fun CoroutineScope.numbersFrom(start: Int) = produce<Int> {
    var x = start
    while (true) send(x++) // infinite stream of integers from start
}

fun CoroutineScope.filter(numbers: ReceiveChannel<Int>, prime: Int) = produce<Int> {
    for (x in numbers) if (x % prime != 0) send(x)
}

同样的算法也能用标准库 iterator 实现。把 produce、send、receive、ReceiveChannel 分别换成 iterator、yield、next、Iterator，再去掉作用域和 runBlocking。通道版如果放在 Dispatchers.Default 上，不同阶段有机会使用多个 CPU 核心。

求素数有更实用的算法。这个例子的价值在于展示管道结构：真实阶段可能需要挂起并等待远程服务，produce 允许这些挂起调用，sequence 或 iterator 的构建块对挂起操作有额外限制。

多个消费者分担工作

多个协程可以从同一个通道接收，各自取走不同元素。先让生产者每秒产生约十个整数。

fun CoroutineScope.produceNumbers() = produce<Int> {
    var x = 1 // start from 1
    while (true) {
        send(x++) // produce next
        delay(100) // wait 0.1s
    }
}

再创建几个处理协程，各自打印自己的编号和收到的数。

fun CoroutineScope.launchProcessor(id: Int, channel: ReceiveChannel<Int>) = launch {
    for (msg in channel) {
        println("Processor #$id received $msg")
    }    
}

启动五个处理协程，让它们工作将近一秒，观察分工。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking<Unit> {
//sampleStart
    val producer = produceNumbers()
    repeat(5) { launchProcessor(it, producer) }
    delay(950)
    producer.cancel() // cancel producer coroutine and thus kill them all
//sampleEnd
}

fun CoroutineScope.produceNumbers() = produce<Int> {
    var x = 1 // start from 1
    while (true) {
        send(x++) // produce next
        delay(100) // wait 0.1s
    }
}

fun CoroutineScope.launchProcessor(id: Int, channel: ReceiveChannel<Int>) = launch {
    for (msg in channel) {
        println("Processor #$id received $msg")
    }    
}

Processor #4 received 2

Processor #3 received 5

Processor #4 received 7

取消生产者后，它的通道会关闭。各处理者对通道的遍历也会相继结束。

launchProcessor 用 for 逐项接收。多个处理者共享接收端时，这样写能让其余处理者在一个处理者退出后继续消费，只要它们的作用域仍然有效。consumeEach 结束时会取消通道，包括异常退出的情况，因此不适合这里的共享接收端。

多个生产者汇入同一通道

也可以让多个协程向同一个通道发送。下面的挂起函数每隔一段时间，就把指定的字符串送进去。

suspend fun sendString(channel: SendChannel<String>, s: String, time: Long) {
    while (true) {
        delay(time)
        channel.send(s)
    }
}

在主线程的主协程里启动两个子协程，各自按自己的节奏发送，再从同一处接收。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking {
//sampleStart
    val channel = Channel<String>()
    launch { sendString(channel, "foo", 200L) }
    launch { sendString(channel, "BAR!", 500L) }
    repeat(6) { // receive first six
        println(channel.receive())
    }
    coroutineContext.cancelChildren() // cancel all children to let main finish
//sampleEnd
}

suspend fun sendString(channel: SendChannel<String>, s: String, time: Long) {
    while (true) {
        delay(time)
        channel.send(s)
    }
}

带缓冲的通道

前面的无缓冲通道要求双方会合。先到的 send 会等 receive，先到的 receive 也会等 send。

Channel() 和 produce 都接受 capacity。缓冲区还有空位时，发送方可以连续交付几个元素。缓冲区满后，再发送就要等待接收方腾出位置。

观察日志与 send 的先后位置，预测发送方会在哪里停下。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

fun main() = runBlocking<Unit> {
//sampleStart
    val channel = Channel<Int>(4) // create buffered channel
    val sender = launch { // launch sender coroutine
        repeat(10) {
            println("Sending $it") // print before sending each element
            channel.send(it) // will suspend when buffer is full
        }
    }
    // don't receive anything... just wait....
    delay(1000)
    sender.cancel() // cancel sender coroutine
//sampleEnd    
}

查看完整示例。

容量是四，日志却会打印五次「sending」。

Sending 0
Sending 1
Sending 2
Sending 3
Sending 4

前四个元素进入了缓冲区。第五次打印发生在 send 之前，真正发送第五个元素时才挂起。

等待队列中的先来后到

已经排队的发送或接收请求按先来先服务处理。例如先调用 receive 并进入等待的协程先拿到值。下面让 ping 和 pong 在名为 table 的通道上传递同一个球。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

//sampleStart
data class Ball(var hits: Int)

fun main() = runBlocking {
    val table = Channel<Ball>() // a shared table
    launch { player("ping", table) }
    launch { player("pong", table) }
    table.send(Ball(0)) // serve the ball
    delay(1000) // delay 1 second
    coroutineContext.cancelChildren() // game over, cancel them
}

suspend fun player(name: String, table: Channel<Ball>) {
    for (ball in table) { // receive the ball in a loop
        ball.hits++
        println("$name $ball")
        delay(300) // wait a bit
        table.send(ball) // send the ball back
    }
}
//sampleEnd

查看完整示例。

ping 先启动，因此先拿球。它把球送回去后马上又想接球，此时 pong 已经在等，所以下一球轮到 pong。

ping Ball(hits=1)
pong Ball(hits=2)
ping Ball(hits=3)
pong Ball(hits=4)

执行器的调度方式有时会让观察到的顺序显得不均匀。原文所附 issue 讨论了这种现象。 this issue

定时发送的 ticker 通道

ticker 是一种按时间交付 Unit 的会合通道。它可以充当窗口计算等时间管道的输入，也可以配合 select 在每次计时到点时执行一个分支。 produce

用 ticker 创建通道，用 ReceiveChannel.cancel 告知生产者后续不再需要计时信号。

运行例子，观察消费者暂停前后的间隔。

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.*

//sampleStart
fun main() = runBlocking<Unit> {
    val tickerChannel = ticker(delayMillis = 200, initialDelayMillis = 0) // create a ticker channel
    var nextElement = withTimeoutOrNull(1) { tickerChannel.receive() }
    println("Initial element is available immediately: $nextElement") // no initial delay

    nextElement = withTimeoutOrNull(100) { tickerChannel.receive() } // all subsequent elements have 200ms delay
    println("Next element is not ready in 100 ms: $nextElement")

    nextElement = withTimeoutOrNull(120) { tickerChannel.receive() }
    println("Next element is ready in 200 ms: $nextElement")

    // Emulate large consumption delays
    println("Consumer pauses for 300ms")
    delay(300)
    // Next element is available immediately
    nextElement = withTimeoutOrNull(1) { tickerChannel.receive() }
    println("Next element is available immediately after large consumer delay: $nextElement")
    // Note that the pause between `receive` calls is taken into account and next element arrives faster
    nextElement = withTimeoutOrNull(120) { tickerChannel.receive() }
    println("Next element is ready in 100ms after consumer pause in 300ms: $nextElement")

    tickerChannel.cancel() // indicate that no more elements are needed
}
//sampleEnd

查看完整示例。

一次运行的输出如下。

Initial element is available immediately: kotlin.Unit
Next element is not ready in 100 ms: null
Next element is ready in 200 ms: kotlin.Unit
Consumer pauses for 300ms
Next element is available immediately after large consumer delay: kotlin.Unit
Next element is ready in 100ms after consumer pause in 300ms: kotlin.Unit

默认模式会考虑消费者的停顿，调整下一个元素的等待时间，尽可能维持固定频率。 ticker

将 mode 设为 TickerMode.FIXED_DELAY，则按固定延迟安排后续信号。
