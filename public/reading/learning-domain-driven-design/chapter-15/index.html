事件驱动架构

事件不会天然带来解耦。本章真正讨论的是：跨边界时应发布哪一种事件，以及怎样避免把内部实现、执行顺序和重复逻辑一起扩散到整个系统。

这章不是在劝你“多发事件”

作者先拆开三个常被混用的概念，再用一个失败案例说明：消息异步，不代表系统已经解耦。全章的判断标准始终是“边界外的人到底需要知道什么”。

和微服务一样，事件驱动架构（event-driven architecture，EDA）在现代分布式系统中无处不在。设计松耦合、可扩展、容错的分布式系统时，许多人建议默认采用事件驱动的通信方式来集成各个部分。

事件驱动架构也经常与领域驱动设计联系在一起。毕竟，EDA 建立在事件之上，而事件在 DDD 中十分突出：我们有领域事件；必要时，甚至会把事件作为系统的事实来源。因此，人们很容易想把 DDD 中的事件直接拿来作为事件驱动架构的基础。但这是个好主意吗？

事件并不是一种神秘调料，不能往遗留系统上一撒，就把它变成松耦合的分布式系统。恰恰相反，不谨慎地应用 EDA，可能把一个模块化单体变成分布式大泥球。

本章将探讨 EDA 与 DDD 之间的关系。你将了解事件驱动架构的基本构件、EDA 项目失败的常见原因，以及如何借助 DDD 的工具设计有效的异步集成系统。

事件驱动架构

简单来说，事件驱动架构是一种架构风格：系统组件通过交换事件消息，以异步方式彼此通信，如图 15-1 所示。组件不再同步调用服务端点，而是发布事件，通知系统中的其他元素领域发生了变化。其他组件可以订阅系统中产生的事件，并据此作出反应。第 9 章介绍的 Saga 模式，就是事件驱动执行流程的典型例子。

主线提示

先把 EDA 和事件溯源分开

一个解决服务之间怎样交流，另一个解决服务内部怎样记录状态。它们都用“事件”，却处在不同边界；后面所有取舍都建立在这个区分上。

必须特别强调事件驱动架构与事件溯源之间的区别。正如第 7 章所讨论的，事件溯源是一种把状态变化记录为一系列事件的方法。

虽然事件驱动架构和事件溯源都以事件为基础，但两种模式在概念上并不相同。EDA 指的是服务之间的通信，而事件溯源发生在服务内部。为事件溯源设计的事件，表示服务中实现的状态转换——也就是事件溯源领域模型里聚合的状态转换。它们旨在捕捉业务领域的细微之处，默认并不是为了把服务与系统中的其他组件集成起来。

本章稍后会介绍三种事件类型，其中有些比另一些更适合集成。

事件

在 EDA 系统中，交换事件是集成各个组件、使它们成为一个系统的关键通信机制。下面更细致地看看事件，并了解它与消息有何不同。

事件、命令与消息

到目前为止，事件的定义似乎与消息模式的定义相近。1 但两者并不相同。事件是一种消息，但消息未必是事件。消息有两种类型：

事件（Event）
描述一个已经发生的变化的消息。
命令（Command）
描述一个必须执行的操作的消息。

事件表示已经发生的事，命令则是要求去做某件事。事件和命令都可以作为消息异步传递。不过，命令可能被拒绝：命令的目标可以拒绝执行，例如命令无效，或与系统业务规则冲突。事件的接收方却无法取消事件，因为事件描述的是已经发生的事实。想要推翻事件，只能发出一个补偿动作——也就是一个命令，正如 Saga 模式中的做法。

因为事件描述已经发生的事，事件名称应该使用过去时，例如 DeliveryScheduled（配送已排期）、ShipmentCompleted（发货已完成）或 DeliveryConfirmed（配送已确认）。

结构

事件是一条数据记录，可以被序列化，并通过所选择的消息平台传输。典型的事件模式包括事件的元数据和载荷，也就是该事件传达的信息：

{
  "type": "delivery-confirmed",
  "event-id": "14101928-4d79-4da6-9486-dbc4837bc612",
  "correlation-id": "08011958-6066-4815-8dbe-dee6d9e5ebac",
  "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
  "timestamp": 1615718833,
  "payload": {
    "confirmed-by": "17bc9223-bdd6-4382-954d-f1410fd286bd",
    "delivery-time": 1615701406
  }
}

事件的载荷不仅描述事件所传递的信息，也定义了事件的类型。下面详细讨论三类事件以及它们之间的差异。

事件类型

事件可以归入三种类型之一：2事件通知（event notification）、事件携带状态转移（event-carried state transfer，ECST），或领域事件（domain event）。

事件通知

事件通知是一条关于业务领域发生变化的消息，其他组件会对此作出反应。例如 PaycheckGenerated（工资单已生成）、CampaignPublished（营销活动已发布）等。

事件通知不应该冗长：目标是把事件告知感兴趣的各方，但通知本身不应携带订阅者作出反应所需的全部信息。例如：

{
  "type": "paycheck-generated",
  "event-id": "537ec7c2-d1a1-2005-8654-96aee1116b72",
  "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
  "timestamp": 1615726445,
  "payload": {
    "employee-id": "456123",
    "link": "/paychecks/456123/2021/01"
  }
}

上面的代码通知外部组件：一张工资单已经生成。它没有携带与工资单相关的全部信息，接收方可以用其中的链接获取更详细的信息。这个通知流程如图 15-2 所示。

主线提示

通知只负责“叫你来看”

它故意不把详情塞进消息里。这样一来，敏感数据仍在生产者手里；消费者需要时再查询，也能拿到较新的状态。代价是消费时仍依赖生产者在线。

从某种意义上说，通过事件通知进行集成，类似美国的无线紧急警报（WEA）系统和欧洲的 EU-Alert 系统，如图 15-3 所示。这些系统利用蜂窝基站广播短消息，向市民通知公共卫生事件、安全威胁和其他紧急情况。系统发送的消息最长只有 360 个字符。这条短消息足以让你知道发生了紧急情况，但要获得更多细节，你必须主动查阅其他信息来源。

简洁的事件通知在多种场景下更合适。下面详细看看其中两种：安全性与并发。

安全性。强制接收方显式查询详细信息，可以避免在消息基础设施上传播敏感信息；订阅者要访问这些数据，还需要经过额外授权。

并发。由于事件驱动集成本质上是异步的，信息到达订阅者时可能已经过时。如果信息容易受到竞态条件影响，显式查询能取得最新状态。

此外，在并发消费者场景中，如果一个事件只应由一个订阅者处理，那么查询过程可以与悲观锁集成。这样，生产者一侧就能保证不会有其他消费者处理同一条消息。

事件携带状态转移

事件携带状态转移（ECST）消息向订阅者通知生产者内部状态的变化。与事件通知不同，ECST 消息包含能够反映状态变化的全部数据。

ECST 消息可以有两种形式。第一种是修改后实体状态的完整快照：

{
  "type": "customer-updated",
  "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
  "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
  "timestamp": 1615728520,
  "payload": {
    "first-name": "Carolyn",
    "last-name": "Hayes",
    "phone": "555-1022",
    "status": "follow-up-set",
    "follow-up-date": "2021/05/08",
    "birthday": "1982/04/05",
    "version": 7
  }
}

上例中的 ECST 消息包含客户更新后状态的完整快照。处理大型数据结构时，也可以只在 ECST 消息中包含实际被修改的字段：

{
  "type": "customer-updated",
  "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
  "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
  "timestamp": 1615728520,
  "payload": {
    "status": "follow-up-set",
    "follow-up-date": "2021/05/10",
    "version": 8
  }
}

无论 ECST 消息包含完整快照，还是只包含更新字段，这类事件组成的流都能让消费者在本地保存实体状态缓存，并以此工作。从概念上说，使用事件携带状态转移消息，就是一种异步数据复制机制。这种方法能提高系统容错能力：即使生产者不可用，消费者也能继续工作。对于需要处理多个来源数据的组件，它也能改善性能。消费者无需每次使用数据时都查询各个来源，而可以把所有数据缓存在本地，如图 15-4 所示。

主线提示

ECST 负责“把状态带过来”

消费者因此可以拥有本地副本，减少同步查询并提高容错；但它收到的是某个时刻的状态，不是发生这次变化的业务原因。

领域事件

第三种事件消息，是第 6 章介绍过的领域事件。从某种意义上说，领域事件位于事件通知与 ECST 消息之间：它们都描述业务领域中的重大事件，并且包含描述该事件的全部数据。尽管如此，这几类消息在概念上仍然不同。

领域事件与事件通知

领域事件和事件通知都描述生产者业务领域中的变化，但二者存在两个概念差异。

第一，领域事件包含描述事件的全部信息。消费者不需要进一步操作，就能得到完整图景。

第二，建模意图不同。事件通知是为了减轻与其他组件集成的成本而设计；领域事件则是为了建模和描述业务领域。即使没有外部消费者感兴趣，领域事件也可能有用。在事件溯源系统中尤其如此：领域事件用来建模所有可能的状态转换。让外部消费者对全部可用领域事件都产生兴趣，会得到次优设计。本章后面会更详细地讨论这一点。

领域事件与事件携带状态转移

领域事件包含的数据，与典型 ECST 消息的模式在概念上不同。

一条 ECST 消息会提供足够的信息，让消费者保存生产者数据的本地缓存。任何单个领域事件都不应该暴露如此丰富的模型。即便某个领域事件包含了一些数据，它也不足以缓存聚合状态，因为消费者没有订阅的其他领域事件也可能影响相同字段。

此外，与事件通知一样，两类消息的建模意图也不同。领域事件中的数据不是为了描述聚合状态，而是为了描述聚合生命周期中发生的业务事件。

事件类型：示例

下面用三种方式表示“结婚”这件事，以说明三类事件的差异：

eventNotification = {
  "type": "marriage-recorded",
  "person-id": "01b9a761",
  "payload": {
    "person-id": "126a7b61",
    "details": "/01b9a761/marriage-data"
  }
};

ecst = {
  "type": "personal-details-changed",
  "person-id": "01b9a761",
  "payload": {
    "new-last-name": "Williams"
  }
};

domainEvent = {
  "type": "married",
  "person-id": "01b9a761",
  "payload": {
    "person-id": "126a7b61",
    "assumed-partner-last-name": true
  }
};

marriage-recorded 是事件通知。除了指定 ID 的人已经结婚这一事实，它没有包含别的信息。它只提供事件的最少信息；想知道更多细节的消费者，需要访问 details 字段中的链接。

personal-details-changed 是事件携带状态转移消息。它描述这个人的个人资料发生了什么变化，也就是姓氏已经改变；但没有解释变化的原因。这个人是结婚了，还是离婚了？

最后，married 是领域事件。它尽可能贴近业务领域中事件本身的性质来建模，包含当事人的 ID，以及此人是否采用伴侣姓氏的标记。

设计事件驱动集成

主线提示

前半章在分辨工具，后半章开始用工具检查边界

选择事件类型，本质上是在决定哪些信息可以穿过限界上下文。选错以后，异步消息也会把消费者绑到生产者的执行顺序和内部模型上。

正如第 3 章所讨论的，软件设计主要是在设计边界。边界规定什么属于内部、什么留在外部，更重要的是规定什么会穿过边界——也就是各组件如何彼此集成。在基于 EDA 的系统中，事件是一等设计元素：它既影响组件之间如何集成，也影响组件自身的边界。选择正确的事件消息类型，可能成就一个解耦的分布式系统，也可能把它彻底耦合起来。

本节将介绍应用不同事件类型的启发式方法。但在此之前，先看看怎样用事件设计出一个强耦合的分布式大泥球。

分布式大泥球

考虑图 15-5 所示的系统。

CRM 限界上下文采用事件溯源领域模型实现。CRM 系统需要与 Marketing（营销）限界上下文集成时，团队决定利用事件溯源数据模型的灵活性，让消费者——也就是 Marketing——订阅 CRM 的领域事件，并投影出适合自己需要的模型。

后来引入 AdsOptimization（广告优化）限界上下文，它同样需要处理 CRM 限界上下文产生的信息。团队再次决定让 AdsOptimization 订阅 CRM 产生的所有领域事件，并投影出适合 AdsOptimization 需要的模型。

有意思的是，Marketing 和 AdsOptimization 两个限界上下文都需要以相同格式呈现客户信息，因此最终都从 CRM 的领域事件中投影出了同一个模型：每位客户状态的扁平快照。

Reporting（报表）限界上下文只订阅 CRM 发布的一部分领域事件，并把这些事件当作事件通知，用来获取 AdsOptimization 上下文完成的计算结果。不过，由于两个下游上下文都使用同样的事件触发自己的计算，为了确保 Reporting 模型更新时 AdsOptimization 已经完成处理，Reporting 引入了延迟：消息收到五分钟后才开始处理。

这个设计糟透了。下面分析系统中的几类耦合。

时间耦合

AdsOptimization 和 Reporting 两个限界上下文存在时间耦合：它们依赖严格的执行顺序。AdsOptimization 组件必须先完成处理，Reporting 模块才能被触发。如果顺序颠倒，Reporting 系统就会产生不一致的数据。

为了强制实现所需的执行顺序，工程师在 Reporting 系统中加入处理延迟。五分钟延迟给 AdsOptimization 组件留出了完成计算的时间。显然，这并不能真正防止错误的执行顺序：

  • AdsOptimization 可能负载过高，无法在五分钟内完成处理；
  • 网络问题可能延迟消息到达 AdsOptimization 服务；
  • AdsOptimization 组件可能发生故障，停止处理进入的消息。

功能耦合

Marketing 和 AdsOptimization 两个限界上下文都订阅了 CRM 的领域事件，最终实现了相同的客户数据投影。换句话说，把进入的领域事件转换成基于状态的表示，这段业务逻辑在两个限界上下文里重复实现，而且两份逻辑拥有相同的变化原因：它们必须以相同格式呈现客户数据。因此，只要其中一个组件改变投影，另一个限界上下文也必须同步复制这项变化。

这就是功能耦合：多个组件实现同一种业务功能；一旦功能变化，多个组件就必须同时变化。

实现耦合

这种耦合更隐蔽。Marketing 和 AdsOptimization 订阅了 CRM 事件溯源模型生成的全部领域事件。因此，CRM 的任何实现变化——例如增加新的领域事件，或修改现有事件的模式——都必须同步反映在两个订阅方中！做不到就可能产生不一致数据。例如，如果事件模式改变，订阅者的投影逻辑会失败；如果 CRM 模型增加了新领域事件，它又可能影响投影模型，忽略它同样会投影出不一致的状态。

重构事件驱动集成

主线提示

修复方法不是“换消息中间件”

三种耦合都来自边界信息设计：生产者公开了太多内部事件、消费者重复解释同一模型、报表猜测上游何时完成。重构就是逐一收回这些泄漏。

可见，盲目地向系统倾倒事件，既不会让它解耦，也不会让它更有韧性。你也许会觉得这个例子不现实，但遗憾的是，它来自真实故事。下面看看怎样调整事件，从而显著改善设计。

公开构成 CRM 数据模型的全部领域事件，会让订阅者耦合到生产者的实现细节。解决实现耦合，可以只公开一组严格受限的事件，或改用其他类型的事件。

Marketing 和 AdsOptimization 订阅者因为实现同样的业务功能而彼此形成了功能耦合。

实现耦合和功能耦合，可以一起通过把投影逻辑封装到生产者——CRM 限界上下文——中来解决。CRM 不再暴露实现细节，而是遵循消费者驱动契约模式：投影消费者需要的模型，并把它作为限界上下文发布语言的一部分。这个集成专用模型与内部实现模型解耦。于是，消费者得到了所需的全部数据，却不需要知道 CRM 的实现模型。

为了消除 AdsOptimization 与 Reporting 限界上下文之间的时间耦合，AdsOptimization 组件可以在计算完成后发布一条事件通知，触发 Reporting 组件获取所需数据。重构后的系统如图 15-6 所示。

事件驱动设计启发式

让事件类型与手头任务相匹配，能够让最终设计的耦合度下降几个数量级，同时更灵活、更容错。下面把前述修改背后的设计启发式归纳出来。

假设最坏情况一定会发生

用安迪·格鲁夫的话说，只有偏执狂才能生存。3设计事件驱动系统时，应把这句话作为指导原则：

  • 网络一定会变慢；
  • 服务器一定会在最不方便的时刻出故障；
  • 事件一定会乱序到达；
  • 事件一定会重复。

最重要的是，这些情况最常发生在周末和公共假期。

“事件驱动”中的“驱动”意味着：整个系统依赖消息的成功投递。因此，要像躲避瘟疫一样，避开“事情总会没问题”的心态。无论遇到什么情况，都要确保事件能够一致、可靠地交付：

  • 使用发件箱（outbox）模式可靠发布消息；
  • 发布消息时，确保订阅者能够对消息去重，并能识别、重新排序乱序消息；
  • 编排跨限界上下文、并且需要发出补偿动作的流程时，利用 Saga 和流程管理器模式。

区分公共事件与私有事件

主线提示

领域事件不等于公共 API

服务内部可以拥有细腻、频繁变化的事件；跨边界时却应重新设计一套稳定的发布语言。否则消费者会被迫理解你的内部模型。

发布领域事件时，要警惕暴露实现细节，尤其是事件溯源聚合中的事件。事件应被视为限界上下文公共接口的内在组成部分。因此，实现开放主机服务模式时，要确保这些事件反映在限界上下文的发布语言中。第 9 章讨论了转换事件模型的模式。

设计限界上下文的公共接口时，应利用不同类型的事件。事件携带状态转移消息会把实现模型压缩为更紧凑的模型，只传达消费者真正需要的信息。

事件通知消息可以进一步缩小公共接口。最后，使用领域事件与外部限界上下文通信时要保持克制；可以考虑专门设计一套公共领域事件。

评估一致性要求

设计事件驱动通信时，还要评估限界上下文的一致性要求，把它作为选择事件类型的另一条启发式：

  • 如果组件可以接受最终一致的数据，使用事件携带状态转移消息；
  • 如果消费者必须读取生产者状态中的最后一次写入，发送事件通知，然后由消费者查询生产者的最新状态。
选择事件类型的快捷问题：消费者要的是“知道有事发生”“拿到一份可本地使用的状态”，还是“理解发生了什么业务事实”？

小结

本章把事件驱动架构呈现为设计限界上下文公共接口的内在组成部分。你学到了三种可用于跨限界上下文通信的事件：

事件通知
通知某件重要事情已经发生，但要求消费者显式查询生产者，取得额外信息。
事件携带状态转移
一种基于消息的数据复制机制。每个事件包含一个状态快照，可用于维护生产者数据的本地缓存。
领域事件
描述生产者业务领域中所发生事件的消息。

使用不合适的事件类型，会让基于 EDA 的系统脱轨，并在无意中变成大泥球。要为集成选择正确的事件类型，需要评估限界上下文的一致性要求，同时警惕暴露实现细节。应显式设计公共事件与私有事件。最后，要确保即使面对技术问题和系统故障，消息仍能被可靠交付。
