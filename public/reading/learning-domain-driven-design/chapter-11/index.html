第 11 章

演进设计决策

业务、组织、认知和规模都会变化。设计不是一次性答案，而是需要随着这些变化持续重新评估的假设。

在我们生活的这个高速运转的现代世界里，企业承担不起行动迟缓的代价。为了跟上竞争，它们必须持续变化、演进，甚至不断重新定义自己。设计系统时不能忽略这个事实，尤其当我们的目标是让软件贴合业务领域的需求时。

如果变化没有得到妥善管理，即使最复杂、最周密的设计，最终也会变成难以维护和演进的噩梦。本章讨论软件项目环境的变化如何影响设计决策，以及怎样相应地演进设计。我们将考察四种最常见的变化向量：业务领域、组织结构、领域知识和增长。

领域变化

白话解释

子域类型不是永久标签

核心、支撑、通用描述的是“这件事此刻对企业的战略价值”，而不是代码目录的固定属性。同一块能力会因为市场、成本和新机会而换类型。

第 2 章介绍了三类业务子域及其差异：

  • 核心子域：企业为了获得竞争优势，采用不同于竞争对手的方式开展的活动。
  • 支撑子域：企业采用了不同做法，但这些做法本身并不会带来竞争优势。
  • 通用子域：所有企业基本都以相同方式完成的事情。

前几章已经说明，所涉及的子域类型会影响战略与战术设计决策：怎样设计限界上下文边界，怎样编排上下文之间的集成，以及选择什么设计模式来容纳业务逻辑的复杂度。

要让软件设计由业务领域的需要驱动，识别业务子域及其类型至关重要。但这还不够。我们同样要警觉子域本身的演进。组织成长和变化时，一些子域从一种类型转变成另一种类型并不少见。

从核心到通用

设想一家名为 BuyIT 的在线零售企业一直在自行实现订单配送方案。它开发了创新算法来优化快递员的配送路线，因此可以收取比竞争对手更低的配送费用。

后来，DeliverIT 公司颠覆了配送行业。它宣称已经解决“旅行商问题”，并把路径优化作为服务提供。DeliverIT 的优化不仅更先进，价格也只有 BuyIT 自行维持同等能力的一小部分。

从 BuyIT 的角度看，一旦 DeliverIT 的方案成为现成商品，原本的核心子域就转变成了通用子域。最优方案现在对所有竞争对手都可获得。除非投入巨额研发资金，否则 BuyIT 已经无法再从路径优化中获得竞争优势。过去的优势变成了所有竞争者都能购买的商品。

从通用到核心

BuyIT 从成立之初就使用现成方案管理库存，但商业智能报告不断显示，它对客户需求的预测并不准确。结果是，热门商品无法及时补货，冷门商品却占用了仓库空间。

在评估了几种替代产品之后，管理层作出战略决策：设计并构建内部系统。这个方案会考虑 BuyIT 所售商品的具体特点，更准确地预测客户需求。

你的项目

Common 化不自动等于“核心子域”

native-text 迁移到 Common，说明跨平台一致性和复用价值上升；但是否成为核心子域，还要看它是否带来真实业务优势。技术投入变大，只是重新评估的信号，不是结论。

用内部实现替换现成产品，使库存管理从通用子域变成了核心子域：如果新系统成功，BuyIT 将拥有竞争对手无法使用的高级需求预测算法。一个现实中的经典例子是 Amazon。像所有服务提供商一样，Amazon 需要运行服务的基础设施；后来它重新发明了管理物理基础设施的方式，并最终把这项能力发展成了盈利业务——Amazon Web Services。

从支撑到通用

BuyIT 的市场部门实现了一套供应商与合同管理系统。系统没有特别之处，也不复杂，只是用于录入数据的一些 CRUD 界面，因此是典型的支撑子域。

几年后，一个开源合同管理方案出现了。它既实现了相同功能，又提供 OCR 和全文搜索等高级能力。这些能力长期位于 BuyIT 的待办列表中，却因业务影响较低从未获得优先级。于是公司放弃内部方案，转而集成开源产品。文档管理因此从支撑子域变成了通用子域。

从支撑到核心

如果企业找到一种优化支撑逻辑的方法，能够降低成本或带来额外利润，那么支撑子域也可能变成核心子域。

这种转变的典型症状，是支撑子域的业务逻辑复杂度不断上升。支撑子域按定义应该比较简单，主要类似 CRUD 界面或 ETL 流程。如果业务逻辑越来越复杂，额外复杂度背后应该有原因。若它不影响企业利润，那就是偶发的业务复杂度；若它提高了盈利能力，则表明支撑子域正在转变为核心子域。

从核心到支撑

核心子域也可能随着时间变成支撑子域。当一个子域的复杂度不再值得，也就是不再盈利时，组织可能决定删去多余复杂度，只保留支撑其他子域所需的最少逻辑。

从通用到支撑

出于类似原因，通用子域也可能变成支撑子域。回到 BuyIT 的文档管理系统：如果公司发现集成开源产品的复杂度不值得，重新使用内部系统，那么这个通用子域就转变成了支撑子域。

战略设计方面的影响

子域类型一旦变化，会直接影响它的限界上下文，继而影响相应的战略设计决策。不同的上下文集成模式适用于不同的子域类型。核心子域需要使用防腐层保护自己的模型，还需要用开放主机服务和发布语言保护消费者，使它们不必跟随实现模型频繁变化。

另一种会受到影响的模式是各行其道。团队可以在支撑和通用子域中采用这种模式；但如果子域变成核心子域，让多个团队重复实现同一项核心能力就不再合适。团队必须整合各自实现。在这种情况下，由一个团队实现核心子域，并建立客户—供应商关系通常更合理。

从实现策略看，核心与支撑子域也不同。支撑子域可以外包，或者用作新员工的练手机会。核心子域必须由内部团队实现，并且尽可能贴近领域知识的来源。因此，当支撑子域变成核心子域时，实现工作应移回内部；反过来，如果核心子域变成支撑子域，则可以考虑外包，让内部研发集中于新的核心能力。

可优化点

给重要边界加“复查触发器”

不要按季度机械重画架构。可以在出现新平台、新盈利点、外部商品化方案、团队归属变化或规则复杂度陡增时，触发一次子域与集成关系复查。

战术设计方面的影响

子域类型发生变化的主要指标，是现有技术设计已经无法支持当前业务需求。

回到支撑子域变成核心子域的例子。支撑子域通常使用相对简单的业务逻辑模式，例如事务脚本或活动记录。但这些模式不适合包含复杂规则和不变量的业务逻辑。

你的项目

“越来越难改”本身就是领域信号

模板切换若只需请求并展示，简单流程足够；当失败回滚、过期回调、二次编辑和平台写回不断叠加，再继续增加布尔值和临时分支，痛苦就说明模型已落后于业务。

如果复杂规则和不变量持续加入，代码库也会越来越复杂。新增功能会变得痛苦，因为当前设计无法支撑新的复杂度水平。这种“痛苦”是重要信号，应当用它来重新评估业务领域和设计选择。

需要改变实现策略并不可怕，这是正常现象。我们无法预见业务未来怎样演变，也不能对所有子域一开始就使用最复杂的设计模式，那既浪费又低效。我们应该选择当下最合适的设计，在确有需要时再演进。

如果最初对业务逻辑模式的选择是有意识的，并且团队理解不同方案及其差异，那么从一种模式迁移到另一种模式并不会特别麻烦。下面是几条常见演进路径。

从事务脚本到活动记录

事务脚本和活动记录的核心原则相同：业务逻辑都以过程式脚本实现。两者的区别在于数据结构的建模方式。活动记录引入了专门的数据结构，用来封装数据到持久化机制之间的映射复杂度。

因此，当事务脚本中“操作数据”本身变得困难时，可以重构为活动记录。找出复杂的数据结构，把它们封装到活动记录对象中；不要继续直接访问数据库，而是让活动记录抽象存储模型和结构。

从活动记录到领域模型

如果操作活动记录的业务逻辑变得复杂，并且不一致和重复越来越多，就应考虑重构为领域模型。

首先识别值对象：哪些数据结构可以建模成不可变对象？找到与之相关的业务逻辑，并把这些逻辑也移入值对象。

然后分析数据结构，寻找事务边界。为了让所有修改状态的逻辑都变得显式，可以先把活动记录的 setter 改为私有，使状态只能在对象内部修改。编译当然会失败，但编译错误会准确暴露哪些外部组件正在控制对象状态。

public class Player
{
    public Guid Id { get; set; }
    public int Points { get; set; }
}

public class ApplyBonus
{
    public void Execute(Guid playerId, byte percentage)
    {
        var player = _repository.Load(playerId);
        player.Points *= 1 + percentage / 100.0;
        _repository.Save(player);
    }
}

第一步先收紧 setter。此时代码还不能编译，但错误会让外部状态修改的位置一目了然：

public class Player
{
    public Guid Id { get; private set; }
    public int Points { get; private set; }
}

下一步，把修改积分的逻辑移到对象边界内部：

public class Player
{
    public Guid Id { get; private set; }
    public int Points { get; private set; }

    public void ApplyBonus(int percentage)
    {
        this.Points *= 1 + percentage / 100.0;
    }
}
你的项目

让非法状态先“写不出来”

把 selectedIndex、committedIndex 或请求代次暴露给任意调用方修改，等价于公开 setter。更稳妥的方向是只暴露 requestTemplate、finishPlatformApply、failActiveApply 这类带业务语义的状态转换。

当所有修改状态的业务逻辑都被移入相应对象边界后，再检查需要哪些层级才能强一致地验证业务规则和不变量。这些层级就是聚合的候选。

遵循第 6 章的聚合设计原则，寻找最小事务边界，也就是业务领域要求保持强一致的最少数据量。沿着这些边界拆分层级结构，外部聚合只能通过 ID 引用。最后，为每个聚合识别聚合根，也就是公共接口的入口；聚合内部其他对象的方法应设为私有，只能从聚合内部调用。

从领域模型到事件溯源领域模型

一旦拥有边界设计合理的聚合，就可以向事件溯源模型迁移。不要再直接修改聚合数据，而是对表达聚合生命周期所需的领域事件进行建模。

最具挑战的部分是已有聚合的历史：怎样把原来“没有时间维度的状态”迁移到基于事件的模型中。旧系统没有保存每一次细粒度状态变化，因此只能尽力生成历史事件，或者明确建模一种迁移事件。

不过，这种方式的缺点必须牢记。事件溯源的目标是获得可靠、强一致的聚合领域事件历史，而近似生成无法恢复完整的状态转换。在这个例子里，我们不知道销售人员实际联系过客户多少次，也就不知道遗漏了多少个 contacted 事件。

建模迁移事件

另一种方式，是承认我们不知道过去发生过什么，并把知识缺失显式建模成一个事件。与其推测哪些事件导致了当前状态，不如定义迁移事件，用它初始化已有聚合的事件流：

  "lead-id": 12,
  "event-id": 0,
  "event-type": "migrated-from-legacy",
  "first-name": "Shauna",
  "last-name": "Mercia",

  "status": "converted",
  "last-contacted-on": "2020-05-27T12:02:12.51Z",

  "followup-on": null

白话解释

诚实的不完整，胜过精确的虚构

migrated-from-legacy 的价值不只是迁移方便，而是永久告诉读者：“从这里向前历史可信；更早的细节我们不知道。”

这种方法的优点是明确表达了历史数据缺失。任何人都不会误以为事件流包含了聚合生命周期里发生过的全部领域事件。缺点则是旧系统的痕迹会永久保留在事件存储中。例如使用 CQRS 时，投影逻辑始终需要识别迁移事件。

你的项目

迁移边界也应该显式

未迁移模块继续走旧链路、Common 只接管指定能力，本质上和迁移事件相似：不要伪装成“全量已经统一”，而要让新旧事实从哪一刻、哪一能力开始分界清晰可见。

组织变化

另一类影响系统设计的变化来自组织本身。第 4 章介绍了限界上下文的多种集成模式：合作关系、共享内核、遵奉者、防腐层、开放主机服务和各行其道。组织结构的变化会改变团队之间的沟通与协作水平，因此上下文的集成方式也需要随之调整。

一个直接例子是研发中心扩张。一个限界上下文只能由一个团队负责，因此新增研发团队时，原本较宽的限界上下文可能需要拆成更小的上下文，让每个团队拥有自己的边界。

研发中心还可能分布在不同地理位置。当已有上下文的工作转移到另一个地点时，团队协作可能受到负面影响。相应地，限界上下文之间的集成模式也需要演进。

从合作关系到客户—供应商

合作关系假设团队之间存在紧密沟通与协作。随着时间推移，这个条件可能不再成立，例如其中一个上下文被转移到远程研发中心。沟通质量下降后，从合作关系转向边界和责任更明确的客户—供应商关系可能更合理。

从客户—供应商到各行其道

团队出现严重沟通问题并不少见，原因可能是地理距离，也可能是组织政治。集成问题会随着时间不断增加；到某个临界点，重复实现一部分功能可能比长期互相等待和协调更经济。

你的项目

边界要匹配真实协作能力

Common、Android 和鸿蒙即使共享代码，也不代表三个宿主拥有同样的发布节奏与领域知识。接口、错误语义和写回契约要能在“沟通不是实时的”情况下仍然成立。

领域知识

领域驱动设计的核心主张是：领域知识对于设计成功的软件系统不可或缺。获取领域知识本身就是软件工程最困难的部分之一，核心子域尤其如此。核心子域的逻辑不仅复杂，还会频繁变化；建模也不是一次性活动，模型必须随着对业务领域理解的加深而改进。

很多时候，业务领域的复杂度最初是隐性的。一开始一切看起来简单直接，这种简单却往往具有欺骗性。随着功能增加，更多边缘情况、不变量和规则被发现，简单很快转化为复杂。新的认识甚至可能是颠覆性的，要求从头重建模型，包括限界上下文、聚合和其他实现细节的边界。

白话解释

早期的大边界是一种可逆选择

领域还没看清时，太早切得很细，会把猜测固化成跨服务契约。先保留稍宽的边界，等词义和规则稳定后再拆，通常更容易纠错。

从战略设计角度看，一个有用的启发式是：根据领域知识的成熟度设计限界上下文边界。把系统拆成错误的上下文，事后修正成本可能很高。因此，当领域逻辑尚不清晰且频繁变化时，适合先采用较宽的边界。随着知识不断积累、业务逻辑趋于稳定，再把宽上下文分解为更窄的上下文或微服务。

新发现的领域知识应当用于演进设计，使其更有韧性。但领域知识也可能流失：文档逐渐过期，参与原始设计的人离开公司，新功能以临时方式不断加入，最终代码库获得“遗留系统”的名号。主动防止领域知识退化至关重要。下一章将介绍一种恢复领域知识的有效工具：EventStorming 工作坊。

可优化点

把知识写进可执行边界

文档记录为什么，类型和状态机限制什么能发生，测试保护关键不变量。只写一次性迁移文档，无法阻止半年后同样的语义再次分叉。

增长

增长是健康系统的标志。持续增加新功能，说明系统给用户带来了价值，团队也在继续满足需求并应对竞争。但增长也有阴暗面：代码库可能逐渐长成一团乱麻。

一团乱麻，是一种结构随意、蔓延失控、粗糙松散、靠胶带和铁丝勉强维持的意大利面式代码丛林。它清楚地表现出不受约束的增长，以及一次又一次只求眼前奏效的修补。1

1　Brian Foote 与 Joseph Yoder，Big Ball of Mud，PLoP 1997。

导致一团乱麻的无序增长，源于扩展系统功能时没有重新评估过去的设计决策。增长不断撑大组件边界，扩展其职责。领域驱动设计中的许多工具，本质上都在设定边界：子域限定业务构件，限界上下文限定模型，值对象限定不可变性，聚合限定一致性。

处理增长复杂度的指导原则，是识别并消除偶发复杂度——也就是过期设计决策造成的复杂度。业务领域内在的本质复杂度则应该用领域驱动设计工具和实践来管理。

子域

子域边界很难识别，因此我们不追求完美边界，而追求有用边界：它们应帮助我们区分不同业务价值的组件，并为每一类选择合适的设计和实现工具。

业务增长时，子域边界会更加模糊，一个粗粒度子域可能实际上横跨多个更细的子域。应当定期重新检查已识别的子域，并使用内聚用例这一启发式：如果一组用例操作同一组数据，它们更可能属于同一个子域；若用例和数据开始分群，就可能出现了拆分位置。

如果能够识别类型不同的细粒度子域，就能更好地管理业务领域的本质复杂度。对子域及其类型了解得越准确，为每个子域选择技术方案就越有效。尤其对于核心子域，应尽量从其他能力中提纯出来，把投入集中在业务战略最重要的地方。

你的项目

按业务链拆，不按平台拆

首次输入、模板选择、二次编辑、完成写回虽然穿过 Common/Android/鸿蒙，但更值得检查的是它们是否拥有不同用例、状态和副作用，而不是简单按源码集把领域切成三块。

限界上下文

限界上下文允许我们为业务领域使用不同模型。与其构建一个“什么都会、什么都不精”的模型，不如构建多个各自聚焦于特定问题的模型。

项目演进和增长时，限界上下文很容易失去焦点，积累解决不同问题的逻辑，这就是偶发复杂度。像检查子域一样，我们也需要定期检查上下文边界，寻找把模型简化为更专注上下文的机会。

增长还会把原先隐蔽的设计问题暴露出来。例如，一些限界上下文可能越来越“话多”，任何操作都必须调用另一个上下文才能完成。这强烈暗示模型无效，应重新设计边界，提高上下文自治性。

你的项目

频繁来回调用可能是事实被切开了

如果 Common 每一步都要询问平台“现在是什么状态”，平台又不断读取 Common 才能决定写回，很可能不是接口不够多，而是同一业务事实被两个所有者拆开了。

聚合

第 6 章给出的聚合边界原则是：聚合应尽可能小，只包含业务领域要求保持强一致的对象。

业务需求增长时，把新功能随手分配给已有聚合很方便，却容易忘记重新检查“小聚合”原则。如果一个聚合包含了并非所有业务逻辑都需要强一致的数据，就产生了应当消除的偶发复杂度。

把业务功能提取到独立聚合，不仅能简化原聚合，还可能简化它所属的限界上下文。这类重构经常会暴露一个隐藏模型；当它被明确表达后，甚至应该进入另一个限界上下文。

可优化点

用强一致问题检查会话边界

  • 哪些状态必须与一次平台写回一起成功？
  • 哪些只是展示或缓存，可以稍后更新？
  • 失败时必须共同回滚的最小集合是什么？

答案比“把所有编辑状态放进一个 Session”更能决定聚合大小。

结论

正如赫拉克利特所说，人生唯一不变的就是变化。企业也不例外。为了保持竞争力，企业会持续演进并重新定义自己；这些变化应该被当成设计过程的一等公民。

业务领域演进时，必须识别子域的变化，并让系统设计作出响应。过去的设计决策要持续与当前业务战略和子域状态对齐，必要时让设计演进到更适合当前需求的形态。

组织结构变化会影响团队沟通与合作，也会改变限界上下文的集成方式。学习业务领域是持续过程；随着新的领域知识出现，战略与战术设计都需要调整。

软件增长本身值得欢迎，但管理不当会对设计和架构造成灾难性影响。因此：

  • 子域功能扩展时，尝试识别更细粒度的子域边界，以支持更准确的设计决策。
  • 不要让限界上下文变成“什么都做”的模型，确保其中的模型始终聚焦于具体问题。
  • 让聚合边界尽可能小，用强一致数据这一启发式寻找可以提取到新聚合的业务逻辑。

最后，要持续检查各种边界是否出现增长驱动的复杂度。消除偶发复杂度，用领域驱动设计工具管理业务领域真正不可避免的本质复杂度。

可优化点

把架构决策写成带复查条件的假设

除了记录“为什么这样设计”，再写清楚“出现哪些信号就要重评”：规则增多、跨边界调用变密、团队归属改变、外部方案商品化、或强一致范围发生变化。
