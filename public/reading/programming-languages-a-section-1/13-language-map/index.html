我们已经在做什么：从阅读记录里得到一个答案

现在手里已经有了一组能配合工作的知识：用列表保存多天的页数，用递归逐项处理，用 option 表达可能没有答案，再用局部函数把内部步骤收好。最后一篇不急着增加新语法，先把这些东西放回同一件事里。

我们要完成的任务是：输入每天的阅读页数，返回其中最大的页数；没有任何记录时，明确返回 NONE。下面把第 10 篇的局部最大值写法放进名为 best_day 的函数里，这个名字在这里表示“某天最多读了多少页”，不返回那一天的编号。

这里没有换算法：外层先处理有没有记录，内部仍是“询问尾部的最大值，再与当前头部比较”。从末尾往回看，[25] 的最大值是 25，[20,25] 的最大值也是 25，再往前加上 0、15、10、18、12，最大值都仍然是 25；外层最后把它包成 SOME 25。

若输入 []，入口直接返回 NONE，内部函数不会被调用；若输入 [0]，得到的是 SOME 0，不会与没有记录混淆。整段计算也没有修改原来的 week。

我们已经可以说明它为什么这样执行了。Dan 在第一节最后提出的更大问题是：学会一门语言时，究竟还需要理解哪些不同方面？接下来就用这同一段程序，逐个看清它们各自在帮什么忙。

第一方面：语法，让程序能被正确写出来

先看一行已经熟悉的代码：

val 开始一个绑定，answer 是新名字，= 右边是要计算的表达式；best_day week 又按照 SML 的函数调用写法，把 week 交给函数。这里回答的是“这些字符怎样组织成合法的程序”，这就是语法（syntax）。

同样，函数声明里的 fun，条件里的 if … then … else …，以及局部表达式里的 let … in … end，都有各自的写法。少一个 end，工具就可能无法确定结构在哪里结束；把 SML 的调用照搬成另一种语言的习惯写法，也不能只凭意思相近就通过。

语法提供了表达想法的形式，但它本身还没有回答“这段程序为什么得到 25”。就像认出了一个句子的词和标点，接下来还需要理解句子在说什么。

第二方面：语义，说明写出来的程序怎样工作

仍看 best_day week。它接收的参数是 int list，返回的是 int option；类型检查会检查各部分是否能按这些类型接起来。执行时又必须先判断 null pages，再决定是返回 NONE，还是进入非空列表的计算。

这些关于程序含义的规则，就是语义（semantics）。在本节里，我们尤其反复使用两部分：类型规则说明哪些组合成立，求值规则说明一次计算怎样走向结果。

例如，best_nonempty 里面会读取 hd xs、tl xs。它能这样使用，靠的是外层已经确认第一次传入的列表非空；只有还存在尾部元素时，才继续递归。因此，遇到空输入时不是“函数进去后碰巧没出错”，而是在入口就选择了另一条路径。

val bestRest = best_nonempty (tl xs) 也有明确含义：先算出尾部结果，再让这个名字在当前局部范围内表示它。每次递归都有自己的参数和局部绑定，不能把各次调用中的 xs 想成同一个不断被修改的变量。

这时还能分清应用含义与类型条件。阅读页数通常非负，但 int list 没有写入这一要求；这段求最大值的函数对 [~8,~3] 也会得到 SOME ~3。类型告诉我们数据是什么形状，阅读业务还会给数据附加自己的约定。

第三方面：惯用法，帮助我们决定该怎样安排代码

能在 let 中声明函数，是语言允许的事情。把只服务 best_day 的 best_nonempty 放进去，则是在利用这一能力解决一个具体问题：外部只走能处理空列表的入口，不直接调用要求非空输入的内部步骤。

这种“遇到一类问题，通常怎样组合已有构造”的写法，叫作惯用法（idioms）。它不是再增加一条语法，而是在选择怎样把合法构造安排得更合适。

这里还有第 9 篇已经见过的选择：把尾部最大值保存到 bestRest，比较和返回时都使用它，避免重复执行同一个递归调用。语言也允许我们把递归调用反复写出来，但那个版本可能做大量重复工作。

所以，理解一段代码既要知道“这样写会执行什么”，也要知道“为什么作者选择这样安排”。把辅助函数限制在局部、保存要反复使用的中间结果，就是本节已经用过的两个具体答案。

第四方面：库，给程序提供已经做好的能力

best_day 是我们用 fun 定义的函数，null、hd、tl 则是已经可以使用的列表操作。我们不必先写出检查空列表和取得头尾的实现，才能开始处理阅读记录；这些现成功能属于语言环境提供的库能力。

**库（libraries）**提供能够调用和组合的功能。了解它们时，同样需要读清输入、输出和适用条件，例如 hd 接收列表，返回头部，但对空列表会失败；“这是现成函数”不会让这些条件消失。

原课还区分了两类库功能。文件读写需要实现或运行环境提供接触文件系统的入口，不能只靠整数加法与递归凭空完成；如果以后要把阅读记录保存到磁盘，就需要这样的能力。树、哈希表、列表等数据结构，则可以在具备足够语言构造后自行实现，也可以直接采用现成库。

目前我们使用已经提供的列表，后续会学到足够的构造，理解类似结构怎样定义出来。这里先分清的是：程序能够表达什么，与某个现成功能是否已经由库提供，是两个有关联但不同的问题。

第五方面：工具，让我们更方便地写和观察程序

把上面的函数定义交给 REPL 后，我们就可以输入一次调用，看看这次计算得到什么。例如，输入 best_day [12,18,10,15,0,20,25];，它显示 SOME 25；换成 best_day [];，它显示 NONE。这就是前面一直使用的小窗口在帮助我们做的事。

REPL 属于工具（tools）：它读取输入、组织执行，并把结果与错误显示给人看。编辑器帮助编写和查看代码，格式化工具帮助统一排版，调试器帮助观察程序运行，也都在这一层发挥作用。

这几样工具不是 SML 语义本身。同一种语言可以由不同实现提供不同的 REPL、提示文字和调试体验；“这个实现提供了好用的 REPL”，与“这门语言的条件表达式怎样求值”，需要分别理解。

因此，找不到还没装入当前 REPL 的函数定义，是当前工具里已经有哪些绑定的问题；函数接收什么类型、调用后选择哪个分支，则是另外一层规则。把问题放回合适的一层，往往比把所有现象都归结为“语言很奇怪”更容易继续读下去。

五方面合在一起，才是这段小程序

现在再看同一个 best_day，五个方面就都有了具体落点：

读这段程序时遇到的问题 所在方面 它帮我们弄清什么
为什么用 fun、then、end 这样组织 语法 怎样写成合法结构
为什么空输入得 NONE、本周记录得 SOME 25 语义 类型怎样匹配，计算怎样执行
为什么把辅助函数放在内部、保存 bestRest 惯用法 怎样安排代码更清楚、避免重复工作
null、hd、tl 从哪里来，使用条件是什么 库 能直接使用哪些已有功能
在哪里输入定义、运行调用、查看错误 工具 怎样编写和观察程序

实际写程序需要五方面互相配合。它们也不能互相代替：换一个编辑器不会改变 hd [] 的含义，背熟关键字也不会自动说明一次递归为何结束；反过来，清楚求值规则，也仍要知道具体调用的是哪个库函数。

这门课为什么把时间多花在语义与惯用法上

Dan 特别希望训练的是中间这两方面：准确理解语言构造的规则，以及认出问题后选择合适的写法。语法当然要学，但围绕某个符号好不好看、花括号是否更顺眼的个人偏好，不是这门课的重点。

他用历史课作类比：知道美国内战在 1865 年结束是必要的基础事实，但理解历史还需要用事实分析更大的问题。记住语法也类似，它让我们能够开始表达和分析，而不是整个学习过程的终点。

库和工具同样重要，只是新库、新工具会不断出现。理解函数怎样工作、接收什么输入、怎样失败、通常如何组合的能力，也会帮助我们学习它们；课程希望优先建立这种可以迁移的分析方式。

这也解释了为什么我们一路只处理阅读量、列表拼接和最大值，而没有立刻做成完整应用。小例子让需要观察的过程都能摆在眼前；若同时加入界面、文件和网络的许多步骤，语言规则反而容易被挡住。

不能据此判断课程使用的语言只能完成这些小计算。原课举出 Ruby 可用于 Web、Racket 可用于桌面软件；用 Java、Python 或 JavaScript 教同样的思想，也仍然可以从这些小例子开始。这里选择它们，是为了把语义与惯用法看得更清楚。

从最初的 val 到现在，主线其实一直没有变：一份阅读记录怎样成为值，名字怎样引用它，函数怎样计算新结果，又怎样把没有答案的情况交还给调用者。之后遇到新写法时，可以先看它正在改善这条过程里的哪一部分。

接着读：数据形状与模式匹配

如果前面的基础已经清楚，下一组会继续回答：一份数据可以有几种形状，程序怎样沿这些形状拆开它，又怎样知道处理过程符合类型规则。后半段再用异常与尾递归，观察计算怎样离开正常路径，以及递归留下的工作占用了什么空间。
