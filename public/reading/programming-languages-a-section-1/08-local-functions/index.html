一周读完多少页，还差多少页

上一篇，我们已经能用 sum_list 把每天的阅读页数加起来。现在想再往前走一步：给定一周记录和本周目标，同时返回“已经读完的页数”和“还差的页数”。例如记录是 [12,18,10,15,0,20,25]，目标是 120 页，总共读了 100 页，还差 20 页，答案应该是元组 (100,20)。如果已经达到目标，“还差的页数”就记作 0。

先在纸上安排计算：算出总页数，给它起名叫 total；再利用 total 算出差额，叫作 remaining；最后把这两个数放进元组。我们不希望每增加一份阅读记录，就在文件外面另起一组名字。这两个中间名字只需要在生成这份进度的计算中使用。

SML 可以用 let 把中间名字写在需要它们的计算里面。下面沿用上一篇的 sum_list，并把它一并列出，便于从这一篇开始运行。reading_progress 接收“页数列表、目标”这一对输入，返回“总页数、剩余页数”这一对结果。

这次调用先让参数 pages 表示这一周的列表，target 表示 120。进入 let 后，第一行计算并记住 total=100；第二行已经可以使用 total，于是得到 remaining=20。到 in 后面，(total,remaining) 得到 (100,20)，这就是整个 let 的值，也是这次函数调用的结果。

total 和 remaining 是局部名字：它们只在这一段计算中可见，外面的代码通过 week_progress 取得最终答案。下一次调用 reading_progress ([30,40],60)，会为那次调用重新算出 70 和 0，得到 (70,0)，不会把上一次调用的中间名字改掉。

再看懂 let 的写法

let 与 in 之间放 val、fun 这样的定义；in 与 end 之间放要得到结果的表达式。这里的“绑定”就是把一个名字与一个值或函数关联起来，和我们前面使用的 val、fun 是同一件事，只是现在名字的可见范围缩小了。

整个 let 是表达式，它会产生一个值。 在阅读进度例子中，主体是元组，所以 let 的类型是 int * int；若主体只写 total，它的值就只是 100，类型也变成 int。不需要额外写 return，也不是把最后定义的那个名字自动交出去。

用原课的短例子，逐行确认顺序

阅读进度的例子说明了用途。原课接着用一个叫 silly1 的小函数，把注意力集中在求值顺序上；名字意为“故意简单、没什么实际用途”。下面采用视频及幻灯片中的版本，它接收整数 z，经过两个中间数算出一个整数。

调用时已有 z=2。第一条定义发现 2>0，得到 x=2；第二条可以使用刚得到的 x 和原有的 z，得到 y=2+2+9=13。最后判断 2>13 为假，选择 y*y，得到 169。

后面的定义可以使用前面的名字，前面的定义却不能使用尚未出现的局部名字。类型检查也按这条顺序了解名字：参数 z 是 int，继而知道 x、y 都是 int；主体的两条分支都是 int，所以整个 let 返回 int。定义 silly1 时会检查函数体是否合理，但这些具体整数要等实际调用时才计算。

局部同名定义，不会改掉外面的值

第三篇已经讲过：后出现的同名定义，会让我们在它的可见范围里使用新的值。这件事也可以发生在 let 里面。下面的目的只是看清内外两个 x：外层已有 x=10，最终得到 doubled=22，而外面的 x 仍然是 10。

计算局部 val x = x+1 的右边时，新 x 还没有建立，因此先用外面的 10，得到 11。从这条定义后面开始，局部的 x 才表示 11，下一行得到 y=22。这叫同名名字的“遮蔽”，不是把外面的 10 改成 11。

普通 val 也没有因此变成递归定义。我们此前能在 sum_list 的函数体中写 sum_list，来自 fun 允许函数递归调用自己的规则，不能把它套到普通的 val 上。

一个 let 结束后，它的局部名字就不再影响旁边

既然 let 会产生值，就可以放在加号两侧。原课的 silly2 没有实际业务目的，是用来确认“一个局部定义影响到哪里”的例子。它接收 () 这个不携带信息的值，调用写成 silly2 ()。

先看左边的内层 let：自己的 x=2，所以 x+1=3。这个 let 到 end 就结束了，它没有把外面的 x=1 改掉。右边没有定义另一个 x，所以 y=x+2=3，再算 y+1=4；两边相加得到 7。

这里的 () 叫作 unit 值，用在不需要提供有意义输入的调用中。它不是要求函数在定义时立即执行。这个例子也不是建议把日常代码刻意写成多层嵌套，而是展示：let 能放在任何需要表达式的地方，例如算术表达式、函数实参或 if 分支中。

还可以把一整个辅助函数放进去

回到阅读记录。假如我们想显示“第 1 天、第 2 天、……、第 7 天”，先需要产生天数列表 [1,2,3,4,5,6,7]。我们把这个任务叫作 countup_from1 x：输入最后一天的编号，输出从 1 到该编号的列表。这里先约定 x 至少是 1。

不变的终点，为什么还要每次传入

调用 countup_from1 3 时，刚才的辅助函数依次收到 (1,3)、(2,3)、(3,3)。变化的是起点，终点始终是 3。而 count 定义的位置本来就能看见外层参数 x=3，所以可以直接用 x，不必再传一份 to。

下面仍然接收最后一天的编号并返回编号列表，只让辅助函数接收会变化的 from。注意：参数定义、第一次调用和递归调用，这三个位置都一起去掉了 to。

这次依次计算 count 1、count 2、count 3，每一步都与外层的 x=3 比较。结果仍从 [3] 向外组成 [2,3]、[1,2,3]。再调用 countup_from1_better 5，那次调用中的局部函数就会使用那次的 x=5。

这个局部函数使用的 x，来自它定义的位置能看见的名字。它不会跑到其他调用者那里临时寻找一个同名 x。后续课程会用“闭包”解释函数如何保留这些信息；眼下先抓住具体关系：外层提供终点，内层每次只推进起点。

把名字放在真正需要它的范围

局部函数的好处，在这个例子里很具体：外面只需要知道“给最后一天编号，得到整段编号”，不需要同时了解内部的 from 怎样推进。以后调整这段辅助过程，也能直接看出它只在这里使用。如果另一个任务确实要共用 count，再把它放到双方都能看到的地方。

原例子还有一个必须保留的条件：从 1 开始，只在等于 x 时停，因此 x=1 得到 [1]，x=0 却不会得到 []，而会继续递增，远离目标。如果希望所有 x<1 都返回 []，需要明确增加这样的判断；这是扩展后的约定，不是原函数已有的行为。

补充：为什么视频重新启动解释器

若先运行过顶层 count 的版本，后来再定义局部版本，原来那个顶层 count 仍然存在。局部同名定义不会删除解释器以前保存的定义。因此原视频重新启动 REPL，再只加载局部版本，才能清楚地看到外面不再有可直接调用的 count。这与第二篇“解释器记着已经执行的定义”是同一件事。

这一篇主要把名字放在了合适的位置。下一篇还会看到一个更直接的收益：用 let 记住已经算出的答案，避免同一段递归反复重算。
