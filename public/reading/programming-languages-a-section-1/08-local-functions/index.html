把一段计算需要的名字，留在它自己的范围里

到目前为止，我们主要在文件顶层写 val、fun 绑定。但一个函数经常需要只服务于自己的中间结果和辅助函数。把这些名字全部放到顶层，会让外部代码看到许多并不应该使用的细节。

let 给出的解决方式很统一：在一个表达式内部建立局部绑定，再用这些绑定算出这个表达式的结果。它的基本结构是：

let 与 in 之间是绑定，可以写 val，也可以写 fun；in 与 end 之间是表达式。整个 let 仍然是一个表达式，类型和结果都由最后这个主体表达式决定。它不是必须配合 return 才有结果的语句块。

类型检查也沿相同顺序进行，只是环境里记录的是类型。先有 z:int，再确定 x:int、y:int；主体的条件是 bool，两条分支都是 int，因此主体、整个 let、这次函数调用的结果类型都是 int。定义一个函数时，检查函数体，不等于立即执行函数体；这些中间值是在实际调用时计算的。

这里的作用域是有方向的：后面的绑定可以用前面的名字，前面的绑定不能反过来用尚未出现的名字。局部名字还可以用于 let 的主体，但不能直接在这个 let 外部使用。

作用域也不是运行期间沿着调用栈临时猜测名字的含义。稍后看到局部函数读取外层参数时，仍然是它定义位置能够看到的绑定。再次调用外层函数，会建立另一份对应那次实参的环境，不会偷偷修改上一次调用使用的参数。

不变化的终点，可以从定义环境直接取得

再仔细看刚才的递归：调用 countup_from1 3 时，count 的 to 一直是 3。递归只改变 from，却每次都重复传入相同终点。而 count 定义的位置本来就能看到外层参数 x。

这次调用里的辅助函数使用 x=3。count 1 发现 1 不等于 3，递归求 count 2；后者再求 count 3，取得 [3]；向外依次组成 [2,3]、[1,2,3]。from 是每次递归调用自己的参数，而 x 来自定义这个辅助函数时已经存在的外层环境。

删掉 to 时，定义、初次调用、递归调用都要一起修改。否则容易出现形参数量与调用结构不一致。这个改进主要是让接口不再携带冗余信息，不应简单宣传成“嵌套函数总比全局函数快”。

这也接上了函数求值的关键规则：实参在调用处求值；函数体里其他名字的含义，由函数定义处的环境决定。后续“闭包”单元会正式深入它，现在可以先理解为：局部函数没有忘记定义时可见的外层绑定。

私有与复用，需要一起考虑

如果辅助函数不太可能独立使用、容易被外部错误调用，或以后很可能修改，限制它的作用域通常会让维护更简单：你能直接看到有哪些使用者。反过来，若许多地方确实需要同一个功能，就要把它放在足够大的范围里，才能复用。

因此，“放得越里面越好”不是这节课的结论。更准确的做法是：让名字只出现在需要它的范围，同时保留有价值的复用机会。离开作用域意味着外部代码不能直接使用这个名字，也不能据此断言所有相关值都会立刻被销毁；函数保留外层环境的具体机制会在后续课程展开。

补充边界：原例子要求 x 至少是 1

原课版本从 1 开始，只在等于 x 时停止。所以 x=1 得到 [1]，但 x=0 不会自然得到 []，而是让 from 继续增加、远离目标。若希望所有不大于 0 的输入返回空列表，需要另外加入 if x < 1 then [] else ...，这是扩展后的输入约定，不是原代码已经具有的行为。
