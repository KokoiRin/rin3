一周的页数已经列出来了，怎样算出总页数？

上一篇把每天的阅读页数保存成列表。现在输入 [12,18,10,15,0,20,25]，我们希望函数交回整数 100，再根据它判断是否达到一周 100 页的目标。函数还应该能处理只记了三天、记了很多天，或者完全没有记录的情况。

我们已经有两个必要能力：函数可以递归调用自身，列表可以拆成头部和尾部。前面学过的 pow 通过减小指数接近结束；这一次，我们可以每次去掉一天，让递归处理更短的列表。

先把当前这一天和剩下的记录分开

对于一份非空记录，总页数等于“第一天的页数，加上剩余所有天的总页数”。第一天可以用 hd 读取，余下的列表可以用 tl 取得。如果已经没有记录，合计就是零。

xs 只是输入列表的名字，末尾的 s 是“一些 x”的命名习惯，没有特殊语法作用。if null xs 先检查记录是否为空；空的情况返回 0。只有进入非空分支，才会读取 hd xs、tl xs，所以不会直接对空列表取头尾。

sum_list (tl xs) 负责的任务与原问题相同，只是少了一天。当前这层保留第一天的页数，等递归交回其余天的合计，再相加。它没有把输入列表改短，也没有修改一个全局累计变量；每次调用拿到自己的输入，计算自己的结果。

注意第五天的 0：它仍是一项记录，所以 [0,20,25] 不是空列表。这一层正常读取页数 0，继续处理 [20,25]；真正停止递归的是最后的 []。

最后一次调用交回零以后，尚未完成的加法才能依次完成：先有 25+0，再加 20，再加前面的各天。原课用更短的 [3,4,5] 演示相同过程，结果是 12。

这也解释了两个容易遗漏的条件。第一，安全读取来自先判断为空，再在非空分支读头尾；若一开始判断 null (tl xs)，空输入在判断前就会因 tl [] 出错。第二，递归能够结束，是因为这里处理有限列表，每次递归的尾部都少一项；类型检查本身不会替我们证明这个事实。

空列表的和取零也不是随意放入的错误标记。没有记录就没有新增页数，而且加上零不会改变其他部分的合计。两个分支最终都给出整数，所以 sum_list 的类型是 int list -> int。

append：把工作日记录和周末记录接起来

现在我们手里可能有两份记录：一份保存五个工作日，一份保存两天周末。我们要得到完整一周，要求工作日在前、周末在后，各自内部顺序保持不变。上一篇的 :: 只能往前放一个元素，这里需要把整个第一份列表逐项接上去。

一天分两次读，列表里就可以放一对页数

我们再把记录细分：每天分别保存上午与晚上的页数。于是 [(3,4),(5,6)] 表示第一天上午三页、晚上四页，第二天上午五页、晚上六页。现在输入的类型是 (int * int) list，列表中的一个元素是一对整数。

最后递归到 [] 时仍然返回零。我们没有改变“空列表或非空列表”的处理方式，只是在处理头部时，多进入了一层元组。先确定外层，再进入元素，是两篇文章连接在一起的地方。

这些已有函数，还能怎样一起解决问题

现在 firsts 能整理上午列表，seconds 能整理晚间列表，sum_list 能给任意整数列表求和。把这三个能力接起来，就得到原课的另一个总和版本：

这次计算先分别得到 [3,5] 和 [4,6]，上午合计为 8，晚间合计为 10，最后得到 18。这叫函数组合：把一个任务拆成已有函数各自能够完成的部分，再连接结果。它没有新增语法，而是在复用我们刚刚写出的能力。

原视频还把数据扩展为 [(3,4),(5,6),(9,~3)]，得到 24。这里的负数用来观察一般整数算法，不再赋予它“实际阅读页数”的含义；SML 中负三写作 ~3。

两个版本都能处理这些例子，但成本并不完全相同：直接版本沿原列表走一遍；组合版本先构造两份中间列表，又分别求和。它们的工作量都随记录数量线性增长，但不能仅凭代码长短判断哪一个做的计算更少。firsts 与 seconds 的重复部分，还会在后续学习中得到更一般的组织方式。

补充边界：类型与整数范围仍然要分别考虑

sum_list 的递归调用之后还有加法要完成，countdown 与 append 也要等递归结果再构造列表；它们不是本课程后面要讲的尾递归。类型检查能检查调用与结果类型，却没有因此证明所有输入都能正常结束、所有极大整数都不溢出。

对本篇这些小数值例子，直接版本与组合版本的结果一致。如果讨论实现中有范围限制的整数，加法重新分组可能改变哪一步先溢出，因此不能把这个等价关系无条件推广到所有极端输入。阅读这节时，先把“当前层做什么、递归替它完成什么、怎样接成最终结果”这一条过程跟清楚。
