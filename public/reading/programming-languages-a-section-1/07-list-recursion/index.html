先回答空列表，再处理“头部加尾部”

认识列表之后，这一节不需要新增语言构造。我们要做的是把列表的结构与递归函数接起来：列表要么为空，要么由一个头部和一个更短的尾部组成。函数的两个分支，也可以顺着这个结构安排。

原课先写求和。参数名 xs 只是命名习惯，表示“一些 x”；末尾的 s 不是 SML 的特殊语法。

空列表的和定义为 0。它不是为了凑一个整数而随便选的错误标记；0 是加法的中性结果，也让递归自然结束。非空时，整个列表的和等于头部加上尾部的和。

sum_list 的类型是 int list -> int。条件的类型是 bool；then 分支的 0 是 int；else 分支也是整数加法，结果仍是 int。只有进入非空分支，才会执行 hd、tl，所以不会对空列表直接取头尾。

先确认判断本身不会读取空列表

这里安全的不只是“代码里面有 null”。关键在于，对 hd、tl 的读取出现在已经确认非空的分支里。若把判断改成 if null (tl xs) then ... else ...，程序在判断之前就得先计算 tl xs；当 xs=[] 时，它还来不及选择分支，便已经引发异常。后面的最大值函数会再次用到这个先后关系。

再区分两个层面：检查递归函数的类型时，类型检查器允许在函数体内使用这个函数自己的类型，然后检查实参与返回结果能否一致。它不会因为看到递归，就自动证明参数正在变小。sum_list 能结束，是因为我们另外分析了有限列表以及每次取尾部的行为；countdown 则还需要检查整数的输入范围。

append：先解决剩下的，再把头部接回去

现在把两个列表连接起来。目标是让第一个列表的元素在前，第二个列表的元素在后；两者内部原有的顺序都保留。

先看空情况：若 xs 已经为空，没有任何东西要放到 ys 前面，答案就是 ys，并不是 []。若 xs 非空，最终结果一定以 hd xs 开头；后面应当是“把 tl xs 接到 ys 前面”的结果，这恰好又是 append 能解决的问题。

递归过程中，变短的是第一个列表，第二个列表保持原样。每次递归去掉一个头部，因此有限的 xs 最终会到达空列表。返回时再把去掉的头部依次放回结果前面，顺序就保住了。

这个函数的类型是 int list * int list -> int list。它没有修改 xs 或 ys。在通常的链表实现中，结果新建第一个列表对应的前缀，并把第二个列表作为共享尾部；不需要把第二个列表重新遍历一遍。共享的安全性将在不可变数据一篇解释。

这里也能看清递归为什么成立：不是只要函数调用自己就算解决了问题，而是每次调用都处理一个严格更小的结构，同时保留足够信息来组成最终结果。

补充：相同思路，也要观察成本与输入边界

组合版本会构造两份中间列表，并多次遍历数据；直接版本只需沿原列表走一遍。两者在通常的链表模型下都是线性增长，但常数与分配量不同。“代码更短”和“计算更少”不能直接画等号。

另外，SML 实现的普通 int 可能有范围限制。上述小整数例子不会受影响；若涉及极大数，整数加法的重新分组还可能改变哪一步先溢出，因此不能不带条件地把两段程序宣称为对所有输入都完全等价。
