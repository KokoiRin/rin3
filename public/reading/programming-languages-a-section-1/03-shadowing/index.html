同一个名字再次出现，究竟发生了什么

前面我们说，ML 的绑定不是“把某个旧变量的内容改掉”。但如果程序里连续写了两个同名的 val，后面读到的数字确实可能不同，这该怎样解释？

课程给这个现象起了一个名字：遮蔽，shadowing。后来的绑定让同一个名字在后续环境中对应一个新结果。关键是“后续环境”：它没有回头修改以前的环境，也没有重新计算已经完成的绑定。

这一节没有新增语法。我们只是继续使用 val、表达式和环境，看看原来的规则能不能准确解释这种情况。老师还提醒，同一个文件里反复使用同名顶层绑定通常不是好风格；这里故意这样做，是为了把规则看清。

val a = a + 1，先用哪个 a

第六行最容易触发旧经验：它看起来很像“自增”。但按照绑定的规则，应该先在当前环境中求右边，再建立新绑定。

到这一行前，当前 a 为 5。因此先计算 a + 1 得到 6，然后让后面的环境拥有新绑定 a → 6。右边的 a 使用的是之前已经存在的绑定，不是一个正在被自己定义的新名字。

为什么 b 不变，要分清两个理由

原课特别把两个理由分开讲。第一个是立即求值：val b = a 被处理时，就把当时的 a 查出来并绑定给 b。之后不再保留“每次读 b 都重新读取 a”的规则。

第二个是绑定不可变：后来 val a = 2 建立另一个绑定，而不是去修改先前 a → 1 这一事实。两个理由叠在一起，就得到最小例子：

最后 result 为 1 : int，后面直接求 a 则得到 2。不要只背“遮蔽以后 b 不变”这个答案；要能说清：b 已经得到值，而新 a 也没有改写旧绑定。

如果把我们的一周阅读页数例子放进来，就像“周一录入了十二页，先算好并保存周一与周二的合计；后来又建立了一个同名的新记录”，先前已经算出的合计不会自动更新。若想算新的合计，需要再写一次对应的计算。

这也让我们理解“声明顺序”不是排版偏好。它决定每条表达式能看见哪些名字。后面定义普通函数时，函数同样可以使用更早的绑定，以及自己的递归名字；不能随意使用之后才出现的普通定义。

REPL 的 hidden value，不是原来的值被改坏了

有些 SML/NJ 的加载结果会把前面已经被遮蔽的同名绑定打印成 <hidden-value>，而不是把它的旧数字完整列出来。这是工具输出方式：它在提醒你，当前环境里直接用这个名字时，看到的是后面的绑定。

它不表示绑定还没求值，也不表示 ML 把数字删掉了。我们理解程序的依据始终是绑定所在位置的环境，而不是 REPL 选择怎样压缩打印历史。

同理，再次 use 同一个文件会增加更多绑定、形成更多遮蔽。旧名字可能残留，或者碰巧被新名字盖住，使一个错误依赖看起来没问题。修改文件后用干净会话重试，检查的是“这个文件本身能否建立它需要的环境”，而不是“它能否借用我刚才留下的状态”。
