为什么同一段递归会突然慢得无法使用

前面用 let 给中间结果取名字，主要是为了看清代码。现在看它更实际的作用：保证一项昂贵的计算只做一次。这一次改动甚至能把指数级的工作量降到线性级，差别远远超过换一台更快的电脑。

沿用列表例子：一周每天读了多少页，现在想找出单日阅读页数的最大值。对一个非空列表，我们可以先求出尾部的最大值，再与第一个数比较。递归的思路完全正确，但把它写成代码时仍然可能出问题。

先看一个答案正确、工作重复的版本

下面是原课 bad_max 的结构。空列表暂时返回 0，这个接口问题留到下一篇处理；先只比较非空列表的计算量。

只有一个元素时，它就是最大值。至少两个元素时，先计算尾部最大值，判断头部是否更大。如果头部更大，就返回头部；否则，在 else 中再次计算尾部最大值。

问题就在最后一句。“这段代码刚才算过”不等于“语言会自动保存它的结果”。每次执行 bad_max (tl xs) 都是一次新的函数调用，它内部也可能继续重复计算。

输入顺序为什么会掩盖这个问题

若输入是严格递减的 [3,2,1]，每一层的头部都比尾部最大值大。比较完成后走 then，不会触发第二次递归，整条调用链只有三次调用。

若输入是严格递增的 [1,2,3]，每一层都走 else，于是每个非末端调用都产生两次递归。全部相等的列表也会走 else，因为代码比较的是 >，而不是 >=。因此，只拿一种顺序做小规模测试，很容易误判这段函数的性能。

这也不限于整段递增：如果唯一的最大值排在很后面，前面的许多层同样会反复计算尾部。随机打乱顺序不能修好这个算法，必须消除重复计算。

用 C(n) 表示处理长度为 n 的严格递增非空列表时，包含最初调用在内的调用总数：

列表长度 递减输入的调用数 递增输入的调用数
3 3 7
10 10 1,023
30 30 1,073,741,823
50 50 1,125,899,906,842,623

原课用一个假设帮助建立量感：假定每次调用中除递归以外的工作只花 10^-7 秒，长度 50 的递增输入仍需约 3.57 年，长度 55 则超过一世纪。这是基于计算量的示意估算，不是任何一台机器的实测成绩。

null、hd 和 tl 在这里都只做常数级工作。特别是 tl 不会复制整段尾部，所以真正应该关注的是递归结果有没有被重复求出。

用 let 保存已经得到的答案

把尾部最大值先绑定到 tailMax：

执行 val tailMax = ... 时，右侧完成一次计算，绑定的是得到的整数值。之后两次出现 tailMax 都是查询这个值，不会重新执行右侧函数。

现在无论列表递增、递减还是混合排列，每个非空后缀只计算一次。长度为 n 的非空列表产生 n 次调用，时间为 O(n)。这段写法还会保留等待递归结果的调用栈，空间为 O(n)；本节尚未讲尾递归，不需要提前把它改造成另一套算法。

也可以再把 hd xs 绑定到一个局部名字，让代码更好读。不过，保存一个常数时间操作，与避免整棵递归树的重复，收益量级不同。先识别最昂贵的重复工作，再考虑小的整理。

原视频演示中还有一个值得保留的排查细节：Dan 一次把 countdown 的上下界传反，程序迟迟不返回。原因是生成测试列表的辅助函数一直递减，无法到达终点，good_max 实际还没被调用。函数实参先求值，因此遇到卡住的程序，要分清是准备输入时卡住，还是目标函数内部卡住；在原课 Emacs 交互环境里可用 C-c C-c 中断。不要把所有停顿都归因于递归求最大值。

下一篇还要修正 good_max [] = 0：空列表没有最大值，而 0 又是一个合法的最大值，调用者不能靠这个数字分辨两种情况。至此我们已经遇到了两个独立问题：算法的代价，以及接口怎样诚实地表达结果。
