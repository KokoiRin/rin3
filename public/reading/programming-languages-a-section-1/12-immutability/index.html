为什么“不能修改”反而能让代码更好写

到这里，我们已经知道怎样构造列表和元组、怎样取出它们的部分、怎样写函数计算新结果。现在停下来关注一件没有出现的事：修改已经构造好的列表或元组。

第一节使用的 SML 值绑定、列表和元组都是不可变的。一个名字绑定到某个值后，这个绑定不会被赋值改变；重新使用同名 val 是建立新绑定并遮蔽旧绑定。列表也没有“把第三个元素原地改掉”的操作。需要不同内容时，就构造一个新的值。

这不意味着完整的 SML 没有任何可变设施；后续课程还会学习引用等机制。此处的结论限定在我们正在使用的不可变数据上。

先认识别名：两个名字可能指向同一份数据

假设 x 和 y 都能访问同一个复合对象，我们称它们形成别名（aliasing）。如果对象可修改，通过 x 改它，随后从 y 读取也会看到变化。这时“内容相同”与“其实是同一个对象”会直接影响程序行为。

若它不可修改，情况就轻松很多：两个名字指向同一份 (3,4)，或者各自指向一份内容相同的 (3,4)，都只会让程序读到 3 和 4。我们无需为了防止另一方改动它，先做一份副本。

不可变数据让安全共享成为可能。 这既减少需要追踪的变化来源，也为实现节省空间留下余地。

第一个版本更直接，也避免了源码中不必要的重新构造。实际编译器是否优化分配属于实现细节，不需要为此改变我们对结果的推理。

原课用一个假想操作说明差别：如果能把 x 的第一项从 3 改成 5，#1 y 究竟还是 3，还是也变为 5？那就取决于结果与输入是否共享对象。SML 这里的元组不允许这种修改，所以这个难题不会发生。

这种“无法区分”讨论的是本节纯数据的程序结果，不是在说两个实现的时间、内存占用也永远完全相同。后者正是实现可以优化的地方。

这张图表达的是列表节点的共享关系。first 自己没有被接上一段尾巴，也没有被修改；combined 的前缀是新构造的。

若列表节点允许修改，后来把共享部分的 3 改成 7，就可能同时改变 second 和 combined 的可见内容。因为本节列表的节点不可变，这种共享不会把一方的意外更新传播给另一方。

tl 同样利用共享：取尾部时，只要返回现成的尾部即可，不需要复制余下的全部节点。因此 tl 是常数时间。补充从这段代码推导的代价：拼接要遍历并重建第一个列表的前缀，时间与新节点数量都随第一个列表长度增长，不随第二个列表长度增长。

让“不可能发生的事”退出推理

“调用者答应不修改”是一条需要每个人遵守的约定；使用真正不可变的数据，则可以由语言或数据接口直接排除这种修改。少一种行为，意味着实现者、调用者和后续维护者都少追踪一种风险。

这并不是说所有程序都应禁止所有修改。原课的要点是理解取舍：可变数据需要仔细区分别名和副本，不可变数据则允许我们把更多注意力放在输入、输出和算法本身。前面学的绑定、列表构造、局部函数，正好一起形成了这种思考方式。
