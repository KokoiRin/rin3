一个结果不够时，先把数据组成一个整体

前面函数的例子大多只返回一个整数。但假如我们要计算 20 除以 3 的商和余数，就有两个结果需要一起交给调用者。SML 可以直接把它们组成一个二元组，也叫 pair：

这里不是先返回 6，再返回 2。整个 (6,2) 才是一个值，answer 绑定的是这个完整的值。类型 int * int 也描述了整体结构：第一部分是整数，第二部分也是整数。类型里的 * 表示组合，不是乘法。

元组首先解决的是“几个部分怎样属于同一份数据”。每个部分可以有不同类型，例如 (3,true) 的类型是 int * bool。但是，一旦这个结构确定，部分的数量、顺序和类型也就确定了；这正是它与后面列表的重要区别。

构造时算什么，读取时又算什么

学习一个新构造，仍然沿用原课的三个问题：怎样写、怎样检查类型、怎样求值。对于 (e1,e2)，类型检查分别确定两部分的类型，整体类型就是 t1 * t2。求值则先把两部分表达式算成值，再组成二元组。

(1+2,3<4) 是表达式，但还不是计算结束的值。(3,true) 才是一个二元组值：两个组成部分都已经没有计算要做了。因此，元组并不是把两段尚未执行的代码保存起来，等以后读取时再执行。

读取使用 #1 和 #2，编号从 1 开始：

#1 e 的含义是：先把 e 求成一个元组值，再取第一部分。它不是“只执行构造元组时写在第一个位置的代码”。例如 #1 (1+2, 8 div 0) 不会因为我们只需要第一部分，就跳过第二部分；构造元组本身需要求值两部分，第二部分会引发除零异常。

类型检查也会检查结构。对一个二元组写 #3 p 是类型错误，不是运行后才报告下标越界。这里的选择器编号也不是一个可以任意变化的列表索引；它与元组的固定结构相配合。

嵌套结构不能随意摊平

元组的各部分本身也可以是元组。这不需要新增一套语言规则，只需继续使用已经学过的构造和读取方式：

理解 #1 (#2 x1) 时，可以先沿结构走：#2 x1 到达里面的二元组，再由 #1 取得里面第一项。不要仅仅把所有叶子从左往右数一遍，因为结构本身也是类型的一部分。

值 整体结构 类型
(7,(true,9)) 外层两部分，第二部分又是二元组 int * (bool * int)
((7,true),9) 外层两部分，第一部分又是二元组 (int * bool) * int
(7,true,9) 外层直接有三部分 int * bool * int

三者保存的基本值相似，但不是同一份形状的数据。函数若要求其中一种，就不能直接传入另一种。较长的嵌套例子也按相同方法读，例如原课的 ((3,5),((4,8),(0,0)))：先确定外层两部分，再分别确定内部结构。

类型说明的不只是“里面有几个数”

看见 int * bool，我们已经知道能够安全读取两个位置，也知道每个位置取出的类型。这些信息不取决于当前存的是 3 还是 300。反过来，即使实际没有走到某条条件分支，类型检查仍然会检查那条分支。例如 if true then (1,true) else (2,3) 不能因为条件写着 true 就通过检查：两个候选结果的第二项类型不同，整体没有统一的元组类型。

原课暂时给元组参数明确标注类型，还有一个实际原因：只有 #1 这样的读取操作，通常不足以告诉类型检查器整个元组到底有多少部分。写成下面这样，输入形状就明确了：

另外，“元组可以任意嵌套”是说我们能够写出任意固定的结构，不是说一个已经确定类型的函数，可以根据运行时的整数参数，忽然返回二元组、三元组或四元组。接收结果的代码仍需事先知道结构。需要长度随输入变化的数据时，下一篇的列表才是合适工具。

这个函数没有把 pr 的第一格和第二格原地交换。输入数据保持不变，函数只是决定返回哪个值。直接返回已有值是否会造成共享，后面的“不可变”一篇会继续解释；此时先记住，构造结果与修改输入是两件事。

补充边界：括号不一定构造元组

(7) 只是给整数表达式加括号，仍然是 int，不是一元组。() 是 unit 类型的唯一值，可以理解为空元组。日常看到的二元组、三元组等，都要通过逗号表达相应的组成结构。
