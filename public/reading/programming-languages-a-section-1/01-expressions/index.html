先抓住一个过程：算出右边，再给结果一个名字

这一节开始学习 Standard ML，后面简称 ML。它和 Kotlin、Java 的写法不同，但我们先不急着把每个符号翻译成旧语言里的对应物。先建立一个小而准确的模型：程序由一串绑定组成；表达式负责计算；绑定把计算结果接到一个名字上。

读 val total = monday + tuesday 时，先看右边：找到两个名字对应的值，算出 30。然后建立一个新绑定，让 total 对应 30。此处的 = 是绑定语法的一部分；不要把它直接想成“修改一个已有变量”。后面关于遮蔽的讲解会进一步说明这个区别。

这里有两种不同的判断。类型检查关心“这个表达式有没有合法的类型”；求值关心“这个表达式运行后得到什么”。例如 monday + tuesday 的类型是 int，它的值是 30。int 告诉我们结果是整数，却没有告诉我们具体是哪一个整数。

为了把它们分清，可以分别画两张表。老师把第一张称为静态环境，保存当前能用的名字及其类型；第二张称为动态环境，保存名字及其值。

处理完的绑定 静态环境新增 动态环境新增
val monday = 12 monday : int monday → 12
val tuesday = 18 tuesday : int tuesday → 18
val total = monday + tuesday total : int total → 30

“环境”在这里不是操作系统的环境变量，也不是 Java 的 static 字段。它只是解释程序时用的名字对应表。读到一个名字，就到相应的表里查找。

处理 z 时，当前动态环境已经有 x → 34、y → 17。左边的子表达式 x + y 得到 51，右边的 y + 2 得到 19，再把两者相加得到 70。接着建立 z → 70，所以最后的 w 得到 71。

类型检查做相似的追踪，但不需要算这些答案。它知道 x、y 都是 int，两次整数加法的结果仍是 int，所以 z 和 w 都是 int。这种区别会一直保留：知道结果的类型，不等于已经求出了结果。

绑定有顺序。上面的 z 可以使用已经出现的 x、y；反过来，在全新环境中先写 val z = x + 1，再写 val x = 34，第一行不能凭借“下面迟早会定义 x”而通过。检查第一行时，静态环境里还没有这个名字。

表达式和值，不是同一个概念

34、x、x + 7 都是表达式，但只有某些表达式已经不需要继续计算。课程把这样的表达式叫作值。

写法 是表达式吗？ 已经是值吗？
34 是 是，求值仍得到自身
true 是 是，类型是 bool
x 是 不是；要查动态环境
8 + 9 是 不是；还要算成 17

因此，“所有值都是表达式，但并非所有表达式都是值”。这里判断的是表达式还需要做什么，不是它看起来长不长。后面看到函数、元组、列表时，也要继续问同一个问题。

表达式能够嵌套。例如加法的某一边还可以是条件表达式，条件分支里又可以有加法。解释大表达式的方法，就是沿着它的结构，解释里面的小表达式。

学一个新表达式，固定问三个问题

原课反复强调一套方法：先问语法怎么写，再问怎样检查类型，最后问怎样求值。语法说明写法；后两者说明它的含义，也就是本节使用的语义。

表达式 类型规则 求值规则
整数常量，如 34 类型为 int 得到自身
名字，如 x 在静态环境中查类型 在动态环境中查值
e1 + e2 本节整数例子中，两边都要有 int 类型，整体是 int 两边分别求值，再相加
e1 < e2 本节整数例子中，两边为 int，整体为 bool 比较两个整数，得到 true 或 false

表里的 e1、e2 是“某个表达式”的占位写法，不是要求你把这两个名字原样输入。后面会学到其他数值类型；这里先把整数版本的规则建立稳。

原例接下来计算 z 的绝对值：

第一行先计算 z < 0。因为 z 是 70，结果为 false，所以只求值 else 后的 z，最终得到 70。then 后的 0 - z 在这次运行中不会被求值。第二行使用已有函数 abs；一个实参的简单调用可以写成 abs z，也可以写成 abs(z)。

条件表达式的一般形式是 if e1 then e2 else e3。类型检查要求 e1 是 bool；e2、e3 可以是整数，也可以是别的类型，但必须相同。整个条件表达式的类型，就是这两个分支共同的类型。

虽然运行时一定会选择 then，类型规则仍然要检查两个分支。12 是 int，false 是 bool，不能给整个表达式一个符合规则的共同类型。“这条分支不会运行”不能成为违反类型规则的理由。

通过类型检查也不意味着程序一定正常结束。后面的课程会看到异常、不终止，以及算出了合法但不符合意图的答案。这一节先把类型与求值分开追踪；下一篇再实际观察这些错误怎样出现。
