REPL 是一个会保留上下文的工作台

上一节解释了绑定怎样增加名字。现在把这个过程放到工具中观察：ML 常用的交互环境叫作 REPL，即 Read、Eval、Print、Loop。它读入一段输入，检查并求值，打印结果，然后给你下一个提示符。

第一行表示 x 绑定到整数 34。第二行里的 it 是 REPL 给这次表达式结果使用的名字，不是你必须写进程序的变量。它告诉我们：x + 7 得到了 41，类型为 int。

REPL 之所以有用，正是因为它保留前面的环境。下一条输入还能使用 x，不用每次重新把整个程序写一遍。但这个方便，也带来了“我到底在什么环境里运行”的问题。

课程笔记还指出，use 自己的结果是 ()，类型是 unit。你可能在加载消息最后看到 val it = () : unit。这不是说文件“没算出结果”，更不是哪个业务变量变成了空值；这是这次 use 操作自身的返回结果。

在 REPL 中，分号用来表示“我这一段输入结束了”。忘记它时，工具可能只是继续等待，并不表示程序正在计算。在 .sml 文件里，顶层绑定末尾通常可以不写分号；但每个变量绑定开头的 val 不能因此省略。

测试写进文件，但重新验证时换一个干净会话

临时试试 x + 7 很合适。如果你已经在提示符里重复输入一整组测试，最好把它们保存成另一个文件：先加载实现，再加载测试。这样测试能复用，也知道自己究竟检查过什么。

修改实现后，老师建议退出并重新启动 REPL，再加载文件。视频中的 Emacs 环境用 C-d 结束会话，用 C-c C-s 启动，再按回车；这些是工具操作，其他编辑器可能不同。历史输入也可以通过 Emacs 的 M-p 调回。

为什么不直接再次 use？因为你上次加载的名字还在。假设第一次文件里有 val pages = 12，后来把这一行删了，却保留 val total = pages + 3；在旧会话中，残留的 pages 可能让代码看起来还能工作。全新会话才会暴露它依赖了一个已经不存在的定义。下一篇会从“遮蔽”的角度讲清这个机制。

报错先分层：写法、类型、求值、意图

原视频故意写了一份满是错误的程序，然后逐个修。这个过程比记住某条报错原文更重要：编译器只看到你实际写下的内容，不知道你原本想写什么。

层次 典型问题 先看什么
语法 缺了 else，用了关键字作名字 当前行以及之前几行是否写完整
类型 条件不是 bool，分支类型不同 每个子表达式各是什么类型
求值 整数除以零，或计算没有结束 实际传入了什么值、递归如何推进
意图 程序正常得到 0，其实想要 14 测试期望与实际结果是否一致

报错行号常常表示“工具读到这里终于没法继续”，不一定是错误真正开始的地方。出现一串报错时，先处理最前面的相关错误，再重新检查，通常比同时修改十处更稳。

算术符号也有自己的规则。ML 用 ~5 表示负五；- 是减法运算符，可以写 0 - 5，却不能照搬很多语言的一元负号写成 -5。整数除法写 div；/ 用于 real 除法，不能直接拿两个整数去用。

三者依次得到 ~5、~5、3，类型都是 int。符号看着熟悉，不代表新语言沿用了你熟悉的全部规则。
