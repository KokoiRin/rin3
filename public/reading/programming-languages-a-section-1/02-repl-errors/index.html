先把目的说清楚：让 ML 算出我们已经会手算的结果

第一篇里，我们在纸面上读懂了三行代码：周一读 12 页，周二读 18 页，合计 30 页。这一篇要做的事很具体：把这三行文字交给 ML 执行，看看它是否真的得到 30；如果没有，怎样判断哪里出了问题。

为此，要认识两个地方：一个是我们保存代码的文件，另一个是接收代码、显示结果的 ML 交互窗口。先跟着下面的过程读即可，不要求你现在安装软件。这里讲的是一次运行从哪里开始、结果从哪里出现。

ML 并不是等你写好一个完整应用才开始工作。它可以读入一段输入，检查并执行，显示结果，再等你输入下一段。这个反复进行的过程叫 REPL，是 Read、Eval、Print、Loop 的缩写。先记住它的作用就够了：一个可以随时试运行 ML 代码的工作台。

为什么又需要一个 .sml 文件

只试一两行时，直接输入很方便。但如果明天还想运行刚才的三行，或者要改一处再运行，反复在窗口里重打就不方便了。我们可以把代码保存下来。

“测试”先理解成：拿实际结果与预期对照

现在代码确实跑起来了，但“显示了一个数字”还不等于“计算正确”。我们原本希望两天合计 30 页，就应该核对 ML 是否真的显示 30。这样的核对就是测试最基本的意思。

为了让过程明确，可以写下两个问题：合计是不是 30？周二比周一多多少，是不是 6？把想观察的表达式放到另一个文件中，之后就可以反复执行，不必每次在窗口里重打。

所以，原课建议修改程序后重新启动 REPL，再依次加载程序文件和测试文件。use 会读入文件，不会先清空会话。下一篇会继续解释：反复出现同名绑定时，旧名字与新名字之间到底是什么关系。

代码没得到预期结果，先看卡在哪一步

刚才的例子缺了一个名字。原视频还故意写了几类错误，教我们区分“代码不能被接受”和“代码能运行，但算错了”。理解这些区别，报错就不只是一串陌生文字。

可以沿着 ML 处理代码的过程想：先看写法能不能组成合法代码，再看各部分类型能不能配合，然后执行计算，最后由我们判断答案是否符合原意。

卡住的位置 具体情况 我们先检查什么
写法 条件表达式缺了一部分 if、then、else 是否完整
类型 把整数当作真假条件 每一部分需要什么类型
执行 做到整数除以零 实际参与计算的值是什么
预期 正常得到 0，原本想算 14 代码是否表达了正确的计算

原视频中还会看到的工具细节

执行 use 后，有时会在页数结果之后看到 val it = () : unit。这是 use 这个操作自身的返回值：() 是 unit 类型的唯一值。它没有把 total 改为空，也不表示文件没有执行；我们需要的合计仍然看 total = 30 那一行。

原课用 Emacs 编辑器操作 REPL：C-d 表示按 Ctrl+D 结束会话，C-c C-s 是依次按 Ctrl+C、Ctrl+S 启动交互环境，M-p 用于调回历史输入。这些是当时工具中的操作，不是 ML 语法；换一种编辑器，操作方式可以不同。
