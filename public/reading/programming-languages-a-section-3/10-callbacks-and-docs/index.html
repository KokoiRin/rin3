先登记一段操作，事件到来时再调用

按钮点击、网络消息或轮到某个玩家行动时，负责事件的代码不应该预先知道所有业务。更灵活的方式是：使用者先交一个函数，等事件发生时，由库调用它。这种“交给别人以后再调用”的函数常叫回调。

本篇模拟按键。整数代表按键编号；回调类型是 int -> unit，接到编号后做一个动作，不返回需要收集的结果。我们手动调用 onEvent 模拟事件，不在这里连接真实键盘。

cbs 初始保存空列表。注册 f 时，把它接到现有列表前面，并替换引用内容；事件发生时，读取列表，依次用同一个按键编号调用每个函数。这里先展示库的实现，使用它的人主要调用 onKeyEvent 登记自己的操作。

相同回调类型，可以各自带着不同配置

第一个使用者只想统计事件总次数。第二个使用者只关心指定按键，希望命中时打印；每次登记都可能关心不同编号。

这时共有五个回调，但没有按键消息输出，!timesPressed 仍为零：登记不是执行。四个打印回调分别保存 4、11、23、4，计数回调则保存 timesPressed 那个引用。它们内部需要的数据不同，交给库的公开类型却都一样，库不必为各种配置设计不同参数表。

11 输出一行，79 不输出，4 输出两行，因为登记了两个关心它的回调；23 输出一行。四次事件后 event_count=4，包括无人打印的那次 79。这是闭包与共享状态的配合：每个回调保存自己的固定配置，有需要时也能保存共享引用。

由于注册接在列表头部，当前实现按最新登记的先执行。onEvent 开头的 !cbs 还取得了本次遍历要用的列表值；某个回调中若再登记新回调，新回调不会凭空插入已经保存的本次列表，而会影响后续事件。若一个回调抛异常又没人处理，后面的回调也不会自动继续。这些是这份具体实现的行为，真实事件库可能另有规定。

回调也不等于多线程。当前代码就是同步地一个个调用函数；真实库可能异步触发，但那需要再看它自己的执行约定。原课刻意省略注销回调等功能，让重点留在“函数和它的环境一起被登记”。

接口文档要回答的，比函数类型更多

你已经能够写出自己的 map，为什么还要查标准库？原课区分了两类价值：一类提供文件、输出等与外界交互的能力；另一类把大家都会用的操作统一成共同名字和参数约定，避免每份程序各造一版。

例如找列表操作，先查 List；字符串查 String，字符查 Char，同时处理两份列表查 ListPair。这些名字是库的组织单位，SML 叫 structure；文档里的 signature 描述它提供哪些类型与值，后面才会正式学习模块。

前三项得到 ["12","18"]、25 与 [#"M",#"L"]。最后一行只查函数值，REPL 显示其类型，可用来确认 List.map 是先接收函数、再接收列表。但类型不会告诉你 List.last [] 抛 Empty，也不能完整说明调用顺序或成本；这些仍要看文字文档。

原视频还展示 structure X = List;、signature X = LIST;，借 REPL 列出模块成员。它们可以作为查接口的快捷方式，不会替代完整说明。比起不断猜 fold、foldleft 是否存在，查到确切的 List.foldl、核对参数顺序与异常约定更可靠。
