记住配置，不代表配置相关的计算只做一次

我们已经知道筛选函数可以记住外面的 s。现在要从字符串列表中保留“比 s 更短”的项：输入 ["1","333","22","4444"] 与 "xxx"，结果应是 ["1","22"]。两种写法都能做到，但比较长度的准备工作发生在不同时间。

先把原课的两种纯计算版本并排写出：

第一版产生的判断闭包保存 s，每次执行函数体都重新出现一次 String.size s。第二版先算 limit=3，产生的判断闭包保存这个结果，每次只取出 3 比较。闭包保存绑定；它不会自动把函数体中用到外部名字的所有表达式提前计算好。

用打印把求值时机看出来

若只看最终列表，区别藏起来了。原课给那次计算加上打印：每执行一次就输出一个 !。这不是性能计时器，只是在显示“这里执行了几次”。

第一条调用输出 !!!!，第二条输出 !，两次得到相同列表。括号里的 e1; e2 先执行 e1 并丢弃它的返回值，再执行 e2，以 e2 的值作为整体结果；被丢掉的是打印的返回值 ()，不是打印这个动作。

可以逐项看第一版：检查 "1" 时算一次参照长度，检查 "333" 再算一次，检查 "22"、"4444" 各再算一次。第二版在进入筛选之前就算好 3，四次比较共享这个绑定。与参照字符串长度相等的 "333" 不满足严格 <，仍然被排除。

“一次”要说清是在哪个范围内

val limit = ... 在每次调用 counted2 时执行一次。再次用另一个列表调用 counted2，仍会重新计算；这不是跨调用的全局缓存，也不是把所有相同输入记下来以后永远复用。

同样，fn x => ... 创建函数值时不会执行函数体；List.filter 之后每检查一项，才执行一次这个函数体。我们因此要区分三个时刻：创建外层调用、创建闭包、以后调用闭包。把计算写在哪一层，就决定它通常在哪个时刻发生。

真实的 String.size 常能直接读取保存好的长度，不能据此宣称它一定逐字符遍历，或把这次改写夸成巨大的性能提升。原课想说明的是一般方法：若参照配置的处理确实昂贵，而每一项都用同一个处理结果，可以把它移到创建判断函数之前。

有副作用时，提前计算不一定是等价替换

空输入能暴露一个容易漏掉的区别。counted1 ([], "xxx") 不调用判断函数，因此打印零次；counted2 ([], "xxx") 先建立 limit，仍打印一次。下面两个结果都是空列表，但可观察动作不同。

如果那项准备工作可能抛异常、读取正在变化的状态，甚至不能结束，把它移到外层也可能改变程序行为。只有确认这些差异符合目标时，才能这样改。对本篇不带打印的纯长度比较，两版筛选结果相同；对一般程序，“结果值相同”还不足以涵盖所有行为。

这就是理解闭包之后能够做的实际判断：不是看到外部名字就猜“已经缓存”，而是找到函数体何时被调用、某个 val 右侧何时被求值，再数清这次调用究竟做了几遍工作。
