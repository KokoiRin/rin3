少调用一次，看起来相同的表达式还相同吗

Rational 的抽象接口让客户端看不见一部分内部变化。现在把问题推广到普通函数：维护代码时减少一次重复调用、换一下计算顺序，究竟需要什么条件，才能说任何允许的客户端都看不出差别？

先看一个完整反例。两个版本分别计算 f x + f x 与 2 * f x；传入的 next 每次会更新计数，并把新计数加到输入上。

得到的是 (first,firstCalls)=(17,2)，(second,secondCalls)=(16,1)。同一个输入也不保证多次调用同一个函数就能拿到同一个值。若 f 只是打印 hi 后返回输入，数值结果虽然相同，打印次数仍会从两次变一次。

本课把哪些行为算作可观察

等价不只是几个测试样例相同。给定等价实参，在任何允许使用它们的程序里，两份实现都要保持相同的可观察行为。

需要保持的项目 为什么只比较返回值不够
正常结果 可能给出不同答案
终止或不终止 一个有答案，另一个永远等不到
客户端可见的内存修改 调用结束后，其他代码还能读到差别
输入输出 打印内容、次数或顺序可能不同
抛出的异常 客户端可能匹配并处理不同失败

这里暂不把时间、空间开销当作等价的判据，下一篇会单独讨论。抽象类型能减少允许的输入与观察方式，无副作用的计算又减少需要追踪的行为，因此都能使等价论证更简单。它们提供的是明确条件，而不是“函数式代码大概比较安全”的印象。

调用顺序同样可能是行为的一部分

先算 g x 再算 h x，与反过来计算，即使最后都返回 (g的结果,h的结果)，也可能不同。若 g 写入一个引用、h 读取它，读到的值就会变化；若它们分别打印，输出顺序也会变化。

异常与终止条件不能漏掉。若 g 抛出异常A，h 抛出异常B，先执行哪个决定外层先看到哪个异常；若一个永不返回，另一个会抛出异常，交换后也可能从“永不返回”变成“立即失败”。对调两个计算，需要的条件强于“都没有打印”。

原课用 map f (map g xs) 与 map (f o g) xs 再次强调这点。前者先对所有元素做 g，再逐项做 f；后者每个元素先 g 后 f，交错前进。纯粹、正常结束的回调可以允许这种融合；有状态、输出、异常或不终止的回调则需要单独论证顺序变化是否可观察。

标准改写一：一致改名，避免变量被捕获

下面保留原课的核心例子。输入3，原函数与安全改名版都返回20；把参数改成已被使用的 y，却得到9。

一致替换局部绑定及其引用，本来不会改变含义。但新名字不能捕获原来指向外层的引用，也不能被内部已有绑定遮住。例如把 fun f x = let val y=3 in x+y end 的参数直接改成 y，内部两处 y 就都读到3，函数变成固定返回6。这是绑定关系改变，不是排版上的小调整。

标准改写二：提取辅助函数，要保留环境

辅助函数与直接写表达式通常能互相转换，但自由变量仍要指向原来的绑定。下面的两个版本故意不等价，输入1分别得到17与10。

helper 的闭包保留定义时的14，direct 则使用后来建立的7。提取代码并不只是复制相同字符串，还要保证那些名字仍然指向同一份环境。这也是编译器做内联、提取或替换时要保持的语义关系。

标准改写三：省略包装，要看被包装的是什么

如果 f 已经绑定到函数，fun g y = f y 与 val g=f 可以提供相同的调用行为。但把一般表达式 e 代进来，fun g y = e y 与 val g=e 就可能改变何时、执行几次 e。

两个结果都为6，但整个示例打印两行：一行来自建立 stored，另一行来自调用 delayed。若 h() 还可能抛出异常，失败时间也随之变化。第3篇为值限制增加函数包装时，同样需要记住它会把函数体里的计算推迟到调用时。

语法糖还必须保留短路顺序与类型条件

x andalso g x 可以展开为 if x then g x else false，其中只有 x=true 才调用 g。若改成 if g x then x else false，就无条件先调用了 g；短路、异常与不终止行为都可能改变。真正的语法糖按定义应当保留原来的求值规则。

最后还有一个 ML 特有的边界：忽略类型时，let val x=e1 in e2 end 与 (fn x => e2) e1 都先算 e1，再在相同扩展环境里算 e2。但 let 绑定可能泛化，普通函数参数不能按相同方式泛化。

letResult 是 (0,true)。对应的匿名函数应用则是单独的预期错误。

如果两种形式都通过类型检查，它们的这套求值过程相同；但不能据此把所有 ML 的 let 都机械改写成匿名函数应用。判断等价时，作用域、求值过程与类型系统是需要一起考虑的三个层次。
