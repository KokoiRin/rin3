把类型推导当作一个约束求解问题

前几节已经见过 REPL 自动显示函数类型。这一节真正新增的，是把“看代码大概知道是什么类型”变成一套可以重复执行的步骤：给未知位置编号，收集表达式要求，再判断这些要求能不能同时成立。如果写过编译器的语义检查，可以把它看成类型检查与约束求解接在了一起。

先看一个完整例子。输入是二项整数元组，输出是第一项绝对值与第二项的和。

score 是7，函数类型是 int * int -> int。这个结果不是运行过 (~3,4) 才猜出来的：即使删掉最后一行，定义本身已经提供足够信息。ML 是静态类型语言，只是通常不要求程序员把每个类型写出来。

先分配未知类型，再逐条记录事实

暂时把函数输入记为 T1，输出记为 T2，局部的 y、z 分别记为 T3、T4。这些符号只是推导过程中待求解的类型，不是四个任意选好、以后互不相关的类型。

从哪里读到要求 得到的约束
pair_score 是函数 pair_score : T1 -> T2
(y,z) 匹配 x T1 = T3 * T4
abs y，且 abs : int -> int T3 = int，这个调用结果为 int
abs y + z 本例中 T4 = int，加法结果为 int
加法是整个函数体的结果 T2 = int

接下来把已经知道的类型代回其他方程：输入从 T3 * T4 变成 int * int，输出变成 int。这种让不同位置的类型要求一致的过程，通常称为统一。类型检查器实际收集事实的顺序可能不同，但不能只满足其中一部分。

这个方法也说明了类型推导的目标：找到一套类型，使整个定义通过类型规则。对于这里讨论的 ML 规则，有解就接受，无解就报错；不需要通过尝试大量输入寻找反例。完整算法还要处理嵌套作用域等细节，本节用例子理解它的主要工作。

分支也会把约束连起来

原课先用一个很小的条件函数说明同一件事。下面两个调用分别得到42与4。

比较、整数常量和乘法使输入成为整数；两条分支都返回整数，所以整体也是整数。若把第一条分支改成 true，同一条件表达式就同时被要求返回 bool 和 int，这些要求互相冲突。

类型检查会考虑所有分支，不能因为某次输入没有走到错误分支就放过它。甚至测试写成常量 true 时，两条分支也仍需满足同一套静态类型规则；它不是先做一次运行路径选择，再只给被选中的代码分配类型。

递归调用也必须回到同一个函数类型

再看已经熟悉的求和。输入 [12,18,10]，结果是40。

先给 sum 一个待求解的 T1 -> T2。列表模式说明 xs : T3 list、x : T3、rest : T3 list，所以 T1=T3 list。空分支的0和另一分支的加法，把输出与元素类型都限定为 int。

递归调用 sum rest 还提供一条一致性检查：它的实参类型必须等于 sum 已经在求解的输入类型。这里 rest : int list，正好符合；不是每递归一次就为同一个定义重新发明一个毫不相关的函数类型。

下面故意把实参从尾部 rest 错写成头部 x。这段要单独检查，预期失败。

模式要求函数输入是元素类型的列表，错误的递归实参又要求它等于元素类型本身。结合整数加法，就出现 int list = int 的冲突。更一般地，普通有限类型也不能靠把 T 设成“等于自己的列表”来解决 T = T list；递归数据类型需要显式定义构造器，并不是让同一类型无限展开成列表。

这能帮助读报错：提示位置可能是递归调用，也可能是某个运算，取决于实现先收集到哪些事实。真正要找的是哪些要求连起来以后矛盾。下一篇看另一种情况：要求彼此一致，但仍有一些类型没有被限定为某个具体类型，这正是多态产生的位置。
