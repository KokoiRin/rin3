同一个格子，不能每次读取都换一种元素类型

上一篇的 identity 可以在一次使用中取整数类型，下一次再取布尔类型。现在考虑一个有状态的值：如果同一个可变格子也能这样自由实例化，写入和读取就可能对里面装什么产生分歧。这就是原课这段选学内容要补上的安全问题。

先用最小例子认识引用。ref 创建一个可变格子，! 读取里面的值，:= 更新同一个格子；引用变量本身仍然是普通绑定。

next 是13。saved 指向一个始终装 int option 的格子：开始装 NONE，后来装 SOME 12。更新并没有让 saved 变成另一个引用，更没有把格子的元素类型从整数变成其他类型。

如果把 ref NONE 当成任意多态，会出什么事

下面是原课反例，要作为一整段单独检查。合法的 ML 实现必须拒绝这条不安全路径。

假设第一行像恒等函数那样，真的建立了可以任意实例化的 'a option ref。赋值时就能把同一个 r 实例化成 string option ref，写入字符串；下一行又把它实例化成 int option ref，试图做整数加法。这不是两个各自安全的格子，而是两次访问同一个格子，却对内部值采用了互不一致的解释。

:= 和 ! 本身也有多态类型，但每次操作的类型关系仍需一致。漏洞来自错误地允许共享存储的元素类型在各次使用间独立变化。类型系统需要拒绝至少一处，而不能接受整个程序、等运行到字符串加一时才发现问题。

值限制保守地挡住这种泛化

ML 的做法叫值限制。在本例中，关键区分是：绑定右边是值限制认可的语法形式，例如已有变量、函数值等，还是一次可能产生状态的函数应用。ref NONE 是调用，不会仅因为结果含有一个暂时未知的类型，就把它泛化为每次使用都可自由选类型的绑定。

REPL 可能显示弱类型变量、dummy type，或给出不能泛化的警告；不同实现及一次提交多少声明，会影响具体展示。它们都不表示已经获得可任意实例化的普通 'a。给引用写明 int option ref，就能得到开头那种明确安全的程序，但再向它写入字符串便会被拒绝。

这也补充了上一篇的泛化条件：只有没有被当前环境固定的未知类型，才可能成为新的通用类型变量。包装在函数里，不会让来自同一个外部共享格子的元素类型突然独立起来。

为什么没有修改数据，也可能受到限制

原课用部分应用给出一个常见情况。我们想把列表里的每个元素配上数字1，却把 List.map 的第二个参数留到以后。

从行为上看，这里只是准备一个函数，没有显式创建引用。但绑定右边仍是函数调用，因此不能凭这段表面代码就期待它获得所需的完整多态类型。限制采用统一、保守的规则，并不逐个证明被调用函数是否绝不会分配可变状态。

此时定义的是一个函数值，类型可以是 'a list -> ('a * int) list。函数体留到调用时执行；这种包装能解决这个纯计算的部分应用问题，却不能不加分析地替换任何有状态表达式。什么时候分配、是否每次重做、异常何时抛出，都可能因此变化，第8篇会回到这些条件。

不能只检查类型名字里有没有 ref

原课还给出下面的别名与函数。调用 allocate 仍然创建引用，换一个类型名没有改变它的行为。

以后模块还会隐藏类型的具体表示，客户端更不能从一个类型名字判断内部是否有可变格子。所以安全规则不能只在表面写出 ref 时才启用。这是保守限制付出的代价，也是抽象类型与状态同时存在时必须考虑的信息边界。

相反，fun fresh () = ref NONE 可以建立每次调用都新分配格子的工厂：不同调用各自固定为整数格子或字符串格子，不会写入同一位置。这与“一个共享格子任意多态”完全不同。真正要跟踪的是同一份状态在哪里被共享，以及哪些类型关系必须跨使用位置保持不变。
