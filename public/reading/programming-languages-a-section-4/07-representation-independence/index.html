同一个接口，可以藏住多大的实现变化

上一篇通过抽象类型，限制客户端只能使用公开操作。现在看它带来的实际自由：能不能改变约分时机，甚至把整个内部数据类型换掉，而不用逐个寻找所有调用者修改代码？

本篇继续使用上一篇完整定义的 RationalCore、RATIONAL_A/B/C。我们会新增两份实现，再通过相同客户端操作观察结果；原实现会命名为 Rational1。关键不是“看起来都叫 rational”，而是允许的客户端到底能观察什么。

第二版：把约分留到转字符串之前

原课 Rational2 仍使用 Whole | Frac，但创建和相加时不再约分。它仍保证分母为正，toString 则负责最后的约分。下面保留完整实现，先命名 Rational2Core 以便比较两种签名。

sameText 是 ("3/2","3/2")。第一版内部已经保存3/2，第二版可能保存9/6，但允许的观察操作返回相同的最简字符串。相加后的结果也应按同一数学有理数来对应，内部形状不必相同。

两版的不变式已经不同：第二版不再承诺内部随时约分，因此 toString 不能照搬第一版的直接显示逻辑。辅助函数只被 toString 使用后，还可以移进它的局部作用域；客户端从未获准依赖这些名字，移动不会破坏那份接口。

是否等价，取决于公开了什么

若同一份实现改用 A 签名，客户端可以直接调用 Frac。下面继续使用前面的核心实现，构造出一个确实能区分两版的客户端。

结果是 ("9/6","3/2")，所以这两版在 A 接口下不等价。B/C 隐藏了这种直接构造与模式观察，才让改变内部约分时机有机会保持所有允许客户端的行为。延迟约分也没有使公开 Frac 突然安全：零分母和负分母仍能破坏实现的前提。

这里的替换，是把同一个模块接口背后的实现换掉，并让客户端始终使用那个接口公开的操作；不是在程序中混用几个模块的内部值。还要先忽略整数溢出，或限定在所有中间算术都能表示的输入范围内。延迟约分可能让中间数更大，真实整数实现的边界不能被数学上的等值关系自动抹掉。

第三版：连 Whole 与 Frac 都不用

第三版用整数对表示全部有理数，包括整数也保存为 (i,1)。它不能满足要求完整数据构造器的 A，但可以满足 B/C。

thirdText 是 "11/2"。客户端仍通过创建、相加、显示这几种操作完成任务，却不用知道内部已经从 datatype 换成类型别名。这就是表示独立性的用途：允许换表示，同时用边界阻止客户端依赖被换掉的细节。

签名匹配如何连接内部与外部类型

第三版的 make_frac 内部是 int * int -> int * int，外部却是 int * int -> rational。实现知道这两个位置用的是同一种整数对，客户端只知道输出属于抽象类型，不能因此直接传任意整数对给 toString。

Whole 更有意思：内部 fun Whole i = (i,1) 可推导为 'a -> 'a * int。匹配签名时，先把两处 'a 一致实例化为 int，再用内部 rational=int*int 对应外部抽象类型，才能得到 int -> rational。不能只替换返回位置，却仍声称接受任意类型输入；'a -> rational 并不是这个接口能承诺的类型。

反过来，把 make_frac 的接口写成 rational -> rational，在第三版内部可能仍匹配整数对到整数对。但若采用没有 Whole 的 B 接口，外部就没有正常创建第一个有理数的入口了：每个操作都先要求已经有一个有理数。类型正确不代表接口可用。

相同签名，不允许跨模块随便混用

下面是单独的预期错误。

Rational1.rational 与 Rational2.rational 在客户端是不同的抽象类型，第三版又有不同内部表示。即便前两版都写了相似的 datatype，也不表示可以让“假设已经约分”的函数接收另一模块产生的未约分值。这个限制正是在保护各实现自己的不变式。

最后，同一个签名只证明操作与类型对得上，不自动证明行为等价。把 add 错写成总返回第一个实参，仍可能符合函数类型，却显然不是有理数加法。等价还需要论证每种允许操作都保持同一个数学含义、失败约定与客户端可观察行为。下一篇把这条要求推广到一般函数。
