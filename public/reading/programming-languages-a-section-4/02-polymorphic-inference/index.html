推导结束，还有未知类型时怎么办

上一篇的求和把元素类型限定成了整数。如果我们只数元素个数，不读取元素内容，情况会不同。这里不需要再猜“默认按整数处理”，而是保留代码实际允许的通用性。

与求和一样，列表模式要求输入是 T list，两个分支要求输出是 int。不同点在于没有任何运算使用头部 x，所以没有事实要求 T=int。解出来的是 T list -> int；把未被其他约束限定的类型一致地写成类型变量，就得到 'a list -> int。

“没限定成整数”，不等于“各处互不相关”

原课接着用一个元组函数说明关系约束。虽然条件恒为真，类型检查仍会检查另一条分支。

kept 是 (12,18,"tag")。设三个输入类型分别为 T1、T2、T3，输出类型为 T4。两分支必须同型，因此同时要求 T4=T1*T2*T3 和 T4=T2*T1*T3，进而要求 T1=T2。

所以函数类型是 'a * 'a * 'b -> 'a * 'a * 'b，而不是任意三种类型组成的元组。第一项与第二项可以共同选择整数，也可以共同选择字符串；不能一个整数、一个布尔值。剩余类型变量的意义，是“这些位置需要共享同一种类型”，不是“系统放弃检查这些位置”。

原课的另一个例子是：外层有 val offset=42，函数 fun gated (y,z,w) = if y then z+offset else 0。条件使 y 为 bool，加法使 z 为 int，没有使用的 w 保留为类型变量，因此类型为 bool * int * 'a -> int。约束还会使用定义时环境中已知的类型，并非只看参数名单。

定义时泛化，使用时分别实例化

下面的恒等函数在定义时没有给输入增加额外要求，因此输入与输出共享同一个类型变量。

从定义得到 'a -> 'a，可以理解为把符合条件的未知类型泛化了：这个绑定能够用于不同的类型。到 identity 12 这个使用位置，再用一份新的类型实例，把本次输入与输出都确定为 int；下一次使用则可以另取 bool。

这里的“符合条件”包括：未知类型不受当前环境已固定的类型关系约束，而且定义满足值限制。不能把所有没写出具体类型的变量一律泛化；下一篇会用共享状态解释为什么需要这条边界。

两个使用位置的实例彼此独立，但同一个实例内部的两处 'a 仍必须一致。因此多态不是让单次调用输入整数、输出任意另一种类型。定义中的类型变量约束怎样连接，实例化以后仍然怎样连接。

也不能把“函数参数”与“已泛化的函数绑定”混为一谈。普通的 fun use f = (f 12,f true) 要在同一次函数定义中给参数 f 一个一致的类型，两个使用会冲突，预期类型错误。ML 不会自动把每个传入的函数参数都提升成可以任意实例化的高层多态接口。

compose：高阶函数也能靠同一套方程推导

原课最后推导了函数组合。目标是先做 g，再把结果交给 f；下面先加一，再转成字符串。

text 是 "13"。先设 x:A；g x 要求 g:A->B，它的结果交给 f，于是 f:B->C，整个匿名函数为 A->C。最终得到 (B->C) * (A->B) -> (A->C)，把未知类型换成类型变量即可。

REPL 可能打印为 ('a -> 'b) * ('c -> 'a) -> 'c -> 'b。字母名字不同没有关系，关键是 g 的输出与 f 的输入连在一起，组合函数的输入来自 g，输出来自 f。没有额外需求，就不该强行把这些类型变成整数。

这套推导为什么依赖语言的规则

类型推导与多态是两个不同能力：一种语言可以自动推导，却没有这样的类型变量；也可以要求显式类型参数，却仍允许泛型。ML 恰好让二者很好地配合，所以既能自动推导，也能保留较一般的类型。

原课还指出这个设计的位置很重要。若加入复杂的子类型关系，元组解构可能只说明“至少有这些部分”，不再唯一确定完整结构，推导与阅读都会更难。反过来没有多态，像 length 这种代码又会面临应该选哪种具体元素类型的问题。下一篇会补上当前描述里缺的一条限制：当未知类型属于一个共享的可变位置时，不能照搬恒等函数的泛化方式。
