UI 层包含与 UI 相关的状态和 UI 逻辑，数据层则包含应用数据与业务逻辑。业务逻辑为应用带来价值，它由现实业务规则构成，决定应用数据必须怎样创建、存储和改变。

这种职责分离让数据层可以被多个页面使用，让应用不同部分共享信息，也能在 UI 之外复现业务逻辑进行单元测试。数据层好处的更多信息，请参阅架构概览。

注意：本页建议和最佳实践适用于多种应用，有助于扩展规模、提高质量和健壮性，并改善可测试性。不过，应把它们视为指导原则，并根据自身需求调整。

数据层架构

数据层由 Repository 组成，每个 Repository 可以包含零个到多个数据来源。应为应用处理的每一种不同数据创建 Repository 类。例如，为电影数据创建 MoviesRepository，为付款数据创建 PaymentsRepository。

Repository 类负责以下任务：

  • 向应用其余部分暴露数据。
  • 集中管理数据变化。
  • 解决多个数据来源之间的冲突。
  • 对应用其余部分隐藏数据来源的具体实现。
  • 包含业务逻辑。

每个 DataSource 类应只负责一个数据来源，可以是文件、网络来源或本地数据库。DataSource 类是应用与系统之间执行数据操作的桥梁。

其他层不应直接访问数据来源，数据层入口始终是 Repository 类。state holder 类（参阅 UI 层指南）或 UseCase 类（参阅领域层指南）不应直接依赖 DataSource。通过 Repository 进入数据层，可以让架构中的各层独立扩展。

这一层暴露的数据应不可变，防止其他类修改它们，造成值不一致。不可变数据也可以由多个线程安全处理。详情请参阅线程一节。

遵循依赖注入最佳实践，Repository 在构造器中接收 DataSource 依赖：

class ExampleRepository(
    private val exampleRemoteDataSource: ExampleRemoteDataSource, // network
    private val exampleLocalDataSource: ExampleLocalDataSource // database
) { /* ... */ }
注意：如果 Repository 只有一个 DataSource，且不依赖其他 Repository，开发者经常把两者的职责合并到 Repository 类中。采用这种方式时，如果后续版本需要处理其他数据来源，不要忘记拆分相关功能。

暴露 API

数据层的类通常暴露函数，用于执行一次性的创建、读取、更新、删除（CRUD）调用，或接收随时间发生的数据变化通知。对于这两种情况，数据层应分别暴露：

  • 一次性操作：暴露挂起函数。
  • 持续接收数据变化通知：暴露 Flow。
class ExampleRepository(
    private val exampleRemoteDataSource: ExampleRemoteDataSource, // network
    private val exampleLocalDataSource: ExampleLocalDataSource // database
) {

    val data: Flow<Example> = ...

    suspend fun modifyData(example: Example) { ... }
}

本指南的命名约定

本指南根据 Repository 负责的数据为其命名，约定如下：

数据类型 + Repository。

例如：NewsRepository、MoviesRepository 或 PaymentsRepository。

DataSource 类根据它负责的数据及使用的来源命名，约定如下：

数据类型 + 来源类型 + DataSource。

来源类型可使用 Remote 或 Local 等通用名称，因为实现可能变化。例如：NewsRemoteDataSource 或 NewsLocalDataSource。如果具体来源很重要，也可以使用来源类型作为名称，例如：NewsNetworkDataSource 或 NewsDiskDataSource。

不要根据实现细节命名 DataSource，例如 UserSharedPreferencesDataSource，因为使用它的 Repository 不应知道数据怎样保存。遵循这一规则，就能在不影响调用层的情况下修改 DataSource 实现，例如从 SharedPreferences 迁移到 DataStore。

注意：迁移到新的 DataSource 实现时，可能会为 DataSource 创建接口，并同时提供旧技术与新技术两种实现。这时，可以在 DataSource 类名中使用技术名称，虽然它属于实现细节，因为 Repository 只接触接口，不接触这些具体类。迁移完成后，可以重命名新类，去掉名称中的实现细节。

多层 Repository

当业务需求更复杂时，某个 Repository 可能需要依赖其他 Repository。原因可能是相关数据需要聚合多个来源，或某项职责需要封装在另一个 Repository 类中。

例如，处理用户认证数据的 UserRepository，可能需要依赖 LoginRepository 和 RegistrationRepository 等其他 Repository 来满足需求。

注意：传统上，一些开发者把依赖其他 Repository 的 Repository 类称为 Manager，例如用 UserManager 而不是 UserRepository。也可以按自己的偏好采用这种命名约定。

事实来源

每个 Repository 都应定义单一事实来源，这一点很重要。事实来源始终包含一致、正确且最新的数据。实际上，Repository 暴露的数据应始终直接来自事实来源。

事实来源可以是 DataSource，例如数据库，也可以是 Repository 内的内存缓存。Repository 组合不同的数据来源并解决潜在冲突，定期或响应用户输入事件更新单一事实来源。

应用中的不同 Repository 可以有不同事实来源。例如，LoginRepository 可以使用缓存，PaymentsRepository 可以使用网络 DataSource。

为支持离线优先，推荐把数据库等本地 DataSource 作为事实来源。

线程

调用 DataSource 和 Repository 应当是主线程安全的，即能安全地从主线程调用。执行长时间的阻塞操作时，这些类负责把逻辑切换到适当线程。例如，DataSource 读取文件，或 Repository 对大列表执行高成本筛选，都应确保从主线程调用是安全的。

多数 DataSource 已提供主线程安全的 API，例如 Room、Retrofit 或 Ktor 提供的挂起方法。API 可用时，Repository 可以直接利用这些能力。

线程的更多信息，请参阅后台处理指南。对于 Kotlin 用户，推荐使用协程。

生命周期

只要数据层实例仍能从垃圾回收根访问到，通常是被应用中的其他对象引用，它们就会继续留在内存中。

如果一个类包含内存中的数据，例如缓存，可能需要在某段时间内复用同一实例。这段时间也称为该类实例的生命周期。

如果类的职责对整个应用都很重要，可以把它的实例限定作用域到 Application 类，让实例遵循应用生命周期。如果只需在特定流程中复用实例，例如注册或登录流程，则应将实例限定到拥有该流程生命周期的类。例如，可把持有内存数据的 RegistrationRepository 限定到 RegistrationActivity，或使用 NavEntryDecorator 限定到返回栈。

实例生命周期是决定如何提供应用依赖的重要因素。推荐遵循依赖注入最佳实践，通过依赖容器管理依赖并限定作用域。Android 作用域的更多信息，请参阅 Android 与 Hilt 中的作用域博客文章。

表示业务模型

数据层希望暴露的数据模型，可能只是各个 DataSource 提供信息的一个子集。理想情况下，网络或本地 DataSource 都只返回应用需要的信息，但实际通常并非如此。

例如，一个新闻 API 服务器不仅返回文章信息，还返回编辑历史、用户评论和一些元数据：

data class ArticleApiModel(
    val id: Long,
    val title: String,
    val content: String,
    val publicationDate: Date,
    val modifications: Array<ArticleApiModel>,
    val comments: Array<CommentApiModel>,
    val lastModificationDate: Date,
    val authorId: Long,
    val authorName: String,
    val authorDateOfBirth: Date,
    val readTimeMin: Int
)

应用不需要那么多信息，因为它只显示文章正文及作者的基本信息。将模型类分开，让 Repository 只暴露其他层所需数据，是一种良好做法。例如，可以精简网络返回的 ArticleApiModel，向领域层和 UI 层暴露 Article 模型类：

data class Article(
    val id: Long,
    val title: String,
    val content: String,
    val publicationDate: Date,
    val authorName: String,
    val readTimeMin: Int
)

分离模型类有以下好处：

  • 只保留所需数据，节省应用内存。
  • 将外部数据类型转换成应用采用的类型，例如应用可能使用不同的日期表示类型。
  • 改善职责分离。例如，预先定义好模型类后，大型团队的成员就可以分别开发某项功能的网络部分和 UI 部分。

也可以把这种做法扩展到架构的其他部分，例如在 DataSource 类和 ViewModel 中定义不同模型。不过，这需要额外的类与逻辑，应做好文档说明和测试。至少在 DataSource 接收的数据与应用其他部分的期望不一致时，建议创建新的模型。

数据操作的类型

数据层可以按重要性处理不同类型的操作：面向 UI、面向应用和面向业务的操作。

面向 UI 的操作

面向 UI 的操作只在用户停留在特定页面时有意义，用户离开页面后就会取消。例如，显示从数据库取得的数据。

这类操作通常由 UI 层触发，并遵循调用方的生命周期，例如 ViewModel 的生命周期。发起网络请求一节给出了示例。

面向应用的操作

面向应用的操作在应用保持打开时都有意义。应用关闭或进程被终止时，这些操作会取消。例如，缓存网络请求结果以供后续使用。详情请参阅实现内存数据缓存一节。

这类操作通常遵循 Application 类或数据层的生命周期。示例请参阅让操作存活得比页面更久。

面向业务的操作

面向业务的操作不能取消，应在进程死亡后继续存活。例如，完成用户要发布到个人资料中的照片上传。

这类操作推荐使用 WorkManager。详情请参阅使用 WorkManager 调度任务。

暴露错误

与 Repository 和 DataSource 交互时，操作可能成功，也可能在失败时抛出异常。协程与 Flow 应采用 Kotlin 内置错误处理机制。对于挂起函数可能产生的错误，适当地使用 try/catch 块；对于 Flow，使用 catch 操作符。在这种方式下，UI 层应在调用数据层时处理异常。

数据层可以理解和处理不同错误，并通过自定义异常暴露它们，例如 UserNotAuthenticatedException。

注意：另一种表示数据层交互结果的方法，是使用 Result 类。该模式为结果处理过程中可能发生的错误和其他信号建模，让数据层返回 Result<T> 而非 T，使 UI 能识别特定场景下可能发生的已知错误。

协程错误的更多信息，请参阅协程中的异常博客文章。

常见任务

以下各节通过示例介绍 Android 应用中常见数据层任务的实现与架构组织。示例沿用本指南前述新闻应用。

发起网络请求

网络请求是 Android 应用最常执行的任务之一。新闻应用需要显示从网络取得的最新新闻，因此需要一个管理网络操作的 DataSource 类：NewsRemoteDataSource。为向应用其余部分暴露数据，还要创建处理新闻数据的 Repository：NewsRepository。

需求是每次用户打开页面都更新最新新闻，因此这属于面向 UI 的操作。

创建 DataSource

DataSource 需要暴露返回最新新闻的函数，结果是一组 ArticleHeadline 实例。它还需要提供一种主线程安全的网络获取方式，因此必须依赖用于执行任务的 CoroutineDispatcher 或 Executor。

网络请求是一次性调用，由新的 fetchLatestNews() 方法处理：

class NewsRemoteDataSource(
  private val newsApi: NewsApi,
  private val ioDispatcher: CoroutineDispatcher
) {
    /**
     * Fetches the latest news from the network and returns the result.
     * This executes on an IO-optimized thread pool, the function is main-safe.
     */
    suspend fun fetchLatestNews(): List<ArticleHeadline> =
        // Move the execution to an IO-optimized thread since the ApiService
        // doesn't support coroutines and makes synchronous requests.
        withContext(ioDispatcher) {
            newsApi.fetchLatestNews()
        }
    }

// Makes news-related network synchronous requests.
interface NewsApi {
    fun fetchLatestNews(): List<ArticleHeadline>
}

NewsApi 接口隐藏网络 API 客户端的实现，底层采用 Retrofit 还是 HttpURLConnection 都不影响调用。依赖接口让应用中的 API 实现可以替换。

要点：依赖接口让应用中的 API 实现可以替换。除了方便扩展和替换依赖，它还改善了可测试性，因为测试时可以注入假的 DataSource 实现。

创建 Repository

这个任务中 Repository 无须额外逻辑，因此 NewsRepository 充当网络 DataSource 的代理。增加这一抽象层的好处会在内存缓存一节解释。

// NewsRepository is consumed from other layers of the hierarchy.
class NewsRepository(
    private val newsRemoteDataSource: NewsRemoteDataSource
) {
    suspend fun fetchLatestNews(): List<ArticleHeadline> =
        newsRemoteDataSource.fetchLatestNews()
}

在 UI 层直接使用 Repository 的方法，请参阅 UI 层指南。

实现内存数据缓存

假设新闻应用增加一个需求：用户打开页面时，如果之前请求过数据，就显示缓存新闻；否则发起请求，获取最新新闻。

这要求应用在保持打开期间，把最新新闻保存在内存中，因此属于面向应用的操作。

缓存

添加内存数据缓存，可以在用户使用应用期间保留数据。缓存会在特定时间内把部分信息留在内存中，本例是整个应用打开期间。缓存实现有多种形式，从简单的可变变量，到保护多线程读写的复杂类。根据场景，缓存可以放在 Repository 或 DataSource 类中。

缓存网络请求结果

为了简单起见，NewsRepository 使用可变变量缓存最新新闻，并用 Mutex 保护不同线程的读写。关于共享可变状态与并发，请参阅 Kotlin 文档。

以下实现把最新新闻存入 Repository 中受 Mutex 写保护的变量。网络请求成功后，数据赋给 latestNews 变量。

class NewsRepository(
  private val newsRemoteDataSource: NewsRemoteDataSource
) {
    // Mutex to make writes to cached values thread-safe.
    private val latestNewsMutex = Mutex()

    // Cache of the latest news got from the network.
    private var latestNews: List<ArticleHeadline> = emptyList()

    suspend fun getLatestNews(refresh: Boolean = false): List<ArticleHeadline> {
        if (refresh || latestNews.isEmpty()) {
            val networkResult = newsRemoteDataSource.fetchLatestNews()
            // Thread-safe write to latestNews
            latestNewsMutex.withLock {
                this.latestNews = networkResult
            }
        }

        return latestNewsMutex.withLock { this.latestNews }
    }
}

让操作存活得比页面更久

如果用户在请求进行时离开页面，请求就会取消，结果也无法缓存。NewsRepository 不应使用调用方的 CoroutineScope 执行这段逻辑，而应使用与自身生命周期关联的 CoroutineScope。获取最新新闻需要改成面向应用的操作。这里的 NewsRepository 应采用这一作用域。

遵循依赖注入最佳实践，NewsRepository 应通过构造器参数接收作用域，而不是创建自己的 CoroutineScope。由于 Repository 的大部分工作应在后台线程执行，应将 CoroutineScope 配置为 Dispatchers.Default 或自己的线程池。

class NewsRepository(
    ...,
    // This could be CoroutineScope(SupervisorJob() + Dispatchers.Default).
    private val externalScope: CoroutineScope
) { ... }

NewsRepository 已通过外部 CoroutineScope 准备好执行面向应用的操作，因此需要在该作用域启动的新协程中调用 DataSource，并保存结果：

class NewsRepository(
    private val newsRemoteDataSource: NewsRemoteDataSource,
    private val externalScope: CoroutineScope
) {
    /* ... */

    suspend fun getLatestNews(refresh: Boolean = false): List<ArticleHeadline> {
        return if (refresh) {
            externalScope.async {
                newsRemoteDataSource.fetchLatestNews().also { networkResult ->
                    // Thread-safe write to latestNews.
                    latestNewsMutex.withLock {
                        latestNews = networkResult
                    }
                }
            }.await()
        } else {
            return latestNewsMutex.withLock { this.latestNews }
        }
    }
}

async 在外部作用域启动协程。对新协程调用 await，会挂起，等待网络结果返回并保存到缓存。如果用户此时还在页面中，就会看到最新新闻；如果已经离开页面，await 会取消，但 async 内部逻辑仍会继续。

更多内容，请参阅 CoroutineScope 的使用模式。

从磁盘保存与读取数据

假设需要保存收藏新闻、用户偏好等数据。这类数据应在进程死亡后保留，并在没有网络时仍可访问。

若数据需要在进程死亡后保留，就应通过以下方式之一存到磁盘：

  • 对需要查询、引用完整性或局部更新的大规模数据集，保存到 Room 数据库。例如，新闻文章或作者信息可以存入数据库。
  • 对只需整体读取和设置、不需要查询或局部更新的小规模数据集，使用 DataStore。例如，用户偏好的日期格式或其他显示偏好。
  • 对 JSON 对象等整块数据，使用文件。

如事实来源一节所述，每个 DataSource 只处理一个来源，并对应一种特定数据类型，例如 News、Authors、NewsAndAuthors 或 UserPreferences。使用它的类不应知道数据是存进数据库还是文件。

Room 作为数据来源

每个 DataSource 应只负责某种数据的一个来源，因此 Room DataSource 会接收数据访问对象（DAO）或数据库作为参数。例如，NewsLocalDataSource 接收 NewsDao 实例，AuthorsLocalDataSource 接收 AuthorsDao 实例。

如果不需要额外逻辑，有些情况下可以直接把 DAO 注入 Repository，因为 DAO 是易于在测试中替换的接口。

Room API 的更多信息，请参阅 Room 指南。

DataStore 作为数据来源

DataStore 很适合保存用户设置等键值对，例如时间格式、通知偏好，或读过新闻后是否隐藏条目。DataStore 也可以通过 Protocol Buffers 保存带类型的对象。

与其他对象一样，基于 DataStore 的 DataSource 应只包含一种数据，或应用某一部分的数据。DataStore 的读取通过 Flow 暴露，每次值变化都会发出新值，因此这一点尤其重要。相关偏好应保存在同一 DataStore 中。

例如，可以用 NotificationsDataStore 只处理通知偏好，用 NewsPreferencesDataStore 只处理新闻页面的偏好。这样能更好地限定更新范围，因为 newsScreenPreferencesDataStore.data Flow 只在该页面相关偏好变化时发出新值。此外，对象生命周期也可以更短，只需在新闻页面显示期间存活。

DataStore API 的更多信息，请参阅 DataStore 指南。

文件作为数据来源

使用 JSON 对象或位图等大型对象时，需要使用 File 对象，并处理线程切换。

文件存储的更多信息，请参阅存储概览。

使用 WorkManager 调度任务

假设新闻应用增加另一个需求：只要设备在充电并连接不按流量计费的网络，就定期自动获取最新新闻。这属于面向业务的操作。如此一来，用户打开应用时即使没有网络，也能看到较新的新闻。

WorkManager 便于调度可靠的异步工作，并能管理执行约束，是持久性工作的推荐库。实现上述任务时，创建一个 Worker 类：RefreshLatestNewsWorker，它依赖 NewsRepository，获取最新新闻并缓存到磁盘。

class RefreshLatestNewsWorker(
    private val newsRepository: NewsRepository,
    context: Context,
    params: WorkerParameters
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result = try {
        newsRepository.refreshLatestNews()
        Result.success()
    } catch (error: Throwable) {
        Result.failure()
    }
}

这类任务的业务逻辑应封装在独立类中，视为单独的 DataSource。WorkManager 只负责在满足所有约束时，保证工作在后台线程执行。遵循这一模式，就能按需快速替换不同环境下的实现。

在本例中，这个新闻任务必须从 NewsRepository 调用，它依赖新的 DataSource：NewsTasksDataSource，实现如下：

private const val REFRESH_RATE_HOURS = 4L
private const val FETCH_LATEST_NEWS_TASK = "FetchLatestNewsTask"
private const val TAG_FETCH_LATEST_NEWS = "FetchLatestNewsTaskTag"

class NewsTasksDataSource(
    private val workManager: WorkManager
) {
    fun fetchNewsPeriodically() {
        val fetchNewsRequest = PeriodicWorkRequestBuilder<RefreshLatestNewsWorker>(
            REFRESH_RATE_HOURS, TimeUnit.HOURS
        ).setConstraints(
            Constraints.Builder()
                .setRequiredNetworkType(NetworkType.TEMPORARILY_UNMETERED)
                .setRequiresCharging(true)
                .build()
        )
            .addTag(TAG_FETCH_LATEST_NEWS)

        workManager.enqueueUniquePeriodicWork(
            FETCH_LATEST_NEWS_TASK,
            ExistingPeriodicWorkPolicy.KEEP,
            fetchNewsRequest.build()
        )
    }

    fun cancelFetchingNewsPeriodically() {
        workManager.cancelAllWorkByTag(TAG_FETCH_LATEST_NEWS)
    }
}

这类类按所负责的数据命名，例如 NewsTasksDataSource 或 PaymentsTasksDataSource。某种数据的所有相关任务，应封装在同一个类中。

如果需要在应用启动时触发任务，推荐通过 App Startup 库提交 WorkManager 请求，并从 Initializer 调用 Repository。

WorkManager API 的更多信息，请参阅 WorkManager 指南。

测试

依赖注入最佳实践有助于测试。与外部资源通信的类采用接口，也能提供帮助。测试某个单元时，可以注入假的依赖，让测试确定且可靠。

单元测试

数据层测试也遵循通用测试指导。单元测试应按需使用真实对象，并用假的依赖替换文件读取、网络读取等访问外部来源的依赖。

集成测试

访问外部来源的集成测试通常确定性较低，因为它们需要在真实设备上运行。推荐在受控环境执行，提高可靠性。

Room 支持创建内存数据库，让测试完全控制数据库。更多信息请参阅测试与调试数据库。

对于网络，WireMock、MockWebServer 等常用库允许模拟 HTTP、HTTPS 调用，并验证请求是否按预期发送。
