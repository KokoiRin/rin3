UI events 是 UI 层需要处理的操作，可以由 UI 或 ViewModel 处理。其中最常见的是用户事件：用户点击屏幕、做出手势等操作都会产生事件，UI 再通过可组合函数上的 Lambda 等回调接收它们。

关键术语：
  • UI：处理用户界面的代码。
  • UI events：应在 UI 层处理的操作。
  • 用户事件：用户与应用交互时产生的事件。

用户点击“刷新”这类操作时，ViewModel 通常负责相应业务逻辑，并提供供 UI 调用的函数。事件中的界面行为则可以由 UI 自己处理，例如跳转页面或显示 Snackbar。

同一应用在不同移动平台或设备形态上的业务逻辑保持一致，而 UI 行为逻辑属于实现细节，可能因这些情况而不同。UI 层页面对这两种逻辑的定义如下：

  • 业务逻辑指状态变化后做什么，例如付款或保存用户偏好。领域层和数据层通常处理这类逻辑。本指南选择 Architecture Components ViewModel 类作为处理业务逻辑的类的一种明确方案。
  • UI 行为逻辑或 UI 逻辑指怎样显示状态变化，例如导航逻辑或向用户显示消息的方式。UI 负责处理这类逻辑。
注意：本页的建议和最佳实践适用于多种应用，有助于扩展规模、提高质量和健壮性，以及改善可测试性。不过，应把它们视为指导原则，并根据自身需求调整。

处理用户事件

如果事件只影响 UI 元素本身，例如展开或收起一个条目，UI 可以直接处理。如果需要执行业务逻辑，例如刷新页面数据，就应交给 ViewModel。

下例使用不同的按钮展开 UI 元素（UI 逻辑）和刷新页面数据（业务逻辑）：

@Composable
fun LatestNewsScreen(viewModel: LatestNewsViewModel = viewModel()) {

    // State of whether more details should be shown
    var expanded by remember { mutableStateOf(false) }

    Column {
        Text("Some text")
        if (expanded) {
            Text("More details")
        }

        Button(
        // The expand details event is processed by the UI that
        // modifies this composable's internal state.
        onClick = { expanded = !expanded }
        ) {
        val expandText = if (expanded) "Collapse" else "Expand"
        Text("$expandText details")
        }

        // The refresh event is processed by the ViewModel that is in charge
        // of the UI's business logic.
        Button(onClick = { viewModel.refreshNews() }) {
            Text("Refresh data")
        }
    }
}

惰性列表中的用户事件

即使操作来自 UI 树更深的位置，例如 LazyColumn 条目，也仍应由 ViewModel 处理用户事件。

例如，考虑一个包含可点击条目的列表。不要把 ViewModel 实例向下传入列表可组合函数（MyList），因为这会使 UI 组件与实现细节紧密耦合。

把事件定义成可组合函数的 Lambda 参数。这样，列表只需触发事件，不必知道后面由谁处理、如何处理。

data class MyItem(val id: Int)

@Composable
fun MyList(
    items: List<String>,
    onItemClick: (MyItem) -> Unit
) {
    Card {
        LazyColumn {
            itemsIndexed(items) { index, string ->
                ListItem(
                    modifier = Modifier.clickable {
                        onItemClick(MyItem(index))
                    },
                    headlineContent = {
                        Text(text = string)
                    }
                )
            }
        }
    }
}

在这种方式下，MyList 可组合函数只处理它显示的数据和暴露的事件，无法访问 ViewModel。事件向上提升，再由上层可组合函数传给 ViewModel。

事件处理的更多信息，请参阅 Compose 中的事件。

用户事件函数与事件处理器的命名约定

本指南中，处理用户事件的 ViewModel 函数按相应操作用动词命名，例如 validateInput() 或 login()。

Compose 的事件处理器遵循标准命名约定，让数据流向更清晰：

  • 参数名：on + Verb + Target，例如 onExpandClicked 或 onValueChange。
  • Lambda 表达式：调用可组合函数时，Lambda 通常就是相应事件的实现。

处理 ViewModel 事件

来自 ViewModel 的 UI 操作，即 ViewModel 事件，应始终转换为 UI state 的更新。这遵循单向数据流，使配置变化后仍可重现事件，保证 UI 操作不丢失。使用 saved state 模块时，还可以让事件在进程死亡后恢复。

把 UI 操作映射为 UI state 并不总是简单，但最终会得到更简单的逻辑。例如，思考不应止于确定怎样让 UI 导航到某个页面，还需要继续考虑怎样在 UI state 中表达整个用户流程。换言之，不要只想 UI 要执行什么操作，而应思考这些操作怎样影响 UI state。

要点：ViewModel 事件应始终导致 UI state 更新。

例如，考虑登录页面。可以用如下方式建模它的 UI state：

data class LoginUiState(
    val isLoginInProgress: Boolean = false,
    val errorMessage: String? = null,
    val isUserLoggedIn: Boolean = false
)

登录页面响应 UI state 的变化。

class LoginViewModel : ViewModel() {

    var uiState by mutableStateOf(LoginUiState())

    fun tryLogin(username: String, password: String) {
        viewModelScope.launch {
            // Emit a new state indicating that login is in progress
            uiState = uiState.copy(isLoginInProgress = true)

            uiState = if (login(username, password)) {
                // Emit a new state indicating that login was successful
                uiState.copy(isLoginInProgress = false, isUserLoggedIn = true)
            } else {
                // Emit a new state with the error message
                LoginUiState(isLoginInProgress = false, errorMessage = "Login failed")
            }
        }
    }

    private suspend fun login(username: String, password: String): Boolean {
        delay(1000)
        return (username == "Hello" && password == "World!")
    }
}

@Composable
fun LoginScreen(viewModel: LoginViewModel, onSuccessfulLogin: () -> Unit) {

    val uiState = viewModel.uiState

    LaunchedEffect(uiState) {
        if (uiState.isUserLoggedIn) {
            onSuccessfulLogin()
        }
    }

    if (uiState.isLoginInProgress) {
        CircularProgressIndicator()
    } else {
        LoginForm(
            onLoginAttempt = { username, password ->
                viewModel.tryLogin(username, password)
            },
            errorMessage = uiState.errorMessage
        )
    }
}
注意：理解本节代码示例，需要先了解协程。

读取事件可能触发状态更新

UI 处理某些 ViewModel 事件后，还需要触发下一次状态更新。例如，要显示一条临时消息，UI 显示完成后应通知 ViewModel。用户关闭消息，或消息因超时消失，都可以视为“用户输入”，因此 ViewModel 也需要知道。相应 UI state 可以这样定义：

// Models the UI state for the Latest news screen.
data class LatestNewsUiState(
    val news: List<News> = emptyList(),
    val isLoading: Boolean = false,
    val userMessage: String? = null
)

当业务逻辑要求向用户显示新的临时消息时，ViewModel 会按以下方式更新 UI state：

class LatestNewsViewModel(/* ... */) : ViewModel() {

    var uiState by mutableStateOf(LatestNewsUiState())
        private set

    fun refreshNews() {
        viewModelScope.launch {
            // If there isn't internet connection, show a new message on the screen.
            if (!internetConnection()) {
                uiState = uiState.copy(userMessage = "No Internet connection")
                return@launch
            }

            // Do something else.
        }
    }

    fun userMessageShown() {
        uiState = uiState.copy(userMessage = null)
    }
}

ViewModel 只需知道有消息待显示，不必知道 UI 具体怎样显示。消息显示后，UI 通知 ViewModel，再次更新状态以清空 userMessage：

@Composable
fun LatestNewsScreen(
    snackbarHostState: SnackbarHostState,
    viewModel: LatestNewsViewModel = viewModel(),
) {
    // Rest of the UI content.

    // If there are user messages to show on the screen,
    // show it and notify the ViewModel.
    viewModel.uiState.userMessage?.let { userMessage ->
        LaunchedEffect(userMessage) {
            snackbarHostState.showSnackbar(userMessage)
            // Once the message is displayed and dismissed, notify the ViewModel.
            viewModel.userMessageShown()
        }
    }
}

即使消息只是临时的，UI state 也始终忠实反映屏幕上显示的内容：用户消息要么正在显示，要么没有显示。

注意：如需更高级的用法，即在屏幕上显示用户消息列表，请参阅 Jetsnack Compose 示例。

导航事件

读取事件可能触发状态更新一节详细说明了如何利用 UI state 在屏幕上显示用户消息。导航事件也是 Android 应用中常见的事件类型。

如果用户点击按钮，在 UI 中触发事件，则由 UI 将事件暴露给调用方可组合函数来处理。

@Composable
fun LoginScreen(
    onHelp: () -> Unit, // Caller navigates to the help screen
    viewModel: LoginViewModel = viewModel()
) {
    // Rest of the UI
    Button(
        onClick = dropUnlessResumed { onHelp() }
    ) {
        Text("Get help")
    }
}

dropUnlessResumed 属于 Lifecycle 库，只有生命周期至少处于 RESUMED 状态时，它才允许执行 onHelp 函数。

如果导航前需要用业务逻辑验证输入数据，ViewModel 就需要把相应状态暴露给 UI。UI 响应状态变化并执行导航。处理 ViewModel 事件一节涵盖了这种场景。类似代码如下：

@Composable
fun LoginScreen(
    onUserLogIn: () -> Unit, // Caller navigates to the right screen
    viewModel: LoginViewModel = viewModel()
) {
    Button(
        onClick = {
            // ViewModel validation is triggered
            viewModel.tryLogin()
        }
    ) {
        Text("Log in")
    }
    // Rest of the UI

    val lifecycle = LocalLifecycleOwner.current.lifecycle
    val currentOnUserLogIn by rememberUpdatedState(onUserLogIn)
    LaunchedEffect(viewModel, lifecycle)  {
        // Whenever the uiState changes, check if the user is logged in and
        // call the `onUserLogin` event when `lifecycle` is at least STARTED
        snapshotFlow { viewModel.uiState }
            .filter { it.isUserLoggedIn }
            .flowWithLifecycle(lifecycle)
            .collect {
                currentOnUserLogIn()
            }
    }
}

上例能按预期运行，因为当前的登录目标不会留在返回栈中，用户按返回键也无法回到它。不过，如果页面可能留在返回栈中，方案就需要额外逻辑。

目标留在返回栈中的导航事件

如果状态触发从 A 导航到 B，而 A 仍留在返回栈中，就需要避免返回 A 后又自动跳到 B。为此，可以额外保存“是否应该导航”的状态。由于导航属于 UI 逻辑，这个状态通常由 UI 持有。以下场景说明这种处理方式。

假设你正在应用的注册流程中。在出生日期验证页面上，用户输入日期并点击“继续”后，ViewModel 会验证日期，并把验证逻辑委托给数据层。如果日期有效，用户进入下一页面。另外，用户可以在不同注册页面之间前后切换，修改部分数据。因此，注册流程中的所有导航目标都留在同一返回栈中。根据这些需求，可以如下实现此页面：

class DobValidationViewModel(/* ... */) : ViewModel() {
    var uiState by mutableStateOf(DobValidationUiState())
        private set
}

@Composable
fun DobValidationScreen(
    onNavigateToNextScreen: () -> Unit, // Caller navigates to the right screen
    viewModel: DobValidationViewModel = viewModel()
) {
    // TextField that updates the ViewModel when a date of birth is selected

    var validationInProgress by rememberSaveable { mutableStateOf(false) }

    Button(
        onClick = {
            viewModel.validateInput()
            validationInProgress = true
        }
    ) {
        Text("Continue")
    }
    // Rest of the UI

    /*
        * The following code implements the requirement of advancing automatically
        * to the next screen when a valid date of birth has been introduced
        * and the user wanted to continue with the registration process.
        */

    if (validationInProgress) {
        val lifecycle = LocalLifecycleOwner.current.lifecycle
        val currentNavigateToNextScreen by rememberUpdatedState(onNavigateToNextScreen)
        LaunchedEffect(viewModel, lifecycle) {
            // If the date of birth is valid and the validation is in progress,
            // navigate to the next screen when `lifecycle` is at least STARTED,
            // which is the default Lifecycle.State for the `flowWithLifecycle` operator.
            snapshotFlow { viewModel.uiState }
                .filter { it.isDobValid }
                .flowWithLifecycle(lifecycle)
                .collect {
                    validationInProgress = false
                    currentNavigateToNextScreen()
                }
        }
    }
}

验证出生日期是 ViewModel 负责的业务逻辑，通常会被委托给数据层。导航到下一页面则是 UI 逻辑，因为相应需求可能随 UI 配置变化。例如，平板同时显示多个注册步骤时，可能不希望自动进入另一个页面。上例的 validationInProgress 变量实现这一功能：当出生日期有效且用户希望继续下一注册步骤时，它决定 UI 是否自动导航。

其他场景

如果认为某个 UI 事件场景无法通过 UI state 更新解决，可能需要重新考虑应用中的数据流。请考虑以下原则：

  • 每个类只做其职责范围内的事。UI 负责屏幕特有的行为逻辑，例如导航调用、点击事件和请求权限。ViewModel 包含业务逻辑，并把更低层的结果转换成 UI state。
  • 思考事件从哪里产生。遵循本指南开头的决策树，让每个类处理自己的职责。例如，事件产生于 UI 并引发导航时，必须在 UI 中处理。部分逻辑可以委托给 ViewModel，但不能把整个事件的处理完全交给 ViewModel。
  • 如果有多个读取者，并担心事件被多次读取，可能需要重新考虑应用架构。多个并发读取者会使恰好交付一次的契约极难保证，复杂性和隐蔽行为也会急剧增加。遇到这种问题时，应考虑把相关职责移到 UI 树更高的位置，可能需要一个作用域位于层级更高处的不同实体。
  • 思考什么时候需要读取状态。有些情况下，应用在后台时不应继续读取状态，例如显示 Toast。这时应考虑在 UI 位于前台时读取。

注意：某些应用通过 Kotlin Channel 或其他响应式流把 ViewModel 事件暴露给 UI。当生成者（ViewModel）比读取者（Compose UI）存活得更久时，这些方案无法保证事件得到交付和处理。这可能给开发者带来后续问题，对多数应用来说也是不可接受的用户体验，因为它可能让应用处于不一致状态、引入错误，或使用户错过关键信息。

遇到这类问题，应先明确这个一次性事件对界面意味着什么，再立即处理并把结果表达成 UI state。这样能更准确地表示当前界面，提供更强的交付和处理保证，也通常更容易测试，并与应用其他部分保持一致。

如果想通过代码示例进一步了解为什么不应使用上述 API，请阅读 ViewModel：一次性事件反模式博客文章。
