UI 的职责是在屏幕上显示应用数据。UI 也是用户交互的主要入口。每当数据因用户交互（例如按下按钮）或外部输入（例如网络响应）而发生变化时，UI 都会更新，以反映这些变化。实际上，UI 是从数据层取得的应用状态的可视化表示。

但是，从数据层取得的应用数据通常与需要显示的信息采用不同的格式。例如，UI 可能只需要其中一部分数据，也可能需要合并两个不同的数据来源，才能向用户呈现相关信息。无论应用了什么逻辑，都需要向 UI 提供完整渲染所需的全部信息。UI 层是一条处理管线：它把应用数据的变化转换成 UI 能够呈现的形式，然后显示出来。

注意：本页的建议和最佳实践适用于多种应用，帮助它们扩展规模、提高质量和健壮性，并更容易测试。请把这些内容视为指导原则，根据自身需求进行调整。

一个基本案例

考虑一个获取新闻文章供用户阅读的应用。它的文章页面显示可阅读的文章，也允许已登录的用户收藏特别喜欢的文章。由于文章可能很多，读者必须能按分类浏览。概括而言，该应用让用户完成以下操作：

  • 查看可阅读的文章。
  • 按分类浏览文章。
  • 登录并收藏特定文章。
  • 在符合条件时使用某些高级功能。

以下各节使用这个案例介绍单向数据流的原则，并说明这些原则在 UI 层应用架构中帮助解决的问题。

UI 层架构

UI 指容器、可组合函数等用于显示数据的 UI 元素。构建 Android UI 时，推荐使用 Jetpack Compose 工具包。由于数据层负责持有、管理应用数据并提供访问入口，UI 层必须执行以下步骤：

  1. 读取应用数据，把它转换成 UI 容易渲染的数据。
  2. 读取可供 UI 渲染的数据，把它转换成呈现给用户的 UI 元素。
  3. 接收这些 UI 元素产生的用户输入事件，并按需把事件的影响反映到 UI 数据中。
  4. 根据需要重复步骤 1 至 3。

本指南的其余部分说明如何实现执行这些步骤的 UI 层，具体涵盖以下任务和概念：

  • 如何定义 UI state。
  • 使用单向数据流（UDF）生成和管理 UI state。
  • 如何遵循 UDF 原则，用可观察数据类型暴露 UI state。
  • 如何实现读取可观察 UI state 的 UI。

其中最基础的是 UI state 的定义。

定义 UI state

在前述案例中，UI 显示文章列表以及文章的一些元数据。应用呈现给用户的这些信息就是 UI state。

换言之，如果 UI 是用户看到的内容，UI state 就是应用认为用户应当看到的内容。两者如同硬币的两面：UI 是 UI state 的可视化表示，UI state 的任何变化都会立即反映在 UI 中。

在这个案例中，为满足新闻应用的需求，完整渲染 UI 所需的信息可以封装在如下定义的 NewsUiState 数据类中：

data class NewsUiState(
    val isSignedIn: Boolean = false,
    val isPremium: Boolean = false,
    val newsItems: List<NewsItemUiState> = listOf(),
    val userMessages: List<Message> = listOf()
)

data class NewsItemUiState(
    val title: String,
    val body: String,
    val bookmarked: Boolean = false,
    // ...
)UiLayer.kt

更多 UI state 信息，请参阅状态与 Jetpack Compose。

不可变性

上例中的 UI state 定义是不可变的。其主要好处是，不可变对象能保证应用在某一时刻的状态。这使 UI 可以专注于主要职责：读取状态并相应更新 UI 元素。除非 UI 本身就是相关数据的唯一来源，否则绝不要直接在 UI 中修改 UI state。违反这一原则会使同一份信息出现多个事实来源，导致数据不一致和隐蔽的错误。

以前述案例为例，如果在 Activity 类中更新 UI state 里的 NewsItemUiState 对象的 bookmarked 标记，这个标记就会与数据层竞争，成为文章收藏状态的事实来源。不可变数据类很适合防止这类不一致。

要点：只有数据来源或数据所有者，才应负责更新它们暴露的数据。

本指南的命名约定

本指南根据屏幕或屏幕局部的功能，为 UI state 类命名。约定如下：

功能名称 + UiState。

例如，新闻页面的状态可以叫作 NewsUiState，新闻列表中一个条目的状态可以叫作 NewsItemUiState。

用单向数据流管理状态

前一节说明，UI state 是渲染 UI 所需信息的不可变快照。不过，应用中的状态会随时间变化，变化可能来自用户交互，也可能来自修改底层数据来源的其他事件。

这些交互可以交由一个中间角色处理：它定义处理各个事件的逻辑，并转换底层数据来源以生成 UI state。虽然这些交互及其逻辑也可以放在 UI 中，但 UI 承担过多职责后，会很快变得难以管理。此外，代码会因此紧密耦合，影响可测试性。除非 UI state 很简单，否则应确保 UI 的唯一职责是读取并显示 UI state。

本节讨论单向数据流（UDF）。这种架构模式有助于落实上述清晰的职责分离。

State holder

State holder 是负责生成 UI state 及其生成逻辑的类。它的规模取决于所管理的 UI 元素范围，可以小到一个底部应用栏，也可以大到整个页面或导航目标。

对于后者，典型实现是 ViewModel 实例，不过根据具体需求，一个普通类也可能足够。例如，案例中的新闻应用使用 NewsViewModel 类作为 state holder，生成该页面显示的 UI state。

要点：对于需要访问数据层的屏幕级 UI state，推荐使用 ViewModel 类型进行管理。此外，它会自动在配置变化后继续存活。ViewModel 类定义处理应用事件的逻辑，并据此生成更新后的 UI state。

UI 与其状态生成者之间的相互依赖可以有多种建模方式。不过，UI 与它的 ViewModel 类之间的关系，基本可以理解为事件输入与随之产生的状态输出，因此可以用下图表示：

状态向下传递、事件向上传递的模式称为单向数据流（UDF）。这对应用架构有以下影响：

  • ViewModel 持有并暴露 UI 读取的状态。UI state 是经 ViewModel 转换后的应用数据。
  • UI 把用户事件通知给 ViewModel。
  • ViewModel 处理用户操作并更新状态。
  • 更新后的状态传回 UI，由 UI 渲染。
  • 每当有事件使状态发生变化时，就重复上述过程。

对于导航目标或页面，ViewModel 与 Repository 或 UseCase 类协作，取得数据并转换成 UI state，同时纳入可能使状态变化的事件影响。前述案例包含一组文章，每篇都有标题、描述、来源、作者姓名、发布日期和收藏状态。每个文章条目的 UI 如下：

用户请求收藏文章，就是一个可能使状态变化的事件。作为状态生成者，ViewModel 负责定义填充全部 UI state 字段所需的逻辑，并处理使 UI 能够完整渲染的事件。

以下各节进一步说明哪些事件会使状态变化，以及如何通过 UDF 处理它们。

逻辑的类型

收藏文章是业务逻辑的例子，因为它为应用带来价值。详情请参阅数据层页面。不过，还需要区分以下逻辑类型：

  • 业务逻辑实现针对应用数据的产品需求。如前所述，案例应用中的收藏文章就是一个例子。业务逻辑通常放在领域层或数据层，绝不放在 UI 层。
  • UI 行为逻辑或 UI 逻辑负责怎样在屏幕上显示状态变化。例如，使用 Android Resources取得要显示的正确文本；用户点击按钮后导航到特定页面；或者通过 toast、snackbar在屏幕上向用户显示消息。

把 UI 逻辑留在 UI 中，不要放进 ViewModel，尤其是涉及 Context 等 UI 类型时。如果 UI 变复杂，希望将 UI 逻辑委托给另一个类以提高可测试性并分离职责，可以创建一个普通类作为 state holder。在 UI 中创建的普通类可以依赖 Android SDK，因为它们遵循 UI 的生命周期；ViewModel 对象的存活时间更长。

关于 state holder 及其在构建 UI 时的位置，请参阅 Jetpack Compose 状态指南。

为什么使用 UDF？

UDF 对图 4 所示的状态生成循环进行建模，还把状态变化的起点、转换位置和最终读取位置分开。这使 UI 能做到它名称所表达的事情：观察状态变化来显示信息，并把变化传给 ViewModel，以传达用户意图。

换言之，UDF 提供以下能力：

  • 数据一致性。UI 具有单一事实来源。
  • 可测试性。状态来源被隔离，因此可以脱离 UI 独立测试。
  • 可维护性。状态变化遵循明确模式，变化来自用户事件以及这些事件使用的数据来源。

暴露 UI state

定义好 UI state 并确定如何管理其生成后，下一步是把生成的状态提供给 UI。

用 UDF 管理状态生成时，可以把生成的状态看作一条流，即随时间产生的多个状态版本。应通过 StateFlow 等可观察数据容器暴露 UI state。这样 UI 可以响应状态的变化，无须手动直接向 ViewModel 拉取数据。此外，容器会始终缓存最新版本的 UI state，有利于配置变化后快速恢复状态。

class NewsViewModel(
    // ...
) : ViewModel() {

    val uiState: NewsUiState = /* ... */
}UiLayer.kt

Kotlin Flow 入门请参阅 Android 上的 Kotlin Flow。使用 StateFlow 作为可观察数据容器的方法，请参阅 Jetpack Compose 中的高级状态与副作用 Codelab。

注意：在 Jetpack Compose 应用中，可以使用 Compose 的可观察 State API，如 mutableStateOf 或 snapshotFlow，来暴露 UI state。本指南中的 StateFlow 等可观察数据容器，都可以通过适当的扩展在 Compose 中读取。

即使暴露给 UI 的数据比较简单，通常也值得把它包装在一个 UI state 类型中，因为这样能体现 state holder 的输出与相应页面或 UI 元素之间的关系。随着 UI 元素变复杂，可以直接扩展 UI state 的定义，容纳渲染该 UI 元素所需的额外信息。

创建 UiState 流的一种常见方式，是通过 private set 暴露一个 mutableStateOf 属性，使状态在 ViewModel 内部可变、对 UI 只读。

class NewsViewModel(
    // ...
) : ViewModel() {

    var uiState by mutableStateOf(NewsUiState())
        private set

    // ...
}UiLayer.kt

随后，ViewModel 可以暴露在内部修改状态的方法，发布更新供 UI 读取。例如，需要执行异步操作时，可以使用 viewModelScope启动协程，在完成后更新可变状态。

class NewsViewModel(
    private val repository: NewsRepository,
    // ...
) : ViewModel() {

    var uiState by mutableStateOf(NewsUiState())
        private set

    private var fetchJob: Job? = null

    fun fetchArticles(category: String) {
        fetchJob?.cancel()
        fetchJob = viewModelScope.launch {
            try {
                val newsItems = repository.newsItemsForCategory(category)
                uiState = uiState.copy(newsItems = newsItems)
            } catch (ioe: IOException) {
                // Handle the error and notify the UI when appropriate.
                val messages = getMessagesFromThrowable(ioe)
                uiState = uiState.copy(userMessages = messages)
            }
        }
    }
}UiLayer.kt

上例中的 NewsViewModel 类尝试获取某个分类的文章，然后把成功或失败的结果反映到 UI state 中，供 UI 作出适当响应。错误处理的更多信息，请参阅在屏幕上显示错误一节。

注意：上例通过 ViewModel 上的函数修改状态，是单向数据流较常见的实现模式之一。

其他注意事项

除上述指导外，暴露 UI state 时还应考虑以下内容：

  • 用单个 UI state 对象处理相互关联的状态。这样可以减少不一致，让代码更容易理解。如果用两条不同的流暴露新闻列表和收藏数量，可能出现其中一个更新而另一个未更新的情况。使用单条流可以让两者同步保持最新。此外，一些业务逻辑需要组合多个来源。例如，只有用户已登录并且订阅了高级新闻服务时，才显示收藏按钮。可以定义如下 UI state 类：

    data class NewsUiState(
    val isSignedIn: Boolean = false,
    val isPremium: Boolean = false,
    val newsItems: List<NewsItemUiState> = listOf()
)

val NewsUiState.canBookmarkNews: Boolean get() = isSignedIn && isPremiumUiLayer.kt

    在这个声明中，收藏按钮的可见性由另外两个属性推导出来。业务逻辑越复杂，使用一个让所有属性都能立即访问的 UiState 类就越重要。

  • UI state：单条流还是多条流？选择单条流或多条流暴露 UI state 时，主要依据是所发出各项数据之间的关系。单条流最大的优势是便利与数据一致性：状态读取者在任何时刻都能取得最新信息。不过，某些情况下也适合由 ViewModel 提供独立的状态流：

    • 不相关的数据类型：渲染 UI 所需的某些状态可能完全独立。这时，把不同状态捆绑在一起的成本可能超过收益，尤其是其中一个状态比另一个更新得更频繁时。

    • UiState 差异比较：UiState 对象中的字段越多，越可能因某个字段更新而使流发出新值。UI 元素没有用于判断连续两次输出相同还是不同的差异比较机制，因此每次输出都会使 UI 元素更新。这意味着可能需要使用 Flow API 的 distinctUntilChanged() 等方法来缓解这一问题。

关于渲染与 UI state 的更多信息，请参阅可组合函数的生命周期。

读取 UI state

在 UI 中读取 UiState 对象流时，使用对应可观察数据类型的终端操作符。例如，对 Kotlin Flow 使用 collect() 方法或其变体。

在 UI 中读取可观察数据容器时，务必考虑 UI 的生命周期。可组合函数未向用户显示时，不要让 UI 观察 UI state。详情请参阅这篇博客文章。使用 Flow 时，最好通过适当的协程作用域和 collectAsStateWithLifecycle API 处理生命周期问题：

@Composable
private fun ConversationScreen(
    conversationViewModel: ConversationViewModel = viewModel()
) {

    val messages by conversationViewModel.messages.collectAsStateWithLifecycle()

    ConversationScreen(
        messages = messages,
        onSendMessage = { message: Message -> conversationViewModel.sendMessage(message) }
    )
}

@Composable
private fun ConversationScreen(
    messages: List<Message>,
    onSendMessage: (Message) -> Unit

    /* ... */

在屏幕上显示错误

错误与进行中的操作都容易用布尔值表示是否存在，因此它们在 UI 中的显示方式相似。不过，错误还可能附带要告诉用户的消息，或用于重试失败操作的关联操作。所以，进行中的操作只有加载与未加载两种情况，而错误状态可能需要用数据类建模，保存适合当前错误情境的元数据。

考虑前述获取文章时显示进度条的例子。如果操作失败，可能希望向用户显示一条或多条消息，说明哪里出了问题。

data class Message(val id: Long, val message: String)

data class NewsUiState(
    val userMessages: List<Message> = listOf(),
    // ...
)UiLayer.kt

随后，可以通过 snackbar 等 UI 元素向用户呈现错误消息。关于 UI 事件如何生成和读取，请参阅 UI events。

线程与并发

确保 ViewModel 执行的所有工作都是主线程安全的，即可以安全地从主线程调用。数据层和领域层负责把工作切换到其他线程。

如果 ViewModel 执行长时间运行的操作，它也负责把相应逻辑切换到后台线程。Kotlin 协程适合管理并发操作，Jetpack 架构组件也内置了协程支持。关于在 Android 应用中使用协程，请参阅 Android 上的 Kotlin 协程。

导航

应用导航的变化经常由类似事件的输出驱动。例如，SignInViewModel 类执行登录后，UiState 中的 isSignedIn 字段可能会设为 true。应像前面的读取 UI state一节那样读取这些触发信号，但将具体的导航执行交给 Navigation 组件。

UI 导航的更多信息，请参阅 Navigation 3。

分页

UI 通过 PagingData 类型使用 Paging 库。由于 PagingData 表示并包含可能随时间变化的条目，也就是它并非不可变类型，因此不要把它放进不可变 UI state。应改为由 ViewModel 用独立的流暴露它。

下例展示 Paging 库的 Compose API：

@Composable
fun MyScreen(flow: Flow<PagingData<String>>) {
    val lazyPagingItems = flow.collectAsLazyPagingItems()
    LazyColumn {
        items(
            lazyPagingItems.itemCount,
            key = lazyPagingItems.itemKey { it }
        ) { index ->
            val item = lazyPagingItems[index]
            Text("Item is $item")
        }
    }
}ComposeWithOtherLibraries.kt
