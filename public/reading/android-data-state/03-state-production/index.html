现代 UI 很少是静态的。用户与 UI 交互，或应用需要显示新数据时，UI 的状态就会发生变化。

本文给出生成与管理 UI state 的指导原则，帮助你理解以下内容：

  • 使用什么 API 生成 UI state。这取决于 state holder 中可用状态变化来源的性质，并遵循单向数据流原则。
  • 如何限定 UI state 生成过程的作用域，以合理使用系统资源。
  • 如何暴露 UI state，供 UI 读取。

状态生成的本质，是把发生的变化逐步应用到 UI state 上。状态一直存在，事件发生时它才变化。两者的差异如下：

事件 状态
短暂、不可预测，只存在有限的时间。 始终存在。
状态生成的输入。 状态生成的输出。
由 UI 或其他来源产生。 由 UI 读取。

可以用“状态存在，事件发生”记住这个区别。下图沿着时间线展示：事件交给相应 state holder 处理后，状态如何发生变化。

事件可以来自以下来源：

  • 用户：与应用 UI 交互时产生。
  • 其他状态变化来源：提供 UI 层、领域层或数据层应用数据的 API，例如分别来自这些层的 Snackbar 超时事件、UseCase 或 Repository。

UI state 生成管线

可以把 Android 应用的状态生成理解成一条处理流程，包含以下部分：

  • 输入：状态变化的来源，可能包括：
    • UI 层内部来源：例如用户在任务管理应用中输入待办事项标题的事件，或者提供 UI 逻辑入口、驱动 UI state 变化的 API。例如，在 Jetpack Compose 中调用 DrawerState 的 open 方法。
    • UI 层外部来源：来自领域层或数据层、引起 UI state 变化的来源，例如从 NewsRepository 加载完成的新闻，或其他事件。
    • 上述来源的组合。
  • State holder：对状态变化来源应用业务逻辑和 UI 逻辑、处理用户事件并生成 UI state 的类型。
  • 输出：应用可以渲染的 UI state，为用户提供所需信息。

状态生成 API

根据所在的管线阶段，状态生成主要使用以下两类 API：

管线阶段 API
输入 使用协程、Flow 等异步 API，在 UI 线程之外执行工作，避免 UI 卡顿。
输出 使用 Compose State、StateFlow 等可观察数据容器 API，在状态变化时使 UI 失效并重新渲染。可观察数据容器保证 UI 始终有可显示的 UI state。

输入端异步 API 的选择，比输出端可观察 API 的选择更影响整个流程，因为输入决定了这个流程能够采用哪些处理方式。

组装状态生成管线

以下各节介绍适合不同输入的状态生成技术，以及与之匹配的输出 API。每条状态生成管线都是输入与输出的组合，并且必须满足：

  • 感知生命周期：除非有明确需求，否则 UI 不可见或不活跃时，状态生成管线不应消耗任何资源。
  • 易于读取：UI 必须能轻松渲染生成的 UI state。在 Jetpack Compose 中，读取状态是 UI 的核心，因为可组合函数可以根据状态变化更新。

状态生成管线的输入

管线通过以下方式获得状态变化来源：

  • 可以同步或异步执行的一次性操作，例如调用 suspend 函数。
  • 流式 API，例如 Flows。
  • 以上方式的组合。

以下各节介绍如何为这些输入分别组装状态生成管线。

用一次性 API 作为状态变化来源

状态由可观察数据容器管理。使用 Compose 文本 API 时，尤其适合 mutableStateOf；状态管理更复杂，或需要连接其他架构组件时，可以使用 MutableStateFlow。两者都支持安全的原子更新，无论更新来自同步还是异步操作。

例如，考虑一个简单掷骰子应用中的状态更新。用户每次掷骰子都会调用同步的 Random.nextInt 方法，并把结果写入 UI state。

Compose State

@Stable
interface DiceUiState {
    val firstDieValue: Int?
    val secondDieValue: Int?
    val numberOfRolls: Int?
}

private class MutableDiceUiState: DiceUiState {
    override var firstDieValue: Int? by mutableStateOf(null)
    override var secondDieValue: Int? by mutableStateOf(null)
    override var numberOfRolls: Int by mutableStateOf(0)
}

class DiceRollViewModel : ViewModel() {

    private val _uiState = MutableDiceUiState()
    val uiState: DiceUiState = _uiState

    // Called from the UI
    fun rollDice() {
        _uiState.firstDieValue = Random.nextInt(from = 1, until = 7)
        _uiState.secondDieValue = Random.nextInt(from = 1, until = 7)
        _uiState.numberOfRolls = _uiState.numberOfRolls + 1
    }
}

StateFlow

data class DiceUiState(
    val firstDieValue: Int? = null,
    val secondDieValue: Int? = null,
    val numberOfRolls: Int = 0,
)

class DiceRollViewModel : ViewModel() {

    private val _uiState = MutableStateFlow(DiceUiState())
    val uiState: StateFlow<DiceUiState> = _uiState.asStateFlow()

    // Called from the UI
    fun rollDice() {
        _uiState.update { currentState ->
            currentState.copy(
            firstDieValue = Random.nextInt(from = 1, until = 7),
            secondDieValue = Random.nextInt(from = 1, until = 7),
            numberOfRolls = currentState.numberOfRolls + 1,
            )
        }
    }
}

从异步调用修改 UI state

需要等待异步结果时，在适当的 CoroutineScope 中启动协程。CoroutineScope 取消后，相应工作就可以停止。state holder 拿到挂起调用的结果，再写入向 UI 提供状态的可观察 API。

例如，架构示例中的 AddEditTaskViewModel：挂起的 saveTask 方法异步保存任务时，MutableStateFlow 上的 update 方法把状态变化传播到 UI state。

Compose State

@Stable
interface AddEditTaskUiState {
    val title: String
    val description: String
    val isTaskCompleted: Boolean
    val isLoading: Boolean
    val userMessage: String?
    val isTaskSaved: Boolean
}

private class MutableAddEditTaskUiState : AddEditTaskUiState() {
    override var title: String by mutableStateOf("")
    override var description: String by mutableStateOf("")
    override var isTaskCompleted: Boolean by mutableStateOf(false)
    override var isLoading: Boolean by mutableStateOf(false)
    override var userMessage: String? by mutableStateOf<String?>(null)
    override var isTaskSaved: Boolean by mutableStateOf(false)
}

class AddEditTaskViewModel(...) : ViewModel() {

   private val _uiState = MutableAddEditTaskUiState()
   val uiState: AddEditTaskUiState = _uiState

   private fun createNewTask() {
        viewModelScope.launch {
            val newTask = Task(uiState.value.title, uiState.value.description)
            try {
                tasksRepository.saveTask(newTask)
                // Write data into the UI state.
                _uiState.isTaskSaved = true
            }
            catch(cancellationException: CancellationException) {
                throw cancellationException
            }
            catch(exception: Exception) {
                _uiState.userMessage = getErrorMessage(exception))
            }
        }
    }
}

StateFlow

data class AddEditTaskUiState(
    val title: String = "",
    val description: String = "",
    val isTaskCompleted: Boolean = false,
    val isLoading: Boolean = false,
    val userMessage: String? = null,
    val isTaskSaved: Boolean = false
)

class AddEditTaskViewModel(...) : ViewModel() {

   private val _uiState = MutableStateFlow(AddEditTaskUiState())
   val uiState: StateFlow<AddEditTaskUiState> = _uiState.asStateFlow()

   private fun createNewTask() {
        viewModelScope.launch {
            val newTask = Task(uiState.value.title, uiState.value.description)
            try {
                tasksRepository.saveTask(newTask)
                // Write data into the UI state.
                _uiState.update {
                    it.copy(isTaskSaved = true)
                }
            }
            catch(cancellationException: CancellationException) {
                throw cancellationException
            }
            catch(exception: Exception) {
                _uiState.update {
                    it.copy(userMessage = getErrorMessage(exception))
                }
            }
        }
    }
}
注意：在 AAC 的 ViewModel 的 viewModelScope 中启动的协程，无论正常还是异常，都会一直执行到结束。UI 是否可见不影响这一点，除非明确取消协程或清除 ViewModel。大多数请求持续时间较短，因此通常没有问题。不要用 viewModelScope 执行持续 5 秒或更久的请求，而应通过 WorkManager 将其排入延后执行或长时间运行的工作。

从后台线程修改 UI state

生成 UI state 时，最好在主调度器上启动协程，即在下面代码片段的 withContext 块之外启动。不过，如果需要在其他后台上下文中更新 UI state，可以按以下方式处理：

  • 使用 withContext 方法，在不同的并发上下文中执行协程。
  • 使用 MutableStateFlow 时，照常调用 update 方法。
  • 使用 Compose State 时，调用 Snapshot.withMutableSnapshot 方法，保证并发上下文中的 State 更新具有原子性。

例如，在下面的 DiceRollViewModel 片段中，假设 SlowRandom.nextInt 是一个计算密集的 suspend 函数，需要从 CPU 密集型协程中调用。

Compose State

class DiceRollViewModel(
    private val defaultDispatcher: CoroutineScope = Dispatchers.Default
) : ViewModel() {

    private val _uiState = MutableDiceUiState()
    val uiState: DiceUiState = _uiState

  // Called from the UI
  fun rollDice() {
        viewModelScope.launch() {
            // Other Coroutines that may be called from the current context
            …
            withContext(defaultDispatcher) {
                Snapshot.withMutableSnapshot {
                    _uiState.firstDieValue = SlowRandom.nextInt(from = 1, until = 7)
                    _uiState.secondDieValue = SlowRandom.nextInt(from = 1, until = 7)
                    _uiState.numberOfRolls = _uiState.numberOfRolls + 1
                }
            }
        }
    }
}

StateFlow

class DiceRollViewModel(
    private val defaultDispatcher: CoroutineScope = Dispatchers.Default
) : ViewModel() {

    private val _uiState = MutableStateFlow(DiceUiState())
    val uiState: StateFlow<DiceUiState> = _uiState.asStateFlow()

  // Called from the UI
  fun rollDice() {
        viewModelScope.launch() {
            // Other Coroutines that may be called from the current context
            …
            withContext(defaultDispatcher) {
                _uiState.update { currentState ->
                    currentState.copy(
                        firstDieValue = SlowRandom.nextInt(from = 1, until = 7),
                        secondDieValue = SlowRandom.nextInt(from = 1, until = 7),
                        numberOfRolls = currentState.numberOfRolls + 1,
                    )
                }
            }
        }
    }
}
注意：如果所有启动的协程都需要在其他上下文中执行，可以直接调用 viewModelScope.launch(defaultDispatcher){ }。
警告：在非 UI 线程中更新 Compose State 而不使用 Snapshot.withMutableSnapshot{ }，可能导致生成的状态不一致。

用流式 API 作为状态变化来源

当多个来源各自持续产生新值时，可以把它们的输出组合成一份一致的整体，作为 UI state。

使用 Kotlin Flow 时，可以通过 combine 函数做到这一点。“Now in Android”示例的 InterestsViewModel 中展示了这种用法：

class InterestsViewModel(
    authorsRepository: AuthorsRepository,
    topicsRepository: TopicsRepository
) : ViewModel() {

    val uiState = combine(
        authorsRepository.getAuthorsStream(),
        topicsRepository.getTopicsStream(),
    ) { availableAuthors, availableTopics ->
        InterestsUiState.Interests(
            authors = availableAuthors,
            topics = availableTopics
        )
    }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = InterestsUiState.Loading
    )
}
注意：可以用 stateIn 操作符，把组合后的 Flow 转换成 StateFlow，作为 UI state 的可观察 API。

用 stateIn 操作符创建 StateFlows，可以让 UI 更精细地控制状态生成管线是否活跃，因为管线可能只需在 UI 可见时保持活跃。

  • 如果以感知生命周期的方式收集 Flow，且管线只需在 UI 可见时活跃，应使用 SharingStarted.WhileSubscribed。
  • 如果用户还有可能返回 UI 时，管线就需要保持活跃，例如 UI 留在返回栈中或位于屏幕外的另一标签页，应使用 SharingStarted.Lazily。

如果不适合聚合基于流的状态来源，Kotlin Flow 等流式 API 还提供合并、展平等丰富的转换操作，帮助把流处理成 UI state。

要点：大多数情况下，combine 是从流式 API 生成状态的推荐方式。

同时用一次性和流式 API 作为状态变化来源

如果状态同时来自一次性调用和持续的数据流，就应以流为组织基础：把一次性调用转换为流，或把调用结果写入流，再沿用前面的流式处理方式。

使用 Flow 时，通常需要创建一个或多个私有的底层 MutableStateFlow 实例来传播状态变化。也可以从 Compose State 创建 snapshot flow。

考虑 architecture-samples 仓库中的 TaskDetailViewModel。它的 UI state 依赖当前任务的流（_task）以及一个在任务删除时更新的一次性来源（_isTaskDeleted）。需要这个标记，才能区分任务因 ID 错误而在数据库中找不到，还是因用户刚刚删除它而找不到：

Compose State

class TaskDetailViewModel @Inject constructor(
    private val tasksRepository: TasksRepository,
    savedStateHandle: SavedStateHandle
) : ViewModel() {

    private var _isTaskDeleted by mutableStateOf(false)
    private val _task = tasksRepository.getTaskStream(taskId)

    val uiState: StateFlow<TaskDetailUiState> = combine(
        snapshotFlow { _isTaskDeleted },
        _task
    ) { isTaskDeleted, taskAsync ->
        TaskDetailUiState(
            task = taskAsync.data,
            isTaskDeleted = isTaskDeleted
        )
    }
        // Convert the result to the appropriate observable API for the UI
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = TaskDetailUiState()
        )

    fun deleteTask() = viewModelScope.launch {
        tasksRepository.deleteTask(taskId)
        _isTaskDeleted = true
    }
}

StateFlow

class TaskDetailViewModel @Inject constructor(
    private val tasksRepository: TasksRepository,
    savedStateHandle: SavedStateHandle
) : ViewModel() {

    private val _isTaskDeleted = MutableStateFlow(false)
    private val _task = tasksRepository.getTaskStream(taskId)

    val uiState: StateFlow<TaskDetailUiState> = combine(
        _isTaskDeleted,
        _task
    ) { isTaskDeleted, taskAsync ->
        TaskDetailUiState(
            task = taskAsync.data,
            isTaskDeleted = isTaskDeleted
        )
    }
        // Convert the result to the appropriate observable API for the UI
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5_000),
            initialValue = TaskDetailUiState()
        )

    fun deleteTask() = viewModelScope.launch {
        tasksRepository.deleteTask(taskId)
        _isTaskDeleted.update { true }
    }
}
注意：Compose State 通过 snapshotFlow API 转换为 Flow。

状态生成管线的输出类型

UI state 输出 API 的选择及其呈现方式，很大程度上取决于应用用于渲染 UI 的 API，例如 Compose。Jetpack Compose 是构建原生 UI 的推荐现代工具包，需要考虑以下事项：

  • 以感知生命周期的方式读取状态。
  • state holder 应通过一个还是多个字段暴露状态。

下表总结了使用 Jetpack Compose 时，状态生成管线应采用的 API：

输入 输出
一次性 API StateFlow 或 Compose State
流式 API StateFlow
一次性与流式 API StateFlow

初始化状态生成管线

初始化状态生成流程，就是准备它运行所需的初始条件。例如，为新闻详情页提供 id，或启动一次异步加载。

尽可能等到需要时再初始化，以节省资源。这通常意味着有读取者开始使用输出后才启动。Flow 可以通过 stateIn 的 started 参数控制；不适用时，则定义幂等的 initialize 函数，明确启动流程，如下例。

class MyViewModel : ViewModel() {

    private var initializeCalled = false

    // This function is idempotent provided it is only called from the UI thread.
    @MainThread
    fun initialize() {
        if(initializeCalled) return
        initializeCalled = true

        viewModelScope.launch {
            // seed the state production pipeline
        }
    }
}
警告：不要在 ViewModel 的 init 块或构造器中启动异步操作。必须避免让创建对象产生启动异步操作的副作用，因为异步代码可能在对象完全初始化前就读取或写入它。这也称为对象泄漏，可能导致隐蔽且难以诊断的错误。使用 Compose State 时尤其要注意：如果 ViewModel 持有 Compose State 字段，不要在 ViewModel 的 init 块中启动更新这些字段的协程，否则可能发生 IllegalStateException。
