Activity 与生命周期

生命周期不是一张要背的回调表，而是系统把“创建、可见、可交互、失去焦点、不可见、销毁”这些状态变化通知给页面实例的协议。

学习主线

先判断用户现在能否看见、能否交互，再判断 Activity 实例是否仍存在；最后才决定资源、播放和状态分别在哪个回调处理。

一条主链，六个关键回调

onCreate创建实例，建立 UI
→
onStart页面可见
→
onResume前台可交互
→
onPause失去前台交互
→
onStop页面不可见
→
onDestroy实例被销毁

`onCreate()` 负责这次 Activity 实例生命中的基础初始化；`onStart()` 后页面可见；`onResume()` 表示它位于前台并能与用户交互。离开时大致反向经过 `onPause()`、`onStop()`，实例永久结束或因配置变化重建时会进入 `onDestroy()`。

不要把 onDestroy() 当成可靠的“应用退出通知”进程可能被系统直接终止，无法保证你的 Activity 总有机会执行 `onDestroy()`。必须持久化的业务数据不能等到这里才保存。

三条必须能独立画出的链

场景典型回调顺序实例是否换了
首次进入onCreate → onStart → onResume新实例
按 Home 后返回onPause → onStop → onRestart → onStart → onResume通常还是原实例；但后台期间进程可能被杀
默认旋转重建旧实例暂停、停止、销毁；新实例重新 onCreate → onStart → onResume换成新实例

这里故意说“典型”而不是“所有设备所有时刻绝对固定”。多窗口、对话框、系统版本和具体导航都会影响精确顺序。学习时先用可见性与交互状态推导，再用日志验证实际设备。

把播放行为放回用户体验

假设贴纸时长编辑页带预览播放：页面进入可交互状态时可以恢复只属于前台的预览；失去焦点或不可见时应暂停消耗资源的能力。但播放进度、用户已编辑的时长和 NLE 业务数据不是同一种状态，不能因为都出现在页面上就一起塞进 Activity 字段。

实例生命周期

这一个 Activity 对象从创建到销毁，旋转可能结束它并创建另一个。

可见性

Started 通常表示可见；是否完整可见还要结合多窗口和覆盖场景判断。

交互性

Resumed 表示位于前台、可以与用户交互，适合前台独占能力。

进程生命周期

由系统按组件重要性和资源需要管理，不等于任何单个 Activity 的生命周期。

最小代码：用日志验证，不凭感觉背

class MainActivity : ComponentActivity() {
    private fun log(event: String) = Log.d("LifecycleDemo", event)

    override fun onCreate(state: Bundle?) {
        super.onCreate(state)
        log("onCreate instance=${hashCode()}")
        setContent { Text("旋转屏幕并观察日志") }
    }

    override fun onStart() { super.onStart(); log("onStart") }
    override fun onResume() { super.onResume(); log("onResume") }
    override fun onPause() { log("onPause"); super.onPause() }
    override fun onStop() { log("onStop"); super.onStop() }
    override fun onDestroy() { log("onDestroy"); super.onDestroy() }
}

`hashCode()` 只用于这个练习中观察对象是否变化，不是生产环境的页面业务 ID。

练习 2：选择暂停点

预览播放只允许在页面可交互时运行。你会在哪些状态开启和暂停？为什么不能只在 `onDestroy()` 停止？

展开参考答案

通常在进入 Resumed 时启用、离开 Resumed 时暂停，并结合 lifecycle-aware 组件实现。只等 `onDestroy()` 太晚：页面可能已不可交互甚至不可见，且进程终止时不保证回调它。
