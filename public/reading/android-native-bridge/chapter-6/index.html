主线程、Looper、MessageQueue 与 Handler

主线程不是“专门画 UI 的一根线”这么简单：组件回调、输入分发、绘制和你投递的任务都要在同一条执行序列中获得时间。

学习主线

Handler 负责把任务放进某个 Looper 所属线程的队列；Looper 持续取出任务执行。任务投到主线程不等于开了后台线程。

从后台结果回到 UI

后台线程完成耗时计算
→
Handler.post投递 Runnable
→
MessageQueue等待轮到它
→
Looper取出并分发
→
主线程安全更新 UI

应用组件首次启动且进程不存在时，Android 创建应用进程及一条主线程。默认情况下，同一应用的组件运行在同一进程和主线程中。生命周期回调、点击事件和 View 绘制都可能在这里执行。

四个名字各自负责什么

主线程

执行组件回调和大多数 UI 工具包操作；同一时刻只能顺序做一件事。

MessageQueue

保存待执行的 Message / Runnable；“进入队列”不代表立刻执行。

Looper

绑定线程，持续从该线程的队列取任务并分发。

Handler

绑定一个 Looper，向它的队列投递任务或消息，并在对应线程处理。

Handler(Looper.getMainLooper()).post { ... } 不会把耗时任务变快它只是把任务排进主线程队列。如果 Runnable 内做图片解码、数据库查询或大计算，仍会堵住输入与绘制。

为什么会掉帧和 ANR

主线程若忙于一个长任务，后面的触摸、生命周期和绘制任务只能等待。短暂等待表现为掉帧或触摸延迟；持续阻塞可能让系统判定应用无响应。核心规则只有两条：

  1. 不要阻塞 UI 线程。
  2. 不要从工作线程直接操作 Android UI 工具包。

协程没有改变这套底层约束。Dispatchers.IO 或其他后台 dispatcher 帮你把阻塞工作移开，回到 Dispatchers.Main 更新 UI；理解 Handler/Looper 后，协程代码不再像魔法。

最小代码：后台计算，主线程显示

class MainActivity : AppCompatActivity() {
    private val mainHandler = Handler(Looper.getMainLooper())

    private fun loadPreview() {
        Thread {
            val result = decodePreview() // 模拟耗时工作，不操作 View

            mainHandler.post {
                findViewById<TextView>(R.id.status).text = result
            }
        }.start()
    }

    private fun decodePreview(): String {
        Thread.sleep(500) // 仅用于演示耗时，生产代码不要这样模拟
        return "预览已就绪"
    }
}

示例用最原始的 Thread + Handler 展示机制，不代表生产项目应手写线程管理。后续 Unit 5 会用协程、Repository 和可取消作用域组织真实异步工作。

延时任务不是精准计时器

postDelayed 表示“不早于某个时间进入可执行条件”，不是保证那一毫秒准时运行。如果前面有长任务，它仍要排队。因此播放进度和动画不能只靠累加固定延时间隔推断真实时间，应使用合适的时钟或帧回调。

动手练习

练习 1：判断运行线程

上面示例中的 decodePreview()、mainHandler.post {} 的 lambda、TextView.text = ... 分别在哪个线程执行？

展开参考答案

decodePreview() 在新建工作线程；post 只是从工作线程投递；其 lambda 随后由主 Looper 在主线程执行，因此 UI 更新也发生在主线程。

练习 2：找到卡顿因果链

点击事件里直接解析 200 MB 文件，随后 Handler post 一个 Toast。为什么 Toast 也迟迟不显示？

展开参考答案

点击回调和文件解析占住主线程；Toast 的任务即使进入主队列，也必须等当前长任务返回。Handler 不会抢占正在执行的代码。
