Monad 与效应

Bartosz Milewski

函数返回类型的不同“装饰”，可以把终止、非确定性、状态、异常、续延和 I/O 重新表达为纯函数；Monad 负责让这些装饰后的函数继续组合。

既然已经知道 Monad 的用途——让装饰后的函数可以复合——真正有趣的问题就是：为什么装饰后的函数在函数式编程中如此重要？我们已经见过 Writer Monad：装饰让我们能够跨多次函数调用创建并累积日志。原本需要不纯函数（例如访问并修改某种全局状态）解决的问题，被纯函数解决了。

问题

下面是一份相似问题的简短清单，摘自 Eugenio Moggi 的奠基论文；传统上，它们都通过放弃函数纯度解决：

  • 偏性（partiality）：可能永不终止的计算；
  • 非确定性（nondeterminism）：可能返回多个结果的计算；
  • 副作用（side effect）：访问或修改状态的计算；
    • 只读状态，即环境；
    • 只写状态，即日志；
    • 读写状态；
  • 异常：可能失败的偏函数；
  • 续延：保存程序状态并在需要时恢复的能力；
  • 交互式输入；
  • 交互式输出。

真正令人震撼的是，这些问题全都可以用同一个聪明技巧解决：转向装饰后的函数。当然，每种情形中的装饰完全不同。

必须意识到，在这个阶段并不要求装饰具备 Monad 结构。只有当我们坚持要求复合——能够把一个装饰后的函数分解成更小的装饰后函数——时，才需要 Monad。同样，因为每种装饰不同，Monad 复合的实现也不同，但总体模式相同。它是一个非常简单的模式：满足结合律并配有恒等元的复合。

下一节包含大量 Haskell 示例。如果急于回到范畴论，或者已经熟悉 Haskell 的 Monad 实现，可以略读甚至跳过。

解决方案

先分析使用 Writer Monad 的方式。我们从完成某项任务的纯函数开始——给定参数，它产生某个输出。随后用另一个函数替换它，把原输出与字符串配成一对来装饰它。这就是日志问题的解决方案。

但不能止步于此，因为我们通常不想处理单体式解决方案。需要把一个产生日志的函数分解成更小的产生日志函数。正是这些小函数的复合把我们引向 Monad。

真正惊人的是，同样的返回类型装饰模式适用于大量通常需要放弃纯度的问题。下面逐项检查清单，为每个问题找出相应装饰。

偏性

对每个可能不终止的函数，把其返回类型改成“提升类型（lifted type）”——它包含原类型的所有值，外加特殊的“底”值 ⊥。例如，作为集合的 Bool 有两个元素 True、False；提升后的 Bool 有三个元素。返回提升 Bool 的函数可能产生 True 或 False，也可能永远执行下去。

有趣的是，在 Haskell 这样的惰性语言中，一个永不结束的函数实际上可能“返回”一个值，而且这个值还能传给下一个函数。我们把这个特殊值称为底（bottom）。只要不显式需要它（例如对它做模式匹配或把它输出），它就能四处传递而不会阻塞程序。因为每个 Haskell 函数都可能不终止，Haskell 的所有类型都被假定为提升类型。这就是我们常谈 Haskell（提升）类型与函数的范畴 Hask，而不是更简单的 Set 的原因。不过 Hask 是否真是范畴并不明确，参见 Andrej Bauer 的文章。

非确定性

若函数可能返回多个不同结果，不妨一次把它们全部返回。从语义上说，非确定函数等价于返回结果列表的函数。在有惰性求值与垃圾回收的语言中，这非常合理。例如，只需一个值时取表头即可，表尾永远不会求值；需要随机值时，用随机数生成器选择列表第 n 个元素。惰性甚至允许返回无限结果列表。

列表 Monad 是 Haskell 对非确定计算的实现，其中 join 实现为 concat。记住，join 应把容器的容器展平；concat 把列表的列表连接成单一列表。return 创建单元素列表：

instance Monad [] where
    join = concat
    return x = [x]

列表 Monad 的 bind 由一般公式给出：先 fmap，再 join；这里得到：

as >>= k = concat (fmap k as)

自身产生列表的函数 k 会应用到列表 as 的每个元素，结果是列表的列表，再用 concat 展平。

从程序员角度看，处理列表比在循环中调用非确定函数，或实现返回迭代器的函数更容易（不过在现代 C++ 中，返回惰性 range 几乎等价于在 Haskell 中返回列表）。

创造性使用非确定性的好例子是游戏编程。例如，计算机与人类下棋时无法预测对手下一步，但可以生成所有可能走法的列表，并逐一分析。同样，非确定解析器可以为给定表达式生成所有可能解析的列表。

尽管可以把返回列表的函数解释为非确定函数，列表 Monad 的用途要广泛得多。把产生列表的计算拼接起来，是命令式编程中迭代构造——循环——的完美函数式替代。单个循环常可改写为 fmap，把循环体应用于列表每个元素；列表 Monad 的 do 记法可替换复杂嵌套循环。

我最喜欢的例子，是生成勾股数组——能够构成直角三角形边长的正整数三元组：

triples = do
    z <- [1..]
    x <- [1..z]
    y <- [x..z]
    guard (x^2 + y^2 == z^2)
    return (x, y, z)

第一行表示 z 从正数无限列表 [1..] 中得到一个元素；随后 x 从 1 到 z 的有限列表 [1..z] 中得到元素；最后 y 从 x 到 z 的列表中得到元素。现在有三个数 1≤x≤y≤z。函数 guard 接受 Bool 表达式，返回单元列表：

guard :: Bool -> [()]
guard True  = [()]
guard False = []

这个函数属于更大的 MonadPlus 类型类，这里用于过滤掉非勾股数组。查看 bind（或相关运算符 >>）的实现会发现，输入空列表时会产生空列表；输入非空列表——这里是包含单元值的单元素列表 [()]——时，bind 调用续延，也就是 return (x,y,z)，产生只含一个已验证勾股数组的列表。外围 bind 会把所有这些单元素列表连接起来，形成最终的无限结果。当然，triples 的调用者永远无法消费整个列表，但 Haskell 是惰性的，所以无妨。

通常需要三层嵌套循环的问题，借助列表 Monad 与 do 记法大幅简化。还不止如此，Haskell 允许用列表推导进一步简化：

triples = [(x, y, z) | z <- [1..]
                     , x <- [1..z]
                     , y <- [x..z]
                     , x^2 + y^2 == z^2]

这只是列表 Monad（严格说是 MonadPlus）的又一层语法糖。

你可能会在其他函数式或命令式语言中，以生成器与协程的面貌看到类似构造。

只读状态

能只读访问某种外部状态或环境的函数，总能换成把环境作为额外参数的函数。纯函数 (a,e)->b（e 是环境类型）乍看不像 Kleisli 箭头；但一旦柯里化为 a->(e->b)，就会认出其装饰是老朋友 Reader 函子：

newtype Reader e a = Reader (e -> a)

可以把返回 Reader 的函数解释为生成一个迷你可执行程序：给定环境就产生所需结果的动作。辅助函数 runReader 用于执行该动作：

runReader :: Reader e a -> e -> a
runReader (Reader f) e = f e

不同环境值可能产生不同结果。

注意，返回 Reader 的函数与 Reader 动作本身都是纯的。

实现 Reader Monad 的 bind，先注意必须产生一个接受环境 e 并生成 b 的函数：

ra >>= k = Reader (\e -> ...)

在 lambda 内，可以执行动作 ra 产生 a：

ra >>= k = Reader (\e -> let a = runReader ra e
                         in ...)

再把 a 传给续延 k，得到新动作 rb：

ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in ...)

最后，用同一个环境 e 运行 rb：

ra >>= k = Reader (\e -> let a  = runReader ra e
                             rb = k a
                         in runReader rb e)

实现 return 时，创建一个忽略环境并原样返回值的动作。

把一切放在一起，再稍作简化，得到：

instance Monad (Reader e) where
    ra >>= k = Reader (\e -> runReader (k (runReader ra e)) e)
    return x = Reader (\e -> x)

只写状态

这就是最初的日志例子。装饰由 Writer 函子给出：

newtype Writer w a = Writer (a, w)

为完整起见，还有一个平凡的辅助函数 runWriter，用于拆开数据构造器：

runWriter :: Writer w a -> (a, w)
runWriter (Writer (a, w)) = (a, w)

如前所见，为让 Writer 可组合，w 必须是幺半群。下面用 bind 写出 Writer 的 Monad 实例：

instance (Monoid w) => Monad (Writer w) where
    (Writer (a, w)) >>= k = let (a', w') = runWriter (k a)
                            in Writer (a', w `mappend` w')
    return a = Writer (a, mempty)

状态

能读写状态的函数结合了 Reader 与 Writer 的装饰。可以把它们想成纯函数：把状态作为额外参数，并产生“值/状态”对作为结果，即 (a,s)->(b,s)。柯里化后得到 Kleisli 箭头形式 a->(s->(b,s))，装饰抽象在 State 函子中：

newtype State s a = State (s -> (a, s))

同样，可把 Kleisli 箭头看成返回动作，再用辅助函数执行：

runState :: State s a -> s -> (a, s)
runState (State f) s = f s

不同初始状态不仅可能产生不同结果，还可能产生不同最终状态。

State Monad 的 bind 实现与 Reader 很相似，只是必须小心地在每一步传递正确状态：

sa >>= k = State (\s -> let (a, s') = runState sa s
                            sb = k a
                        in runState sb s')

完整实例为：

instance Monad (State s) where
    sa >>= k = State (\s -> let (a, s') = runState sa s
                            in runState (k a) s')
    return a = State (\s -> (a, s))

还有两个用于操纵状态的辅助 Kleisli 箭头。一个取出状态供检查：

get :: State s s
get = State (\s -> (s, s))

另一个用全新状态替换它：

put :: s -> State s ()
put s' = State (\s -> ((), s'))

异常

会抛异常的命令式函数其实是偏函数——对某些参数值没有定义。用纯的全函数实现异常，最简单的方式是使用 Maybe 函子。把偏函数扩展为全函数：有意义时返回 Just a，否则返回 Nothing。若还想返回失败原因的信息，可以改用 Either 函子（例如把第一个类型固定为 String）。

下面是 Maybe 的 Monad 实例：

instance Monad Maybe where
    Nothing >>= k = Nothing
    Just a  >>= k = k a
    return a = Just a

注意，Maybe 的 Monad 复合在检测到错误时，会正确地短路计算（续延 k 永远不会调用）。这正是对异常的预期行为。

续延

这就是求职面试后可能遇到的“别打给我们，我们会打给你！”情形。你不会直接得到答案，而要提供一个处理器——一个在结果就绪时被调用的函数。这种编程风格在调用时还不知道结果的情形尤其有用，例如结果正由另一线程计算，或从远程网站传来。这里的 Kleisli 箭头返回一个接受处理器的函数，处理器表示“计算的剩余部分”：

data Cont r a = Cont ((a -> r) -> r)

处理器 a->r 最终被调用时产生 r 类型结果，该结果在最后返回。续延由结果类型参数化。（实践中，它常是某种状态指示器。）

还有一个执行 Kleisli 箭头所返回动作的辅助函数。它接受处理器并传给续延：

runCont :: Cont r a -> (a -> r) -> r
runCont (Cont k) h = k h

续延的复合出了名地困难，因此通过 Monad——尤其是 do 记法——处理它们，优势巨大。

推导 bind 的实现。先看去掉包装后的签名：

(>>=) :: ((a -> r) -> r) ->
         (a -> (b -> r) -> r) ->
         ((b -> r) -> r)

目标是创建接受处理器 b->r 并产生结果 r 的函数，所以从这里开始：

ka >>= kab = Cont (\hb -> ...)

在 lambda 内，要用适当处理器调用函数 ka，该处理器表示其余计算。把处理器实现为 lambda：

runCont ka (\a -> ...)

这里其余计算先用 a 调用 kab，再把 hb 传给得到的动作 kb：

runCont ka (\a -> let kb = kab a
                  in runCont kb hb)

可以看到，续延由内向外复合；最终处理器 hb 从计算最内层调用。完整实例是：

instance Monad (Cont r) where
    ka >>= kab = Cont (\hb -> runCont ka (\a -> runCont (kab a) hb))
    return a = Cont (\ha -> ha a)

交互式输入

这是最棘手的问题，也是许多困惑的来源。显然，如果 getChar 返回键盘输入的字符，它就不可能纯。但如果它把字符放在容器里返回呢？只要没有办法从容器中取出字符，就可以声称函数是纯的。每次调用 getChar 都返回完全相同的容器；概念上，该容器包含所有可能字符的叠加态。

若熟悉量子力学，理解这个类比应该不难。这就像装着薛定谔的猫的盒子——只不过根本无法打开或窥视盒子内部。盒子由特殊的内置 IO 函子定义。在例子中，getChar 可声明为 Kleisli 箭头：

getChar :: () -> IO Char

（实际上，从单元类型出发的函数等价于选取返回类型的一个值，所以声明简化为 getChar :: IO Char。）

作为函子，IO 允许用 fmap 操纵内容；作为函子，它也能保存任意类型内容，不只是字符。真正的用途在于，Haskell 中 IO 是 Monad，所以能复合产生 IO 对象的 Kleisli 箭头。

你可能以为 Kleisli 复合允许窥视 IO 对象的内容（若继续量子类比，就是“使波函数坍缩”）。确实，可以把 getChar 与另一个 Kleisli 箭头复合，后者接受字符并把它转成整数。问题是，第二支 Kleisli 箭头只能把整数作为 IO Int 返回；你仍得到所有可能整数的叠加态，以此类推。薛定谔的猫永远不会从袋子里出来。一旦进入 IO Monad，就无法离开。IO 没有与 runState 或 runReader 对应的东西——没有 runIO！

除了与另一支 Kleisli 箭头复合，还能怎样处理 Kleisli 箭头的结果——IO 对象？可以从 main 返回它。Haskell 中 main 的签名是：

main :: IO ()

也可以把它看作 Kleisli 箭头：

main :: () -> IO ()

从这个视角看，Haskell 程序只是 IO Monad 中一支巨大的 Kleisli 箭头。可以用 Monad 复合，从较小 Kleisli 箭头组合出它。怎样处理最终 IO 对象（也叫 IO 动作），由运行时系统负责。

注意，箭头本身是纯函数——一路到底全是纯函数。脏活被交给系统。系统最终执行 main 返回的 IO 动作时，会做读取用户输入、修改文件、打印讨厌消息、格式化磁盘等各种坏事。Haskell 程序从不弄脏自己的手（好吧，除非调用 unsafePerformIO，但那是另一回事）。

当然，因为 Haskell 是惰性的，main 几乎立即返回，脏活随即开始。在执行 IO 动作期间，纯计算结果会按需请求并求值。因此现实中，程序执行是纯（Haskell）代码与脏（系统）代码的交错。

IO Monad 还有一种更离奇却完全合理的数学模型：把整个宇宙当作程序中的对象。注意，命令式模型在概念上把宇宙视为外部全局对象，所以执行 I/O 的过程通过与它交互而产生副作用；它们既能读取也能修改宇宙状态。

我们已经知道怎样在函数式编程中处理状态——使用 State Monad。但与简单状态不同，宇宙状态无法用标准数据结构轻易描述。不过，只要永远不直接与它交互，就不必描述。只需假设存在类型 RealWorld，并且运行时凭借某种宇宙工程奇迹，可以提供这个类型的对象。IO 动作只是一个函数：

type IO a = RealWorld -> (a, RealWorld)

或者用 State Monad 表达：

type IO = State RealWorld

不过，IO Monad 的 >=> 与 return 必须内建于语言。

交互式输出

同一个 IO Monad 也用于封装交互式输出。RealWorld 被认为包含全部输出设备。你可能会问：为什么不能直接从 Haskell 调用输出函数，并假装它们什么也没做？例如，为什么是：

putStr :: String -> IO ()

而不是更简单的：

putStr :: String -> ()

有两个原因。Haskell 是惰性的，所以永远不会调用输出——这里是单元对象——未被使用的函数。即使它不惰性，也可以自由改变这些调用的顺序，从而打乱输出。在 Haskell 中，强制两个函数顺序执行的唯一办法是建立数据依赖：一个函数的输入必须依赖另一个的输出。在 IO 动作之间传递 RealWorld 会强制排序。

概念上，在下面的程序中：

main :: IO ()
main = do
    putStr "Hello "
    putStr "World!"

打印“World!”的动作，接收到的是屏幕上已经有“Hello ”的宇宙；它输出一个屏幕上出现“Hello World!”的新宇宙。

结论

当然，我只是触及 Monad 编程的表面。Monad 不仅用纯函数完成命令式编程通常靠副作用完成的工作，而且提供了高度控制与类型安全。但它也并非没有缺点。对 Monad 最大的抱怨，是它们彼此不容易组合。诚然，可以用 Monad Transformer 库组合大多数基础 Monad；创建一个把状态与异常等结合起来的 Monad 栈相对容易，但并不存在任意 Monad 叠加的通用公式。
