Kleisli 范畴

Bartosz Milewski · 2014 年 12 月 23 日

副作用不必藏在全局可变状态里。把附加信息放进返回类型，再重新定义函数复合，就能在纯函数世界中表达日志等效应；这正是 Kleisli 范畴提供的自由度。

你已经看到，怎样把类型与纯函数建模为范畴。我也提到过，范畴论中有办法对副作用或非纯函数建模。下面看一个例子：记录日志或跟踪自身执行过程的函数。在命令式语言中，这种功能很可能通过修改某种全局状态来实现，例如：

string logger;

bool negate(bool b) {
     logger += "Not so! ";
     return !b;
}

你知道这不是纯函数，因为它的记忆化版本无法产生日志。这个函数具有副作用。

现代编程会尽可能远离全局可变状态——哪怕只是因为并发会让它复杂不堪。你也绝不会把这样的代码放进程序库。

幸运的是，我们可以把这个函数改成纯函数。只需显式地传入、传出日志。我们增加一个字符串参数，并把常规输出与包含更新后日志的字符串配成一对：

pair<bool, string> negate(bool b, string logger) {
     return make_pair(!b, logger + "Not so! ");
}

这个函数是纯的：它没有副作用；每次用相同参数调用，都会返回相同的 pair；如有必要，也可以将它记忆化。不过，考虑到日志具有累积性质，你必须记忆所有可能通向某次调用的历史。下面两次调用需要不同的记忆条目：

negate(true, "It was the best of times. ");

以及：

negate(true, "It was the worst of times. ");

其他历史也都如此。

这也不是一个很好的程序库函数接口。调用者可以自由忽略返回类型中的字符串，因此这一点负担不大；但他们被迫传入字符串，这可能很不方便。

有没有一种侵入性更低的方式来做同一件事？能否分离关注点？在这个简单例子中，negate 的主要目的，是把一个布尔值变成另一个布尔值，日志记录只是次要任务。诚然，记录的消息由具体函数决定；但把这些消息汇聚成连续日志，是另一个独立关注点。我们仍希望函数产生一段字符串，却想卸下它“生成完整日志”的责任。于是得到下面这个折中方案：

pair<bool, string> negate(bool b) {
     return make_pair(!b, "Not so! ");
}

其思想是：在两次函数调用之间汇聚日志。

为了看看怎样做到这一点，我们换一个稍微真实的例子。先有一个从字符串到字符串的函数，把小写字符转换成大写：

string toUpper(string s) {
    string result;
    int (*toupperp)(int) = &toupper; // toupper 已重载
    transform(begin(s), end(s), back_inserter(result), toupperp);
    return result;
}

另有一个函数按照空白边界拆分字符串，返回字符串向量：

vector<string> toWords(string s) {
    return words(s);
}

真正的工作由辅助函数 words 完成：

vector<string> words(string s) {
    vector<string> result{""};
    for (auto i = begin(s); i != end(s); ++i)
    {
        if (isspace(*i))
            result.push_back("");
        else
            result.back() += *i;
    }
    return result;
}

我们想修改 toUpper 和 toWords：让它们在常规返回值上顺便“捎带”一段消息字符串。

我们要“修饰”这些函数的返回值。为了用通用方式完成它，定义模板 Writer，封装一个 pair：第一项是任意类型 A 的值，第二项是字符串：

template<typename A>
using Writer = pair<A, string>;

下面是修饰后的函数：

Writer<string> toUpper(string s) {
    string result;
    int (*toupperp)(int) = &toupper;
    transform(begin(s), end(s), back_inserter(result), toupperp);
    return make_pair(result, "toUpper ");
}

Writer<vector<string>> toWords(string s) {
    return make_pair(words(s), "toWords ");
}

我们想把这两个函数复合成另一个修饰函数：它把字符串转成大写，再拆分成单词，同时生成这些操作的日志。可以这样做：

Writer<vector<string>> process(string s) {
    auto p1 = toUpper(s);
    auto p2 = toWords(p1.first);
    return make_pair(p2.first, p1.second + p2.second);
}

目标达成了：日志汇聚不再是各个函数自身的关注点。每个函数只产生自己的消息，随后由外部把它们连接成更大的日志。

现在想象一整个程序都按这种风格编写：那会是一场充满重复且容易出错的噩梦。但我们是程序员，知道怎样处理重复代码：抽象它！然而，这次不是寻常的抽象——我们必须抽象函数复合本身。而复合正是范畴论的本质，因此在继续写代码之前，先从范畴论视角分析问题。

Writer 范畴

修饰一批函数的返回类型、借此捎带额外功能，是一个非常富有成果的想法。以后还会看到许多例子。起点是普通的类型与函数范畴。我们保留类型作为对象，但重新定义态射：态射现在是修饰后的函数。

例如，假设要修饰从 int 到 bool 的函数 isEven。我们把它变成由修饰函数表示的态射。要点在于：尽管修饰函数返回 pair，这个态射仍被视为对象 int 与 bool 之间的箭头：

pair<bool, string> isEven(int n) {
     return make_pair(n % 2 == 0, "isEven ");
}

根据范畴定律，我们应该能把这个态射与另一个从对象 bool 指向某个对象的态射复合。特别是，应该能把它与前面的 negate 复合：

pair<bool, string> negate(bool b) {
     return make_pair(!b, "Not so! ");
}

显然，由于输入输出不匹配，不能像复合普通函数一样复合这两个态射。它们的复合应该更像下面这样：

pair<bool, string> isOdd(int n) {
    pair<bool, string> p1 = isEven(n);
    pair<bool, string> p2 = negate(p1.first);
    return make_pair(p2.first, p1.second + p2.second);
}

于是，在这个正在构造的新范畴中，两个态射的复合规则如下：

  1. 执行与第一个态射对应的修饰函数；
  2. 提取结果 pair 的第一项，把它传给与第二个态射对应的修饰函数；
  3. 连接第一个结果的第二项（字符串）与第二个结果的第二项（字符串）；
  4. 返回新的 pair：第一项是最终结果的第一项，第二项是连接后的字符串。

如果想在 C++ 中把这种复合抽象为高阶函数，就必须使用一个由三种类型参数化的模板，分别对应范畴中的三个对象。它接受两个按上述规则可复合的修饰函数，返回第三个修饰函数：

template<typename A, typename B, typename C>
function<Writer<C>(A)> compose(function<Writer<B>(A)> m1,
                               function<Writer<C>(B)> m2)
{
    return [m1, m2](A x) {
        auto p1 = m1(x);
        auto p2 = m2(p1.first);
        return make_pair(p2.first, p1.second + p2.second);
    };
}

现在可以回到早先的例子，使用这个新模板实现 toUpper 与 toWords 的复合：

Writer<vector<string>> process(string s) {
   return compose<string, string, vector<string>>(
       toUpper, toWords)(s);
}

把类型传给 compose 模板时仍有许多噪声。只要编译器符合 C++14，支持带返回类型推导的泛型 lambda，就能避免这些噪声（这段代码归功于 Eric Niebler）：

auto const compose = [](auto m1, auto m2) {
    return [m1, m2](auto x) {
        auto p1 = m1(x);
        auto p2 = m2(p1.first);
        return make_pair(p2.first, p1.second + p2.second);
    };
};

在这个新定义下，process 的实现简化为：

Writer<vector<string>> process(string s) {
   return compose(toUpper, toWords)(s);
}

但事情还没有结束。我们已经定义了新范畴中的复合，那么恒等态射是什么？它们不是普通的恒等函数！它们必须是从类型 A 回到类型 A 的态射，也就是说，是下面形式的修饰函数：

Writer<A> identity(A);

它们在复合下必须表现为单位元。观察复合定义可以看出，恒等态射应该原样传递参数，并且只给日志贡献一个空字符串：

template<typename A>
Writer<A> identity(A x) {
    return make_pair(x, "");
}

你很容易验证，我们刚刚定义的确实是一个合法范畴。特别是，这个复合显然满足结合律。追踪每个 pair 的第一项，会发现它只是普通的函数复合，而函数复合满足结合律；第二项则被连接起来，连接同样满足结合律。

敏锐的读者也许会发现，这个构造很容易推广到任意幺半群，而不只限于字符串幺半群。我们可以在 compose 中使用 mappend，在 identity 中使用 mempty，分别替代 + 与 ""。实在没有理由把日志限制为字符串。优秀的程序库作者应该能识别出使程序库运转所需的最小约束——在这里，日志库唯一的要求，就是日志具备幺半群性质。

Haskell 中的 Writer

同样的内容用 Haskell 写会简洁一些，而且编译器能提供更多帮助。先定义 Writer 类型：

type Writer a = (a, String)

这里只定义了一个类型别名，相当于 C++ 的 typedef（或 using）。类型 Writer 由类型变量 a 参数化，等价于由 a 与 String 构成的 pair。pair 的语法极其简单：把两个项目放进括号，中间用逗号隔开。

我们的态射，是从任意类型到某种 Writer 类型的函数：

a -> Writer b

我们把复合声明成一个有趣的中缀运算符，有时称为“鱼”：

(>=>) ::
  (a -> Writer b) -> (b -> Writer c) -> (a -> Writer c)

这是一个双参数函数，其中每个参数本身都是函数，而返回值仍是函数。第一个参数的类型是 (a -> Writer b)，第二个是 (b -> Writer c)，结果是 (a -> Writer c)。

下面是这个中缀运算符的定义——两个参数 m1 与 m2 分别出现在鱼形符号两侧：

m1 >=> m2 = \x ->
    let (y, s1) = m1 x
        (z, s2) = m2 y
    in (z, s1 ++ s2)

结果是一个接受参数 x 的 lambda 函数。lambda 写作反斜杠——可以把它看成希腊字母 λ 被截掉了一条腿。

let 表达式允许声明辅助变量。这里，调用 m1 的结果通过模式匹配绑定到变量 pair (y, s1)；然后使用第一个模式得到的参数 y 调用 m2，并把结果匹配到 (z, s2)。

Haskell 通常直接对 pair 做模式匹配，而不像前面的 C++ 代码那样使用访问器。除此之外，两种实现之间的对应关系相当直白。

let 表达式的整体值由 in 子句指定：这里是一个 pair，第一项为 z，第二项是两个字符串 s1 ++ s2 的连接结果。

我还会为这个范畴定义恒等态射；不过由于很久以后才会明朗的原因，我把它称为 return：

return :: a -> Writer a
return x = (x, "")

为了完整起见，下面给出修饰函数 upCase 与 toWords 的 Haskell 版本：

upCase :: String -> Writer String
upCase s = (map toUpper s, "upCase ")

toWords :: String -> Writer [String]
toWords s = (words s, "toWords ")

函数 map 对应 C++ 的 transform。它把字符函数 toUpper 应用于字符串 s。辅助函数 words 已在标准 Prelude 库中定义。

最后，借助鱼运算符完成两个函数的复合：

process :: String -> Writer [String]
process = upCase >=> toWords

Kleisli 范畴

你也许已经猜到，这个范畴不是我当场发明的。它是所谓 Kleisli 范畴的一个例子——一种建立在 Monad 上的范畴。我们还没准备好讨论 Monad，但我想先让你尝尝它们能做什么。就目前的有限目标而言，Kleisli 范畴的对象是底层编程语言的类型。从类型 A 到类型 B 的态射，是从 A 到某种由 B 经特定“修饰”得到的类型的函数。每个 Kleisli 范畴都定义自己复合这类态射的方式，也定义相对于该复合的恒等态射。（稍后会看到，这个不够精确的“修饰”一词，对应范畴中的自函子概念。）

本文用作范畴基础的这个 Monad 称为 Writer Monad，用于记录日志或跟踪函数执行。它也是一种更普遍机制的例子：把效应嵌入纯计算。前面已经看到，可以在集合范畴中对编程语言的类型与函数建模（仍然照例忽略底）。这里，我们把模型扩展为一个略有不同的范畴：其中的态射由修饰函数表示，而它们的复合不只负责把一个函数的输出传给下一个函数的输入。现在我们多了一项可供操纵的自由度：复合本身。事实证明，恰恰是这项自由度，让我们能够为命令式语言中传统上依赖副作用实现的程序，赋予简单的指称语义。

习题

没有为所有可能参数值定义的函数称为偏函数。严格说，它不是数学意义上的函数，因此不符合标准范畴模型。不过，可以用一个返回修饰类型 optional 的函数来表示它：

template<typename A> class optional {
    bool _isValid;
    A    _value;
public:
    optional()    : _isValid(false) {}
    optional(A v) : _isValid(true), _value(v) {}
    bool isValid() const { return _isValid; }
    A value() const { return _value; }
};

例如，下面是修饰函数 safe_root 的实现：

optional<double> safe_root(double x) {
    if (x >= 0) return optional<double>{sqrt(x)};
    else return optional<double>{};
}

请完成下列任务：

  1. 构造偏函数的 Kleisli 范畴：定义复合与恒等态射。
    点击展开参考答案
    template<typename A>
optional<A> identity(A x) { return optional<A>{x}; }

template<typename A, typename B, typename C>
auto compose(auto f, auto g) {
    return [f, g](A x) -> optional<C> {
        auto y = f(x);
        return y.isValid() ? g(y.value()) : optional<C>{};
    };
}

    若第一个态射失败，复合立即失败；成功时才把内部值交给第二个态射。恒等态射只把值放入有效的 optional。

  2. 实现修饰函数 safe_reciprocal：当参数不等于零时，返回有效的倒数。
    点击展开参考答案
    optional<double> safe_reciprocal(double x) {
    if (x != 0) return optional<double>{1.0 / x};
    return optional<double>{};
}
  3. 复合 safe_root 与 safe_reciprocal，实现 safe_root_reciprocal，在可能时计算 sqrt(1/x)。
    点击展开参考答案
    optional<double> safe_root_reciprocal(double x) {
    auto r = safe_reciprocal(x);
    if (!r.isValid()) return optional<double>{};
    return safe_root(r.value());
}

    它只在 x > 0 时成功：零没有倒数，负数的倒数没有实数平方根。
