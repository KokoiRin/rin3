Android Runtime（ART）和 Dalvik 虚拟机通过分页（paging）与内存映射（memory-mapping，简称 mmapping）管理内存。这意味着，应用修改过的内存，无论来自新对象的分配，还是对映射页面的访问，都会保留在 RAM 中，无法被换出。要释放这些内存，应用只能解除持有的对象引用，让 GC 能够回收它们。但有一种例外：通过 mmap 映射、且没有修改过的文件，例如代码，可以在系统需要把内存用于其他用途时从 RAM 中换出。

本文介绍 Android 如何管理应用进程和内存分配。如需了解如何在应用中更高效地管理内存，请参阅管理应用内存。

GC（垃圾回收）

ART、Dalvik 这类托管内存环境会跟踪每次内存分配。一旦确定某块内存已不再被程序使用，就会自动将其释放回堆（heap），无需开发者干预。这种自动回收未使用内存的机制称为垃圾回收，即 GC（garbage collection）。GC 有两个目标：找出程序以后不可能再访问到的对象，并回收这些对象占用的资源。

Android 的堆采用分代机制：根据对象的预期存活时间和大小，将分配的对象分组跟踪。例如，刚分配的对象属于年轻代（Young generation）；如果对象持续存活足够长的时间，就可以被提升到更老的一代，之后再进入永久代（Permanent generation）。

堆中的每一代都有自己的内存占用上限。一旦某一代的空间开始趋于饱和，系统就会执行 GC，尝试释放内存。一次 GC 需要多长时间，取决于它要回收哪一代，以及各代中有多少存活对象。

GC 即使执行得很快，也仍可能影响应用性能。通常，你无法在代码中控制 GC 的执行时机；系统会持续根据一组条件判断是否需要 GC，条件满足时，就暂停进程执行并开始回收。如果 GC 恰好发生在动画等需要密集处理的循环中，或发生在音乐播放期间，就可能延长处理时间，使应用代码的执行时间超过流畅渲染一帧所建议的 16 毫秒阈值。

代码中的某些操作还可能让 GC 更频繁，或让每次 GC 耗时更长。例如，在 alpha blending（透明度混合）动画的每一帧中，如果都在 for 循环的最内层分配多个对象，堆里就可能堆积大量对象，迫使 GC 多次执行，从而降低应用性能。

如需进一步了解 GC 的一般原理，请参阅垃圾回收。

共享内存

为了让 RAM 容纳所需的全部内容，Android 会尽量让不同进程共享 RAM 页面，主要采用以下方式：

  • 每个应用进程都由一个已有的 Zygote 进程 fork 而来。Zygote 在系统启动时运行，并加载通用的 framework 代码和资源，例如 Activity 主题。启动新应用进程时，系统会先 fork Zygote，再在新进程中加载并运行应用代码。因此，为 framework 代码和资源分配的大部分 RAM 页面，都能由所有应用进程共享。
  • 大多数静态数据通过 mmap 映射到进程中。这样，数据既能在进程之间共享，也能在需要时被换出。例如：Dalvik 代码会放进预链接的 .odex 文件，以便直接 mmap；应用资源的资源表会采用可 mmap 的结构，并对齐 APK 中的 ZIP 条目；.so 文件中的 native code 等常规项目内容也属于这类静态数据。
  • Android 还会在许多地方显式分配共享内存区域，通过 ashmem 或 gralloc，让不同进程共用同一片动态 RAM。例如，窗口的 surface 由应用和屏幕合成器通过共享内存访问，cursor buffer（游标缓冲区）则由 ContentProvider 和客户端通过共享内存访问。

由于大量使用了共享内存，计算应用实际占用多少内存时需要格外注意。如何正确评估内存使用量，请参阅调查 RAM 使用情况。

分配和回收应用内存

每个应用进程的 Dalvik 堆都被限制在一段虚拟内存范围内，由此确定堆的逻辑大小。它可以按需增长，但不能超过系统为该应用设定的上限。

堆的逻辑大小不等于它实际占用的物理内存。检查应用的堆时，Android 会计算 PSS（Proportional Set Size）：与其他进程共享的 dirty page（脏页）和 clean page（干净页）都会计入，但共享部分只按使用这片 RAM 的应用数量分摊。系统把汇总得到的 PSS 视为应用的物理内存占用。如需进一步了解 PSS，请参阅调查 RAM 使用情况。

Dalvik 不会通过压缩来减小堆的逻辑大小，也就是说，它不会整理堆内碎片、合并空闲空间；只有堆末尾出现空闲空间时，Android 才能缩小逻辑堆。不过，系统仍能减少堆实际占用的物理内存：GC 完成后，Dalvik 会遍历堆，找出未使用的页面，并通过 madvise 将它们归还内核。因此，大块内存在分配后再被释放时，应能收回其占用的全部或几乎全部物理内存。小块内存的回收效率则可能低得多，因为它所在的页面可能还存放着其他尚未释放的数据。

应用内存的限制

为了让多任务环境正常运行，Android 会对每个应用的堆大小设置硬性上限。这个上限因设备而异，取决于设备整体可用的 RAM 容量。如果应用已用满堆空间，却还尝试分配更多内存，就可能遇到 OutOfMemoryError。

有时，你需要查询当前设备允许应用使用多少堆空间，例如据此判断缓存可以安全地保留多少数据。调用 getMemoryClass() 就能获取这个值；它返回一个整数，表示应用堆可用的容量，单位为 MB。

切换应用

用户切换应用时，Android 会缓存不处于前台的应用，也就是既不对用户可见、也没有运行音乐播放等 foreground service（前台服务）的应用。例如，用户第一次启动应用时，系统会为它创建进程；用户离开应用后，这个进程不会立即退出，而是被系统缓存。用户稍后返回时，系统就能复用该进程，让应用切换更快。

如果应用进程已被缓存，却仍持有当前用不到的资源，那么即使用户没有使用它，它也会影响系统整体性能。系统的内存等资源不足时，就会终止缓存中的进程；系统还会考虑哪些进程占用内存最多，并可能通过终止这些进程来释放 RAM。

注意：应用进程被缓存时，占用的内存越少，就越有可能被保留下来，从而快速恢复。不过，系统会根据当时的需求决定是否终止进程，因此缓存进程无论占用多少资源，都可能随时被终止。

如需了解后台进程如何被缓存，以及 Android 如何决定终止哪些进程，请参阅进程与线程。

内存压力测试

高端设备较少遇到内存压力问题，但低 RAM 设备的用户仍可能受影响，例如使用 Android（Go edition）的设备。你应尝试复现这种内存紧张的环境，再编写 instrumentation test（插桩测试）验证应用行为，从而改善低内存设备上的使用体验。

Stressful Application Test

Stressful Application Test（stressapptest）是一种内存接口测试，可用于构造接近真实情况的高负载环境，测试应用面临的各种内存和硬件限制。它允许设置时间和内存限制，便于编写 instrumentation test，验证现实中的高内存使用场景。例如，以下命令会把静态库推送到 data 文件系统，赋予执行权限，再运行一项持续 20 秒、使用 990 MB 内存的压力测试：

    adb push stressapptest /data/local/tmp/
    adb shell chmod 777 /data/local/tmp/stressapptest
    adb shell /data/local/tmp/stressapptest -s 20 -M 990
如需了解工具安装、常用参数和错误处理，请参阅 stressapptest 文档。

观察 stressapptest 的运行结果

stressapptest 等工具可以申请超过当前空闲容量的内存。这类申请可能触发多种告警，开发者需要了解其含义。内存不足主要可能引发以下三种告警：

  • SIGABRT：系统已处于内存紧张状态时，如果申请的内存超过空闲容量，进程就会发生这种致命的 native crash。
  • SIGQUIT：被 instrumentation test 检测到时，会生成 core dump（核心内存转储），并终止进程。
  • TRIM_MEMORY_EVENTS：Android 4.1（API level 16）及以上版本提供这些回调，用于向进程报告详细的内存告警。
