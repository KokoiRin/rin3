Android Runtime（ART）和 Dalvik 虚拟机通过分页（paging）与内存映射（memory-mapping，简称 mmapping）管理内存。这里有一个结果：应用修改过的内存会一直留在 RAM 中，不能被换出。无论这些修改来自分配新对象，还是访问映射的页面，都是如此。要释放这些内存，应用只能放开自己持有的对象引用，让 GC 可以回收它们。不过有一个例外：如果文件通过 mmap 映射进来后没有被修改，比如代码，系统需要把内存用于其他地方时，就可以将它从 RAM 中换出。

这一篇会介绍 Android 怎样管理应用进程，以及怎样分配内存。如果想进一步了解应用该怎样更高效地使用内存，可以看管理应用内存。

GC（垃圾回收）

ART、Dalvik 这样的托管内存环境，会记下每一次内存分配。只要确认某块内存已经不再被程序使用，就会自动把它释放回堆（heap），不用你手动处理。这种自动收回闲置内存的机制，就是垃圾回收，也叫 GC（garbage collection）。它要做两件事：找出程序以后不可能再访问到的数据对象，再收回这些对象占用的资源。

Android 会把堆里的对象按“代”分组，并根据对象预计会存活多久、占多大空间，分别跟踪各组的内存分配。例如，刚分配的对象先放在年轻代（Young generation）。如果对象一直存活了足够长的时间，就可以被提升到更老的一代，之后再进入永久代（Permanent generation）。

每一代都有自己的内存占用上限。当某一代的空间开始变满，系统就会执行一次 GC，尝试腾出内存。这次回收要花多久，取决于回收的是哪一代，以及各代还有多少存活对象。

即使 GC 很快，也仍然可能影响应用性能。通常，你没法通过代码决定它什么时候发生。系统会持续检查一组条件，一旦条件满足，就暂停进程的执行，开始回收。如果这时应用正在执行动画这样需要密集处理的循环，或者正在播放音乐，GC 就可能拉长处理时间。这样一来，应用代码的执行时间，就可能超过建议的 16 毫秒阈值，影响一帧画面的高效、流畅渲染。

你的代码也可能让 GC 更频繁，或者让每次 GC 比平时花更长时间。比如，在 alpha blending（透明度混合）动画的每一帧里，都在 for 循环的最内层分配多个对象，堆中就可能塞进大量对象。GC 因而需要执行多次，应用性能也可能下降。

想了解 GC 更一般的原理，可以看垃圾回收。

共享内存

为了让需要的内容都能放进 RAM，Android 会尽量让不同进程共享 RAM 页面。主要有下面几种方式：

  • 每个应用进程，都是从一个已有的 Zygote 进程 fork 出来的。Zygote 在系统启动时运行，先加载通用的 framework 代码和资源，比如 Activity 主题。等到要启动应用进程时，系统就 fork Zygote，再在新进程里加载、运行应用自己的代码。这样，为 framework 代码和资源分配的大部分 RAM 页面，就能由所有应用进程共用。
  • 大多数静态数据会通过 mmap 映射进进程。这样既能让不同进程共享这些数据，也能在需要时把它们换出。例如，Dalvik 代码放在预链接的 .odex 文件中，就可以直接 mmap；应用资源的资源表会做成可 mmap 的结构，APK 里的 ZIP 条目也会做对齐处理。还有一些常规项目内容，比如 .so 文件里的 native code，也属于这类静态数据。
  • Android 还会在许多地方专门分配共享内存区域，用 ashmem 或 gralloc，让不同进程共用同一片动态 RAM。比如，应用和屏幕合成器通过共享内存访问窗口的 surface；ContentProvider 和客户端也通过共享内存访问 cursor buffer（游标缓冲区）。

正因为共享内存用得很多，判断应用究竟占了多少内存时，要格外留意。具体怎样计算，可以看调查 RAM 使用情况。

分配和回收应用内存

对每个应用进程来说，Dalvik 堆都被限定在一段虚拟内存范围内，这决定了堆的逻辑大小。堆可以按需要增长，但不能超过系统为该应用规定的上限。

堆的逻辑大小，和它实际占用多少物理内存，不是一回事。检查应用的堆时，Android 会计算 PSS（Proportional Set Size）。它会把与其他进程共享的 dirty page（脏页）和 clean page（干净页）都算进去，但不会把共享部分全部算在一个应用头上，而是按共享这片 RAM 的应用数量来分摊。系统把汇总后的 PSS 看作应用的物理内存占用。关于 PSS 的更多说明，可以看调查 RAM 使用情况。

Dalvik 不会通过整理堆中的碎片、合并空隙，来缩小堆的逻辑大小。只有堆的末尾出现空闲空间，Android 才能把逻辑堆缩小。不过，实际占用的物理内存仍然可以减少。GC 结束后，Dalvik 会遍历堆，找出没有使用的页面，再用 madvise 把它们归还内核。所以，分配一大块内存，再把它释放，通常应能收回它占用的全部或几乎全部物理内存。小块内存就可能没这么高效：它所在的页面里，可能还放着其他没有释放的数据。

应用内存的限制

为了让多个应用能正常一起运行，Android 会给每个应用的堆设一个硬性上限。设备整体有多少 RAM 可用，会影响这个上限，所以不同设备的上限并不相同。如果应用已经用满堆空间，还要继续分配内存，就可能收到 OutOfMemoryError。

有时，你需要知道当前设备到底允许应用使用多大的堆，比如据此判断缓存里可以安全地留多少数据。这时可以调用 getMemoryClass()。它会返回一个整数，表示应用堆可用的容量，单位是 MB。

切换应用

用户切换应用时，Android 会把不处于前台的应用缓存起来。这里说的“不处于前台”，是指用户看不到它，它也没有运行音乐播放这样的 foreground service（前台服务）。比如，用户第一次打开应用时，系统会为它创建进程。用户离开后，这个进程不会就此退出，而是先留在缓存中。等用户再回来，系统就能复用这个进程，让应用切换更快。

应用进程留在缓存中时，如果还占着当前用不到的资源，即使用户没有使用这个应用，它也会拖累系统整体性能。等到内存等资源不够用，系统就会结束缓存里的进程。系统也会看哪些进程占的内存最多，并可能结束这些进程来腾出 RAM。

注意：应用进程留在缓存中时，占的内存越少，就越有机会被保留下来，之后也就能快速恢复。但这并没有保证：系统会根据当时的需求作决定，无论缓存进程占了多少资源，都可能随时把它结束。

后台进程怎样进入缓存、Android 怎样决定结束哪些进程，进程与线程 中有更多说明。

内存压力测试

高端设备比较少遇到内存紧张的问题，但 RAM 较少的设备仍可能受影响，比如运行 Android（Go edition）的设备。因此，你应尝试复现内存紧张的环境，再编写 instrumentation test（插桩测试），检查应用在这种情况下的表现，改善低内存设备用户的体验。

Stressful Application Test

Stressful Application Test（stressapptest）是一个内存接口测试工具。它能构造接近实际使用情况的高负载环境，用来测试应用遇到的各种内存和硬件限制。你可以指定时间和内存限制，再编写 instrumentation test，检查实际使用中内存占用很高时的表现。比如，下面这组命令会先把静态库推送到 data 文件系统，赋予它执行权限，然后运行一项持续 20 秒、使用 990 MB 内存的压力测试：

    adb push stressapptest /data/local/tmp/
    adb shell chmod 777 /data/local/tmp/stressapptest
    adb shell /data/local/tmp/stressapptest -s 20 -M 990
工具怎样安装、常用参数有哪些、错误怎样处理，都可以查看 stressapptest 文档。

观察 stressapptest 的运行结果

使用 stressapptest 这样的工具时，你可以申请比当前空闲内存更多的内存。这可能触发多种告警，开发时需要知道它们是什么意思。内存不足时，主要可能出现下面三种告警：

  • SIGABRT：系统已经内存紧张时，如果进程还申请超过空闲容量的内存，就会发生这种致命的 native crash。
  • SIGQUIT：instrumentation test 检测到这个信号时，会生成 core dump（核心内存转储），并终止进程。
  • TRIM_MEMORY_EVENTS：从 Android 4.1（API level 16）开始提供这些回调，用来向进程报告详细的内存告警。
