Android Runtime（ART）和 Dalvik 虚拟机使用分页和内存映射（mmapping）管理内存。这意味着，应用修改的任何内存——无论是通过分配新对象还是访问映射页面——都会常驻 RAM，无法被换出。释放应用内存的唯一方法是释放应用持有的对象引用，使垃圾回收器能够回收这些内存。但有一个例外：以 mmap 方式映射且未经修改的文件，例如代码，在系统需要将内存用于其他用途时，可以从 RAM 中换出。

本页介绍 Android 如何管理应用进程和内存分配。有关在应用中更高效地管理内存的更多信息，请参阅管理应用内存。

垃圾回收

ART 或 Dalvik 虚拟机这样的托管内存环境，会跟踪每次内存分配。一旦确定某块内存已不再被程序使用，就会将其释放回堆中，无需程序员干预。在托管内存环境中回收未使用内存的机制称为垃圾回收。垃圾回收有两个目标：找到程序中将来无法再访问的数据对象；回收这些对象使用的资源。

Android 的内存堆采用分代机制，这意味着它会根据所分配对象的预期寿命和大小，跟踪不同组的分配。例如，最近分配的对象属于年轻代。当一个对象保持活动的时间足够长时，它可以被提升到更老的一代，之后再进入永久代。

堆的每一代都有各自的内存占用上限，用于限制该代对象能够占用的内存量。每当某一代开始填满时，系统就会执行一次垃圾回收，尝试释放内存。垃圾回收的持续时间取决于正在回收哪一代对象，以及各代中有多少活动对象。

虽然垃圾回收可以相当快，但它仍然会影响应用性能。通常无法在代码中控制垃圾回收何时发生。系统有一组持续生效的判断标准，用于决定何时执行垃圾回收。当这些标准得到满足时，系统会停止执行进程并开始垃圾回收。如果垃圾回收发生在动画等密集处理循环的中间，或发生在音乐播放期间，就可能增加处理时间。这种增加可能使应用中的代码执行时间超过为高效、流畅的帧渲染所建议的 16 毫秒阈值。

此外，代码流程可能执行某些工作，迫使垃圾回收更频繁地发生，或持续时间比正常情况更长。例如，如果在透明度混合动画的每一帧中，都在 for 循环最内层分配多个对象，就可能用大量对象污染内存堆。在这种情况下，垃圾回收器会执行多次垃圾回收，并可能降低应用性能。

有关垃圾回收的更多一般信息，请参阅垃圾回收。

共享内存

为了将所需内容全部容纳在 RAM 中，Android 会尝试在进程之间共享 RAM 页面。可通过以下方式实现：

  • 每个应用进程都从一个名为 Zygote 的现有进程 fork 而来。Zygote 进程在系统启动时启动，加载通用框架代码和资源（例如 Activity 主题）。启动新应用进程时，系统会 fork Zygote 进程，然后在新进程中加载并运行应用代码。这种方式使为框架代码和资源分配的大部分 RAM 页面能够在所有应用进程间共享。
  • 大多数静态数据以 mmap 方式映射到进程中。该技术既允许进程间共享数据，也允许在需要时将数据换出。静态数据的例子包括：Dalvik 代码（放入预链接的 .odex 文件以便直接 mmap）、应用资源（将资源表设计为可 mmap 的结构，并对齐 APK 中的 ZIP 条目），以及 .so 文件中的原生代码等传统项目元素。
  • 在许多地方，Android 通过显式分配的共享内存区域（使用 ashmem 或 gralloc），在进程间共享相同的动态 RAM。例如，窗口 surface 在应用与屏幕合成器之间使用共享内存，游标缓冲区在内容提供程序与客户端之间使用共享内存。

由于大量使用共享内存，确定应用实际使用多少内存时需要谨慎。调查 RAM 使用情况介绍了正确确定应用内存使用量的技术。

分配和回收应用内存

对于每个应用进程，Dalvik 堆被限制在一个虚拟内存范围内。这定义了逻辑堆大小，它可以按需增长，但最多只能达到系统为每个应用规定的上限。

逻辑堆大小与堆使用的物理内存量不同。检查应用的堆时，Android 会计算一个称为比例集大小（PSS）的值，它将与其他进程共享的脏页面和干净页面都计入，但只按共享该 RAM 的应用数量按比例计入。系统将这一 PSS 总量视为应用的物理内存占用。有关 PSS 的更多信息，请参阅调查 RAM 使用情况指南。

Dalvik 堆不会压缩逻辑堆大小，也就是说，Android 不会通过整理堆碎片来合并空闲空间。只有堆末尾存在未使用空间时，Android 才能缩小逻辑堆大小。不过，系统仍然可以减少堆使用的物理内存。垃圾回收后，Dalvik 遍历堆，找到未使用的页面，再通过 madvise 将这些页面归还内核。因此，成对分配和释放大块内存，应能回收全部或几乎全部使用的物理内存。但回收小块分配的内存可能低效得多，因为该小块内存使用的页面可能仍与其他尚未释放的内容共享。

限制应用内存

为了维持正常工作的多任务环境，Android 会对每个应用的堆大小设置硬性限制。具体的堆大小上限因设备而异，取决于设备整体可用的 RAM 容量。如果应用已达到堆容量上限，又尝试分配更多内存，就可能收到 OutOfMemoryError。

在某些情况下，你可能希望查询系统，以确定当前设备上究竟有多少可用堆空间——例如，确定可以安全地在缓存中保留多少数据。可以通过调用 getMemoryClass() 查询这个值。此方法返回一个整数，表示应用堆可用的兆字节数。

切换应用

当用户在应用之间切换时，Android 会将不处于前台的应用保留在缓存中，也就是那些对用户不可见、也没有运行音乐播放等前台服务的应用。例如，用户首次启动某个应用时，系统会为它创建一个进程；但用户离开应用时，该进程不会退出。系统会将进程保留在缓存中。如果用户稍后返回应用，系统会复用该进程，从而加快应用切换。

如果应用有一个缓存进程，而且它保留着当前不需要的资源，那么即使用户没有使用应用，它也会影响系统的整体性能。当系统的内存等资源不足时，会终止缓存中的进程。系统也会考虑哪些进程占用的内存最多，并可以终止它们以释放 RAM。

注意：应用在缓存中消耗的内存越少，就越有可能不被终止，并能够快速恢复。不过，根据系统即时需求，缓存进程可能随时被终止，无论其资源使用情况如何。

如需详细了解进程不在前台运行时如何被缓存，以及 Android 如何决定可以终止哪些进程，请参阅进程与线程指南。

内存压力测试

虽然高端设备较少出现内存压力问题，但它们仍可能影响低 RAM 设备上的用户，例如运行 Android（Go 版本）的设备。应尝试复现这种内存紧张环境，以便编写插桩测试来验证应用行为，改善低内存设备用户的体验。

应用压力测试

Stressful Application Test（stressapptest）是一种内存接口测试，有助于创建真实的高负载情境，以测试应用所面临的各种内存和硬件限制。它支持定义时间和内存限制，因此可以编写插桩测试，验证现实中的高内存使用场景。例如，使用以下命令将静态库推送到数据文件系统，使其可执行，并运行一个持续 20 秒、使用 990 MB 内存的压力测试：

    adb push stressapptest /data/local/tmp/
    adb shell chmod 777 /data/local/tmp/stressapptest
    adb shell /data/local/tmp/stressapptest -s 20 -M 990
有关工具安装、常用参数和错误处理的更多信息，请参阅 stressapptest 文档。

关于 stressapptest 的观察

stressapptest 等工具可以请求分配超出当前可用量的内存。此类请求可能触发多种警报，开发时应有所了解。内存不足可能引发的三种主要警报包括：

  • SIGABRT：当系统已处于内存压力下，又请求分配超过空闲内存大小的内存时，进程会发生这种致命的原生崩溃。
  • SIGQUIT：由插桩测试检测到时，会生成核心内存转储并终止进程。
  • TRIM_MEMORY_EVENTS：这些回调可用于 Android 4.1（API 级别 16）及更高版本，为进程提供详细的内存警报。
