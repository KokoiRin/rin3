StateFlow 和 SharedFlow 都是 Flow API。它们让 Flow 能更合适地发送状态更新，也能把值发给多个消费者。

StateFlow

StateFlow 是一种可以观察、也会保存状态的 Flow。它会把当前状态和之后的更新发给收集者，你也可以直接读 value 来取得当前值。想修改状态并把它发出去，就给 MutableStateFlow 的 value 赋一个新值。

如果一个类需要维护可变化、又能被观察的状态，StateFlow 就很适合。

沿用 Kotlin Flow 的例子，可以由 LatestNewsViewModel 向外提供一个 StateFlow，让 View 监听 UI 状态的变化。这样，页面状态也能自然地保留到配置变化之后。

class LatestNewsViewModel(
    private val newsRepository: NewsRepository
) : ViewModel() {

    // Backing property to avoid state updates from other classes
    private val _uiState = MutableStateFlow(LatestNewsUiState.Success(emptyList()))
    // The UI collects from this StateFlow to get its state updates
    val uiState: StateFlow<LatestNewsUiState> = _uiState

    init {
        viewModelScope.launch {
            newsRepository.favoriteLatestNews
                // Update UI with the latest favorite news
                // Writes to the value property of MutableStateFlow,
                // adding a new element to the flow and updating all
                // of its collectors
                .collect { favoriteNews ->
                    _uiState.value = LatestNewsUiState.Success(favoriteNews)
                }
        }
    }
}

// Represents different states for the LatestNews screen
sealed class LatestNewsUiState {
    data class Success(val news: List<ArticleHeadline>) : LatestNewsUiState()
    data class Error(val exception: Throwable) : LatestNewsUiState()
}

负责更新 MutableStateFlow 的类是生产者，从 StateFlow 收集数据的类都是消费者。通过 flow 构建器创建的 Flow 是冷的，而 StateFlow 是热的：开始收集它，不会触发任何生产者代码。StateFlow 始终处于活动状态并留在内存中；只有从 GC root（垃圾回收根）出发，已经没有其他引用能找到它时，它才可以被垃圾回收。

新消费者开始收集时，会先收到流里最近的状态，再收到后续状态。LiveData 等其他可观察类也有类似行为。

View 监听 StateFlow，和监听其他 Flow 一样：

class LatestNewsActivity : ComponentActivity() {
    private val latestNewsViewModel: LatestNewsViewModel = TODO() // getViewModel()

    override fun onCreate(savedInstanceState: Bundle?) {
        // ...
        // Start a coroutine in the lifecycle scope
        lifecycleScope.launch {
            // repeatOnLifecycle launches the block in a new coroutine every time the
            // lifecycle is in the STARTED state (or above) and cancels it when it's STOPPED.
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                // Trigger the flow and start listening for values.
                // Note that this happens when lifecycle is STARTED and stops
                // collecting when the lifecycle is STOPPED
                latestNewsViewModel.uiState.collect { uiState ->
                    // New value received
                    when (uiState) {
                        is LatestNewsUiState.Success -> showFavoriteNews(uiState.news)
                        is LatestNewsUiState.Error -> showError(uiState.exception)
                    }
                }
            }
        }
    }
}

警告：如果收集到的数据要用来更新 UI，不要在 UI 中直接通过 launch 或 launchIn 扩展函数收集。即使 View 已经不可见，它们仍会处理事件，可能导致应用崩溃。应像上面的例子一样，使用 repeatOnLifecycle。

注意：只有 androidx.lifecycle:lifecycle-runtime-ktx:2.4.0 及更高版本的库，才提供 repeatOnLifecycle API。

StateFlow、Flow 与 LiveData

StateFlow 和 LiveData 有相似之处：它们都保存可以被观察的数据，在应用架构中的使用方式也类似。

但 StateFlow 和 LiveData 的行为并不完全相同：

  • 创建 StateFlow 时，必须在构造器里传入初始状态；LiveData 不需要。
  • View 进入 STOPPED 状态时，LiveData.observe() 会自动取消消费者的注册。但收集 StateFlow 或其他 Flow，不会自动停止。要得到相同的行为，就要在 Lifecycle.repeatOnLifecycle 代码块中收集。

使用 shareIn 将冷 Flow 转为热 Flow

StateFlow 是热 Flow。只要还有人收集它，或者从 GC root 出发仍有其他引用能找到它，它就会留在内存中。想把冷 Flow 变成热 Flow，可以用 shareIn。

拿 Kotlin Flow 中创建的 callbackFlow 来说，每个收集者各建一个 Flow，会重复获取数据。可以改用 shareIn，让收集者共享从 Firestore 取得的数据。调用时需要传入三样东西：

  • 用来共享 Flow 的 CoroutineScope。这个作用域应比所有消费者都活得更久，确保需要共享 Flow 的时候，它仍然存在。
  • 每个新收集者加入时，要把之前的多少个数据项重新发给它。
  • 什么时候开始运行的策略。

class NewsRemoteDataSource(
    private val externalScope: CoroutineScope
) {
    val latestNews: Flow<List<ArticleHeadline>> = flow {
        // ...
    }.shareIn(
        externalScope,
        replay = 1,
        started = SharingStarted.WhileSubscribed()
    )
}
StateFlowAndSharedFlow.kt

这个例子里的 latestNews 会把最后发出的数据项重新发给新收集者。只要 externalScope 还在，并且还有活跃收集者，Flow 就保持活动。SharingStarted.WhileSubscribed() 策略会在有活跃订阅者时保持上游生产者运行。也可以选其他策略：SharingStarted.Eagerly 会立即启动生产者；SharingStarted.Lazily 则等第一个订阅者出现后才开始共享，之后让 Flow 一直保持活动。

注意：externalScope 有哪些常见用法，可以看这篇文章。

SharedFlow

shareIn 返回的是 SharedFlow，它是一种热 Flow，会把值发给所有正在收集它的消费者。SharedFlow 可以看作 StateFlow 更通用、支持更多配置的形式。

不通过 shareIn，也能创建 SharedFlow。比如，用 SharedFlow 给应用其他部分发送定时信号，让所有内容定期一起刷新：除了最新新闻，还可以同时刷新用户信息和用户收藏的主题。下面的 TickHandler 对外提供一个 SharedFlow，告诉其他类什么时候刷新。和 StateFlow 一样，类内部使用 MutableSharedFlow 类型的后备属性，向流里发送数据：

// Class that centralizes when the content of the app needs to be refreshed
class TickHandler(
    private val externalScope: CoroutineScope,
    private val tickIntervalMs: Long = 5000
) {
    // Backing property to avoid flow emissions from other classes
    private val _tickFlow = MutableSharedFlow<Unit>(replay = 0)
    val tickFlow: SharedFlow<Unit> = _tickFlow

    init {
        externalScope.launch {
            while (true) {
                _tickFlow.emit(Unit)
                delay(tickIntervalMs)
            }
        }
    }
}

可以通过下面这些设置，调整 SharedFlow 的行为：

  • replay：新订阅者加入时，把之前发出的若干个值重新发送给它。
  • onBufferOverflow：待发送的数据填满缓冲区后，应该怎么办。默认是 BufferOverflow.SUSPEND，也就是让调用方挂起；还可以选择 DROP_LATEST 或 DROP_OLDEST。

MutableSharedFlow 的 subscriptionCount 会告诉你目前有多少活跃收集者，可以据此调整业务逻辑。如果不想再向新收集者重放最近发出的信息，MutableSharedFlow 还提供了 resetReplayCache。
