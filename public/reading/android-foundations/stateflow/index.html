StateFlow 和 SharedFlow 是 Flow API，使 Flow 能够以更优的方式发出状态更新，并向多个消费者发出值。

StateFlow

StateFlow 是一个持有状态的可观察 Flow，会向其收集者发出当前状态和新的状态更新。也可以通过其 value 属性读取当前状态值。要更新状态并将其发送到 Flow，请为 MutableStateFlow 类的 value 属性赋一个新值。

在 Android 中，StateFlow 非常适合需要维护可观察可变状态的类。

沿用 Kotlin Flow 中的示例，可以从 LatestNewsViewModel 公开一个 StateFlow，使 View 能够监听 UI 状态更新，并自然地让屏幕状态在配置变更后保留下来。

class LatestNewsViewModel(
    private val newsRepository: NewsRepository
) : ViewModel() {

    // Backing property to avoid state updates from other classes
    private val _uiState = MutableStateFlow(LatestNewsUiState.Success(emptyList()))
    // The UI collects from this StateFlow to get its state updates
    val uiState: StateFlow<LatestNewsUiState> = _uiState

    init {
        viewModelScope.launch {
            newsRepository.favoriteLatestNews
                // Update UI with the latest favorite news
                // Writes to the value property of MutableStateFlow,
                // adding a new element to the flow and updating all
                // of its collectors
                .collect { favoriteNews ->
                    _uiState.value = LatestNewsUiState.Success(favoriteNews)
                }
        }
    }
}

// Represents different states for the LatestNews screen
sealed class LatestNewsUiState {
    data class Success(val news: List<ArticleHeadline>) : LatestNewsUiState()
    data class Error(val exception: Throwable) : LatestNewsUiState()
}

负责更新 MutableStateFlow 的类是生产者，所有从 StateFlow 收集数据的类都是消费者。与使用 flow 构建器创建的冷 Flow 不同，StateFlow 是热的：从 Flow 收集数据不会触发任何生产者代码。StateFlow 始终处于活动状态并保留在内存中，只有当垃圾回收根不再通过其他引用指向它时，它才符合垃圾回收条件。

当新消费者开始从 Flow 收集数据时，它会收到流中最后的状态以及之后的所有状态。在 LiveData 等其他可观察类中，也能看到这种行为。

View 监听 StateFlow 的方式与监听其他 Flow 相同：

class LatestNewsActivity : ComponentActivity() {
    private val latestNewsViewModel: LatestNewsViewModel = TODO() // getViewModel()

    override fun onCreate(savedInstanceState: Bundle?) {
        // ...
        // Start a coroutine in the lifecycle scope
        lifecycleScope.launch {
            // repeatOnLifecycle launches the block in a new coroutine every time the
            // lifecycle is in the STARTED state (or above) and cancels it when it's STOPPED.
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                // Trigger the flow and start listening for values.
                // Note that this happens when lifecycle is STARTED and stops
                // collecting when the lifecycle is STOPPED
                latestNewsViewModel.uiState.collect { uiState ->
                    // New value received
                    when (uiState) {
                        is LatestNewsUiState.Success -> showFavoriteNews(uiState.news)
                        is LatestNewsUiState.Error -> showError(uiState.exception)
                    }
                }
            }
        }
    }
}

警告：如果需要更新 UI，绝不要从 UI 直接通过 launch 或 launchIn 扩展函数收集 Flow。即使 View 不可见，这些函数仍会处理事件。这种行为可能导致应用崩溃。为避免这种情况，应使用上面展示的 repeatOnLifecycle API。

注意：repeatOnLifecycle API 仅在 androidx.lifecycle:lifecycle-runtime-ktx:2.4.0 及更高版本的库中可用。

要将任何 Flow 转换为 StateFlow，请使用 stateIn 中间操作符。

注意：测试 StateFlow 可能需要额外注意，尤其是在它们通过 stateIn 创建时。有关详情，请参阅在 Android 上测试 Kotlin Flow页面。

StateFlow、Flow 与 LiveData

StateFlow 与 LiveData 有相似之处。两者都是可观察的数据持有者类，在应用架构中使用时，也都遵循类似的模式。

不过，请注意，StateFlow 与 LiveData 的行为确实有所不同：

  • StateFlow 要求向构造函数传入初始状态，而 LiveData 不需要。
  • 当 View 进入 STOPPED 状态时，LiveData.observe() 会自动取消消费者的注册，而从 StateFlow 或其他任何 Flow 收集数据时，不会自动停止收集。要实现相同行为，需要在 Lifecycle.repeatOnLifecycle 块中收集 Flow。

使用 shareIn 将冷 Flow 转为热 Flow

StateFlow 是热 Flow——只要 Flow 正被收集，或垃圾回收根仍通过其他引用指向它，它就会留在内存中。可以使用 shareIn 操作符将冷 Flow 转为热 Flow。

以 Kotlin Flow 中创建的 callbackFlow 为例，可以通过 shareIn 在收集者之间共享从 Firestore 获取的数据，而不是让每个收集者创建新的 Flow。需要传入以下内容：

  • 用于共享 Flow 的 CoroutineScope。此作用域的存活时间应长于任何消费者，以便让共享 Flow 在需要的时间内保持存活。
  • 向每个新收集者重放的条目数量。
  • 启动行为策略。

class NewsRemoteDataSource(
    private val externalScope: CoroutineScope
) {
    val latestNews: Flow<List<ArticleHeadline>> = flow {
        // ...
    }.shareIn(
        externalScope,
        replay = 1,
        started = SharingStarted.WhileSubscribed()
    )
}

在此示例中，latestNews Flow 会向新收集者重放最后发出的条目，并在 externalScope 存活且存在活动收集者时保持活动。SharingStarted.WhileSubscribed() 启动策略会在存在活动订阅者时让上游生产者保持活动。也有其他启动策略，例如使用 SharingStarted.Eagerly 立即启动生产者，或使用 SharingStarted.Lazily 在第一个订阅者出现后开始共享，并让 Flow 永久保持活动。

注意：如需详细了解 externalScope 的使用模式，请参阅这篇文章。

SharedFlow

shareIn 函数返回一个 SharedFlow，它是向所有收集它的消费者发出值的热 Flow。SharedFlow 是 StateFlow 的高度可配置的泛化形式。

也可以不使用 shareIn 而创建 SharedFlow。例如，可以使用 SharedFlow 向应用其余部分发送定时信号，让所有内容周期性地同时刷新。除了获取最新新闻，你可能还希望刷新用户信息区域及其收藏主题集合。在以下代码段中，TickHandler 公开了一个 SharedFlow，使其他类知道何时刷新自身内容。与 StateFlow 一样，在类中使用 MutableSharedFlow 类型的后备属性，向 Flow 发送条目：

// Class that centralizes when the content of the app needs to be refreshed
class TickHandler(
    private val externalScope: CoroutineScope,
    private val tickIntervalMs: Long = 5000
) {
    // Backing property to avoid flow emissions from other classes
    private val _tickFlow = MutableSharedFlow<Unit>(replay = 0)
    val tickFlow: SharedFlow<Unit> = _tickFlow

    init {
        externalScope.launch {
            while (true) {
                _tickFlow.emit(Unit)
                delay(tickIntervalMs)
            }
        }
    }
}

可以通过以下方式自定义 SharedFlow 的行为：

  • replay 允许向新订阅者重新发送一定数量的先前已发出的值。
  • onBufferOverflow 允许指定缓冲区被待发送条目填满时采用的策略。默认值为 BufferOverflow.SUSPEND，会使调用方挂起。其他选项包括 DROP_LATEST 或 DROP_OLDEST。

MutableSharedFlow 还有一个 subscriptionCount 属性，其中包含活动收集者的数量，使你可以据此优化业务逻辑。如果不希望重放最近发送到 Flow 的信息，MutableSharedFlow 还提供了 resetReplayCache 函数。
