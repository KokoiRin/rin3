高质量的 Android 应用，需要良好的架构作为基础。架构清楚，应用才更容易扩展和维护，也更容易适应不断增加的 Android 设备类型：手机、平板、折叠屏、ChromeOS 设备、车载显示屏，以及 XR。

应用组成

一个典型的 Android 应用，由多个应用组件组成，比如服务、内容提供程序和广播接收器。这些组件需要在应用清单中声明。

应用界面本身也是一个组件。过去，界面通常用多个 Activity 来构建。现代应用则采用单 Activity 架构：用一个 Activity 作为容器，承载各个页面或 Jetpack Compose 导航目的地。

多种设备形态

应用不只运行在手机上，也可能运行在平板、可折叠设备、ChromeOS 等设备上。不要假定它会一直保持竖屏或横屏。设备旋转、折叠屏折起或展开时，配置会发生变化，应用必须重新组合 UI，应用状态也会受到影响。

资源限制

移动设备的资源是有限的，大屏设备也一样。因此，操作系统随时可能结束你的应用进程，把资源交给其他进程使用。

可变的启动条件

资源有限时，应用组件可能各自单独启动，顺序也不固定；操作系统或用户还可能随时销毁它们。所以，不要把应用数据或状态存放在应用组件中。各个组件应能独立工作，彼此不依赖。

通用架构原则

既然不该把应用数据和状态存在应用组件里，那应用应该怎样设计？

应用越做越大，就越需要能支撑后续扩展的架构。好的架构会说清楚：应用各部分的边界在哪里，每一部分负责什么。

关注点分离

设计架构时，应遵循下面几项原则。

最重要的是关注点分离：把应用拆分成方法、类、文件、包、模块和层，让它们各有明确的职责和边界。

一个常见错误，是把所有代码都塞进一个 Activity。

Activity 主要负责承载应用界面。它的生命周期由 Android 控制：用户旋转屏幕，或者系统内存不足，都可能让系统销毁它，再重新创建。

因为这些组件可能很快就被销毁，所以不适合用来持有应用数据或状态。如果把数据放在 Activity 里，组件重建时，数据就会丢失。要保住数据、让用户体验稳定，就不要把状态交给这些 UI 组件保管。

自适应布局

应用需要妥善应对配置变化，比如设备方向变化，或者应用窗口大小改变。使用自适应的规范布局，能让应用在不同设备形态上都提供良好的体验。

通过数据模型驱动 UI

另一个重要原则，是让数据模型驱动 UI，最好使用能够持久保存数据的模型。数据模型表示应用的数据，独立于 UI 元素和其他应用组件。也就是说，它们不会跟着 UI 或应用组件的生命周期一起变化。但如果操作系统把应用进程从内存中移除，这些模型仍然会被销毁。

能持久保存数据的模型更理想，原因有两个：

  • 即使 Android 为腾出资源销毁了应用，用户的数据也不会丢失。

  • 即使网络时断时续，或者完全连不上，应用也能继续工作。

用数据模型类作为架构的基础，可以让应用更可靠，也更容易测试。

单一事实来源

每当应用定义一种新的数据类型，都要为它指定一个 single source of truth（SSOT，单一事实来源）。SSOT 是这份数据的所有者，只有它能修改数据。对外，它用不可变类型提供数据；其他类型想修改数据，就调用它提供的函数，或者向它发送事件。

这样做有几个好处：

  • 同一种数据的修改，都集中在一个地方
  • 其他类型不能随意篡改这份数据
  • 更容易追踪数据怎样变化，也更容易发现问题

对于离线优先的应用，这个数据来源通常是数据库。在其他一些场景里，也可以由 ViewModel 担任。

单向数据流

单一事实来源原则常常和单向数据流（UDF）一起使用。UDF 要求状态只沿一个方向流动，通常从父组件传给子组件；要求修改数据的事件，则向相反的方向传递。

在 Android 中，状态或数据通常从层次结构里作用域较大的类型，传给作用域较小的类型。事件通常由作用域较小的类型发起，一路传到那份数据的 SSOT。比如，应用数据从数据源传到 UI；用户按下按钮后，事件从 UI 传回 SSOT，由它修改应用数据，再以不可变类型提供出去。

这种模式更容易保持数据一致，也更少出错、更方便调试，同时保留了 SSOT 模式的全部好处。

关于 UDF 的更多说明，可以看 Jetpack Compose 中的单向数据流。

推荐的应用架构

按照前面的通用原则，每个应用至少应有两层：

  • UI 层：在屏幕上显示应用数据
  • 数据层：包含应用的业务逻辑，并公开应用数据

还可以在中间增加一个可选的 domain layer（领域层），让 UI 层与数据层之间的交互更简单，也更容易复用。

现代应用架构

现代 Android 应用架构会使用下面这些技术，当然也不止这些：

  • 自适应的分层架构
  • 在应用所有层中使用单向数据流（UDF）
  • UI 层通过 state holder（状态持有者）管理复杂的界面状态
  • 协程和 Flow
  • 依赖注入最佳实践

具体可以看 Android 架构建议。

UI 层

UI 层，也叫呈现层，负责把应用数据展示到屏幕上。数据一变，UI 就随之更新。变化可能来自用户操作，比如按下按钮；也可能来自外部输入，比如收到网络响应。

UI 层包含两类内容：

  • 把数据画到屏幕上的 UI 元素。用 Jetpack Compose 函数构建这些元素，可以支持自适应布局。
  • 保存数据、向 UI 提供数据并处理逻辑的 state holder，例如 ViewModel。它应该和自己服务的 UI 元素存活一样长的时间。比如，某个页面的 ViewModel 应一直留在内存中，直到这个页面被移出应用的导航返回栈。具体可以看状态的存活时长。

对于自适应 UI，ViewModel 这样的 state holder 会提供适应不同窗口大小类别的 UI 状态。你可以用 currentWindowAdaptiveInfo() 推导出这个状态。然后，NavigationSuiteScaffold 等组件就能根据这些信息和可用的屏幕空间，自动切换导航方式，比如 NavigationBar、NavigationRail 或 NavigationDrawer。

更多说明可以看 UI 层和 Compose UI 架构。

想了解自适应应用和导航，可以看构建自适应应用和构建自适应导航。

数据层

数据层保存应用的业务逻辑。这些逻辑规定数据怎样创建、保存和修改，也正是它们让应用产生价值。

数据层由 Repository 组成，每个 Repository 可以有零个、一个或多个数据源。应用处理的每一种数据，都应有对应的 Repository 类。比如，电影数据用 MoviesRepository，支付数据用 PaymentsRepository。

Repository 负责这些事：

  • 向应用的其他部分提供数据
  • 把数据修改集中起来处理
  • 解决多个数据源之间的冲突
  • 封装数据来源，让应用其他部分不必了解来源的具体细节
  • 包含业务逻辑

每个数据源类只和一个数据来源打交道，比如文件、网络或本地数据库。应用与系统进行数据操作时，就通过这些数据源类衔接。

更多说明可以看数据层页面。

领域层

领域层是可选的，位于 UI 层与数据层之间。

领域层用来封装复杂的业务逻辑，也可以封装较简单、但被多个 ViewModel 共用的业务逻辑。并不是每个应用都有这些需求，所以只有确实需要时才加这一层，比如逻辑太复杂，或希望提高复用程度。

领域层的类通常叫 use case（用例）或 Interactor。每个 use case 只负责一项功能。比如，多个 ViewModel 都要根据时区显示合适的消息，就可以提供一个 GetTimeZoneUseCase 类。

更多说明可以看领域层页面。

管理组件之间的依赖项

应用里的类通常需要依赖其他类才能工作。要取得这些依赖，可以选择下面两种设计模式之一：

  • 依赖注入（DI）：类只需声明自己需要什么，不必自己创建。运行时，由另一个类把这些依赖提供给它。
  • 服务定位器：提供一个注册表，类从里面取得所需依赖，不必自己创建。

这两种模式都给出了清晰的依赖管理方式，不必重复代码，也不必增加复杂度，有助于代码继续扩展。它们还让你能快速切换测试用的实现和生产环境的实现。

要点：Android 应用应使用依赖注入模式和 Hilt 库。Hilt 会沿着依赖树自动创建对象，在编译时验证依赖，并为 Android 框架类建立依赖容器。

通用最佳实践

编程需要创造力，开发 Android 应用也是如此。同一个问题，往往有不止一种解法。你可能需要在多个 Activity 或 Fragment 之间传数据，也可能需要把远程数据取回来、存在本地，以便离线使用；复杂应用还会遇到许多其他常见场景。

下面这些建议不是强制规定，但在大多数情况下，照着做会让代码更可靠、更容易测试，也更容易维护。

不要在应用组件中存储数据。

不要把 Activity、Service、BroadcastReceiver 这些应用入口当作数据来源。让它们与其他组件协作，只取得当前入口需要的那部分数据。每个应用组件都可能只存活很短时间，具体取决于用户怎样操作设备，以及系统有多少资源可用。

减少对 Android 类的依赖。

把对 Android 框架 SDK API 的依赖，比如 Context 或 Toast，限制在应用组件中。让其他类与这些组件分开，可以让测试更容易，也能减少应用内部的耦合。

在应用模块之间定义清晰的职责边界。

从网络加载数据的代码，不要散落在不同的类和包里。同样，也不要把数据缓存、数据绑定这样不相关的职责塞进同一个类。应遵循推荐的应用架构。

让每个模块尽可能少地公开内容。

不要为了省事，把模块内部的实现细节暴露出去。眼下可能省一点时间，但代码继续演进后，可能要付出数倍的技术债务。

专注于应用独特的核心，使其有别于其他应用。

不要一遍遍地写相同的样板代码、重复造轮子。把时间和精力放在应用独有的价值上，重复工作交给 Jetpack 和其他推荐的库。

使用标准布局和应用设计模式。

Jetpack Compose 提供了可靠的 API，帮助你构建自适应界面。在应用中使用标准布局，可以改善不同设备形态和屏幕尺寸下的体验。再参考应用设计模式图库，选择最适合当前场景的布局。

在配置变化期间保留 UI 状态。

设计自适应布局时，显示区域调整大小、设备折叠或方向改变，都不应丢掉 UI 状态。架构需要保证用户当前的状态能保留下来，让操作体验连续。

设计可复用、可组合的 UI 组件。

把 UI 组件做成可以复用、可以组合的形式，能更好地支持自适应设计。面对不同屏幕大小和设备姿态，只需组合、重新排列这些组件，就不必大幅重构。

考虑如何让应用各部分能够单独测试。

如果网络取数有清晰的 API，那么测试“把数据存进本地数据库”的模块就会更容易。反过来，把这两部分逻辑混在一起，或者让网络代码散落在整个项目里，测试就会困难得多，甚至没法做。

类型负责自己的并发策略。

如果某个类型需要执行耗时、会阻塞线程的工作，就应由它自己把计算切换到合适的线程。因为它最清楚自己在算什么、应该在哪个线程算。这样的类型应做到 main-safe（主线程安全）：调用方可以放心地从主线程调用它，而不会把主线程阻塞住。

尽可能持久化相关且最新的数据。

这样，即使设备离线，用户仍然可以使用应用功能。别忘了，不是所有用户都能一直连着高速网络；即使平时网络很好，在人多拥挤的地方也可能信号不佳。

架构的好处

好的架构落到应用中，会给项目和开发团队带来很多好处：

  • 提高整个应用的可维护性、质量和健壮性。
  • 应用更容易扩展。更多人、更多团队可以在同一套代码上协作，同时尽量减少代码冲突。
  • 新成员更容易上手。架构让项目保持一致，新加入团队的人能更快熟悉工作，更早提高效率。
  • 测试更容易。好的架构鼓励使用简单的类型，而简单类型通常更好测试。
  • 排查问题时，可以沿着明确的流程，有条理地找到原因。

做好架构需要在前期投入时间，但用户也会直接受益：应用更稳定，开发团队效率更高，也能提供更多功能。
