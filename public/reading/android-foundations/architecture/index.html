通用架构原则

如果不能使用应用组件存储应用数据和状态，应该如何设计应用？

随着 Android 应用规模增长，定义一种让应用能够扩展的架构非常重要。设计良好的应用架构会明确应用各部分之间的边界，以及每个部分承担的职责。

关注点分离

设计应用架构时，应遵循几项具体原则。

最重要的原则是关注点分离：将应用拆分成职责和边界明确的方法、类、文件、包、模块和层。

将所有代码都写在一个 Activity 中，是一种常见错误。

Activity 的主要职责是承载应用的 UI。Android 操作系统控制它们的生命周期，经常为响应屏幕旋转等用户操作，或内存不足等系统事件，而销毁和重新创建它们。

这种短暂的特性使它们不适合持有应用数据或状态。如果将数据存储在 Activity 中，组件重建时这些数据就会丢失。为了确保数据保留并提供稳定的用户体验，不要将状态托付给这些 UI 组件。

自适应布局

构建能够妥善处理配置变更的应用，例如设备方向变化或应用窗口大小变化。实现自适应的规范布局，为多种设备形态提供最佳用户体验。

通过数据模型驱动 UI

另一项重要原则是通过数据模型驱动 UI，最好使用持久化模型。数据模型代表应用的数据。它们独立于应用中的 UI 元素和其他组件。这意味着它们不与 UI 和应用组件的生命周期绑定，但当操作系统将应用进程从内存中移除时，它们仍会被销毁。

持久化模型之所以理想，有以下原因：

  • 如果 Android 操作系统为释放资源而销毁应用，用户不会丢失数据。

  • 网络连接时断时续或不可用时，应用仍可继续工作。

以数据模型类作为应用架构的基础，使应用健壮且易于测试。

单一事实来源

在应用中定义新数据类型时，为它指定一个单一事实来源（SSOT）。SSOT 是该数据的所有者，只有 SSOT 可以修改或变更它。为此，SSOT 使用不可变类型公开数据；为了修改数据，SSOT 会公开其他类型可以调用的函数，或接收它们发来的事件。

这种模式有多项好处：

  • 将对某种数据的所有修改集中在一个位置
  • 保护数据，使其他类型无法篡改它
  • 使数据变化更容易追踪，从而更容易发现错误

在离线优先的应用中，应用数据的事实来源通常是数据库。在其他一些情况下，事实来源可以是 ViewModel。

单向数据流

单一事实来源原则通常与单向数据流（UDF）模式一起使用。在 UDF 中，状态只沿一个方向流动，通常从父组件流向子组件。修改数据的事件则沿相反方向流动。

在 Android 中，状态或数据通常从层次结构中作用域较大的类型流向作用域较小的类型。事件通常由作用域较小的类型触发，直到到达对应数据类型的 SSOT。例如，应用数据通常从数据源流向 UI。按钮按下等用户事件则从 UI 流向 SSOT，应用数据在那里被修改，并以不可变类型公开。

这种模式能更好地维持数据一致性，更不容易出错，更容易调试，并具有 SSOT 模式的全部好处。

有关 UDF 的更多信息，请参阅 Jetpack Compose 中的单向数据流。

推荐的应用架构

考虑通用架构原则，每个应用都应设计为至少包含两层：

  • UI 层：在屏幕上显示应用数据
  • 数据层：包含应用的业务逻辑，并公开应用数据

可以添加一个称为领域层的额外层，以简化和复用 UI 层与数据层之间的交互。

现代应用架构

现代 Android 应用架构使用以下技术，以及其他技术：

  • 自适应的分层架构
  • 在应用所有层中使用单向数据流（UDF）
  • UI 层使用状态持有者管理 UI 的复杂性
  • 协程和 Flow
  • 依赖注入最佳实践

有关详情，请参阅 Android 架构建议。

UI 层

UI 层（或呈现层）的职责是在屏幕上显示应用数据。无论是用户交互（例如按下按钮），还是外部输入（例如网络响应）导致数据变化，UI 都会更新以反映这些变化。

UI 层由两类构造组成：

  • 将数据渲染到屏幕上的 UI 元素。使用 Jetpack Compose 函数构建这些元素，以支持自适应布局。
  • 状态持有者（例如 ViewModel），负责持有数据、向 UI 公开数据并处理逻辑。状态持有者的存活时长应与它为之提供状态的 UI 元素相同。例如，屏幕的 ViewModel 应一直保留在内存中，直到该屏幕从应用的导航返回栈中移除。有关详情，请参阅状态的存活时长。

对于自适应 UI，ViewModel 对象等状态持有者会公开适应不同窗口大小类别的 UI 状态。可以使用 currentWindowAdaptiveInfo() 推导此 UI 状态。随后，NavigationSuiteScaffold 等组件可以使用这些信息，根据可用屏幕空间，在不同导航模式（例如 NavigationBar、NavigationRail 或 NavigationDrawer）之间自动切换。

如需了解更多信息，请参阅 UI 层和 Compose UI 架构。

有关自适应应用和导航的更多信息，请参阅构建自适应应用和构建自适应导航。

数据层

应用的数据层包含业务逻辑。业务逻辑赋予应用价值——它由决定应用如何创建、存储和更改数据的规则组成。

数据层由 Repository 组成，每个 Repository 可以包含零个到多个数据源。为应用处理的每种不同类型的数据创建一个 Repository 类。例如，可以为电影相关数据创建 MoviesRepository 类，或为支付相关数据创建 PaymentsRepository 类。

Repository 类负责以下事项：

  • 向应用其余部分公开数据
  • 集中处理数据变更
  • 解决多个数据源之间的冲突
  • 向应用其余部分抽象数据来源
  • 包含业务逻辑

每个数据源类只负责与一个数据来源交互，该来源可以是文件、网络来源或本地数据库。数据源类是应用与系统之间进行数据操作的桥梁。

如需了解更多信息，请参阅数据层页面。

领域层

领域层是 UI 层与数据层之间的一个可选层。

领域层负责封装复杂的业务逻辑，或被多个 ViewModel 复用的较简单的业务逻辑。领域层是可选的，因为并非所有应用都有这些需求。只在需要时使用它——例如，为了处理复杂性或提高复用性。

领域层中的类通常称为用例或 Interactor。每个用例负责一项功能。例如，如果多个 ViewModel 都依赖时区来在屏幕上显示适当的消息，应用可以有一个 GetTimeZoneUseCase 类。

如需了解更多信息，请参阅领域层页面。
