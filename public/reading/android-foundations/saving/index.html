本指南讨论用户对 UI 状态的预期，以及可用于保留状态的方案。

在系统销毁宿主 Activity 或应用进程后，迅速保存和恢复 UI 状态，对于良好的用户体验至关重要。用户期望 UI 状态保持不变，但系统可能会销毁承载该屏幕的 Activity 及其中存储的状态。

为了弥合用户预期与系统行为之间的差距，应组合使用以下方法：

  • ViewModel 对象。
  • 以下上下文中的保存状态：
    • 可组合项：rememberSerializable 和 rememberSaveable。
    • ViewModel：SavedStateHandle。
  • 使用本地存储，在应用和屏幕切换期间持久保存 UI 状态。

最佳方案取决于 UI 数据的复杂程度、应用的用例，以及如何在数据访问速度与内存使用之间取得平衡。

确保应用满足用户预期，并提供快速、响应灵敏的界面。避免将数据加载到 UI 时出现延迟，尤其是在旋转等常见配置变更之后。

用户预期与系统行为

根据所执行的操作，用户会期望 UI 状态被清除或被保留。在某些情况下，系统会自动执行用户预期的行为；在另一些情况下，系统的行为则恰好相反。

用户发起的 UI 状态清除

用户期望导航到某个屏幕后，该屏幕的临时 UI 状态会保持不变，直到用户将其完全关闭。用户可以通过以下方式完全关闭屏幕或应用：

  • 从概览（最近使用的应用）屏幕中滑动移除应用。
  • 在“设置”屏幕中终止或强制退出应用。
  • 重新启动设备。
  • 完成某种“结束”操作（其背后调用了 Activity.finish()）。

在这些完全关闭的情况下，用户认为自己已经永久离开了该屏幕；如果再次返回，他们期望屏幕从一个干净的状态开始。这些关闭场景下的底层系统行为符合用户预期——宿主 Activity 实例会被销毁并从内存中移除，其中存储的任何状态，以及与其关联的任何已保存状态记录，也会一起被移除。

这条关于完全关闭的规则也有一些例外——例如，用户可能期望在使用返回按钮退出浏览器后，浏览器能让他们回到退出前正在查看的那个网页。

系统发起的 UI 状态清除

用户期望屏幕的 UI 状态在配置变更（例如旋转或切换到多窗口模式）期间保持不变。不过，默认情况下，系统会在发生这类配置变更时销毁宿主 Activity，清除其中存储的任何 UI 状态。如需详细了解设备配置，请参阅在 Jetpack Compose 中响应配置变更。

注意，可以重写配置变更的默认行为，但不推荐这样做。有关详情，请参阅处理配置变更。

用户也期望在暂时切换到其他应用、之后再返回你的应用时，应用的 UI 状态保持不变。例如，用户在某个屏幕上执行搜索，然后按下主屏幕按钮或接听电话——返回搜索屏幕时，他们期望搜索关键词和结果仍然存在，与之前完全一样。

在这种情况下，应用会被置于后台，系统会尽力将应用进程保留在内存中。不过，在用户离开并与其他应用交互期间，系统可能会销毁应用进程。此时，宿主 Activity 及其中存储的任何状态都会被销毁。当用户重新启动应用时，屏幕会出乎意料地处于一个干净的状态。如需详细了解进程死亡，请参阅进程与应用生命周期。

保留 UI 状态的方案

当用户对 UI 状态的预期与默认系统行为不一致时，必须保存并恢复用户的 UI 状态，以确保用户不会察觉系统发起的销毁。

各种保留 UI 状态的方案，在以下影响用户体验的维度上有所不同：

ViewModel保存状态持久存储
存储位置内存中内存中磁盘或网络上
配置变更后仍保留是是是
系统发起的进程死亡后仍保留否是是
用户完全关闭屏幕或调用 finish() 后仍保留否否是
数据限制可以存储复杂对象，但空间受可用内存限制仅适用于基本类型，以及 String 等简单的小型对象仅受磁盘空间，或从网络资源检索数据的成本／时间限制
读写时间快（仅访问内存）慢（需要序列化／反序列化）慢（需要磁盘访问或网络事务）
注意：上表中的保存状态包括用于可组合项的 rememberSerializable API（如果未使用 KTX 序列化，则是 rememberSaveable），以及用于 ViewModel 的 SavedStateHandle。

使用 ViewModel 处理配置变更

在用户主动使用应用期间，ViewModel 非常适合存储和管理与 UI 相关的数据。它允许快速访问 UI 数据，并帮助你在旋转、调整窗口大小以及其他常见配置变更期间，避免重新从网络或磁盘获取数据。如需了解如何实现 ViewModel，请参阅 ViewModel 指南。

ViewModel 将数据保留在内存中，这意味着检索这些数据比从磁盘或网络检索数据的开销更小。ViewModel 与某个生命周期所有者（例如 Navigation 目的地或 Activity）关联。在配置变更期间，它会留在内存中，系统会自动将 ViewModel 与配置变更产生的新生命周期所有者实例关联。

与保存状态不同，ViewModel 会在系统发起的进程死亡期间被销毁。要在系统发起的进程死亡后，在 ViewModel 中重新加载数据，请使用 SavedStateHandle API。或者，如果数据与 UI 相关，且无需保存在 ViewModel 中，则使用 rememberSerializable。对于基本数据类型，或不想使用 @Serializable 的场景，应使用 rememberSaveable。如果数据属于应用数据，那么将其持久保存到磁盘可能更合适。

如果已经有一套在配置变更期间将 UI 状态保存在内存中的方案，可能就不需要使用 ViewModel。

使用保存状态作为后备方案，处理系统发起的进程死亡

Compose 中的 rememberSerializable、rememberSaveable 以及 ViewModel 中的 SavedStateHandle 等 API，会存储在系统销毁组件、之后又重新创建组件时重新加载 UI 状态所需的数据。为了更高效地处理复杂数据结构，SavedStateHandle 通过 saved {} 扩展支持 Kotlinx Serialization，使你能够在标准基本类型之外，无缝地持久保存和恢复类型安全的对象。如需了解如何使用 rememberSaveable 实现保存状态，请参阅状态与 Jetpack Compose。

保存状态的 Bundle 可以在配置变更和进程死亡后保留下来，但由于各个 API 会对数据进行序列化，它们会受到存储空间和速度的限制。如果被序列化的对象很复杂，序列化可能消耗大量内存。由于此过程会在配置变更期间发生在主线程上，耗时较长的序列化可能导致丢帧和画面卡顿。

要点：保存状态 API 只会在 Activity 停止时保存写入其中的数据。在两次进入此生命周期状态之间写入数据，会将保存操作推迟到下一个停止生命周期事件。

不要使用保存状态来存储大量数据（例如位图），也不要存储需要长时间序列化或反序列化的复杂数据结构。应只存储基本类型，以及 String 等简单的小型对象。因此，应使用保存状态来存储最低限度的必要数据（例如 ID），以便在其他持久化机制失效时，重新创建将 UI 恢复到先前状态所需的数据。大多数应用都应该实现此机制，以处理系统发起的进程死亡。

注意：Android 会在进程之外的内存中保留一份序列化的数据副本。根据各种因素，系统可能会尝试优化这一过程，让同一个 Bundle 对象未经序列化就留在内存中，以便更快访问。不过，这些行为可能会随 Android API 版本而变化。
警告：如果使用 PersistableBundle 而不是 Bundle，系统有可能将数据存储到磁盘。不过，Jetpack Compose 和其他 AndroidX 库不支持它。因此，应使用 Bundle。

根据应用的用例，可能根本不需要使用保存状态。例如，浏览器可能会让用户回到退出浏览器之前正在查看的那个网页。如果 Activity 的行为如此，可以放弃使用保存状态，改为将所有内容持久保存在本地。

要点：通常，保存状态中存储的数据是依赖于用户输入或导航的临时状态。例如，列表的滚动位置、用户想进一步了解的条目的 ID、正在进行中的用户偏好选择，或文本字段中的输入。

此外，通过 Intent 打开 Activity 时，无论是配置发生变更，还是系统恢复 Activity，附加数据的 Bundle 都会传递给该 Activity。如果某项 UI 状态数据（例如搜索查询）在 Activity 启动时作为 Intent 附加数据传入，就可以使用附加数据的 Bundle，而不必使用保存状态的 Bundle。如需详细了解 Intent 附加数据，请参阅 Intent 与 Intent Filter。

在上述任一场景下，仍应使用 ViewModel，避免在配置变更期间浪费处理周期从数据库重新加载数据。

如果需要保留的 UI 数据简单且轻量，可以只使用保存状态 API 来保留状态数据。

要点：使用哪个 API，取决于状态存放在哪里，以及它所需的逻辑。对于用于业务逻辑的状态，应将其放在 ViewModel 中，并使用 SavedStateHandle 保存。对于用于 UI 逻辑的状态，应使用 rememberSerializable 或 rememberSaveable。

使用本地持久化处理进程死亡时的复杂数据或大量数据

只要应用仍安装在用户设备上，数据库或 DataStore 等持久化本地存储就会一直存在（除非用户清除了应用数据）。虽然这种本地存储可以在系统发起的应用进程死亡后保留下来，但检索它的开销可能很大，因为必须将数据从本地存储读入内存。通常，这种持久化本地存储可能已经是应用架构的一部分，用来存储那些在打开和关闭应用时不希望丢失的所有数据。

ViewModel，以及使用 rememberSerializable、rememberSaveable 或 SavedStateHandle 保存的状态，都不是长期存储方案，因此不能替代数据库等本地存储。应只使用这些机制来暂时存储临时 UI 状态，并使用持久存储来保存其他应用数据。如需详细了解如何利用本地存储长期保留应用模型数据（例如跨越设备重启），请参阅应用架构指南。

管理 UI 状态：分而治之

通过让不同类型的持久化机制分担工作，可以高效地保存和恢复 UI 状态。在大多数情况下，应根据数据复杂度、访问速度和存活时长之间的权衡，让每种机制存储应用使用的不同类型的数据：

  • 本地持久化：存储所有在打开和关闭应用时不希望丢失的应用数据。
    • 示例：歌曲对象集合，其中可能包含音频文件和元数据。
  • ViewModel：在内存中存储显示关联 UI 所需的全部数据，即屏幕 UI 状态。
    • 示例：最近一次搜索得到的歌曲对象，以及最近一次搜索查询。
  • 保存状态（rememberSerializable、rememberSaveable 和 SavedStateHandle）：存储少量数据，以便系统停止并重新创建 UI 时重新加载 UI 状态。不要在这里存储复杂对象，而应将复杂对象持久保存在本地存储中，并在保存状态 API 中存储这些对象的唯一 ID。
    • 示例：存储最近一次搜索查询。

以一个允许搜索歌曲库的应用为例。不同事件应按如下方式处理：

用户添加歌曲时，ViewModel 会立即将这项数据的本地持久化工作委托出去。如果新添加的歌曲应显示在 UI 中，还应更新 ViewModel 对象中的数据，以反映歌曲的加入。请记住，所有数据库插入操作都应在主线程之外执行。

用户搜索歌曲时，无论从数据库加载了哪些复杂的歌曲数据，都应立即将它们存储在 ViewModel 对象中，作为屏幕 UI 状态的一部分。

当应用进入后台，系统保存状态时，应使用保存状态 API 存储搜索查询，以备进程重新创建。由于这些信息是加载此处持久保存的应用数据所必需的，应将搜索查询存储在 ViewModel 的 SavedStateHandle 中，或在可组合项中使用 rememberSerializable 或 rememberSaveable。这就是加载数据并将 UI 恢复到当前状态所需的全部信息。

恢复复杂状态：重新组装各个部分

用户返回应用时，重新创建 UI 有两种可能的场景：

  • 系统结束应用进程后重新创建 UI。系统保存了通过保存状态 API 存储的查询。ViewModel（使用 SavedStateHandle）或可组合项（使用 rememberSerializable 或 rememberSaveable）会自动恢复查询。如果查询由可组合项恢复，它会将查询传给 ViewModel。ViewModel 发现自己没有缓存的搜索结果，就会委托执行使用给定搜索查询加载搜索结果的工作。
  • 配置变更后重新创建 UI。由于 ViewModel 实例没有被销毁，所有信息都已缓存在 ViewModel 的内存中，无需重新查询数据库。
注意：屏幕最初创建时，保存状态中没有数据，ViewModel 对象也是空的。创建 ViewModel 对象时，传入一个空查询，告知 ViewModel 对象目前没有需要加载的数据。因此，UI 从空状态开始。
