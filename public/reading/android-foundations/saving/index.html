本指南介绍用户对 UI 状态有哪些预期，以及可以用哪些方案保留这些状态。

要提供良好的用户体验，就需要保存 UI 状态，并在系统销毁承载页面的 Activity 或应用进程后迅速恢复它。用户希望 UI 状态保持不变，但系统可能会销毁承载页面的 Activity，以及其中保存的状态。

要让应用在这些系统行为下仍能符合用户预期，应结合使用以下方法：

  • ViewModel 对象。
  • 在以下位置使用 saved state（已保存的状态）：
    • composable（可组合函数）中：rememberSerializable 和 rememberSaveable。
    • ViewModel：SavedStateHandle。
  • 使用本地存储持久保存 UI 状态，使其在应用或页面切换时仍能保留。

哪种方案最合适，取决于 UI 数据的复杂程度、应用的使用场景，以及数据访问速度和内存占用之间的取舍。

应确保应用符合用户预期，界面流畅、响应及时。向 UI 加载数据时应避免延迟，尤其是在屏幕旋转等常见的配置变更（configuration change）之后。

用户预期与系统行为

用户执行不同操作时，对 UI 状态的预期也不同：有时希望清除，有时希望保留。有些情况下，系统的默认行为正好符合用户预期；另一些情况下，则与用户预期相反。

用户主动关闭页面时清除 UI 状态

用户进入一个页面后，会希望它的临时 UI 状态一直保留，直到自己完全关闭这个页面。用户可以通过以下方式完全关闭页面或应用：

  • 在 Overview / Recents（最近使用的应用）界面中划掉应用。
  • 在“设置”界面中终止或强制退出应用。
  • 重新启动设备。
  • 执行某种“结束”操作，其底层会调用 Activity.finish()。

在这些完全关闭的场景中，用户认为自己已经彻底离开了页面；如果再次打开，就应从不带上次临时状态的初始状态开始。此时，系统的底层行为符合用户预期：承载页面的 Activity 实例会被销毁并从内存中移除，其中存储的状态，以及与它关联的 saved state 记录，也都会被移除。

不过，完全关闭后的行为也有例外。例如，用户通过返回按钮退出浏览器后，可能仍希望下次打开浏览器时回到退出前正在查看的网页。

系统销毁组件时清除 UI 状态

发生屏幕旋转、切换到多窗口模式等配置变更时，用户希望页面的 UI 状态保持不变。但系统默认会在这类变更发生时销毁承载页面的 Activity，其中存储的 UI 状态也会随之被清除。如需进一步了解设备配置，请参阅在 Jetpack Compose 中响应配置变更。

你可以修改配置变更时的默认处理行为，但不推荐这样做。详情请参阅处理配置变更。

用户暂时切换到其他应用、稍后再返回时，也希望 UI 状态保持不变。例如，用户在页面中搜索后，按下 Home 按钮或接听电话；再次回到搜索页面时，会希望搜索词和搜索结果都还在，与离开前一样。

此时，应用会进入后台，系统会尽量把应用进程保留在内存中。不过，用户使用其他应用期间，系统仍可能终止你的应用进程，承载页面的 Activity 及其中存储的状态也会随之被销毁。用户再次启动应用时，就会意外发现页面回到了初始状态。如需进一步了解进程终止（process death），请参阅进程与应用生命周期。

保留 UI 状态的方案

如果用户对 UI 状态的预期与系统默认行为不一致，就必须保存并恢复 UI 状态，让用户察觉不到系统销毁组件所带来的影响。

不同的 UI 状态保留方案，在以下几个方面存在差异，这些差异会影响用户体验：

ViewModelsaved state持久存储
存储位置内存中内存中磁盘或网络上
配置变更后能否保留是是是
进程被系统终止后能否保留否是是
用户完全关闭页面或调用 finish() 后能否保留否否是
数据限制可以保存复杂对象，但容量受可用内存限制只能保存基本类型，以及 String 等简单的小对象仅受磁盘容量，或从网络获取数据的成本与耗时限制
读写耗时快（仅访问内存）慢（需要序列化／反序列化）慢（需要访问磁盘或进行网络传输）
注意：上表中的 saved state 包括 composable 使用的 rememberSerializable API（如果不使用 KTX 序列化，则使用 rememberSaveable），以及 ViewModel 使用的 SavedStateHandle。

使用 ViewModel 处理配置变更

用户正在使用应用时，ViewModel 很适合存储和管理 UI 相关数据。它能让你快速访问这些数据，并避免在屏幕旋转、窗口大小调整等常见配置变更后，再次从网络或磁盘获取数据。如需了解如何实现 ViewModel，请参阅ViewModel 指南。

ViewModel 把数据保存在内存中，因此访问开销比从磁盘或网络读取更小。每个 ViewModel 都与一个 LifecycleOwner（生命周期所有者）关联，例如一个 Navigation destination（导航目的地）或 Activity。发生配置变更时，ViewModel 会继续保留在内存中，系统会自动将它关联到配置变更后新建的 LifecycleOwner 实例。

与 saved state 不同，进程被系统终止时，ViewModel 也会被销毁。要在进程被系统终止后，让 ViewModel 重新加载数据，可以使用 SavedStateHandle API。如果数据只与 UI 有关，不需要放在 ViewModel 中，则可以使用 rememberSerializable。对于基本数据类型，或不想使用 @Serializable 的场景，应使用 rememberSaveable。如果属于应用数据，将其持久保存到磁盘可能更合适。

如果你已经有一套方案，能在配置变更期间将 UI 状态保留在内存中，就可能不必再使用 ViewModel。

使用 saved state 作为后备方案，应对进程被系统终止

Compose 中的 rememberSerializable、rememberSaveable，以及 ViewModel 中的 SavedStateHandle 等 API，会保存恢复 UI 状态所需的数据，以便系统销毁组件、随后重新创建组件时使用。为了更高效地处理复杂数据结构，SavedStateHandle 通过 saved {} 扩展支持 Kotlinx Serialization；这样，除了标准基本类型，你也能方便地保存和恢复类型安全的对象。如需了解如何使用 rememberSaveable 实现 saved state，请参阅状态与 Jetpack Compose。

用于 saved state 的 Bundle 能在配置变更和进程终止后保留下来，但保存容量和速度都有限，因为这些 API 需要对数据进行序列化。如果对象比较复杂，序列化可能消耗大量内存。配置变更时，这一过程会在主线程上执行；如果序列化耗时过长，就可能导致丢帧和画面卡顿。

要点：saved state API 只会在 Activity 停止时，保存此前写入的数据。如果在两次停止事件之间写入数据，就要等到下一次停止事件发生时，才会执行保存。

不要用 saved state 保存 bitmap（位图）等大量数据，也不要保存序列化或反序列化耗时较长的复杂数据结构。它应当只保存基本类型，以及 String 等简单的小对象。因此，只需在 saved state 中保存 ID 等最少量的必要数据；这样，即使其他持久化机制失效，也能据此重新构建所需的数据，将 UI 恢复到先前状态。大多数应用都应实现这套机制，以应对进程被系统终止的情况。

注意：Android 会在应用进程之外的内存中，保留一份序列化后的数据副本。系统可能根据不同因素优化这一过程：让同一个 Bundle 对象直接保留在内存中，省去序列化，以加快访问。不过，具体行为可能随 Android API 版本而变化。
警告：如果使用 PersistableBundle 而不是 Bundle，系统有可能把数据保存到磁盘。但 Jetpack Compose 和其他 AndroidX 库不支持前者，因此应使用 Bundle。

某些使用场景可能完全不需要 saved state。例如，浏览器可能希望用户再次打开时，仍能回到退出前查看的网页。如果你的 Activity 也需要这样的行为，可以不使用 saved state，而是把所有内容持久保存在本地。

要点：saved state 通常保存由用户输入或导航决定的临时状态，例如列表滚动位置、用户想查看详情的条目 ID、尚未完成的偏好设置选择，以及文本输入框中的内容。

此外，通过 Intent 打开 Activity 时，其中的 extras（附加数据）Bundle 会在配置变更或系统恢复 Activity 时，再次交给该 Activity。如果搜索词等 UI 状态数据在启动 Activity 时已通过 Intent extras 传入，就可以使用这份 extras Bundle，而不必再使用 saved state Bundle。如需进一步了解 Intent extras，请参阅Intent 与 Intent Filter。

无论采用上述哪种方式，都仍应使用 ViewModel，避免在配置变更时重复从数据库加载数据，浪费处理资源。

如果需要保留的 UI 数据简单且轻量，也可以只使用 saved state API 来保存。

要点：选择哪种 API，取决于状态由谁持有，以及哪些逻辑需要使用它。业务逻辑需要使用的状态，应放在 ViewModel 中，并用 SavedStateHandle 保存；UI 逻辑需要使用的状态，则应使用 rememberSerializable 或 rememberSaveable。

通过 SavedStateRegistry 接入 saved state

从 Fragment 1.1.0 或其间接依赖的 Activity 1.0.0 开始，ComponentActivity 等 UI 组件实现了 SavedStateRegistryOwner，并提供一个与自身绑定的 SavedStateRegistry。借助 SavedStateRegistry，其他组件可以读取 saved state，也可以向其中提供要保存的数据。例如，ViewModel 的 Saved State 模块会通过 SavedStateRegistry 创建 SavedStateHandle，再将它交给 ViewModel 对象使用。你可以在 LifecycleOwner 内部调用 savedStateRegistry，获取 SavedStateRegistry。

要向 saved state 提供数据，组件必须实现 SavedStateRegistry.SavedStateProvider；这个接口只定义了一个方法：saveState()。组件通过 saveState() 返回一个 Bundle，其中包含自身需要保存的状态。SavedStateRegistry 会在 LifecycleOwner 的生命周期进入状态保存阶段时，调用这个方法。

重要：SavedStateRegistry 只会在承载它的 Activity 停止时保存写入的数据。如果在 Activity 已停止期间继续写入，这些新数据不会被保存，除非该 Activity 再次经历 onStart，然后经历 onStop。
注意：如果你只是想在 Compose UI 中保存自定义数据对象，而不是编写自定义的生命周期感知组件，就不必直接接入 SavedStateRegistry；使用 @Parcelize 或自定义 Saver 即可。详情请参阅在 Compose 中保存 UI 状态。
  class SearchManager : SavedStateRegistry.SavedStateProvider {
      companion object {
          private const val QUERY = "query"
      }

      private val query: String? = null

      ...

      override fun saveState(): Bundle {
          return bundleOf(QUERY to query)
      }
  }

要注册 SavedStateProvider，需调用 SavedStateRegistry 的 registerSavedStateProvider()，传入 provider 本身，以及用于关联其数据的 key（键）。要取回之前为这个 provider 保存的数据，则调用 SavedStateRegistry 的 consumeRestoredStateForKey()，并传入同一个关联数据的 key。

在 ComponentActivity 的 onCreate() 中，调用 super.onCreate() 之后，就可以注册 SavedStateProvider。另一种做法是：在实现了 LifecycleOwner 的 SavedStateRegistryOwner 上设置一个 LifecycleObserver，等到 ON_CREATE 事件发生时再注册 SavedStateProvider。使用 LifecycleObserver 后，注册状态保存逻辑和读取先前状态的代码，就可以与 SavedStateRegistryOwner 本身分离。

  class SearchManager(registryOwner: SavedStateRegistryOwner) : SavedStateRegistry.SavedStateProvider {
      companion object {
          private const val PROVIDER = "search_manager"
          private const val QUERY = "query"
      }

      private val query: String? = null

      init {
          // Register a LifecycleObserver for when the Lifecycle hits ON_CREATE
          registryOwner.lifecycle.addObserver(LifecycleEventObserver { _, event ->
              if (event == Lifecycle.Event.ON_CREATE) {
                  val registry = registryOwner.savedStateRegistry

                  // Register this object for future calls to saveState()
                  registry.registerSavedStateProvider(PROVIDER, this)

                  // Get the previously saved state and restore it
                  val state = registry.consumeRestoredStateForKey(PROVIDER)

                  // Apply the previously saved state
                  query = state?.getString(QUERY)
              }
          }
      }

      override fun saveState(): Bundle {
          return bundleOf(QUERY to query)
      }

      ...
  }

  class SearchActivity : ComponentActivity() {
    private var searchManager = SearchManager(this)

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // Set up your Compose UI here
        setContent {
            // ...
        }
    }
  }
注意：SavedStateRegistry 与其他 saved state API 使用同一个 Bundle 存储数据，因此也适用相同的注意事项和数据限制。

用本地持久化保存复杂或大量数据，应对进程终止

数据库、DataStore 等本地持久化存储中的数据，只要应用还安装在用户设备上，就会一直保留，除非用户清除了应用数据。这些数据能在应用进程被系统终止后继续保留，但读取开销可能较大，因为需要先从本地存储读入内存。你的应用架构中可能已经使用了这类存储，来保存所有不希望随应用打开、关闭而丢失的数据。

ViewModel，以及通过 rememberSerializable、rememberSaveable 或 SavedStateHandle 保存的状态，都不能作为长期存储方案，因此不能替代数据库等本地存储。这些机制只应用于暂时保存临时 UI 状态，其他应用数据则应使用持久存储。如需了解如何通过本地存储长期保留应用模型数据，让数据在设备重启后仍然存在，请参阅应用架构指南。

管理 UI 状态：让不同机制分工处理

让不同的持久化机制分担工作，可以更高效地保存和恢复 UI 状态。通常，应综合考虑数据复杂度、访问速度和存活时长，让每种机制负责保存不同类型的数据：

  • 本地持久化：保存所有不希望在应用打开、关闭时丢失的应用数据。
    • 示例：一组歌曲对象，其中可能包含音频文件和 metadata（元数据）。
  • ViewModel：在内存中保存显示关联 UI 所需的全部数据，也就是屏幕 UI 状态。
    • 示例：最近一次搜索得到的歌曲对象，以及那次搜索使用的搜索词。
  • saved state（rememberSerializable、rememberSaveable 和 SavedStateHandle）：保存少量必要数据，以便系统停止并重新创建 UI 时恢复 UI 状态。不要在这里保存复杂对象，而应将它们持久保存在本地存储中，saved state API 中只保存这些对象的唯一 ID。
    • 示例：保存最近一次使用的搜索词。

以一个支持搜索歌曲库的应用为例，看看不同事件发生时应如何处理：

用户添加歌曲时，ViewModel 应立即委托相应部分将数据持久保存到本地。如果新歌曲需要显示在 UI 中，还应同步更新 ViewModel 对象中的数据，让 UI 能反映这次添加。所有数据库插入操作都应在主线程之外执行。

用户搜索歌曲时，从数据库加载出的复杂歌曲数据，都应立即存入 ViewModel 对象，作为页面 UI 状态的一部分。

应用进入后台、系统保存状态时，应通过 saved state API 保存搜索词，以便进程重建后使用。重新加载已经持久保存的应用数据需要这个搜索词，因此应将它存入 ViewModel 的 SavedStateHandle，或者在 composable 中使用 rememberSerializable 或 rememberSaveable 保存。只需这些信息，就能重新加载数据，让 UI 回到当前状态。

恢复复杂状态：重新组合各部分数据

用户返回应用时，UI 的重建可能发生在以下两种场景中：

  • 系统终止应用进程后重建 UI。系统已通过 saved state API 保存了搜索词，ViewModel（使用 SavedStateHandle）或 composable（使用 rememberSerializable 或 rememberSaveable）会自动恢复它。如果由 composable 恢复搜索词，它会再把搜索词传给 ViewModel。ViewModel 发现自己没有缓存搜索结果，就会委托相应部分，根据恢复的搜索词重新加载结果。
  • 配置变更后重建 UI。由于 ViewModel 实例并未被销毁，所需信息都还缓存在 ViewModel 的内存中，因此不必再次查询数据库。
注意：页面首次创建时，saved state 中没有数据，ViewModel 对象也是空的。创建 ViewModel 对象时传入一个空查询，就相当于告诉 ViewModel 目前没有需要加载的数据，因此 UI 会从空状态开始。
