协程是一种并发设计模式。在 Android 上，它能让异步执行的代码更容易写。Kotlin 从 1.3 版本开始加入协程，其设计借鉴了其他语言中已有的成熟概念。

在 Android 上，耗时任务如果处理不当，就会阻塞主线程，让应用失去响应。协程可以帮助管理这些任务。使用协程的专业开发者中，超过 50% 表示自己的开发效率提高了。本文会介绍怎样用 Kotlin 协程解决这类问题，让应用代码更清楚、更简洁。

特性

对于 Android 异步编程，我们推荐使用协程。它主要有这些特点：

  • 轻量：协程支持挂起，挂起时不会阻塞它所在的线程，所以一个线程就能运行许多协程。相比阻塞线程，挂起既能支持大量并发操作，也更节省内存。
  • 减少内存泄漏：通过结构化并发，把操作放在作用域内运行。
  • 内置取消机制：取消会自动沿着正在运行的协程层次结构传递。
  • 与 Jetpack 集成：许多 Jetpack 库通过扩展完整支持协程。有些还提供自己的协程作用域，方便使用结构化并发。

示例概览

本文的例子按照应用架构指南组织代码：先发起网络请求，再把结果带回主线程，由应用显示给用户。

具体来说，ViewModel 架构组件会在主线程上调用 Repository 层，发起网络请求。下面会一步步调整实现，展示怎样用协程避免阻塞主线程。

ViewModel 提供了一组可以直接使用协程的 KTX 扩展。它们位于 lifecycle-viewmodel-ktx 库中，后面的例子会用到。

依赖项信息

想在 Android 项目中使用协程，先把下面的依赖加到应用的 build.gradle 文件里：

Groovy

dependencies {
    implementation 'org.jetbrains.kotlinx:kotlinx-coroutines-android:1.3.9'
}

Kotlin

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-android:1.3.9")
}

在后台线程中执行

在主线程上发起网络请求，主线程就需要一直等待响应，也就是被阻塞。这时，操作系统无法调用 onDraw()，应用界面就会卡住，甚至弹出“应用无响应”（ANR）对话框。为了让体验更好，下面把这个操作移到后台线程。

先看看 Repository 类目前怎样发起网络请求：

sealed class Result<out R> {
    data class Success<out T>(val data: T) : Result<T>()
    data class Error(val exception: Exception) : Result<Nothing>()
}

private const val loginUrl = "https://example.com/login"

class LoginRepository(private val responseParser: LoginResponseParser) {
    // Function that makes the network request, blocking the current thread
    fun makeLoginRequest(
        jsonBody: String
    ): Result<LoginResponse> {
        val url = URL(loginUrl)
        (url.openConnection() as? HttpURLConnection)?.run {
            requestMethod = "POST"
            setRequestProperty("Content-Type", "application/json; utf-8")
            setRequestProperty("Accept", "application/json")
            doOutput = true
            outputStream.write(jsonBody.toByteArray())
            return Result.Success(responseParser.parse(inputStream))
        }
        return Result.Error(Exception("Cannot open HttpURLConnection"))
    }
}
Coroutines.kt

makeLoginRequest 是同步执行的，会阻塞调用它的线程。为了表示网络请求返回的结果，这里还定义了一个 Result 类。

用户点击按钮等元素时，ViewModel 会发起网络请求：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        val jsonBody = "{ username: \"$username\", token: \"$token\"}"
        loginRepository.makeLoginRequest(jsonBody)
    }
}
Coroutines.kt

照前面的写法，LoginViewModel 发起请求时会阻塞 UI 线程。最简单的改法，是新建一个协程，把网络请求交给 I/O 线程执行：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        // Create a new coroutine to move the execution off the UI thread
        viewModelScope.launch(Dispatchers.IO) {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"
            loginRepository.makeLoginRequest(jsonBody)
        }
    }
}
Coroutines.kt

把 login 中的协程代码拆开看：

  • viewModelScope 是 ViewModel KTX 扩展预先提供的 CoroutineScope。所有协程都必须在一个作用域中运行，而 CoroutineScope 就用来管理一个或多个相关协程。
  • launch 会创建一个协程，再由对应的 dispatcher（调度器）安排函数体在哪里执行。
  • Dispatchers.IO 表示让这个协程在专门处理 I/O 的线程上执行。

现在，login 的执行顺序是：

  • 应用在主线程上，从 View 层调用 login。
  • launch 创建一个新协程，网络请求独立地在 I/O 线程上执行。
  • 协程运行的同时，login 会继续往下执行并返回。它可能在网络请求完成前就返回了。为了让例子简单些，这里暂时不处理网络响应。

这个协程由 viewModelScope 启动，因此属于 ViewModel 的作用域。如果用户离开页面，导致 ViewModel 被销毁，viewModelScope 就会自动取消，其中所有正在运行的协程也会一起取消。

不过，这个版本有个问题：任何调用 makeLoginRequest 的地方，都得自己记住先离开主线程。接下来修改 Repository，让它自己负责切换。

使用协程保证主线程安全

一个函数如果不会阻塞主线程上的 UI 更新，就称为 main-safe（主线程安全）。makeLoginRequest 目前不是：从主线程调用它，会把 UI 阻塞住。可以用协程库的 withContext()，把协程的执行切换到另一个线程：

class LoginRepository(
    // ...
) {
    // ...
    suspend fun makeLoginRequest(
        jsonBody: String
    ): Result<LoginResponse> {

        // Move the execution of the coroutine to the I/O dispatcher
        return withContext(Dispatchers.IO) {
            // Blocking network request code
        }
    }
}
Coroutines.kt

withContext(Dispatchers.IO) 会把协程切换到 I/O 线程执行。这样，调用这个函数就不会阻塞主线程，UI 也能在需要时正常更新。

另外，makeLoginRequest 加上了 suspend 关键字。Kotlin 通过这个关键字，要求函数从协程内部调用。

注意：为了方便测试，建议把 Dispatchers 注入 Repository 层。具体可以看在 Android 上测试协程。

下面仍然在 LoginViewModel 中创建协程，但 makeLoginRequest 现在会自己把工作移出主线程，所以 login 中的协程可以直接在主线程上运行：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {

        // Create a new coroutine on the UI thread
        viewModelScope.launch {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"

            // Make the network call and suspend execution until it finishes
            val result = loginRepository.makeLoginRequest(jsonBody)

            // Display result of the network request to the user
            when (result) {
                is Result.Success<LoginResponse> -> { /* Happy path */ }
                else -> { /* Show error in UI */ }
            }
        }
    }
}
Coroutines.kt

这里仍然需要协程，因为 makeLoginRequest 是 suspend 函数，所有 suspend 函数都必须在协程中执行。

和前一个 login 例子相比，现在有两处变化：

  • 调用 launch 时不再传入 Dispatchers.IO。如果没有给 launch 指定 Dispatcher，通过 viewModelScope 启动的协程就会在主线程运行。
  • 现在会处理请求结果，并在界面上显示成功或失败。

调整后，登录过程变成这样：

  • 应用在主线程上，从 View 层调用 login()。
  • launch 在主线程上创建一个新协程，协程开始执行。
  • 在协程里调用 loginRepository.makeLoginRequest() 时，协程后续的执行会先挂起，等 makeLoginRequest() 里的 withContext 代码块运行完再继续。
  • withContext 代码块结束后，login() 中的协程就带着网络结果，回到主线程继续执行。
注意：按照应用架构指南的建议，ViewModel 层应使用 LiveData 与 View 通信。采用这种方式时，ViewModel 的代码在主线程上执行，所以可以直接调用 MutableLiveData 的 setValue()。

处理异常

Repository 层可能抛出异常，可以用 Kotlin 内置的异常支持来处理。下面用 try-catch 代码块处理 Repository 层的异常：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        viewModelScope.launch {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"
            val result = try {
                loginRepository.makeLoginRequest(jsonBody)
            } catch (e: Exception) {
                Result.Error(Exception("Network request failed"))
            }
            when (result) {
                is Result.Success<LoginResponse> -> { /* Happy path */ }
                else -> { /* Show error in UI */ }
            }
        }
    }
}
Coroutines.kt

在这个例子中，makeLoginRequest() 抛出的任何意外异常，都会在 UI 中作为错误来处理。
