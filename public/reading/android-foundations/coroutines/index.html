协程是一种并发设计模式，可以在 Android 上用它简化异步执行的代码。协程在 Kotlin 1.3 版本中加入，基于其他语言中已经确立的概念。

在 Android 上，协程有助于管理长时间运行的任务，否则这些任务可能阻塞主线程，导致应用无响应。使用协程的专业开发者中，超过 50% 表示生产力有所提高。本主题介绍如何使用 Kotlin 协程解决这些问题，让你能够编写更清晰、更简洁的应用代码。

特性

协程是我们推荐的 Android 异步编程方案。值得注意的特性包括：

  • 轻量：由于支持挂起，可以在单个线程上运行许多协程；挂起不会阻塞协程所在的线程。与阻塞相比，挂起在支持许多并发操作的同时节省内存。
  • 更少的内存泄漏：使用结构化并发，在作用域内运行操作。
  • 内置取消支持：取消会自动沿运行中的协程层次结构传播。
  • Jetpack 集成：许多 Jetpack 库包含提供完整协程支持的扩展。有些库还提供自己的协程作用域，可用于结构化并发。

示例概览

基于应用架构指南，本主题中的示例会发起网络请求，并将结果返回主线程，应用随后可以在那里将结果显示给用户。

具体来说，ViewModel 架构组件在主线程上调用 Repository 层，以触发网络请求。本指南会逐步介绍多种使用协程保持主线程不被阻塞的方案。

ViewModel 包含一组直接与协程配合使用的 KTX 扩展。这些扩展位于 lifecycle-viewmodel-ktx 库中，本指南会使用它们。

依赖项信息

要在 Android 项目中使用协程，请将以下依赖项添加到应用的 build.gradle 文件：

Groovy

dependencies {
    implementation 'org.jetbrains.kotlinx:kotlinx-coroutines-android:1.3.9'
}

Kotlin

dependencies {
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-android:1.3.9")
}

在后台线程中执行

在主线程上发起网络请求，会使它等待，也就是阻塞，直到收到响应。由于线程被阻塞，操作系统无法调用 onDraw()，这会使应用卡住，并可能导致“应用无响应”（ANR）对话框。为了获得更好的用户体验，让我们在后台线程上运行此操作。

首先，看一下我们的 Repository 类，了解它如何发起网络请求：

sealed class Result<out R> {
    data class Success<out T>(val data: T) : Result<T>()
    data class Error(val exception: Exception) : Result<Nothing>()
}

private const val loginUrl = "https://example.com/login"

class LoginRepository(private val responseParser: LoginResponseParser) {
    // Function that makes the network request, blocking the current thread
    fun makeLoginRequest(
        jsonBody: String
    ): Result<LoginResponse> {
        val url = URL(loginUrl)
        (url.openConnection() as? HttpURLConnection)?.run {
            requestMethod = "POST"
            setRequestProperty("Content-Type", "application/json; utf-8")
            setRequestProperty("Accept", "application/json")
            doOutput = true
            outputStream.write(jsonBody.toByteArray())
            return Result.Success(responseParser.parse(inputStream))
        }
        return Result.Error(Exception("Cannot open HttpURLConnection"))
    }
}
Coroutines.kt

makeLoginRequest 是同步的，会阻塞调用线程。为了表示网络请求的响应，我们定义了自己的 Result 类。

当用户点击按钮等元素时，ViewModel 会触发网络请求：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        val jsonBody = "{ username: \"$username\", token: \"$token\"}"
        loginRepository.makeLoginRequest(jsonBody)
    }
}
Coroutines.kt

使用上述代码时，LoginViewModel 会在发起网络请求时阻塞 UI 线程。将执行移出主线程的最简单方案，是创建一个新协程，并在 I/O 线程上执行网络请求：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        // Create a new coroutine to move the execution off the UI thread
        viewModelScope.launch(Dispatchers.IO) {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"
            loginRepository.makeLoginRequest(jsonBody)
        }
    }
}
Coroutines.kt

让我们逐项分析 login 函数中的协程代码：

  • viewModelScope 是 ViewModel KTX 扩展中包含的预定义 CoroutineScope。请注意，所有协程都必须在作用域中运行。CoroutineScope 管理一个或多个相关协程。
  • launch 函数会创建一个协程，并将其函数体的执行分派给对应的调度器。
  • Dispatchers.IO 表示此协程应在为 I/O 操作保留的线程上执行。

login 函数的执行过程如下：

  • 应用从 View 层在主线程上调用 login 函数。
  • launch 创建一个新协程，网络请求会在为 I/O 操作保留的线程上独立发起。
  • 协程运行期间，login 函数继续执行并返回，可能在网络请求完成之前就已返回。请注意，为了简单起见，暂时忽略网络响应。

由于此协程通过 viewModelScope 启动，它会在 ViewModel 的作用域中执行。如果 ViewModel 因用户离开屏幕而被销毁，viewModelScope 会自动取消，所有正在运行的协程也会被取消。

上述示例的一个问题是，任何调用 makeLoginRequest 的代码都需要记得显式地将执行移出主线程。让我们看看如何修改 Repository，由它来解决这个问题。

使用协程保证主线程安全

如果一个函数不会阻塞主线程上的 UI 更新，我们就认为它是主线程安全的。makeLoginRequest 函数不是主线程安全的，因为从主线程调用它确实会阻塞 UI。使用协程库中的 withContext() 函数，将协程的执行移到另一个线程：

class LoginRepository(
    // ...
) {
    // ...
    suspend fun makeLoginRequest(
        jsonBody: String
    ): Result<LoginResponse> {

        // Move the execution of the coroutine to the I/O dispatcher
        return withContext(Dispatchers.IO) {
            // Blocking network request code
        }
    }
}
Coroutines.kt

withContext(Dispatchers.IO) 会将协程的执行移到 I/O 线程，使调用函数具备主线程安全性，并让 UI 能够按需更新。

makeLoginRequest 也标有 suspend 关键字。Kotlin 使用这个关键字，强制要求从协程内部调用该函数。

注意：为了更容易测试，我们建议将 Dispatchers 注入 Repository 层。有关详情，请参阅在 Android 上测试协程。

在以下示例中，协程在 LoginViewModel 中创建。由于 makeLoginRequest 会将执行移出主线程，login 函数中的协程现在可以在主线程中执行：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {

        // Create a new coroutine on the UI thread
        viewModelScope.launch {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"

            // Make the network call and suspend execution until it finishes
            val result = loginRepository.makeLoginRequest(jsonBody)

            // Display result of the network request to the user
            when (result) {
                is Result.Success<LoginResponse> -> { /* Happy path */ }
                else -> { /* Show error in UI */ }
            }
        }
    }
}
Coroutines.kt

请注意，这里仍然需要协程，因为 makeLoginRequest 是一个 suspend 函数，而所有 suspend 函数都必须在协程中执行。

这段代码与之前的 login 示例有几处不同：

  • launch 不接收 Dispatchers.IO 参数。如果没有向 launch 传递 Dispatcher，从 viewModelScope 启动的任何协程都会在主线程中运行。
  • 现在会处理网络请求的结果，以显示成功或失败的 UI。

登录函数现在的执行过程如下：

  • 应用从 View 层在主线程上调用 login() 函数。
  • launch 在主线程上创建一个新协程，协程开始执行。
  • 在协程内部，调用 loginRepository.makeLoginRequest() 现在会挂起协程的后续执行，直到 makeLoginRequest() 中的 withContext 块运行完毕。
  • withContext 块完成后，login() 中的协程会携带网络请求的结果，在主线程上恢复执行。
注意：要从 ViewModel 层与 View 通信，请按应用架构指南中的建议使用 LiveData。遵循此模式时，ViewModel 中的代码在主线程上执行，因此可以直接调用 MutableLiveData 的 setValue() 函数。

处理异常

要处理 Repository 层可能抛出的异常，请使用 Kotlin 内置的异常支持。以下示例使用 try-catch 块：

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        viewModelScope.launch {
            val jsonBody = "{ username: \"$username\", token: \"$token\"}"
            val result = try {
                loginRepository.makeLoginRequest(jsonBody)
            } catch (e: Exception) {
                Result.Error(Exception("Network request failed"))
            }
            when (result) {
                is Result.Success<LoginResponse> -> { /* Happy path */ }
                else -> { /* Show error in UI */ }
            }
        }
    }
}
Coroutines.kt

此示例中，makeLoginRequest() 调用抛出的任何意外异常，都会在 UI 中作为错误处理。
