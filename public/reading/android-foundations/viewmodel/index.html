尝试与 Kotlin Multiplatform 配合使用
Kotlin Multiplatform 可以让你与其他平台共享业务逻辑。下面介绍怎样在 KMP 中配置和使用 ViewModel。
为 KMP 设置 ViewModel →

ViewModel 是一种业务逻辑或屏幕级状态持有者。它向 UI 提供状态，并把相关的业务逻辑封装起来。最大的好处是：它能缓存状态，并在配置变化时保留下来。因此，在 Activity 之间切换，或者旋转屏幕等配置变化之后，UI 不必重新获取数据。

目标：这篇指南会介绍 ViewModel 的基础知识、它在现代 Android 开发中的位置，以及怎样在应用中实现它。

想进一步了解 state holder（状态持有者），可以看状态持有者指南。UI 层的整体介绍则在 UI 层指南中。

ViewModel 的优势

不用 ViewModel，也可以用一个普通类保存 UI 要显示的数据。但在 Activity 或 Navigation 目的地之间切换时，这种做法可能出问题：如果没有通过保存实例状态机制保存，数据就会被销毁。ViewModel 提供了方便的状态保留 API，来解决这个问题。

如果只是保存状态，Compose 还提供了 retain：普通类也能在配置变化后继续存在，不必引入 ViewModel 的整套机制。两者都能保留状态，但生命周期和清理方式不同。因此，通常更安全的做法，是把 ViewModel 提供给被保留的实例使用，而不是反过来。

ViewModel 最主要的好处有两个：

  • 保留 UI 状态。
  • 让 UI 能访问业务逻辑。
注意：ViewModel 完全支持与 Jetpack Compose 以及 Hilt、Navigation 等其他关键 Jetpack 库集成。

保留

ViewModel 不仅能保留自己持有的状态，也能保留由它发起的操作。有了这些缓存，屏幕旋转等常见配置变化发生后，就不必再获取一次数据。

作用域

创建 ViewModel 时，要传入一个实现 ViewModelStoreOwner 接口的对象。它可以是 Navigation 目的地、导航图、Activity，或其他实现了这个接口的类型。你也可以用 rememberViewModelStoreOwner，把 ViewModel 的作用域直接设为某个 composable（可组合项）。这样，ViewModel 就会关联到 ViewModelStoreOwner 的 Lifecycle。只要 ViewModelStoreOwner 还没有永久消失，ViewModel 就会留在内存里；例如，作为所有者的 composable 退出 Composition（组合）时，这个所有者就消失了。

不少类直接或间接实现了 ViewModelStoreOwner 接口。直接实现它的是 ComponentActivity 和 NavBackStackEntry，间接实现的完整列表可以看 ViewModelStoreOwner 参考文档。如果你想让 LazyList 或 Pager 中的每个条目各有自己的 ViewModel 作用域，就用 rememberViewModelStoreProvider()，把所有者的管理交给父级。

宿主 Activity 发生配置变化时，ViewModel 中的异步工作会继续执行。无论 ViewModel 的作用域是 Activity，还是某个 composable，都是如此。这是它能够保留工作的关键。

更多说明可以看后面的 ViewModel 生命周期一节、ViewModel 作用域 API，以及 Jetpack Compose 的状态提升指南。

SavedStateHandle

SavedStateHandle 能保留数据，不仅能应对配置变化，也能应对进程被结束。也就是说，即使用户关闭应用、之后再打开，UI 状态也能保留下来。

关于怎样保存 UI 状态，可以看在 Compose 中保存 UI 状态。

访问业务逻辑

绝大部分业务逻辑都在数据层，但 UI 层也可能需要业务逻辑。比如，页面要把多个 Repository 的数据组合成 UI 状态，或者某类数据本身不需要数据层时。

UI 层的业务逻辑适合放在 ViewModel 里。ViewModel 也负责处理事件；如果需要运用业务逻辑修改应用数据，它会把相关工作交给其他层。

实现 ViewModel

下面是一个掷骰子页面的 ViewModel 实现，用户可以在这个页面上掷骰子。

重要：这个示例把获取、保存用户列表的职责交给 ViewModel，而不是让 Activity 直接承担。
data class DiceUiState(
    val firstDieValue: Int? = null,
    val secondDieValue: Int? = null,
    val numberOfRolls: Int = 0,
)

class DiceRollViewModel : ViewModel() {

    // Expose screen UI state
    private val _uiState = MutableStateFlow(DiceUiState())
    val uiState: StateFlow<DiceUiState> = _uiState.asStateFlow()

    // Handle business logic
    fun rollDice() {
        _uiState.update { currentState ->
            currentState.copy(
                firstDieValue = Random.nextInt(from = 1, until = 7),
                secondDieValue = Random.nextInt(from = 1, until = 7),
                numberOfRolls = currentState.numberOfRolls + 1,
            )
        }
    }
}

然后，在页面级的 composable 中，就可以这样访问 ViewModel：

import androidx.lifecycle.viewmodel.compose.viewModel

// Use the 'viewModel()' function from the lifecycle-viewmodel-compose artifact
@Composable
fun DiceRollScreen(
    viewModel: DiceRollViewModel = viewModel()
) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    // Update UI elements
}

在 ViewModel 中使用协程

ViewModel 支持 Kotlin 协程。就像保留 UI 状态一样，它也能保留异步工作。

具体可以看在 Android 架构组件中使用 Kotlin 协程。

ViewModel 的生命周期

ViewModel 能存活多久，直接取决于它的作用域。只要关联的 ViewModelStoreOwner 还在，ViewModel 就会保留在内存中。所有者可能在下面这些时机消失：

  • 如果所有者是 Activity：Activity 结束时。
  • 如果是 Navigation 条目：条目从返回栈中移除时。
  • 如果是 composable：它退出 Composition 时。用 rememberViewModelStoreOwner，可以把 ViewModel 的作用域直接设为任意一部分 UI，比如 Pager 或 LazyList。

因此，对于需要在配置变化后继续保留的数据，ViewModel 很合适。

图 1 展示了 Activity 从屏幕旋转到最终结束所经历的生命周期状态。旁边同时画出了关联的 ViewModel 存活多久，方便对照。图中具体列出的是 Activity 的各个状态。

通常，系统第一次调用 Activity 的 onCreate() 时，你就会请求一个 ViewModel。在 Activity 存续期间，onCreate() 可能被调用多次，比如设备旋转屏幕时。但从第一次请求 ViewModel 开始，ViewModel 就会一直存在，直到 Activity 最终结束并被销毁。

清理 ViewModel 依赖项

当 ViewModelStoreOwner 在生命周期中销毁 ViewModel 时，ViewModel 会调用 onCleared。你可以在这里清理那些与 ViewModel 一起存活的工作和依赖。

下面演示怎样替代 viewModelScope。viewModelScope 是内置的 CoroutineScope，会自动跟随 ViewModel 的生命周期，ViewModel 可以用它发起业务操作。如果为了更方便地测试，你想用自定义作用域替代 viewModelScope，可以通过构造器把 CoroutineScope 作为依赖传给 ViewModel。等到生命周期结束，ViewModelStoreOwner 清理 ViewModel 时，ViewModel 也会取消这个 CoroutineScope。

class MyViewModel(
    private val coroutineScope: CoroutineScope =
        CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)
) : ViewModel() {

    // Other ViewModel logic ...

    override fun onCleared() {
        coroutineScope.cancel()
    }
}

从 Lifecycle 2.5 版本开始，可以在 ViewModel 构造器里传入一个或多个 Closeable 对象。ViewModel 实例被清理时，这些对象也会自动关闭。

class CloseableCoroutineScope(
    context: CoroutineContext = SupervisorJob() + Dispatchers.Main.immediate
) : Closeable, CoroutineScope {
    override val coroutineContext: CoroutineContext = context
    override fun close() {
        coroutineContext.cancel()
   }
}

class MyViewModel(
    private val coroutineScope: CoroutineScope = CloseableCoroutineScope()
) : ViewModel(coroutineScope) {
    // Other ViewModel logic ...
}

最佳实践

实现 ViewModel 时，应遵循下面几项重要做法：

  • 考虑到 ViewModel 的作用域机制，应把 ViewModel 用作页面级 state holder 的内部实现，不要让它担任标签组、表单等可复用 UI 组件的 state holder。否则，在同一个 ViewModelStoreOwner 下多次使用同一种组件，会拿到同一个 ViewModel 实例；除非你为每个标签明确指定不同的 ViewModel key。
  • ViewModel 不应了解 UI 的具体实现。它对外提供的方法名、UI 状态的字段名，都应尽量通用。这样无论界面出现在手机、折叠屏、平板，还是 Chromebook 上，ViewModel 都能适用。
  • ViewModel 可能比 ViewModelStoreOwner 活得更久。因此，为了避免内存泄漏，不应在里面持有 Context、Resources 等与生命周期有关的 API 引用。
  • 不要把 ViewModel 传给其他类、函数或 UI 组件。它由平台管理，所以应尽量靠近平台使用，也就是靠近 Activity、页面级 composable 函数或 Navigation 目的地。这样，较低层的组件就不会接触到超出自身需要的数据和逻辑。
