本页介绍若干最佳实践，帮助应用在使用协程时提高可扩展性和可测试性。

注意：这些建议适用于广泛的应用。不过，应将它们视为指导原则，并根据自身需求调整。

注入 Dispatcher

创建新协程或调用 withContext 时，不要硬编码 Dispatchers。

// DO inject Dispatchers
class NewsRepository(
    private val defaultDispatcher: CoroutineDispatcher = Dispatchers.Default
) {
    suspend fun loadNews() = withContext(defaultDispatcher) { /* ... */ }
}

// DO NOT hardcode Dispatchers
class NewsRepository {
    // DO NOT use Dispatchers.Default directly, inject it instead
    suspend fun loadNews() = withContext(Dispatchers.Default) { /* ... */ }
}
CoroutinesBestPractices.kt

这种依赖注入模式使测试更容易，因为可以在单元测试和插桩测试中用测试调度器替换这些调度器，使测试更具确定性。

注意：ViewModel 类的 viewModelScope 属性硬编码为 Dispatchers.Main。在测试中应调用 Dispatchers.setMain，传入测试调度器来替换它。
注意：虽然你可能在本站代码片段和 Codelab 中见过硬编码的调度器，但这只是为了保持示例代码简洁。在应用中，应注入调度器。

挂起函数应可安全地从主线程调用

挂起函数应当是主线程安全的，也就是说，从主线程调用它们是安全的。如果某个类在协程中执行长时间运行的阻塞操作，它就有责任使用 withContext 将执行移出主线程。这适用于应用中的所有类，无论它位于架构的哪个部分。

class NewsRepository(private val ioDispatcher: CoroutineDispatcher) {

    // As this operation is manually retrieving the news from the server
    // using a blocking HttpURLConnection, it needs to move the execution
    // to an IO dispatcher to make it main-safe
    suspend fun fetchLatestNews(): List<Article> {
        withContext(ioDispatcher) { /* ... implementation ... */ }
    }
}

// This use case fetches the latest news and the associated author.
class GetLatestNewsWithAuthorsUseCase(
    private val newsRepository: NewsRepository,
    private val authorsRepository: AuthorsRepository
) {
    // This method doesn't need to worry about moving the execution of the
    // coroutine to a different thread as newsRepository is main-safe.
    // The work done in the coroutine is lightweight as it only creates
    // a list and add elements to it
    suspend operator fun invoke(): Result<List<ArticleWithAuthor>> {
        val news = newsRepository.fetchLatestNews()

        val response = mutableListOf<ArticleWithAuthor>()
        for (article in news) {
            val author = authorsRepository.getAuthor(article.author)
            response.add(ArticleWithAuthor(article, author))
        }
        return Result.Success(response)
    }
}

这种模式使应用更容易扩展，因为调用挂起函数的类无需担心哪种工作应该使用哪个 Dispatcher。这项职责属于实际执行工作的类。

应由 ViewModel 创建协程

ViewModel 类应优先创建协程来执行业务逻辑，而不是公开挂起函数。如果无需通过数据流公开状态，仅需发出单个值，ViewModel 中的挂起函数可能很有用。

// DO create coroutines in the ViewModel
class LatestNewsViewModel(
    private val getLatestNewsWithAuthors: GetLatestNewsWithAuthorsUseCase
) : ViewModel() {

    private val _uiState = MutableStateFlow<LatestNewsUiState>(LatestNewsUiState.Loading)
    val uiState: StateFlow<LatestNewsUiState> = _uiState

    fun loadNews() {
        viewModelScope.launch {
            val latestNewsWithAuthors = getLatestNewsWithAuthors()
            _uiState.value = LatestNewsUiState.Success(latestNewsWithAuthors)
        }
    }
}

// Prefer observable state rather than suspend functions from the ViewModel
class LatestNewsViewModel(
    private val getLatestNewsWithAuthors: GetLatestNewsWithAuthorsUseCase
) : ViewModel() {
    // DO NOT do this. News would probably need to be refreshed as well.
    // Instead of exposing a single value with a suspend function, news should
    // be exposed using a stream of data as in the code snippet above.
    suspend fun loadNews() = getLatestNewsWithAuthors()
}
CoroutinesBestPractices.kt

View 不应直接触发协程来执行业务逻辑，而应将该职责交给 ViewModel。这使业务逻辑更易测试，因为 ViewModel 对象可以进行单元测试，而测试 View 则需要插桩测试。

此外，如果工作在 viewModelScope 中启动，协程会自动跨配置变化存活。如果改用 lifecycleScope 创建协程，就需要手动处理。如果协程需要比 ViewModel 的作用域存活更久，请参阅在业务层和数据层中创建协程一节。

注意：View 应为 UI 相关逻辑触发协程，例如从互联网获取图片或格式化字符串。

不要公开可变类型

应优先向其他类公开不可变类型。这样，对可变类型的所有修改都集中在一个类中，出现问题时更易调试。

// DO expose immutable types
class LatestNewsViewModel : ViewModel() {

    private val _uiState = MutableStateFlow(LatestNewsUiState.Loading)
    val uiState: StateFlow<LatestNewsUiState> = _uiState

    /* ... */
}

数据层和业务层应公开挂起函数及 Flow

数据层和业务层中的类通常公开函数，用于执行一次性调用，或在数据随时间变化时接收通知。这些层中的类应为一次性调用公开挂起函数，为数据变化通知公开 Flow。

// Classes in the data and business layer expose
// either suspend functions or Flows
class ExampleRepository {
    suspend fun makeNetworkRequest() { /* ... */ }

    fun getExamples(): Flow<Example> {
        /* ... */
    }
}

此最佳实践让调用方（通常是表现层）能够控制这些层中工作的执行和生命周期，并在需要时取消。

在业务层和数据层中创建协程

对于因不同原因需要创建协程的数据层或业务层类，可以选择不同的方式。

如果协程中的工作只在用户停留于当前屏幕时才有意义，就应遵循调用方的生命周期。在大多数情况下，调用方是 ViewModel；用户离开屏幕并且 ViewModel 被清理时，调用会取消。此时应使用 coroutineScope 或 supervisorScope。

class GetAllBooksAndAuthorsUseCase(
    private val booksRepository: BooksRepository,
    private val authorsRepository: AuthorsRepository,
) {
    suspend fun getBookAndAuthors(): BookAndAuthors {
        // In parallel, fetch books and authors and return when both requests
        // complete and the data is ready
        return coroutineScope {
            val books = async { booksRepository.getAllBooks() }
            val authors = async { authorsRepository.getAllAuthors() }
            BookAndAuthors(books.await(), authors.await())
        }
    }
}
CoroutinesBestPractices.kt

如果只要应用处于打开状态，工作就有意义，且不绑定到某个特定屏幕，那么工作应比调用方的生命周期存活更久。此情形应使用外部 CoroutineScope，如协程与不应取消的工作模式博文所述。

class ArticlesRepository(
    private val articlesDataSource: ArticlesDataSource,
    private val externalScope: CoroutineScope,
) {
    // As we want to complete bookmarking the article even if the user moves
    // away from the screen, the work is done creating a new coroutine
    // from an external scope
    suspend fun bookmarkArticle(article: Article) {
        externalScope.launch { articlesDataSource.bookmarkArticle(article) }
            .join() // Wait for the coroutine to complete
    }
}
CoroutinesBestPractices.kt

externalScope 应由比当前屏幕存活更久的类创建和管理，可以由 Application 类管理，也可以由作用域限定到某个导航图的 ViewModel 管理。

在测试中注入 TestDispatcher

测试时应向类中注入 TestDispatcher 实例。kotlinx-coroutines-test 库提供两种实现：

  • StandardTestDispatcher：通过调度器将其上启动的协程排入队列，并在测试线程不忙时执行。可以使用 advanceUntilIdle 等方法挂起测试线程，让其他排队协程运行。

  • UnconfinedTestDispatcher：以阻塞方式立即运行新协程。这通常使测试更易编写，但会减少对测试期间协程执行方式的控制。

更多细节请参阅各调度器实现的文档。

要测试协程，请使用 runTest 协程构建器。runTest 使用 TestCoroutineScheduler 跳过测试中的延迟，并允许控制虚拟时间。也可以根据需要使用该调度器创建其他测试调度器。

class ArticlesRepositoryTest {

    @Test
    fun testBookmarkArticle() = runTest {
        // Pass the testScheduler provided by runTest's coroutine scope to
        // the test dispatcher
        val testDispatcher = UnconfinedTestDispatcher(testScheduler)

        val articlesDataSource = FakeArticlesDataSource()
        val repository = ArticlesRepository(
            articlesDataSource,
            defaultDispatcher = testDispatcher
        )
        val article = Article()
        repository.bookmarkArticle(article)
        assertThat(articlesDataSource.isBookmarked(article)).isTrue()
    }
}
CoroutinesBestPracticesTest.kt

所有 TestDispatcher 应共享同一个调度器。这样，所有协程代码都可以在单个测试线程上运行，使测试具有确定性。runTest 会等待同一调度器上的所有协程以及测试协程的子协程完成后才返回。

注意：如果被测代码中未使用其他 Dispatchers，上述方式效果最佳。这也是不建议在类中硬编码 Dispatchers 的原因。
注意：协程测试 API 在 kotlinx.coroutines 1.6.0 中发生了重大变化。如果需要从旧版测试 API 迁移，请参阅迁移指南。

避免使用 GlobalScope

这与注入 Dispatcher 最佳实践类似。使用 GlobalScope 就是在硬编码类所使用的 CoroutineScope，会带来以下缺点：

  • 促使值被硬编码。如果硬编码了 GlobalScope，也可能硬编码 Dispatchers。

  • 使测试非常困难，因为代码在不受控制的作用域中执行，无法控制其执行过程。

  • 无法为该作用域内创建的所有协程提供一个共同的执行 CoroutineContext。

相反，对于需要比当前作用域存活更久的工作，应考虑注入 CoroutineScope。有关此主题的更多信息，请参阅在业务层和数据层中创建协程一节。

// DO inject an external scope instead of using GlobalScope.
// GlobalScope can be used indirectly. Here as a default parameter makes sense.
class ArticlesRepository(
    private val articlesDataSource: ArticlesDataSource,
    private val externalScope: CoroutineScope = GlobalScope,
    private val defaultDispatcher: CoroutineDispatcher = Dispatchers.Default
) {
    // As we want to complete bookmarking the article even if the user moves
    // away from the screen, the work is done creating a new coroutine
    // from an external scope
    suspend fun bookmarkArticle(article: Article) {
        externalScope.launch(defaultDispatcher) {
            articlesDataSource.bookmarkArticle(article)
        }
            .join() // Wait for the coroutine to complete
    }
}

// DO NOT use GlobalScope directly
class ArticlesRepository(

    // As we want to complete bookmarking the article even if the user moves away

使协程可取消

协程的取消是协作式的，这意味着当协程的 Job 被取消时，协程要等到挂起或检查取消状态时才会被取消。如果在协程中执行阻塞操作，请确保协程是可取消的。

例如，如果正在从磁盘读取多个文件，应在开始读取每个文件之前检查协程是否已被取消。检查取消状态的一种方式是调用 ensureActive 函数。

someScope.launch {
    for (file in files) {
        ensureActive() // Check for cancellation
        readFile(file)
    }
}
CoroutinesBestPractices.kt

kotlinx.coroutines 中的所有挂起函数，例如 withContext 和 delay，都是可取消的。如果协程调用它们，就不需要做任何额外工作。

有关协程取消的更多信息，请参阅协程中的取消博客文章。

注意异常

协程中抛出的未处理异常可能使应用崩溃。如果可能出现异常，应在通过 viewModelScope 或 lifecycleScope 创建的任何协程的函数体中捕获它们。

class LoginViewModel(
    private val loginRepository: LoginRepository
) : ViewModel() {

    fun login(username: String, token: String) {
        viewModelScope.launch {
            try {
                loginRepository.login(username, token)
                // Update UI, user logged in successfully
            } catch (exception: IOException) {
                // Update UI, login attempt failed
            }
        }
    }
}
CoroutinesBestPractices.kt
注意：为了允许协程取消，不要吞掉 CancellationException 类型的异常（不要捕获它们，或者在捕获后始终重新抛出）。优先捕获 IOException 等具体异常类型，而不是 Exception 或 Throwable 等通用类型。

有关更多信息，请参阅协程中的异常博客文章，或 Kotlin 文档中的协程异常处理。
