当用户在应用中导航、离开应用并返回应用时，应用中的 Activity 实例会经历其生命周期中的不同状态。Activity 类提供了一系列回调，使 Activity 能够得知状态何时发生变化，或者系统正在创建、停止、恢复 Activity，或销毁 Activity 所在的进程。

在生命周期回调方法中，可以声明用户离开和重新进入 Activity 时，Activity 应当如何表现。例如，如果正在构建流式视频播放器，可以在用户切换到其他应用时暂停视频并终止网络连接。当用户返回时，可以重新连接网络，让用户从同一位置继续播放视频。

每个回调都允许执行适合某种特定状态变化的具体工作。在正确的时机执行正确的工作，并妥善处理状态转换，可以让应用更加健壮、性能更好。例如，良好地实现生命周期回调，可以帮助应用避免以下问题：

  • 用户在使用应用时接到电话或切换到其他应用，导致应用崩溃。
  • 用户未主动使用应用时，仍消耗宝贵的系统资源。
  • 用户离开应用并在稍后返回时，丢失用户的进度。
  • 屏幕在横屏和竖屏方向之间旋转时，应用崩溃或丢失用户的进度。

本文详细介绍 Activity 生命周期。首先介绍生命周期模型，接着说明各个回调：执行期间内部会发生什么，以及需要在其中实现什么。

随后，本文简要介绍 Activity 状态与进程被系统终止的可能性之间的关系。最后，讨论与 Activity 状态转换相关的几个主题。

有关处理生命周期的信息，包括最佳实践指导，请参阅 Jetpack Compose 中的生命周期和保存 UI 状态。如需了解如何将 Activity 与架构组件结合，构建健壮、达到生产质量的应用，请参阅应用架构指南。

Activity 生命周期概念

为了处理 Activity 生命周期各阶段之间的转换，Activity 类提供了六个核心回调：onCreate、onStart、onResume、onPause、onStop 和 onDestroy。系统会在 Activity 进入新状态时调用相应的回调。

图 1 以可视化方式展示了这一模型。

当用户开始离开 Activity 时，系统会调用一些方法来拆解该 Activity。在某些情况下，Activity 只会被部分拆解，并且仍然驻留在内存中，例如用户切换到其他应用时。在这些情况下，Activity 仍然可以回到前台。

如果用户返回该 Activity，它会从用户离开的位置恢复。除少数例外，应用在后台运行时启动 Activity 会受到限制。

系统终止某个进程及其中 Activity 的可能性，取决于 Activity 当时所处的状态。有关状态与被从内存中移除的可能性之间的关系，请参阅 Activity 状态与内存回收一节。

根据 Activity 的复杂程度，你可能不需要实现所有生命周期方法。不过，理解每个方法，并实现那些能让应用表现符合用户预期的方法，这一点很重要。

Compose 与生命周期

在 Compose 中，应避免将业务逻辑或手动设置观察者的代码直接放在 onStart 或 onResume 等 Activity 回调中。应使用能够感知 Lifecycle 的副作用和能够感知状态的观察者，使它们自动与 UI 在屏幕上的显示情况保持一致。

  • 感知生命周期的收集：使用 collectAsStateWithLifecycle 来消费来自 ViewModel 的 Flow。当 UI 进入 Started 状态时，此 API 会自动开始收集；当 UI 进入后台时，它会停止收集，从而避免不必要的资源消耗。将 Flow 收集为状态后，可以使用 LifecycleEffects 在生命周期事件发生时运行代码。
  • 逻辑流程：使用这些 API，UI 会通过组合树自然地响应生命周期状态，确保业务逻辑仅在用户主动与组件交互时执行。

有关 Compose 和生命周期的更多信息，请参阅 Jetpack Compose 中的生命周期。

生命周期回调

本节提供 Activity 生命周期中所使用回调方法的概念和实现信息。

有些操作适合放在 Activity 生命周期方法中。不过，实现依赖组件行为的代码应放在组件本身中，而不是放在 Activity 生命周期方法中。为此，需要让依赖组件具备感知生命周期的能力。如需了解如何让依赖组件感知生命周期，请参阅 Jetpack Compose 中的生命周期。

onCreate

必须实现此回调，它会在系统首次创建 Activity 时触发。Activity 创建时会进入 Created 状态。在 onCreate 方法中，执行在 Activity 整个生命周期内只发生一次的基本应用启动逻辑。

例如，onCreate 的实现可以将数据绑定到列表，将 Activity 与 ViewModel 关联，并实例化一些类作用域变量。此方法接收 savedInstanceState 参数，它是一个包含 Activity 先前保存状态的 Bundle 对象。如果该 Activity 从未存在过，则此 Bundle 对象的值为 null。

如果有一个感知生命周期的组件连接到了 Activity 的生命周期，它会收到 ON_CREATE 事件。标有 @OnLifecycleEvent 注解的方法会被调用，以便这个感知生命周期的组件执行 Created 状态所需的任何设置代码。

以下示例展示了如何在一个最简 Activity 中集成 Text 可组合项：

class ExampleActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        setContent { // In here, we can call composables!
            MaterialTheme {
                Greeting(name = "compose")
            }
        }
    }
}

@Composable
fun Greeting(name: String) {
    Text(text = "Hello $name!")
}InteroperabilityAPIsSnippets.kt

Activity 不会一直停留在 Created 状态。onCreate 方法执行完毕后，Activity 会进入 Started 状态，系统会紧接着先后调用 onStart 和 onResume 方法。

onStart

当 Activity 进入 Started 状态时，系统会调用 onStart。应用正在为 Activity 进入前台并变得可交互做准备，此调用会使 Activity 对用户可见。例如，维护 UI 的代码会在此方法中初始化。

当 Activity 进入 Started 状态时，任何与该 Activity 生命周期关联的感知生命周期的组件都会收到 ON_START 事件。

onStart 方法会很快完成；与 Created 状态一样，Activity 不会一直停留在 Started 状态。此回调完成后，Activity 会进入 Resumed 状态，系统会调用 onResume 方法。

onResume

当 Activity 进入 Resumed 状态时，它会进入前台，系统会调用 onResume 回调。应用在此状态下与用户交互。应用会一直停留在此状态，直到发生某件事使焦点离开应用，例如设备接到电话、用户导航到另一个 Activity，或设备屏幕关闭。

当 Activity 进入 Resumed 状态时，任何与该 Activity 生命周期关联的感知生命周期的组件都会收到 ON_RESUME 事件。生命周期组件可以在此处启用那些需要在组件可见且处于前台时运行的功能，例如启动相机预览。

当发生中断事件时，Activity 会进入 Paused 状态，系统会调用 onPause 回调。

如果 Activity 从 Paused 状态返回 Resumed 状态，系统会再次调用 onResume 方法。因此，应实现 onResume，以初始化在 onPause 期间释放的组件，并执行每次 Activity 进入 Resumed 状态时都必须进行的其他初始化。

下面是一个感知生命周期的组件示例，该组件收到 ON_RESUME 事件时会访问相机：

class CameraComponent : LifecycleObserver {
    ...
    @OnLifecycleEvent(Lifecycle.Event.ON_RESUME)
    fun initializeCamera() {
        if (camera == null) {
            getCamera()
        }
    }
    ...
}

上述代码会在 LifecycleObserver 收到 ON_RESUME 事件后初始化相机。不过，在多窗口模式下，即使 Activity 处于 Paused 状态，它也可能完全可见。例如，当应用处于多窗口模式，用户点按不包含该 Activity 的窗口时，该 Activity 会进入 Paused 状态。

如果只希望在应用处于 Resumed 状态（在前台可见且处于活动状态）时启用相机，就应如前所示，在 ON_RESUME 事件之后初始化相机。如果希望在 Activity 处于 Paused 状态但仍可见时（例如在多窗口模式下）继续启用相机，则应在 ON_START 事件之后初始化相机。

不过，在 Activity 处于 Paused 状态时仍启用相机，可能会使多窗口模式下另一个处于 Resumed 状态的应用无法访问相机。有时确实需要在 Activity 处于 Paused 状态时继续启用相机，但这样做实际上可能会降低整体用户体验。

因此，在多窗口模式的情况下，应仔细考虑在生命周期的哪个位置取得共享系统资源的控制权最合适。如需详细了解如何支持多窗口模式，请参阅支持多窗口模式。

无论选择在哪个建立阶段的事件中执行初始化操作，都要确保使用对应的生命周期事件来释放资源。如果在 ON_START 事件之后初始化某个资源，就应在 ON_STOP 事件之后释放或终止它。如果在 ON_RESUME 事件之后初始化，就应在 ON_PAUSE 事件之后释放。

上述代码段将相机初始化代码放在感知生命周期的组件中。也可以将这段代码直接放入 Activity 生命周期回调，例如 onStart 和 onStop，但我们不推荐这样做。将此逻辑放入一个独立的、感知生命周期的组件，可以在多个 Activity 中复用该组件，而不必复制代码。如需了解如何创建感知生命周期的组件，请参阅 Jetpack Compose 中的生命周期。

onPause

系统调用此方法，是用户正在离开 Activity 的第一个信号，但这并不总意味着 Activity 正在被销毁。它表明 Activity 已不再处于前台，但如果用户正在使用多窗口模式，该 Activity 仍然可见。Activity 可能由于以下几种原因进入此状态：

  • 发生了 onResume 回调一节中所述的中断应用执行的事件，使当前 Activity 暂停。这是最常见的情况。
  • 在多窗口模式下，任意时刻只有一个应用拥有焦点，系统会暂停所有其他应用。
  • 打开一个新的半透明 Activity（例如对话框），会使它覆盖的 Activity 暂停。只要该 Activity 仍部分可见但没有焦点，它就会保持暂停状态。

当 Activity 进入 Paused 状态时，任何与该 Activity 生命周期关联的感知生命周期的组件都会收到 ON_PAUSE 事件。生命周期组件可以在此处停止那些在组件不处于前台时无需运行的功能，例如停止相机预览。

使用 onPause 方法暂停或调整这样的操作：当 Activity 处于 Paused 状态时，它们无法继续，或可以适度继续，并且你预计很快就会恢复它们。

在 Activity 处于 Paused 状态且用户不需要相关资源时，也可以使用 onPause 方法释放系统资源、传感器（例如 GPS）的句柄，或任何影响电池续航的资源。

不过，如 onResume 一节所述，如果应用处于多窗口模式，Paused 状态的 Activity 仍可能完全可见。可以考虑使用 onStop 而不是 onPause，来完全释放或调整与 UI 相关的资源和操作，从而更好地支持多窗口模式。

以下 LifecycleObserver 响应 ON_PAUSE 事件的示例，与前面的 ON_RESUME 事件示例相对应：它会释放在收到 ON_RESUME 事件后初始化的相机：

class CameraComponent : LifecycleObserver {
    ...
    @OnLifecycleEvent(Lifecycle.Event.ON_PAUSE)
    fun releaseCamera() {
        camera?.release()
        camera = null
    }
    ...
}

此示例将释放相机的代码放在 LifecycleObserver 收到 ON_PAUSE 事件之后。

onPause 的执行时间非常短，不一定能提供足够的时间来执行保存操作。因此，不要使用 onPause 保存应用或用户数据、发起网络调用，或执行数据库事务。这类工作可能在方法完成之前仍未完成。

应改为在 onStop 期间执行负载较重的关闭操作。有关适合在 onStop 期间执行的操作，请参阅下一节。有关保存数据的更多信息，请参阅保存和恢复状态一节。

onPause 方法完成并不意味着 Activity 会离开 Paused 状态。相反，Activity 会一直停留在此状态，直到 Activity 恢复运行，或对用户完全不可见。如果 Activity 恢复运行，系统会再次调用 onResume 回调。

如果 Activity 从 Paused 状态返回 Resumed 状态，系统会让 Activity 实例继续驻留在内存中，并在调用 onResume 时重新使用该实例。在这种情况下，不需要重新初始化那些在进入 Resumed 状态之前的各个回调方法中创建的组件。如果 Activity 变得完全不可见，系统会调用 onStop。

onStop

当 Activity 不再对用户可见时，它会进入 Stopped 状态，系统会调用 onStop 回调。当一个新启动的 Activity 覆盖整个屏幕时，就可能发生这种情况。当 Activity 运行结束、即将终止时，系统也会调用 onStop。

当 Activity 进入 Stopped 状态时，任何与该 Activity 生命周期关联的感知生命周期的组件都会收到 ON_STOP 事件。生命周期组件可以在此处停止那些在组件不显示于屏幕上时无需运行的功能。

在 onStop 方法中，应释放或调整那些在应用对用户不可见时不再需要的资源。例如，应用可以暂停动画，或将精细位置更新切换为粗略位置更新。使用 onStop 而不是 onPause，意味着即使用户在多窗口模式下查看 Activity，与 UI 相关的工作也会继续进行。

此外，还应使用 onStop 执行相对耗费 CPU 的关闭操作。例如，如果找不到更合适的时机将信息保存到数据库，可以在 onStop 期间进行。以下示例展示了一种 onStop 实现，它将笔记草稿的内容保存到持久存储中：

override fun onStop() {
    super.onStop()

    // Delegate the save operation to the ViewModel, which handles the
    // background thread operations (e.g., using Kotlin Coroutines and Room).
    noteViewModel.saveDraft()
}

当 Activity 进入 Stopped 状态时，Activity 对象会继续驻留在内存中：它保留所有状态和成员信息，但不再附着于窗口管理器。当 Activity 恢复运行时，它会重新使用这些信息。

从 Stopped 状态出发，Activity 要么回来与用户交互，要么运行结束并消失。如果 Activity 回来，系统会调用 onRestart。如果 Activity 运行结束，系统会调用 onDestroy。

onDestroy

onDestroy 会在 Activity 被销毁之前调用。系统出于以下两个原因之一调用此回调：

  1. Activity 正在结束，原因是用户完全关闭了该 Activity，或对该 Activity 调用了 finish。
  2. 系统因配置变更（例如设备旋转或进入多窗口模式）而暂时销毁该 Activity。

当 Activity 进入已销毁状态时，任何与该 Activity 生命周期关联的感知生命周期的组件都会收到 ON_DESTROY 事件。生命周期组件可以在此处清理 Activity 被销毁之前需要清理的任何内容。

不要在 Activity 中放置用于判断它为何被销毁的逻辑，而应使用 ViewModel 对象来保存 Activity 的相关视图数据。如果 Activity 因配置变更而重建，ViewModel 无需做任何事，因为它会被保留并交给下一个 Activity 实例。

如果 Activity 没有重建，ViewModel 的 onCleared 方法就会被调用，它可以在此处清理销毁之前需要清理的任何数据。可以通过 isFinishing 方法区分这两种情况。

如果 Activity 正在结束，onDestroy 就是它收到的最后一个生命周期回调。如果 onDestroy 是因配置变更而被调用，系统会立即创建一个新的 Activity 实例，然后在新配置下对这个新实例调用 onCreate。

onDestroy 回调会释放所有未被先前回调（例如 onStop）释放的资源。

保存和恢复临时 UI 状态

用户期望 Activity 的 UI 状态在配置变更期间保持不变，例如旋转屏幕或切换到多窗口模式。不过，发生此类配置变更时，系统默认会销毁 Activity，清除 Activity 实例中存储的任何 UI 状态。

类似地，用户期望在暂时从你的应用切换到另一个应用、稍后再返回时，UI 状态保持不变。不过，在用户离开且 Activity 已停止期间，系统可能销毁应用进程。

当系统约束导致 Activity 被销毁时，应组合使用 ViewModel（用于复杂业务逻辑和屏幕状态）、Jetpack Compose 的 rememberSaveable API（用于轻量 UI 状态）以及／或者本地存储，保留用户的临时 UI 状态。如需详细了解用户预期与系统行为的对比，以及如何在系统发起的 Activity 和进程死亡期间最好地保留复杂 UI 状态数据，请参阅保存 UI 状态。

rememberSaveable 通过在底层将状态打包到 Bundle 中，自动跨越配置变更和系统发起的进程死亡保留状态，提供无缝体验，而无需 Activity 级样板代码。

注意：如需详细了解配置变更、必要时如何限制 Activity 重建，以及如何在 Jetpack Compose 中响应这些配置变更，请参阅处理配置变更页面。

实例状态

在某些场景中，Activity 会因正常的应用行为而被销毁，例如用户按下返回按钮，或 Activity 调用 finish 方法来表明自身应被销毁。

当 Activity 因用户按下返回按钮或自行结束而被销毁时，在系统和用户的认知中，该 Activity 实例都已永久消失。在这些场景中，用户预期与系统行为一致，你不需要做任何额外工作。

不过，如果系统因系统约束（例如配置变更或内存压力）销毁 Activity，虽然实际的 Activity 实例已经消失，系统仍记得它曾经存在。如果用户尝试导航回该 Activity，系统会使用一组已保存的数据创建其新实例，这些数据描述了 Activity 被销毁时的状态。

系统用于恢复先前状态的已保存数据称为实例状态。底层实现中，它是一组键值对。默认情况下，系统使用实例状态保存 UI 布局的基本信息，例如用户输入的文本或滚动位置。

可以使用 rememberSaveable 接入此系统行为。如果 Activity 实例被销毁并重建，任何由 rememberSaveable 包装的 UI 状态都会自动恢复，无需你编写额外的 Activity 级代码。

不过，Activity 很可能还有你希望恢复的更复杂的状态信息，例如用户数据、网络响应，或跟踪用户进度的成员变量。实例状态机制（以及由此扩展的 rememberSaveable）不适合保留超出极少量的数据，因为它需要在主线程上序列化，并消耗系统进程的内存。

要保留超过极少量的数据，应组合使用持久化本地存储、ViewModel 类和 Compose 状态提升，具体见保存 UI 状态。

使用 rememberSaveable 保存简单、轻量的 UI 状态

当 Activity 开始停止时，系统会准备将状态信息保存到实例状态 Bundle 中。要接入此系统行为，可以直接在可组合函数中使用 rememberSaveable。rememberSaveable 会在 Activity 重建前后自动保存和恢复临时 UI 状态，例如用户输入的文本或滚动位置。

要保存自定义的轻量状态信息（例如用户在游戏中的进度），请使用 rememberSaveable 声明状态。Compose 框架会在底层处理将其序列化到实例状态 Bundle 的工作：

var userTypedQuery by rememberSaveable(typedQuery, stateSaver = TextFieldValue.Saver) {
    mutableStateOf(
        TextFieldValue(text = typedQuery, selection = TextRange(typedQuery.length))
    )
}StateOverviewSnippets.kt
注意：当用户明确关闭 Activity，或在其他调用 finish 的情况下，系统的实例状态机制（因此也包括 rememberSaveable）不会触发。

要保存用户偏好或数据库数据等持久数据，应在 Activity 处于前台时寻找适当时机。如果没有这样的机会，就在 onStop 方法期间保存持久数据。

使用已保存的实例状态恢复 Activity UI 状态

Activity 在先前被销毁后重新创建时，状态会自动恢复。使用 rememberSaveable 时，无需编写任何显式恢复逻辑、检查 Bundle 是否为 null，或重写 Activity 回调。初始化和保存状态的代码，也会在 Activity 返回时无缝地恢复状态：

var userTypedQuery by rememberSaveable(typedQuery, stateSaver = TextFieldValue.Saver) {
    mutableStateOf(
        TextFieldValue(text = typedQuery, selection = TextRange(typedQuery.length))
    )
}StateOverviewSnippets.kt

Activity 与导航

应用在其生命周期内很可能会多次切换屏幕，例如用户点按设备的返回按钮，或选择新的目的地时。现代 Android 应用通常采用单 Activity 架构。应用不会为每个屏幕启动新的 Activity，而是承载一个 Activity，并使用 Navigation 组件在该 Activity 内切换可组合屏幕。

如需了解如何实现现代的、以 Compose 为先的导航，请参阅 Jetpack Compose Navigation 3 库指南。

从一个 Activity 启动另一个 Activity

Activity 可能在某个时刻需要启动另一个 Activity。例如，当应用需要从当前屏幕转到新屏幕时，就会产生这种需求。

根据当前 Activity 是否希望从即将启动的新 Activity 接收返回结果，可以使用 startActivity 方法或 startActivityForResult 方法启动新 Activity。无论哪种情况，都需要传入一个 Intent 对象。

Intent 对象可以指定你希望启动的确切 Activity，也可以描述希望执行的操作类型。系统会为你选择适当的 Activity，它甚至可以来自另一个应用。Intent 对象还可以携带少量数据，供被启动的 Activity 使用。有关 Intent 类的更多信息，请参阅 Intent 与 Intent Filter。

注意：在 Compose 中，我们建议整个应用采用单 Activity 架构。不过，如果无法做到这一点，可能就需要从一个 Activity 启动另一个 Activity。

startActivity

如果新启动的 Activity 不需要返回结果，当前 Activity 可以通过调用 startActivity 方法启动它。

在自己的应用中工作时，通常只需启动一个已知的 Activity。例如，以下代码段展示了如何启动名为 SignInActivity 的 Activity。

val context = LocalContext.current

Button(onClick = {
    val intent = Intent(context, SignInActivity::class.java)
    context.startActivity(intent)
}) {
    Text("Sign In")
}

启动外部 Activity

虽然应用内部导航由 Navigation 处理，但 Activity 偶尔仍需要启动其他 Activity。这通常发生在希望借助外部应用执行特定操作时，例如打开网页浏览器、发送电子邮件或拍照。

为此，可以使用 Intent 对象描述希望执行的操作类型，系统会从另一个应用启动适当的 Activity。

例如，如果希望让用户发送电子邮件，可以创建以下 Intent：

val intent = Intent(Intent.ACTION_SEND).apply {
    putExtra(Intent.EXTRA_EMAIL, recipientArray)
}
startActivity(intent)

如果需要启动外部 Activity 并获取返回结果（例如，请求相机应用拍照并返回图片），应使用现代的 Activity 结果 API，而不是已弃用的 startActivityForResult 回调。

协调 Activity

当一个 Activity 启动另一个 Activity 时，两者都会经历生命周期转换。第一个 Activity 停止工作，进入 Paused 或 Stopped 状态，同时另一个 Activity 被创建。如果这些 Activity 共享保存在磁盘或其他位置的数据，就必须理解：第二个 Activity 创建之前，第一个 Activity 并没有完全停止。相反，启动第二个 Activity 的过程，与停止第一个 Activity 的过程相互重叠。

生命周期回调的顺序是明确定义的，尤其是在两个 Activity 位于同一个进程（也就是同一个应用）中，并且其中一个启动另一个时。当 Activity A 启动 Activity B 时，操作顺序如下：

  1. 执行 Activity A 的 onPause 方法。
  2. 依次执行 Activity B 的 onCreate、onStart 和 onResume 方法。此时，Activity B 获得用户焦点。
  3. 如果 Activity A 在屏幕上不再可见，则执行它的 onStop 方法。

这个生命周期回调序列，使你能够管理信息从一个 Activity 向另一个 Activity 的转移。
