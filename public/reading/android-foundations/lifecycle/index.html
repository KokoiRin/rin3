用户在应用内切换页面、离开应用或返回应用时，应用中的 Activity 实例会随之进入不同的生命周期状态。Activity 类提供了一系列回调，用来通知 Activity：状态何时发生了变化，以及系统何时正在创建、停止或恢复 Activity，或销毁它所在的进程。

你可以在生命周期回调方法中定义：用户离开 Activity 或重新进入时，Activity 应如何响应。例如，开发流式视频播放器时，可以在用户切换到其他应用后暂停视频，并断开网络连接；用户返回后，再重新连接网络，让视频从之前的位置继续播放。

每个回调都对应特定的状态变化，你可以在其中执行适合这一变化的工作。在合适的时机执行相应操作，并妥善处理状态转换，能让应用更稳定、性能更好。例如，合理实现生命周期回调，可以帮助应用避免以下问题：

  • 用户使用应用时，因接到电话或切换到其他应用而导致应用崩溃。
  • 用户没有主动使用应用时，应用仍在消耗宝贵的系统资源。
  • 用户离开应用、稍后返回时，之前的进度丢失。
  • 屏幕在横屏与竖屏之间切换时，应用崩溃或用户进度丢失。

本文将详细介绍 Activity 生命周期：先说明生命周期模型，再逐一讲解各个回调，包括回调执行时内部会发生什么，以及你需要在其中实现哪些操作。

接着，本文会简要说明 Activity 所处的状态如何影响其所在进程被系统终止的可能性，最后讨论几个与 Activity 状态转换有关的主题。

如需了解如何处理生命周期及相关最佳实践，请参阅Jetpack Compose 中的生命周期和保存 UI 状态。如需了解如何结合 Activity 与架构组件，构建稳定、可用于生产环境的应用，请参阅应用架构指南。

Activity 生命周期概念

为了处理 Activity 在各个生命周期阶段之间的转换，Activity 类提供了六个核心回调：onCreate、onStart、onResume、onPause、onStop 和 onDestroy。Activity 进入新状态时，系统就会调用相应的回调。

图 1 展示了这一生命周期模型。

用户开始离开 Activity 时，系统会调用相应方法，逐步执行 Activity 的清理工作。有些情况下只会完成部分清理，Activity 仍保留在内存中，例如用户切换到其他应用时；此时，Activity 仍然可以回到前台。

用户返回该 Activity 后，它会从用户离开时的位置继续运行。除少数例外，应用在后台运行时启动 Activity 会受到限制。

系统是否容易终止某个进程及其中的 Activity，取决于 Activity 当时所处的状态。如需了解 Activity 状态与其被移出内存的可能性之间的关系，请参阅Activity 状态与内存回收一节。

你可能不必实现所有生命周期方法，具体取决于 Activity 的复杂程度。不过，你仍需要理解每个方法，并实现其中必要的方法，让应用的行为符合用户预期。

Compose 与生命周期

在 Compose 中，应避免把业务逻辑或手动设置观察者的代码直接写在 onStart、onResume 等 Activity 回调中；应使用能感知 Lifecycle 的副作用和能感知状态的观察者，让它们根据 UI 是否显示在屏幕上自动调整行为。

  • 根据生命周期收集数据：使用 collectAsStateWithLifecycle 收集并使用 ViewModel 中的 Flow。UI 进入 Started 状态时，这个 API 会自动开始收集；UI 进入后台时，则停止收集，以免消耗不必要的资源。将 Flow 收集为状态后，还可以使用 LifecycleEffects 在生命周期事件发生时执行代码。
  • 逻辑如何运转：使用这些 API 后，UI 会通过组合树自然地响应生命周期状态，使业务逻辑只在用户主动与组件交互时执行。

如需进一步了解 Compose 与生命周期，请参阅Jetpack Compose 中的生命周期。

生命周期回调

本节介绍 Activity 生命周期回调的基本概念，以及如何实现这些回调。

有些操作适合写在 Activity 的生命周期方法中；但如果某段代码实现的是 Activity 所依赖组件的行为，就应把它放在组件自身内部，而不是放在 Activity 的生命周期方法中。为此，需要让这些组件能够感知生命周期。如需了解具体做法，请参阅Jetpack Compose 中的生命周期。

onCreate

你必须实现这个回调，系统首次创建 Activity 时会调用它。Activity 创建后会进入 Created 状态。在 onCreate 方法中，应执行应用启动所需的基础逻辑，这些逻辑在该 Activity 实例的整个生命周期中只执行一次。

例如，可以在 onCreate 中将数据绑定到列表、将 Activity 与 ViewModel 关联，以及实例化一些类级变量。此方法接收的 savedInstanceState 参数是一个 Bundle 对象，其中保存着该 Activity 之前存下的状态。如果这是该 Activity 第一次创建，这个 Bundle 对象的值就是 null。

如果一个能感知生命周期的组件已关联到该 Activity 的生命周期，它就会收到 ON_CREATE 事件。随后，标有 @OnLifecycleEvent 注解的方法会被调用，让这个组件执行 Created 状态所需的初始化代码。

下面的示例展示了如何在最简单的 Activity 中使用 Text 可组合函数：

class ExampleActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        setContent { // In here, we can call composables!
            MaterialTheme {
                Greeting(name = "compose")
            }
        }
    }
}

@Composable
fun Greeting(name: String) {
    Text(text = "Hello $name!")
}

Activity 不会一直停留在 Created 状态。onCreate 方法执行完后，Activity 会进入 Started 状态，系统随即依次调用 onStart 和 onResume 方法。

onStart

Activity 进入 Started 状态时，系统会调用 onStart，使 Activity 对用户可见，同时为它进入前台、与用户交互做好准备。例如，负责维护 UI 的代码会在这个方法中完成初始化。

Activity 进入 Started 状态时，所有能感知生命周期、且已关联到该 Activity 生命周期的组件，都会收到 ON_START 事件。

onStart 方法会很快执行完；与 Created 状态一样，Activity 不会一直停留在 Started 状态。这个回调结束后，Activity 会进入 Resumed 状态，系统接着调用 onResume 方法。

onResume

Activity 进入 Resumed 状态时，就会来到前台，系统会调用 onResume 回调。应用在这一状态下与用户交互，并保持这一状态，直到某个事件使它失去焦点，例如设备接到电话、用户切换到另一个 Activity，或设备屏幕关闭。

Activity 进入 Resumed 状态时，所有能感知生命周期、且已关联到该 Activity 生命周期的组件，都会收到 ON_RESUME 事件。这些组件可以在此时启用需要在组件可见且处于前台时运行的功能，例如启动相机预览。

发生中断事件时，Activity 会进入 Paused 状态，系统随即调用 onPause 回调。

如果 Activity 从 Paused 状态回到 Resumed 状态，系统会再次调用 onResume 方法。因此，应在 onResume 中重新初始化那些在 onPause 期间被释放的组件，并完成每次进入 Resumed 状态时都需要执行的其他初始化工作。

下面是一个能感知生命周期的组件，它会在收到 ON_RESUME 事件时访问相机：

class CameraComponent : LifecycleObserver {
    ...
    @OnLifecycleEvent(Lifecycle.Event.ON_RESUME)
    fun initializeCamera() {
        if (camera == null) {
            getCamera()
        }
    }
    ...
}

上述代码会在 LifecycleObserver 收到 ON_RESUME 事件后初始化相机。不过，在多窗口模式下，Activity 即使处于 Paused 状态，也可能仍完整地显示在屏幕上。例如，应用处于多窗口模式时，如果用户点按的是另一个窗口，当前 Activity 就会进入 Paused 状态。

如果只希望在应用处于 Resumed 状态（在前台可见且处于活动状态）时启用相机，就应像前面的示例一样，在收到 ON_RESUME 事件后初始化相机。如果希望 Activity 处于 Paused 状态但仍可见时也继续启用相机，例如在多窗口模式下，就应在收到 ON_START 事件后初始化相机。

不过，Activity 处于 Paused 状态时如果仍占用相机，就可能导致多窗口模式下另一个处于 Resumed 状态的应用无法访问相机。有时确实需要这样做，但这也可能影响整体用户体验。

因此，在多窗口模式下，应仔细考虑在生命周期的哪个阶段取得共享系统资源的控制权才合适。如需了解如何支持多窗口模式，请参阅支持多窗口模式。

无论选择在哪个生命周期启动阶段的事件中执行初始化，都应在与之对应的生命周期事件中释放资源。如果在 ON_START 事件后初始化某个资源，就应在 ON_STOP 事件后释放或终止它；如果在 ON_RESUME 事件后初始化，就应在 ON_PAUSE 事件后释放。

上述代码段把相机初始化逻辑放在了一个能感知生命周期的组件中。你也可以把这段代码直接放进 Activity 的生命周期回调，例如 onStart 和 onStop，但我们不推荐这样做。把逻辑放进独立且能感知生命周期的组件后，就可以在多个 Activity 中复用该组件，无需重复编写代码。如需了解如何创建这样的组件，请参阅Jetpack Compose 中的生命周期。

onPause

系统调用这个方法，是用户开始离开 Activity 的第一个信号，但这并不一定意味着 Activity 即将被销毁。它表示 Activity 已不再处于前台；不过，在多窗口模式下，该 Activity 仍然可见。Activity 可能因以下原因进入这一状态：

  • 发生了中断应用执行的事件，使当前 Activity 暂停，例如 onResume 回调一节中介绍的情况。这是最常见的原因。
  • 在多窗口模式下，同一时刻只有一个应用拥有焦点，系统会暂停其他所有应用。
  • 打开一个新的半透明 Activity（例如对话框形式的 Activity）时，被它覆盖的 Activity 会暂停。只要被覆盖的 Activity 仍部分可见、但没有焦点，它就会保持暂停状态。

Activity 进入 Paused 状态时，所有能感知生命周期、且已关联到该 Activity 生命周期的组件，都会收到 ON_PAUSE 事件。这些组件可以在此时停止那些在组件不处于前台时无需运行的功能，例如相机预览。

在 onPause 方法中，可以暂停或调整那些预计很快就会恢复的操作：当 Activity 处于 Paused 状态时，有些操作无法继续，有些则可以适度继续。

Activity 处于 Paused 状态时，如果用户已不再需要相关资源，也可以在 onPause 方法中释放系统资源、传感器（例如 GPS）的句柄，以及其他会影响电池续航的资源。

不过，如 onResume 一节所述，多窗口模式下处于 Paused 状态的 Activity 仍可能完整地显示在屏幕上。为了更好地支持多窗口模式，可以考虑在 onStop 而不是 onPause 中，完全释放或调整与 UI 相关的资源和操作。

下面的示例展示了 LifecycleObserver 如何响应 ON_PAUSE 事件，与前面的 ON_RESUME 事件示例相对应：在收到 ON_RESUME 事件后初始化的相机，会在这里被释放。

class CameraComponent : LifecycleObserver {
    ...
    @OnLifecycleEvent(Lifecycle.Event.ON_PAUSE)
    fun releaseCamera() {
        camera?.release()
        camera = null
    }
    ...
}

在这个示例中，LifecycleObserver 收到 ON_PAUSE 事件后，就会执行释放相机的代码。

onPause 的执行时间很短，不一定有足够的时间完成保存操作。因此，不要在 onPause 中保存应用数据或用户数据、发起网络调用，或执行数据库事务，否则方法结束时，这些工作可能还没有完成。

负载较重的关闭和清理操作，应放在 onStop 中执行。下一节会介绍哪些操作适合在 onStop 中执行；如需进一步了解如何保存数据，请参阅保存和恢复状态一节。

onPause 方法执行完，并不代表 Activity 已离开 Paused 状态。Activity 会继续保持这一状态，直到恢复运行，或变得完全不可见。如果恢复运行，系统会再次调用 onResume 回调。

如果 Activity 从 Paused 状态回到 Resumed 状态，系统会保留内存中的 Activity 实例，并在调用 onResume 时继续使用它。此时，无需重新初始化那些在进入 Resumed 状态之前的各个回调中创建的组件。如果 Activity 变得完全不可见，系统则会调用 onStop。

onStop

Activity 对用户完全不可见时，会进入 Stopped 状态，系统会调用 onStop 回调，例如新启动的 Activity 覆盖整个屏幕时，就可能出现这种情况。Activity 运行结束、即将终止时，系统也会调用 onStop。

Activity 进入 Stopped 状态时，所有能感知生命周期、且已关联到该 Activity 生命周期的组件，都会收到 ON_STOP 事件。这些组件可以在此时停止那些在组件不可见时无需运行的功能。

在 onStop 方法中，应释放或调整应用不可见时不再需要的资源。例如，可以暂停动画，或把精确的位置更新改为粗略的位置更新。将这些操作放在 onStop 而不是 onPause 中，可以让与 UI 相关的工作在用户通过多窗口模式查看 Activity 时继续进行。

此外，还应在 onStop 中执行比较耗费 CPU 的关闭和清理操作。例如，如果找不到更合适的时机把信息存入数据库，可以在 onStop 中保存。下面的示例展示了如何在 onStop 中把笔记草稿保存到持久存储中：

override fun onStop() {
    super.onStop()

    // Delegate the save operation to the ViewModel, which handles the
    // background thread operations (e.g., using Kotlin Coroutines and Room).
    noteViewModel.saveDraft()
}

Activity 进入 Stopped 状态后，Activity 对象仍保留在内存中，所有状态和成员信息也都保留着，但它已与窗口管理器解除关联。Activity 恢复运行时，会继续使用这些信息。

进入 Stopped 状态后，Activity 可能重新回来与用户交互，也可能结束运行并被销毁。如果重新回来，系统会调用 onRestart；如果 Activity 结束运行，系统则会调用 onDestroy。

onDestroy

Activity 被销毁前，系统会调用 onDestroy。调用这个回调的原因有两种：

  1. Activity 即将结束：用户完全关闭了该 Activity，或者该 Activity 的 finish 方法被调用。
  2. 发生了配置变更，例如设备旋转或进入多窗口模式，系统因此暂时销毁该 Activity。

Activity 进入已销毁状态时，所有能感知生命周期、且已关联到该 Activity 生命周期的组件，都会收到 ON_DESTROY 事件。这些组件可以在此时完成 Activity 销毁前所需的清理工作。

应使用 ViewModel 对象保存 Activity 的相关视图数据，而不是在 Activity 中编写逻辑来判断它为何被销毁。如果 Activity 因配置变更而重建，ViewModel 不需要做额外处理，因为它会被保留下来，并交给新的 Activity 实例使用。

如果 Activity 不再重建，系统就会调用 ViewModel 的 onCleared 方法，让它在自身被销毁前完成必要的数据清理。你可以通过 isFinishing 方法区分这两种情况。

如果 Activity 正在结束，onDestroy 就是它收到的最后一个生命周期回调。如果 onDestroy 是由配置变更触发的，系统会立即创建一个新的 Activity 实例，并按照新的配置调用该实例的 onCreate 方法。

在 onDestroy 回调中，应释放此前的回调（例如 onStop）尚未释放的所有资源。

保存和恢复临时 UI 状态

用户希望在旋转屏幕、切换到多窗口模式等配置变更发生时，Activity 的 UI 状态仍能保持不变。但系统默认会在发生这类变更时销毁 Activity，保存在 Activity 实例中的 UI 状态也会随之被清除。

同样，用户暂时切换到其他应用、稍后再返回时，也希望 UI 状态保持不变。但在用户离开、Activity 已停止期间，系统可能会销毁应用进程。

如果 Activity 因系统限制而被销毁，应结合使用 ViewModel（处理复杂业务逻辑和屏幕状态）、Jetpack Compose 的 rememberSaveable API（处理轻量 UI 状态）以及／或者本地存储，保留用户的临时 UI 状态。如需了解用户预期与系统行为之间的差异，以及系统销毁 Activity 或终止进程时，如何更好地保留复杂的 UI 状态数据，请参阅保存 UI 状态。

rememberSaveable 会在底层把状态打包到 Bundle 中，让状态在配置变更或进程被系统终止后仍能保留下来，使用户的操作体验保持连贯，而无需编写 Activity 层面的样板代码。

注意：如需进一步了解配置变更、如何在必要时限制 Activity 重建，以及如何在 Jetpack Compose 中响应这些变更，请参阅处理配置变更。

实例状态

有些情况下，Activity 会随着应用的正常操作而被销毁，例如用户按下返回按钮，或 Activity 调用 finish 方法，主动请求结束自身。

如果 Activity 是因为用户按返回或主动结束自身而被销毁，那么无论对系统还是用户来说，这个 Activity 实例都已永久结束。此时，系统行为符合用户预期，你无需做额外处理。

但如果 Activity 是因配置变更、内存压力等系统限制而被销毁，即使实际的 Activity 实例已经不存在，系统仍会记得它曾经存在。用户尝试返回这个 Activity 时，系统会根据一组已保存的数据创建新的实例，这些数据记录了它被销毁时的状态。

系统用来恢复先前状态的这组已保存数据，称为实例状态，底层以键值对的形式存储。默认情况下，系统通过实例状态保存 UI 布局的基本信息，例如用户输入的文本和滚动位置。

你可以通过 rememberSaveable 使用这套系统机制。Activity 实例被销毁并重建后，由 rememberSaveable 管理的 UI 状态会自动恢复，无需额外编写 Activity 层面的代码。

不过，你可能还希望恢复 Activity 中更复杂的状态，例如用户数据、网络响应，或用于记录用户进度的成员变量。实例状态机制（也包括基于它的 rememberSaveable）只适合保存极少量数据，因为这套机制需要在主线程上进行序列化，还会占用系统进程的内存。

如果需要保存的数据不止极少量，应结合使用本地持久化存储、ViewModel 类和 Compose 状态提升，具体做法请参阅保存 UI 状态。

使用 rememberSaveable 保存简单、轻量的 UI 状态

Activity 开始停止时，系统会准备将状态信息保存到实例状态 Bundle 中。你可以直接在可组合函数中使用 rememberSaveable 来利用这套机制；rememberSaveable 会在 Activity 重建前后自动保存和恢复临时 UI 状态，例如用户输入的文本和滚动位置。

要保存自定义的轻量状态，例如用户在游戏中的进度，可以用 rememberSaveable 声明状态；Compose 框架会在底层负责将其序列化并写入实例状态 Bundle：

var userTypedQuery by rememberSaveable(typedQuery, stateSaver = TextFieldValue.Saver) {
    mutableStateOf(
        TextFieldValue(text = typedQuery, selection = TextRange(typedQuery.length))
    )
}

注意：用户明确关闭 Activity，或因其他原因调用 finish 时，系统不会触发实例状态机制，因此也不会触发 rememberSaveable 的相应机制。

用户偏好、数据库数据等需要长期保留的数据，应尽量在 Activity 处于前台时选择合适的时机保存；如果没有这样的机会，就在 onStop 方法中保存。

使用已保存的实例状态恢复 Activity UI 状态

Activity 被销毁后重新创建时，状态会自动恢复。如果使用了 rememberSaveable，你就无需另外编写恢复逻辑、检查 Bundle 是否为 null，或重写 Activity 回调；负责初始化和保存状态的那段代码，也会在 Activity 返回时自动恢复状态，让用户的操作得以继续：

var userTypedQuery by rememberSaveable(typedQuery, stateSaver = TextFieldValue.Saver) {
    mutableStateOf(
        TextFieldValue(text = typedQuery, selection = TextRange(typedQuery.length))
    )
}

Activity 与导航

应用运行期间，往往会多次切换页面，例如用户点按设备的返回按钮，或选择新的导航目的地时。现代 Android 应用通常采用单 Activity 架构：应用只使用一个 Activity，通过 Navigation 组件在其中切换由可组合函数构建的页面，而不为每个页面启动新的 Activity。

如需了解如何实现以 Compose 为核心的现代导航，请参阅 Jetpack Compose Navigation 3 库指南。

从一个 Activity 启动另一个 Activity

Activity 有时需要启动另一个 Activity，例如应用要从当前页面切换到新页面时。

启动新的 Activity 时，可以选择 startActivity 或 startActivityForResult 方法，具体取决于当前 Activity 是否需要接收新 Activity 返回的结果；无论使用哪种方法，都需要传入一个 Intent 对象。

Intent 对象既可以直接指定要启动哪个 Activity，也可以描述要执行哪种操作，让系统选择合适的 Activity 来处理，所选的 Activity 甚至可以属于另一个应用。Intent 对象还可以携带少量数据，供新启动的 Activity 使用。如需进一步了解 Intent 类，请参阅Intent 与 Intent Filter。

注意：在 Compose 中，我们建议整个应用采用单 Activity 架构；如果无法采用这种架构，就可能需要从一个 Activity 启动另一个 Activity。

startActivity

如果新启动的 Activity 不需要返回结果，当前 Activity 可以通过调用 startActivity 方法启动它。

在自己的应用内部，通常只需启动一个已知的 Activity。下面的代码段展示了如何启动名为 SignInActivity 的 Activity。

val context = LocalContext.current

Button(onClick = {
    val intent = Intent(context, SignInActivity::class.java)
    context.startActivity(intent)
}) {
    Text("Sign In")
}

启动外部 Activity

虽然应用内部的页面导航由 Navigation 处理，但 Activity 有时仍需要启动其他 Activity，通常是为了借助外部应用完成某项操作，例如打开网页浏览器、发送电子邮件或拍照。

为此，可以用 Intent 对象描述要执行的操作类型，系统会从其他应用中启动合适的 Activity 来处理。

例如，要让用户发送电子邮件，可以创建下面的 Intent：

val intent = Intent(Intent.ACTION_SEND).apply {
    putExtra(Intent.EXTRA_EMAIL, recipientArray)
}
startActivity(intent)

如果需要启动外部 Activity 并接收返回结果，例如让相机应用拍照并返回图片，应使用现代的 Activity 结果 API，而不是已弃用的 startActivityForResult 回调。

协调 Activity

一个 Activity 启动另一个 Activity 时，两者都会经历生命周期转换：第一个 Activity 停止工作，进入 Paused 或 Stopped 状态，另一个 Activity 则开始创建。如果它们共享保存在磁盘或其他位置的数据，就需要注意：系统并不是等第一个 Activity 完全停止后才创建第二个，而是让第二个 Activity 的启动过程与第一个 Activity 的停止过程交错进行。

生命周期回调有明确的调用顺序，尤其是两个 Activity 位于同一个进程（也就是同一个应用）中，且由其中一个启动另一个时。Activity A 启动 Activity B 时，调用顺序如下：

  1. 执行 Activity A 的 onPause 方法。
  2. 依次执行 Activity B 的 onCreate、onStart 和 onResume 方法，此时 Activity B 获得用户焦点。
  3. 如果 Activity A 已经在屏幕上完全不可见，就会执行它的 onStop 方法。

了解这一回调顺序后，你就可以据此管理两个 Activity 之间的信息传递。
