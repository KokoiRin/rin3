当一个应用组件启动，而应用没有其他组件正在运行时，Android 系统会为该应用启动一个新的 Linux 进程，其中只有一个执行线程。默认情况下，同一应用的所有组件都在同一进程和线程中运行，这个线程称为主线程。

如果某个应用组件启动时，该应用已经有一个进程（因为该应用的另一个组件已经启动），那么该组件会在这个进程内启动，并使用同一个执行线程。不过，可以让应用中的不同组件在独立的进程中运行，也可以为任何进程创建额外的线程。

本文讨论进程和线程在 Android 应用中如何工作。

进程

默认情况下，应用的所有组件都在同一个进程中运行，大多数应用不会改变这一点。不过，如果发现需要控制某个组件属于哪个进程，可以在清单文件中进行设置。

每种组件元素——<activity>、<service>、<receiver> 和 <provider>——在清单中的条目都支持 android:process 属性，可以用它指定组件运行的进程。可以设置此属性，让每个组件在自己的进程中运行，或让某些组件共享一个进程，而其他组件不共享。

也可以设置 android:process，让不同应用的组件在同一个进程中运行，前提是这些应用共享同一个 Linux 用户 ID，并使用相同的证书签名。

<application> 元素也支持 android:process 属性，可以用它设置适用于所有组件的默认值。

当其他更直接为用户提供服务的进程需要资源时，Android 可能会决定关闭某个进程。因此，被关闭进程中运行的应用组件也会被销毁。当这些组件有工作需要执行时，系统会再次为它们启动进程。

在决定关闭哪些进程时，Android 系统会权衡它们对用户的相对重要性。例如，与承载可见 Activity 的进程相比，系统更容易关闭承载的 Activity 已不再显示于屏幕上的进程。因此，是否终止进程的决定，取决于该进程中运行的组件的状态。

有关进程生命周期及其与应用状态之间关系的详细信息，请参阅进程与应用生命周期。

线程

应用启动时，系统会为应用创建一个执行线程，称为主线程。这个线程非常重要，因为它负责将事件（包括绘制事件）分派给相应的用户界面控件。应用也几乎总是在这个线程中，与 Android UI 工具包的 android.widget 和 android.view 包中的组件交互。因此，主线程有时也称为 UI 线程。不过，在特殊情况下，应用的主线程可能不是其 UI 线程。有关详情，请参阅线程注解。

系统不会为组件的每个实例创建独立线程。在同一进程中运行的所有组件都会在 UI 线程中实例化，系统对各组件的调用也从这个线程分派。因此，响应系统回调的方法——例如用于报告用户操作的 onKeyDown()，或生命周期回调方法——始终在该进程的 UI 线程中运行。

例如，当用户触摸屏幕上的按钮时，应用的 UI 线程会将触摸事件分派给该控件，控件随后设置其按下状态，并向事件队列投递一个失效请求。UI 线程从队列中取出该请求，并通知控件重新绘制自身。

如果应用实现不当，这种单线程模型可能会在应用为响应用户交互而执行密集工作时导致性能不佳。在 UI 线程中执行网络访问或数据库查询等长时间操作，会阻塞整个 UI。线程被阻塞时，任何事件都无法分派，包括绘制事件。

从用户的角度看，应用似乎停止了响应。更糟的是，如果 UI 线程被阻塞超过几秒，系统就会向用户显示“应用无响应”（ANR）对话框。用户随后可能决定退出应用，甚至卸载它。

请记住，Android UI 工具包不是线程安全的。因此，不要从工作线程操作 UI。对用户界面的所有操作都应在 UI 线程中进行。Android 的单线程模型有两条规则：

  1. 不要阻塞 UI 线程。
  2. 不要从 UI 线程之外访问 Android UI 工具包。

工作线程

由于采用这种单线程模型，不阻塞 UI 线程对于应用 UI 的响应能力至关重要。如果需要执行无法立即完成的操作，务必在独立的后台线程或工作线程中执行。只需记住，不能从 UI 线程（即主线程）以外的任何线程更新 UI。

为了帮助遵守这些规则，Android 提供了多种从其他线程访问 UI 线程的方式。以下方法可以提供帮助：

  • Activity.runOnUiThread(Runnable)
  • View.post(Runnable)
  • View.postDelayed(Runnable, long)

以下示例展示了如何将任务移交给后台线程，并在任务完成后更新 UI 线程：

Kotlin

// Kotlin coroutines implementation.
fun onClick(v: View) {
    // Launch a coroutine in the lifecycle scope (e.g., in an Activity or Fragment).
    lifecycleScope.launch {
        // Run the blocking task on the IO dispatcher.
        val bitmap = withContext(Dispatchers.IO) {
            BitmapFactory.decodeFile("image.png")
        }
        // Back on the main thread, update the UI.
        imageView.setImageBitmap(bitmap)
    }
}

Java

// Java Executor implementation.
// (executorService is assumed to be defined elsewhere).
public void onClick(View v) {
    executorService.execute(() -> {
        // Run the heavy task on a background thread.
        Bitmap bitmap = BitmapFactory.decodeFile("image.png");

        // Update the View on the UI thread.
        imageView.post(() -> imageView.setImageBitmap(bitmap));
    });
}

此实现是线程安全的，因为后台操作在独立线程中完成，而 ImageView 始终从 UI 线程进行操作。

不过，随着操作复杂程度增加，这类代码可能变得复杂且难以维护。为了处理与工作线程之间更复杂的交互，可以考虑在工作线程中使用 Handler，处理从 UI 线程传来的消息。如需完整了解如何在后台线程中调度工作并与 UI 线程通信，请参阅后台工作概览。

线程安全方法

在某些情况下，实现的方法会由多个线程调用，因此必须以线程安全的方式编写。

这主要适用于可以被远程调用的方法，例如绑定型服务中的方法。当对 IBinder 中实现的方法的调用，来自 IBinder 所在的同一进程时，该方法会在调用方的线程中执行。不过，当调用来自另一个进程时，该方法会在一个线程中执行，这个线程来自系统在 IBinder 所在进程中维护的线程池。它不会在该进程的 UI 线程中执行。

例如，服务的 onBind() 方法会从服务进程的 UI 线程调用，而在 onBind() 返回的对象中实现的方法（例如实现远程过程调用（RPC）方法的子类）则会从线程池中的线程调用。由于一个服务可以有多个客户端，多个线程池线程可能同时调用同一个 IBinder 方法，因此必须以线程安全的方式实现 IBinder 方法。

类似地，内容提供程序可以接收来自其他进程的数据请求。ContentResolver 和 ContentProvider 类隐藏了进程间通信（IPC）的管理细节，但响应这些请求的 ContentProvider 方法——query()、insert()、delete()、update() 和 getType()——会从内容提供程序所在进程的线程池调用，而不是从该进程的 UI 线程调用。由于这些方法可能同时被任意数量的线程调用，因此也必须以线程安全的方式实现。

进程间通信

Android 提供了一种使用 RPC 实现 IPC 的机制：Activity 或其他应用组件调用某个方法，但该方法在另一个进程中远程执行，任何结果都会返回给调用方。这需要将方法调用及其数据分解到操作系统可以理解的层次，将它们从本地进程和地址空间传输到远程进程和地址空间，然后在那里重新组装并执行调用。

返回值随后沿相反方向传输。Android 提供了执行这些 IPC 事务所需的全部代码，因此你可以专注于定义和实现 RPC 编程接口。

要执行 IPC，应用必须使用 bindService() 绑定到一个服务。有关详情，请参阅服务概览。
