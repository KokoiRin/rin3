一个应用组件启动时，如果该应用还没有其他组件在运行，Android 就会为它启动一个新的 Linux 进程，并创建一个执行线程。默认情况下，同一应用的所有组件都在这个进程和线程中运行，这个线程称为主线程（main thread）。

如果应用的其他组件已经启动，使应用已有一个进程，那么新组件就会在这个现有进程中启动，并使用同一个执行线程。不过，你也可以让不同组件分别运行在独立进程中，还可以在任意进程内创建更多线程。

本文介绍 Android 应用中的进程和线程如何工作。

进程

默认情况下，一个应用的所有组件都运行在同一进程中，大多数应用会沿用这一设置。如果需要指定某个组件在哪个进程中运行，可以在 Manifest 中配置。

Manifest 中的四类组件元素——<activity>、<service>、<receiver> 和 <provider>——都支持 android:process 属性，用来指定组件的运行进程。通过这个属性，可以让每个组件独立运行在自己的进程中，也可以让部分组件共享进程，其余组件使用其他进程。

还可以通过 android:process 让不同应用的组件运行在同一个进程中，但前提是这些应用使用同一个 Linux 用户 ID，并由相同的证书签名。

<application> 元素也支持 android:process 属性，可以在这里为所有组件设置默认的运行进程。

当其他更直接为用户提供服务的进程需要资源时，Android 可能会终止某个进程，该进程中运行的应用组件也会随之被销毁。等这些组件再次有工作需要执行时，系统会重新为它们启动进程。

决定终止哪些进程时，Android 会比较各个进程对用户的重要程度。例如，与包含可见 Activity 的进程相比，系统更倾向于终止其中 Activity 已不可见的进程。因此，一个进程是否会被终止，取决于它内部各组件的状态。

如需了解进程生命周期及其与应用状态的关系，请参阅进程与应用生命周期。

线程

应用启动时，系统会为它创建一个执行线程，称为主线程。这个线程负责把包括绘制事件在内的各种事件分发给相应的 UI 控件，因此十分重要。应用也几乎总是在这个线程中，调用 Android UI toolkit 的 android.widget 和 android.view 包中的组件。因此，主线程有时也称为UI 线程（UI thread）。不过，特殊情况下，应用的主线程可能并不是它的 UI 线程，详情请参阅线程注解。

系统不会为每个组件实例分别创建一个线程。同一进程中的所有组件都在 UI 线程上实例化，系统对组件的调用也由这个线程分发。因此，用于响应系统回调的方法，例如报告用户操作的 onKeyDown() 或生命周期回调，始终在该进程的 UI 线程上执行。

例如，用户触摸屏幕上的按钮时，UI 线程会把触摸事件分发给这个控件；控件将自身设为按下状态，并向事件队列投递一个 invalidate（请求重绘）请求。UI 线程随后从队列中取出请求，通知控件重新绘制。

在这种单线程模型下，如果应用需要执行大量工作来响应用户操作，而实现方式又不合理，就容易出现性能问题。例如，在 UI 线程上访问网络或查询数据库等耗时操作，会阻塞整个 UI；一旦线程被阻塞，包括绘制事件在内的所有事件都无法继续分发。

用户看到的现象就是应用失去响应。更严重的是，如果 UI 线程阻塞超过几秒，系统会显示“应用无响应”（ANR）对话框；用户可能因此退出应用，甚至将其卸载。

Android UI toolkit 不是线程安全的，因此不能在 worker thread（工作线程）中操作 UI，所有 UI 操作都应在 UI 线程上完成。Android 的单线程模型有两条规则：

  1. 不要阻塞 UI 线程。
  2. 不要在 UI 线程之外访问 Android UI toolkit。

Worker thread（工作线程）

在这种单线程模型下，要让界面及时响应，就必须避免阻塞 UI 线程。无法立即完成的操作，应放到独立的后台线程或工作线程中执行；但更新 UI 时，仍只能使用 UI 线程，也就是主线程。

为了遵守这些规则，Android 提供了多种从其他线程转到 UI 线程执行操作的方式，例如以下方法：

  • Activity.runOnUiThread(Runnable)
  • View.post(Runnable)
  • View.postDelayed(Runnable, long)

下面的示例展示了如何把操作放到后台线程执行，并在完成后回到 UI 线程更新界面：

Kotlin

// Kotlin coroutines implementation.
fun onClick(v: View) {
    // Launch a coroutine in the lifecycle scope (e.g., in an Activity or Fragment).
    lifecycleScope.launch {
        // Run the blocking task on the IO dispatcher.
        val bitmap = withContext(Dispatchers.IO) {
            BitmapFactory.decodeFile("image.png")
        }
        // Back on the main thread, update the UI.
        imageView.setImageBitmap(bitmap)
    }
}

Java

// Java Executor implementation.
// (executorService is assumed to be defined elsewhere).
public void onClick(View v) {
    executorService.execute(() -> {
        // Run the heavy task on a background thread.
        Bitmap bitmap = BitmapFactory.decodeFile("image.png");

        // Update the View on the UI thread.
        imageView.post(() -> imageView.setImageBitmap(bitmap));
    });
}

这种实现是线程安全的：后台操作在独立线程上执行，而 ImageView 始终由 UI 线程操作。

不过，随着操作变复杂，这类代码也可能越来越难以维护。如果需要与 worker thread 进行更复杂的交互，可以考虑在 worker thread 中使用 Handler，处理 UI 线程发来的消息。如需完整了解如何在后台线程中调度工作，以及如何再与 UI 线程通信，请参阅后台工作概览。

线程安全的方法

有些情况下，你实现的方法可能由多个线程调用，因此必须保证它是线程安全的。

可以被远程调用的方法尤其需要注意这一点，例如绑定型服务（bound service）中的方法。如果调用来自 IBinder 所在的同一进程，那么 IBinder 中实现的方法会在调用方的线程上执行；如果调用来自另一个进程，系统则会从 IBinder 所在进程的线程池中选一个线程来执行，而不会使用该进程的 UI 线程。

例如，Service 的 onBind() 方法在该 Service 所在进程的 UI 线程上调用；而 onBind() 返回的对象中实现的方法，例如子类实现的 RPC（远程过程调用）方法，则由线程池中的线程调用。一个 Service 可以有多个客户端，因此可能有多个线程同时调用同一个 IBinder 方法；所以，IBinder 方法必须保证线程安全。

类似地，ContentProvider 也可能收到其他进程发来的数据请求。ContentResolver 和 ContentProvider 隐藏了 IPC（进程间通信）的处理细节，但响应这些请求的 ContentProvider 方法——query()、insert()、delete()、update() 和 getType()——由 ContentProvider 所在进程的线程池调用，而不是由 UI 线程调用。这些方法可能同时被多个线程调用，因此同样必须保证线程安全。

IPC（进程间通信）

Android 提供了通过 RPC 实现 IPC 的机制：Activity 或其他应用组件发起方法调用，方法实际在另一个进程中执行，执行结果再返回给调用方。为此，系统需要把方法调用及其数据拆解成操作系统能够理解的形式，从本地进程及其地址空间传到远程进程及其地址空间，再在那里重新组装并执行这次调用。

返回值会沿相反方向传回。Android 已提供完成这些 IPC 事务所需的全部代码，你可以专注于定义和实现 RPC 接口。

要进行 IPC，应用必须通过 bindService() 绑定到一个 Service。详情请参阅服务概览。
