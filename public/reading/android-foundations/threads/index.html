一个应用组件启动时，如果这个应用还没有其他组件在运行，Android 就会为应用新建一个 Linux 进程，并在其中创建一个执行线程。默认情况下，同一应用的所有组件都在这个进程、这个线程里运行。这个线程就是主线程（main thread）。

如果应用的其他组件已经先启动，应用也已经有了进程，那么新组件就会进入已有进程，使用同一个执行线程。当然，你也可以让不同组件各自在独立进程中运行，还可以在任意进程里创建更多线程。

本文介绍 Android 应用中的进程和线程如何工作。

进程

默认情况下，一个应用的所有组件共用同一个进程，大多数应用也会保留这个设置。如果你需要指定某个组件在哪个进程里运行，可以在 Manifest 文件中设置。

Manifest 中声明组件的四种元素——<activity>、<service>、<receiver> 和 <provider>——都支持 android:process 属性。这个属性用来指定组件在哪个进程里运行。你可以让每个组件各用一个进程，也可以让一部分组件共用进程，其他组件使用别的进程。

通过 android:process，你甚至可以让不同应用的组件共用一个进程。不过，这些应用必须使用同一个 Linux 用户 ID，并且由相同的证书签名。

<application> 元素也支持 android:process 属性。在这里设置的值，会作为所有组件的默认值。

如果其他正在更直接地为用户服务的进程需要资源，Android 就可能结束某个进程。这个进程里运行的应用组件，也会一起被销毁。等这些组件又有工作要做时，系统会再次为它们启动进程。

那么，Android 会先结束哪个进程？系统会比较它们对用户的重要程度。例如，一个进程里的 Activity 已经不在屏幕上显示，另一个进程里的 Activity 还看得见，系统就更倾向于结束前一个。所以，进程里各个组件的状态，会影响系统是否结束这个进程。

进程的生命周期和应用状态有什么关系，可以继续看进程与应用生命周期。

线程

应用启动时，系统会为它创建一个执行线程，也就是主线程。它很重要，因为各种事件，包括绘制事件，都要由它分发给对应的 UI 控件。应用与 Android UI toolkit 中 android.widget、android.view 这两个包里的组件交互时，也几乎总是在这个线程上进行。因此，主线程有时也叫UI 线程（UI thread）。不过，在特殊情况下，主线程和 UI 线程可能不是同一个线程，具体可以看线程注解。

系统不会为每个组件实例都单独创建一个线程。同一进程里的所有组件，都在 UI 线程上创建实例；系统对这些组件的调用，也从这个线程分发。因此，响应系统回调的方法始终在该进程的 UI 线程上运行。比如，报告用户操作的 onKeyDown()，以及各种生命周期回调方法，都属于这种情况。

比如，用户点了一下屏幕上的按钮。UI 线程会先把触摸事件交给按钮控件；控件把自己设为“已按下”，再向事件队列发出一个 invalidate（请求重绘）请求。随后，UI 线程从队列里取出这个请求，通知控件重新绘制自己。

这种单线程模型也容易带来性能问题：用户操作之后，如果应用要做大量工作，而代码又没有安排好，就可能把 UI 卡住。例如，把网络访问、数据库查询这类耗时操作放在 UI 线程上，就会阻塞整个 UI。线程一旦被阻塞，所有事件都无法继续分发，绘制事件也不例外。

在用户看来，应用就是不响应了。更糟的是，如果 UI 线程被阻塞超过几秒，系统还会弹出“应用无响应”（ANR）对话框。用户可能因此退出应用，甚至把它卸载。

还要记住，Android UI toolkit 不是线程安全的。不要在 worker thread（工作线程）中操作 UI，所有 UI 操作都要放在 UI 线程上。Android 的单线程模型有两条规则：

  1. 不要阻塞 UI 线程。
  2. 不要在 UI 线程之外访问 Android UI toolkit。

Worker thread（工作线程）

要让这种单线程模型下的界面及时响应，就不能阻塞 UI 线程。如果某项操作无法立即完成，把它放到独立的后台线程或工作线程里做。但到了更新 UI 的时候，仍然只能用 UI 线程，也就是主线程。

为了方便你遵守这两条规则，Android 提供了几种从其他线程转到 UI 线程执行操作的方法：

  • Activity.runOnUiThread(Runnable)
  • View.post(Runnable)
  • View.postDelayed(Runnable, long)

下面的例子会先把工作放到后台线程，等工作完成，再回到 UI 线程更新界面：

Kotlin

// Kotlin coroutines implementation.
fun onClick(v: View) {
    // Launch a coroutine in the lifecycle scope (e.g., in an Activity or Fragment).
    lifecycleScope.launch {
        // Run the blocking task on the IO dispatcher.
        val bitmap = withContext(Dispatchers.IO) {
            BitmapFactory.decodeFile("image.png")
        }
        // Back on the main thread, update the UI.
        imageView.setImageBitmap(bitmap)
    }
}

Java

// Java Executor implementation.
// (executorService is assumed to be defined elsewhere).
public void onClick(View v) {
    executorService.execute(() -> {
        // Run the heavy task on a background thread.
        Bitmap bitmap = BitmapFactory.decodeFile("image.png");

        // Update the View on the UI thread.
        imageView.post(() -> imageView.setImageBitmap(bitmap));
    });
}

这样写是线程安全的：后台工作在单独的线程里完成，ImageView 则始终在 UI 线程上操作。

不过，操作越来越复杂时，这种代码也可能变得复杂、难以维护。如果你需要和 worker thread 做更复杂的交互，可以考虑在 worker thread 中使用 Handler，让它处理 UI 线程发来的消息。关于怎样把工作安排到后台线程，以及怎样再与 UI 线程通信，后台工作概览 中有完整说明。

线程安全的方法

你实现的方法，有时会被不止一个线程调用。遇到这种情况，就必须保证方法是线程安全的。

可以被远程调用的方法尤其如此，比如绑定型服务（bound service）里的方法。以 IBinder 中实现的方法为例：如果调用方和 IBinder 在同一个进程里，方法就在调用方的线程上执行。如果调用来自另一个进程，系统会从自己维护的线程池里选一个线程来执行。这个线程池位于 IBinder 所在的进程中，执行方法的不是该进程的 UI 线程。

比如，Service 的 onBind() 方法会在 Service 所在进程的 UI 线程上调用。但 onBind() 返回的对象里实现的方法，比如子类实现的 RPC（远程过程调用）方法，会在线程池的线程上调用。一个 Service 可以有多个客户端，因此，线程池里的多个线程可能同时调用同一个 IBinder 方法。这就是 IBinder 方法必须保证线程安全的原因。

ContentProvider 也是类似的情况：数据请求可能来自其他进程。ContentResolver 和 ContentProvider 已经把 IPC（进程间通信）的处理细节封装起来了，但负责响应请求的 ContentProvider 方法，也就是 query()、insert()、delete()、update() 和 getType()，会由 ContentProvider 所在进程的线程池调用，而不是由 UI 线程调用。多个线程可能同时调用这些方法，所以它们也必须保证线程安全。

IPC（进程间通信）

Android 提供了一种用 RPC 实现 IPC 的机制：Activity 或其他应用组件发起方法调用，方法却在另一个进程中执行，结果再传回调用方。要做到这一点，系统先把方法调用和它携带的数据，拆成操作系统能理解的形式，再从本地进程及其地址空间，传到远程进程及其地址空间。到了那里，系统再重新组装这次调用，并执行它。

返回值会沿着相反的方向传回来。这些 IPC 事务所需的代码，Android 都已经提供了，你可以专注于定义和实现 RPC 接口。

要进行 IPC，应用必须用 bindService() 绑定到一个 Service。具体可以看服务概览。
