Jetpack Compose 是 Android 的现代声明式 UI 工具包。它通过声明式 API来绘制界面，你不必再用命令式的写法逐个修改界面上的 View，编写和维护 UI 因而更简单。“声明式”“命令式”这些词还需要解释，但它们的区别会直接影响应用的设计。

声明式编程范式

传统的 Android 界面，可以看作一棵由 UI 控件组成的树。用户操作等因素改变应用状态后，就需要更新这棵树，让界面显示最新数据。常见的做法是用 findViewById() 等函数在树里寻找控件，再调用 button.setText(String)、container.addChild(View) 或 img.setImageBitmap(Bitmap) 修改节点。这些方法会改变控件内部保存的状态。

手动改 View 容易出错。同一份数据如果显示在好几个地方，你可能漏掉其中一个 View。两次更新也可能意外冲突，让界面进入不合法的状态，比如某个节点刚从 UI 中移除，另一次更新却还想给它赋值。通常，需要手动更新的 View 越多，维护就越复杂。

过去几年，整个行业开始转向声明式 UI 模型，让构建和更新界面更简单。

从概念上看，声明式 UI 会根据数据重新生成整个屏幕，再只把必要的变化应用到界面上。这样就不用手动维护一棵各自带有状态的 View 树。Compose 就是这样的声明式 UI 框架。

但重新生成整个屏幕，可能很耗时、耗计算资源，也耗电。为了减少开销，Compose 会判断当前究竟哪些 UI 部分需要重绘。这也会影响你该怎样设计 UI 组件，后面的重组一节会详细说明。

可组合函数示例

使用 Compose 时，你可以定义一组 composable（可组合）函数：接收数据，生成对应的 UI 元素，再用这些函数组成界面。比如，Greeting 控件接收一个 String，生成一个 Text 控件来显示问候语。

这个函数有几个地方需要留意：

  • 注解：函数带有 @Composable 注解。所有 composable 函数都必须有这个注解，它告诉 Compose 编译器：这个函数要把数据转换为 UI。
  • 数据输入：函数通过参数接收数据，让应用逻辑能够描述 UI。这里接收的是一个 String，因此可以用用户的姓名打招呼。
  • UI 显示：函数调用 Text()，把文本显示到界面上，真正创建文本 UI 元素的是这个 composable 函数。composable 就是通过调用其他 composable 来构成 UI 层次结构的。
  • 没有返回值：这个函数不返回任何内容。用来生成 UI 的 Compose 函数，描述的是屏幕应该呈现的状态，而不是去构造 UI 控件，因此不需要返回任何内容。

  • 特性：这个函数执行很快，具有幂等性，而且没有副作用。

    • 相同的参数传入多次，函数的行为仍然相同。它不会依赖全局变量，也不会依赖调用 random() 等方式得到的其他值。
    • 函数只描述 UI，不做修改属性、全局变量等会产生副作用的操作。

    通常，所有 composable 函数都必须具备这些特性，原因会在重组一节说明。

声明式范式转变

在许多采用命令式、面向对象方式的 UI 工具包中，初始化界面就是创建一棵控件树，通常通过加载 XML 布局来完成。每个控件保管自己的内部状态，再用 getter 和 setter 方法，让应用逻辑读取或修改它。

Compose 采用声明式方式，控件相对无状态，也不提供 getter 或 setter。实际上，它并不会把控件作为对象交给你。你只需换一组参数，再次调用同一个 composable 函数，就能更新 UI。这样，向 ViewModel 等架构模式提供状态会更简单，应用架构指南中有相关说明。之后，每当可观察数据更新，composable 就负责把当前应用状态转换成 UI。

用户操作界面时，UI 会发出 onClick 这样的事件。事件通知应用逻辑，应用逻辑再修改状态。状态一变，composable 函数就会带着新数据再次被调用，UI 元素随之重新绘制。这个过程叫作 recomposition（重组）。

动态内容

composable 用 Kotlin 编写，不用 XML，因此能像普通 Kotlin 代码一样灵活地生成动态内容。比如，你想做一个界面，向列表中的每个用户打招呼：

@Composable
fun Greeting(names: List<String>) {
    for (name in names) {
        Text("Hello $name")
    }
}

这个函数接收一组姓名，为每个人生成问候语。composable 也可以写得更复杂：用 if 决定某个 UI 元素要不要显示，使用循环，或者调用辅助函数。Kotlin 语言的灵活性都可以用上，这正是 Jetpack Compose 的主要优势之一。

重组

在命令式 UI 中，更新控件要调用 setter，修改它的内部状态。Compose 则是用新数据再次调用 composable 函数，也就是让它重组。函数生成的控件会在需要时根据新数据重绘。Compose 能判断哪些组件变了，只重组这些组件。

比如，下面这个 composable 函数会显示一个按钮：

@Composable
fun ClickCounter(clicks: Int, onClick: () -> Unit) {
    Button(onClick = onClick) {
        Text("I've been clicked $clicks times")
    }
}
ThinkingInComposeSnippets.kt

每点一次按钮，调用方就更新 clicks。Compose 会再次执行包含 Text 的 lambda，把新值显示出来，这就是重组。其他不依赖这个值的函数，不会因此重组。

前面提到，重组整棵 UI 树可能很耗计算资源，也会消耗电量。Compose 用这种智能重组来减少开销。

重组，就是输入变化时再次调用 composable 函数。收到新输入后，Compose 只调用可能发生变化的函数或 lambda，其他部分直接跳过。参数没变的部分不必重跑，重组就能更高效。

不要依赖 composable 执行时产生的副作用，因为它可能直接跳过重组。否则，应用就可能出现奇怪、难以预测的行为。“副作用”指的是应用其他部分也能观察到的变化。比如，下面这些操作都会产生危险的副作用：

  • 写入共享对象的属性
  • 更新 ViewModel 中的可观察对象
  • 更新 SharedPreferences（共享偏好设置）

composable 可能运行得非常频繁，比如动画每一帧都重新执行一次。所以函数要足够快，避免动画卡顿。如果需要读取 SharedPreferences 这样的高开销操作，就放到后台协程里做，再把结果作为参数传给 composable。

比如，下面这个 composable 用来更新 SharedPreferences 中的值。它不应该自己读写 SharedPreferences，所以代码把读写工作放进了 ViewModel 的后台协程。应用逻辑只向 composable 传入当前值，以及一个用来发起更新的回调。

@Composable
fun SharedPrefsToggle(
    text: String,
    value: Boolean,
    onValueChanged: (Boolean) -> Unit
) {
    Row {
        Text(text)
        Checkbox(checked = value, onCheckedChange = onValueChanged)
    }
}

使用 Compose 时，需要留意下面几件事，本文会逐项说明：

  • 重组会尽量跳过不需要执行的 composable 函数和 lambda。
  • 重组采用乐观方式，可能中途取消。
  • composable 可能运行得很频繁，甚至动画每一帧都运行。
  • composable 函数可以并行执行。
  • composable 函数可以按任意顺序执行。

下面会介绍怎样编写能正确应对重组的 composable。不论哪种情况，都应让函数执行快、保持幂等，而且没有副作用。

重组会尽可能跳过内容

当某些 UI 部分失效，需要更新时，Compose 会尽量只重组这些部分。它可能直接重跑某个 Button 的 composable，而不执行 UI 树中它上方或下方的任何 composable。

每个 composable 函数和 lambda，都可能单独重组。下面用列表的例子展示哪些部分可能被跳过：

/**
 * Display a list of names the user can click with a header
 */
@Composable
fun NamePicker(
    header: String,
    names: List<String>,
    onNameClicked: (String) -> Unit
) {
    Column {
        // this will recompose when [header] changes, but not when [names] changes
        Text(header, style = MaterialTheme.typography.bodyLarge)
        HorizontalDivider()

        // LazyColumn is the Compose version of a RecyclerView.
        // The lambda passed to items() is similar to a RecyclerView.ViewHolder.
        LazyColumn {
            items(names) { name ->
                // When an item's [name] updates, the adapter for that item
                // will recompose. This will not recompose when [header] changes
                NamePickerItem(name, onNameClicked)
            }
        }
    }
}

/**
 * Display a single name the user can click.
 */
@Composable
private fun NamePickerItem(name: String, onClicked: (String) -> Unit) {
    Text(name, Modifier.clickable(onClick = { onClicked(name) }))
}

一次重组可能只执行这些作用域中的某一个。比如，header 变化时，Compose 可能直接执行 Column 的 lambda，不执行它的任何父级。而执行 Column 时，如果 names 没变，也可能跳过 LazyColumn 里的条目。

因此，所有 composable 函数和 lambda 都应没有副作用。确实需要做有副作用的操作时，从回调中发起。

重组是乐观的

只要 Compose 认为某个 composable 的参数可能变了，就会开始重组。所谓乐观，是指它预期在参数再次变化之前，能完成这次重组。如果重组还没结束，参数确实又变了，Compose 可能取消当前重组，再用新参数重新开始。

取消重组时，Compose 会丢掉这次重组生成的 UI 树。但如果你已经执行了依赖“这个 UI 会显示出来”的副作用，即使组合被取消，副作用仍然已经生效。应用状态就可能因此不一致。

要应对这种乐观重组，就要确认所有 composable 函数和 lambda 都是幂等的，而且没有副作用。

可组合函数可能频繁运行

某些情况下，UI 动画每一帧都会执行 composable。如果里面有读取设备存储这样开销较大的操作，界面就可能卡顿。

比如，控件如果每次都读取设备设置，就可能一秒读取几百次，严重拖慢应用。

composable 需要什么数据，就为它定义对应的参数。这样，耗时的工作可以移出 Composition，放到别的线程执行，再通过 mutableStateOf 或 LiveData 把结果作为参数传进来。

可组合函数可能并行运行

注意：目前 composable 还不能并行运行，但编写 Compose 代码时，应按多线程的要求来写，因为将来 Compose 可能使用多线程。

Compose 可以通过并行执行 composable 来优化重组。这样就能利用多个 CPU 核心，也能让当前不在屏幕上的 composable 以较低优先级运行。

如果采用这种优化，composable 就可能在线程池的后台线程中执行。如果它调用 ViewModel 的某个函数，那个函数也可能同时被多个线程调用。

要让应用行为正确，composable 就不应产生副作用。应把这些操作放到 onClick 等回调中发起，因为这些回调始终在 UI 线程上执行。

composable 执行时，可能和调用方不在同一个线程。因此，不要在 composable lambda 里修改变量：这样写既不线程安全，也会产生它不应有的副作用。

下面这个 composable 会显示一个列表，以及列表项的数量：

@Composable
fun ListComposable(myList: List<String>) {
    Row(horizontalArrangement = Arrangement.SpaceBetween) {
        Column {
            for (item in myList) {
                Text("Item: $item")
            }
        }
        Text("Count: ${myList.size}")
    }
}
ThinkingInComposeSnippets.kt

这段代码没有副作用，只把传入的列表转换为 UI，很适合显示小列表。但如果函数转而写入局部变量，就既不线程安全，结果也不正确：

@Composable
fun ListWithBug(myList: List<String>) {
    var items = 0

    Row(horizontalArrangement = Arrangement.SpaceBetween) {
        Column {
            for (item in myList) {
                Card {
                    Text("Item: $item")
                    items++ // Avoid! Side-effect of the column recomposing.
                }
            }
        }
        Text("Count: $items")
    }
}
ThinkingInComposeSnippets.kt

在这个例子里，每次重组都会修改 items。可能是动画每一帧都重组，也可能是列表更新时重组；无论哪种，界面显示的计数都会出错。所以 Compose 不支持这样的写入。禁止这种写法，框架才能切换线程来执行 composable lambda。

可组合函数可以按任意顺序执行

注意：Compose 在主线程上运行，但从一开始就考虑了多线程，不保证将来一直使用单线程模型。因此，编写 composable 时，始终要考虑它可能在多个线程上运行。

看代码时，你可能以为 composable 会照着书写顺序执行，但不一定如此。如果一个 composable 调用了其他 composable，这些函数可能按任意顺序运行。Compose 可以判断某些 UI 元素优先级更高，先把它们画出来。

比如，下面的代码在标签页布局中绘制三个页面：

@Composable
fun ButtonRow() {
    MyFancyNavigation {
        StartScreen()
        MiddleScreen()
        EndScreen()
    }
}
ThinkingInComposeSnippets.kt

StartScreen、MiddleScreen 和 EndScreen 可能以任意顺序被调用。因此，不能让 StartScreen() 先修改一个全局变量，再指望 MiddleScreen() 使用这个变化；那属于副作用。每个函数都需要能独立完成自己的工作。
