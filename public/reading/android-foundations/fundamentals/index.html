Android 应用可以使用 Kotlin、Java 和 C++ 语言编写。Android SDK 工具会将代码以及所有数据和资源文件一起编译成 APK 或 Android App Bundle。

Android 软件包是一个以 .apk 为后缀的归档文件，包含 Android 应用在运行时所需的内容，也是 Android 设备用来安装应用的文件。

Android App Bundle 是一个以 .aab 为后缀的归档文件，包含 Android 应用项目的内容，其中还包括一些运行时并不需要的额外元数据。AAB 是一种发布格式，不能安装到 Android 设备上。它将 APK 的生成和签名推迟到后续阶段。

例如，通过 Google Play 分发应用时，Google Play 的服务器会生成经过优化的 APK，其中只包含请求安装该应用的特定设备所需的资源和代码。

每个 Android 应用都处于自己的安全沙箱中，并受到以下 Android 安全机制的保护：

  • Android 操作系统是一个多用户 Linux 系统，其中每个应用都是一个不同的用户。
  • 默认情况下，系统会为每个应用分配一个唯一的 Linux 用户 ID。这个 ID 仅供系统使用，应用并不知道它。系统会为应用中的所有文件设置权限，使其只能由分配给该应用的用户 ID 访问。
  • 每个进程都有自己的虚拟机（VM），因此应用的代码与其他应用隔离运行。
  • 默认情况下，每个应用都在自己的 Linux 进程中运行。当应用中的任意组件需要执行时，Android 系统会启动该进程；当不再需要该进程，或者系统必须为其他应用回收内存时，系统会关闭它。

Android 系统实行最小权限原则。也就是说，默认情况下，每个应用只能访问完成自身工作所必需的组件，不能访问更多组件。这会形成一个非常安全的环境：应用无法访问未获授权的系统部分。

不过，应用仍可以通过一些方式与其他应用共享数据，以及访问系统服务：

  • 可以让两个应用共享同一个 Linux 用户 ID，此时它们就能访问彼此的文件。为了节省系统资源，使用相同用户 ID 的应用还可以在同一个 Linux 进程中运行，并共享同一个 VM。这些应用还必须使用同一个证书签名。
  • 应用可以请求访问设备数据的权限，例如设备位置、相机和蓝牙连接。用户必须明确授予这些权限。有关权限的更多信息，请参阅 Android 权限。

本文的其余部分介绍以下概念：

  • 构成应用的核心框架组件。
  • 用于声明应用组件及其所需设备功能的清单文件。
  • 与应用代码分离的资源；这些资源使应用能够针对各种设备配置，妥善优化自身行为。

应用组件

应用组件是 Android 应用的基本构成单元。每个组件都是一个入口点，系统或用户可以通过它进入应用。有些组件依赖于其他组件。

应用组件共有四种类型：

  • Activity
  • Service（服务）
  • 广播接收器
  • 内容提供程序

每种类型都有各自的用途和生命周期，生命周期规定了组件如何创建和销毁。下面介绍这四种应用组件。

Activity
Activity 是与用户交互的入口点，代表一个带有用户界面的屏幕。例如，电子邮件应用可能有一个 Activity 用于显示新邮件列表，另一个用于撰写邮件，还有一个用于阅读邮件。虽然这些 Activity 共同构成电子邮件应用中连贯的用户体验，但它们彼此独立。

如果电子邮件应用允许，其他应用可以启动其中任意一个 Activity。例如，相机应用可以启动电子邮件应用中用于撰写新邮件的 Activity，让用户分享图片。

Activity 支持系统与应用之间的以下关键交互：

  • 跟踪用户当前关心的内容，也就是屏幕上显示的内容，以便系统维持承载该 Activity 的进程运行。
  • 了解之前使用过的哪些进程中包含已停止、但用户可能返回的 Activity，并提高这些进程的优先级，使其保持可用。
  • 帮助应用处理进程被终止的情况，使用户能够返回 Activity，并恢复之前的状态。
  • 为应用提供在彼此之间实现用户操作流程的方式，并让系统协调这些流程。分享就是一个主要例子。

通过继承 Activity 类来实现 Activity。有关 Activity 类的更多信息，请参阅 Activity 简介。

Service（服务）
Service 是一种通用入口点，可出于各种原因使应用保持在后台运行。它是在后台执行长时间操作，或者为远程进程执行工作的组件。Service 不提供用户界面。

例如，用户使用其他应用时，Service 可以在后台播放音乐，也可以通过网络获取数据，而不阻塞用户与 Activity 的交互。其他组件（例如 Activity）可以启动 Service 并让其运行，也可以绑定到它以与之交互。

有两种 Service 会告知系统如何管理应用：启动型服务和绑定型服务。

启动型服务会告知系统让其持续运行，直到工作完成。这项工作可能是在后台同步一些数据，也可能是在用户离开应用后继续播放音乐。在后台同步数据和播放音乐代表不同类型的启动型服务，系统会以不同方式处理它们：

  • 音乐播放是用户能够直接感知的事情。应用通过声明自己希望在前台运行，并显示通知告诉用户它正在运行，将这一点传达给系统。在这种情况下，系统会优先维持该服务所在进程的运行，因为如果它消失，用户体验就会受到影响。
  • 普通后台服务并不是用户能够直接感知的，因此系统在管理其进程时有更大的自由。如果需要将 RAM 用于用户更迫切关心的事情，系统可以允许该服务被终止，并在稍后重新启动它。

绑定型服务之所以运行，是因为其他应用或系统表示需要使用该服务。绑定型服务向另一个进程提供 API，系统知道这些进程之间存在依赖关系。因此，如果进程 A 绑定到进程 B 中的某个服务，系统就知道必须为 A 维持进程 B 及其服务的运行。此外，如果进程 A 是用户关心的，系统也知道应当将进程 B 视为用户关心的进程。

由于 Service 很灵活，它们能够成为各种更高层系统概念的有用构成单元。动态壁纸、通知监听器、屏幕保护程序、输入法、无障碍服务以及许多其他核心系统功能，都是以 Service 的形式构建的：应用实现这些 Service，系统在它们运行时绑定到它们。

Service 通过继承 Service 来实现。有关 Service 类的更多信息，请参阅服务概览。

注意：如果应用以 Android 5.0（API 级别 21）或更高版本为目标，请使用 JobScheduler 类调度操作。JobScheduler 通过优化作业调度来降低耗电量，并与 Doze API 配合，从而节省电量。有关该类的更多使用信息，请参阅 JobScheduler 参考文档。

广播接收器
广播接收器是一种组件，允许系统在常规用户操作流程之外向应用传递事件，使应用能够响应系统范围的广播通知。广播接收器也是明确定义的应用入口，因此系统甚至可以向当前没有运行的应用传递广播。

例如，应用可以设置一个闹钟，在事件即将发生时发布通知提醒用户。由于闹钟会传递给应用中的 BroadcastReceiver，应用不必一直保持运行直到闹钟响起。

许多广播来自系统，例如通知屏幕已经关闭、电池电量不足或照片已经拍摄完成的广播。应用也可以主动发出广播，例如通知其他应用：某些数据已经下载到设备上，可以使用了。

虽然广播接收器不显示用户界面，但它们可以创建状态栏通知，在广播事件发生时提醒用户。不过，更常见的情况是，广播接收器只是通往其他组件的入口，设计上只应执行极少量工作。

例如，广播接收器可以根据某个事件，使用 JobScheduler 调度一个 JobService 来执行工作。广播接收器经常涉及应用之间的交互，因此在设置它们时，了解相关安全影响非常重要。

广播接收器通过继承 BroadcastReceiver 来实现，每条广播都以 Intent 对象的形式传递。更多信息请参阅 BroadcastReceiver 类。

内容提供程序
内容提供程序管理一组共享的应用数据。你可以将这些数据存储在文件系统、SQLite 数据库、网络，或应用能够访问的任何其他持久化存储位置。只要内容提供程序允许，其他应用就可以通过它查询或修改数据。

例如，Android 系统提供了管理用户联系人信息的内容提供程序。具备相应权限的任何应用，都可以查询该内容提供程序，例如使用 ContactsContract.Data 读写某个人的信息。

内容提供程序内置了大量面向数据库这一常见使用场景的 API 和支持，因此人们很容易把它理解为数据库的抽象。不过，从系统设计的角度看，它具有不同的核心目的。

对系统而言，内容提供程序是应用中发布具名数据项的入口点，这些数据项由 URI 方案标识。因此，应用可以决定如何将自身数据映射到 URI 命名空间，再把这些 URI 交给其他实体，供它们访问数据。这让系统在管理应用时能够做到以下几点：

  • 分配 URI 不要求应用保持运行，因此 URI 可以在所属应用退出后继续存在。只有从相应 URI 获取应用数据时，系统才需要确保数据所属应用正在运行。
  • 这些 URI 还提供了一种重要的细粒度安全模型。例如，应用可以将自己某张图片的 URI 放到剪贴板上，同时保持内容提供程序的访问限制，使其他应用无法自由访问它。当第二个应用尝试访问剪贴板上的这个 URI 时，系统可以通过临时授予 URI 权限，让该应用访问数据，从而仅访问该 URI 对应的数据，而不能访问第二个应用中的其他内容。

内容提供程序也适用于读写应用私有、不对外共享的数据。

内容提供程序通过继承 ContentProvider 来实现，并且必须实现一组标准 API，使其他应用能够执行事务。更多信息请参阅内容提供程序开发指南。

Android 系统设计的一个独特之处在于，任何应用都可以启动另一个应用的组件。例如，如果希望用户使用设备相机拍照，很可能已经有另一个应用提供这一功能，你可以使用它，而不必自己开发拍照的 Activity。你无需把相机应用的代码引入自己的应用，甚至无需链接这些代码。相反，你可以直接启动相机应用中负责拍照的 Activity。拍摄完成后，照片还会返回你的应用，供你使用。对用户而言，相机就像是你的应用的一部分。

系统启动组件时，如果其所属应用的进程尚未运行，就会先启动该进程，并实例化组件所需的类。例如，如果你的应用启动相机应用中负责拍照的 Activity，该 Activity 会在相机应用所属的进程中运行，而不是在你的应用进程中运行。因此，与大多数其他系统上的应用不同，Android 应用没有单一入口点：没有 main() 函数。

由于系统让每个应用在独立进程中运行，并通过文件权限限制对其他应用的访问，你的应用不能直接激活另一个应用中的组件。不过，Android 系统可以。要激活另一个应用中的组件，你需要向系统发送一条消息，表明启动特定组件的意图。随后，系统会代你激活该组件。

激活组件

一种称为 Intent 的异步消息可以激活四类组件中的三类：Activity、Service 和广播接收器。Intent 在运行时将各个组件连接起来。你可以把它看作信使，负责向其他组件请求执行某项操作，无论该组件属于你的应用还是其他应用。

Intent 使用 Intent 对象创建。该对象定义一条消息，用于激活某个特定组件（显式 Intent），或者某一类组件（隐式 Intent）。

对于 Activity 和 Service，Intent 定义要执行的操作，例如查看或发送某项内容；它还可能指定操作所涉及数据的 URI，以及被启动组件需要知道的其他信息。

例如，Intent 可以向 Activity 传达显示图片或打开网页的请求。在某些情况下，你可以启动 Activity 并接收结果，此时 Activity 也会通过 Intent 返回结果。你还可以发出 Intent，让用户选择一位联系人并将其返回给你。返回的 Intent 中包含指向所选联系人的 URI。

对于广播接收器，Intent 定义广播通知的内容。例如，表示设备电量不足的广播只包含一个已知的操作字符串，用来表示电量不足。

与 Activity、Service 和广播接收器不同，内容提供程序会在 ContentResolver 的请求指向它时被激活。内容解析器负责与内容提供程序之间的所有直接事务；需要与内容提供程序进行事务交互的组件，会调用 ContentResolver 对象上的方法。出于安全考虑，这在内容提供程序与请求信息的组件之间保留了一层抽象。

激活各类组件分别使用不同的方法：

  • 将 Intent 传给 startActivity()，可以启动 Activity 或让它执行新任务；如果希望 Activity 返回结果，则传给 startActivityForResult()。
  • 在 Android 5.0（API 级别 21）及更高版本上，可以使用 JobScheduler 类调度操作。对于更早的 Android 版本，可以将 Intent 传给 startService()，启动 Service 或向正在运行的 Service 发出新指令。将 Intent 传给 bindService()，可以绑定到 Service。
  • 将 Intent 传给 sendBroadcast() 或 sendOrderedBroadcast() 等方法，可以发出广播。
  • 调用 ContentResolver 上的 query()，可以向内容提供程序发起查询。

有关使用 Intent 的更多信息，请参阅 Intent 与 Intent Filter。以下文档提供了激活特定组件的更多信息：Activity 简介、服务概览、BroadcastReceiver 和内容提供程序。

清单文件

Android 系统要启动某个应用组件，必须先读取应用的清单文件 AndroidManifest.xml，确认该组件存在。应用在这个文件中声明自己的全部组件；它位于应用项目目录的根目录。

除了声明应用组件，清单还执行多项工作，例如：

  • 标识应用所需的任何用户权限，例如访问互联网或读取用户的联系人。
  • 根据应用使用的 API，声明应用所需的最低 API 级别。
  • 声明应用使用或要求的硬件和软件功能，例如相机、蓝牙服务或多点触控屏幕。
  • 声明应用需要链接的 API 库（Android 框架 API 除外），例如 Google 地图库。

声明组件

清单的首要任务是向系统告知应用的组件。例如，清单文件可以按如下方式声明一个 Activity：

<?xml version="1.0" encoding="utf-8"?>
<manifest ... >
    <application android:icon="@drawable/app_icon.png" ... >
        <activity android:name="com.example.project.ExampleActivity"
                  android:label="@string/example_label" ... >
        </activity>
        ...
    </application>
</manifest>

在 <application> 元素中，android:icon 属性指向用于标识应用的图标资源。

在 <activity> 元素中，android:name 属性指定 Activity 子类的完全限定类名，android:label 属性指定向用户显示的 Activity 标签字符串。

必须使用以下元素声明所有应用组件：

  • 使用 <activity> 元素声明 Activity
  • 使用 <service> 元素声明服务
  • 使用 <receiver> 元素声明广播接收器
  • 使用 <provider> 元素声明内容提供程序

包含在源代码中但未在清单中声明的 Activity、服务和内容提供程序对系统不可见，因此永远无法运行。不过，广播接收器既可以在清单中声明，也可以在代码中动态创建为 BroadcastReceiver 对象，并调用 registerReceiver() 向系统注册。

有关应用清单文件结构的更多信息，请参阅应用清单概览。

声明组件能力

如激活组件一节所述，可以使用 Intent 启动 Activity、服务和广播接收器。为此，可以在 Intent 中使用组件类名显式指定目标组件。也可以使用隐式 Intent，描述要执行的操作类型，并可选择指定操作所针对的数据。隐式 Intent 让系统在设备上查找能够执行该操作的组件并启动它。如果多个组件都能执行 Intent 描述的操作，用户可以选择使用哪一个。

注意：如果使用 Intent 启动 Service，请使用显式 Intent 来确保应用安全。使用隐式 Intent 启动服务存在安全隐患，因为无法确定哪个服务会响应 Intent，而且用户无法看到启动的是哪个服务。从 Android 5.0（API 级别 21）开始，如果使用隐式 Intent 调用 bindService()，系统会抛出异常。不要为服务声明 Intent 过滤器。

系统通过比较收到的 Intent 与设备上其他应用清单文件提供的 Intent 过滤器，识别能够响应该 Intent 的组件。

在应用清单中声明 Activity 时，可以选择添加 Intent 过滤器来声明 Activity 的能力，使其能够响应其他应用的 Intent。做法是在组件声明元素内添加一个 <intent-filter> 子元素。

例如，如果构建的电子邮件应用包含用于撰写新邮件的 Activity，可以声明一个 Intent 过滤器来响应发送新邮件的“send”Intent，如以下示例所示：

<manifest ... >
    ...
    <application ... >
        <activity android:name="com.example.project.ComposeEmailActivity">
            <intent-filter>
                <action android:name="android.intent.action.SEND" />
                <data android:type="*/*" />
                <category android:name="android.intent.category.DEFAULT" />
            </intent-filter>
        </activity>
    </application>
</manifest>

如果另一个应用创建一个带有 ACTION_SEND 操作的 Intent，并将其传递给 startActivity()，系统可能会启动你的 Activity，以便用户撰写和发送电子邮件。

有关创建 Intent 过滤器的更多信息，请参阅 Intent 与 Intent 过滤器文档。

声明应用要求

运行 Android 的设备种类繁多，并非所有设备都提供相同的功能和能力。为防止应用安装到缺少其所需功能的设备上，必须在清单文件中声明设备和软件要求，清楚地定义应用支持的设备类型。

这些声明大多仅用于提供信息。系统不会读取它们，但 Google Play 等外部服务会读取，以便用户从设备搜索应用时进行过滤。

例如，假设应用需要相机，并使用了 Android 8.0（API 级别 26）中引入的 API，就必须声明这些要求。minSdkVersion 和 targetSdkVersion 的值在应用模块的 build.gradle 文件中设置：

android {
  ...
  defaultConfig {
    ...
    minSdkVersion 26
    targetSdkVersion 29
  }
}

注意：不要直接在清单文件中设置 minSdkVersion 和 targetSdkVersion，因为 Gradle 会在构建过程中覆盖它们。详情请参阅指定 API 级别要求。

在应用清单文件中声明相机功能：

<manifest ... >
    <uses-feature android:name="android.hardware.camera.any"
                  android:required="true" />
    ...
</manifest>

采用这些示例中的声明后，没有相机或 Android 版本低于 8.0 的设备无法从 Google Play 安装你的应用。不过，也可以声明应用使用相机，但并不要求相机。为此，将 required 属性设为 false，在运行时检查设备是否有相机，并根据需要停用相机功能。

有关管理应用与不同设备兼容性的更多信息，请参阅设备兼容性概览。

应用资源

Android 应用不仅由代码组成，还需要独立于源代码的资源，例如图片、音频文件，以及所有与应用视觉呈现有关的内容。例如，可以使用 XML 文件定义动画、菜单、样式、颜色，以及 Activity 用户界面的布局。

使用应用资源，可以在不修改代码的情况下轻松更新应用的各种特性。提供多组替代资源，还可以针对不同的设备配置优化应用，例如不同语言和屏幕尺寸。

对于 Android 项目中的每一项资源，SDK 构建工具都会定义一个唯一的整数 ID。你可以在应用代码中，或在其他以 XML 定义的资源中，使用该 ID 引用资源。例如，如果应用包含一个名为 logo.png 的图片文件（保存在 res/drawable/ 目录中），SDK 工具就会生成名为 R.drawable.logo 的资源 ID。这个 ID 映射到应用专属的一个整数，你可以用它引用该图片，并将其加入用户界面。

将资源与源代码分离的一个重要作用，是能够针对不同设备配置提供替代资源。

例如，在 XML 中定义 UI 字符串后，可以将这些字符串翻译成其他语言，并保存在不同文件中。随后，Android 会根据资源目录名称后附加的语言限定符（例如表示法语字符串的 res/values-fr/），以及用户的语言设置，为 UI 应用合适的语言字符串。

Android 为替代资源支持多种限定符。限定符是资源目录名称中的一个短字符串，用来定义这些资源适用的设备配置。

例如，可以根据设备屏幕的方向和尺寸，为 Activity 创建不同的布局。当设备屏幕为纵向（较高）时，你可能希望按钮垂直排列；而屏幕为横向（较宽）时，可能希望按钮水平排列。要根据方向改变布局，可以定义两个布局，并为每个布局的目录名称加上合适的限定符。随后，系统会根据设备当前方向自动采用合适的布局。

有关应用可包含的不同资源类型，以及如何为不同设备配置创建替代资源的更多信息，请阅读应用资源概览。要进一步了解最佳实践以及如何设计健壮、达到生产质量要求的应用，请参阅应用架构指南。
