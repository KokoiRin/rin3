在协程中，Flow 可以按顺序发出多个值；挂起函数则只返回一个值。比如，要持续接收数据库的实时变化，就可以用 Flow。

Flow 基于协程构建，可以持续提供多个值。从概念上看，它是一条可以异步计算的数据流。发出的值必须属于同一种类型，比如 Flow<Int> 发出的都是整数。

Flow 和 Iterator 很像，都会依次产生一组值。但 Flow 用挂起函数异步生产和消费这些值。比如，它可以安全地发起网络请求，取得下一个值，而不阻塞主线程。

一条数据流里有三种角色：

  • 生产者负责生成数据，放进流中。借助协程，这个过程也可以异步进行。
  • 中间环节（可选）负责修改流里发出的每个值，或者修改流本身。
  • 消费者负责接收和使用流里的值。

在 Android 中，Repository 通常负责生产 UI 数据，UI 则作为消费者，把数据展示出来。但角色也可能反过来：UI 产生用户输入事件，其他层消费这些事件。夹在生产者与消费者之间的层，通常就充当中间环节，调整数据流，让它适合下一层使用。

创建 Flow

创建 Flow 可以用 Flow 构建器 API。flow 构建器会创建一个新 Flow，你可以在里面调用 emit，主动向流里发出新值。

下面的例子会按固定间隔自动获取最新新闻。由于一个挂起函数不能连续返回多个值，数据源会创建并返回 Flow。在这里，数据源就是生产者。

class NewsRemoteDataSource(
    private val newsApi: NewsApi,
    private val refreshIntervalMs: Long = 5000
) {
    val latestNews: Flow<List<ArticleHeadline>> = flow {
        while (true) {
            val latestNews = newsApi.fetchLatestNews()
            emit(latestNews) // Emits the result of the request to the flow
            delay(refreshIntervalMs) // Suspends the coroutine for some time
        }
    }
}

// Interface that provides a way to make network requests with suspend functions
interface NewsApi {
    suspend fun fetchLatestNews(): List<ArticleHeadline>
}
Flow.kt

flow 构建器在协程中执行，所以能使用同样的异步 API，但也要遵守一些限制：

  • Flow 是顺序执行的。生产者调用挂起函数时，会先挂起，等函数返回再继续。比如这里要等 fetchLatestNews 网络请求完成，才会把结果发到流里。
  • 使用 flow 构建器时，生产者不能跑到另一个 CoroutineContext 里 emit 值。因此，不要新建协程或用 withContext 切换到不同的 CoroutineContext，再调用 emit。有这种需要时，可以改用 callbackFlow 等其他 Flow 构建器。

修改数据流

中间环节可以用中间操作符调整数据流，而不消费其中的值。这些操作符本身也是函数，把它们应用到流上，就会组成一串操作，但此时还不会执行。直到后面真正消费数据时，这些操作才会运行。具体可以看 Flow 参考文档。

下面的 Repository 用中间操作符 map 转换数据，再交给 View 显示：

class NewsRepository(
    private val newsRemoteDataSource: NewsRemoteDataSource,
    private val userData: UserData
) {
    /**
     * Returns the favorite latest news applying transformations on the flow.
     * These operations are lazy and don't trigger the flow. They just transform
     * the current value emitted by the flow at that point in time.
     */
    val favoriteLatestNews: Flow<List<ArticleHeadline>> =
        newsRemoteDataSource.latestNews
            // Intermediate operation to filter the list of favorite topics
            .map { news -> news.filter { userData.isFavoriteTopic(it) } }
            // Intermediate operation to save the latest news in the cache
            .onEach { news -> saveInCache(news) }
}
Flow.kt

你可以连续使用多个中间操作符，把它们接成一条操作链。它们会等到 Flow 发出数据项时才按需执行。注意，仅仅加上中间操作符，并不会开始收集 Flow。

从 Flow 收集

要让 Flow 开始监听数据，需要调用终止操作符。想逐个接收流发出的所有值，可以使用 collect。关于终止操作符的更多说明，见 Flow 官方文档。

collect 是挂起函数，需要在协程中执行。传给它的 lambda 会在每个新值到来时被调用。由于它可以挂起，调用 collect 的协程可能要一直等到 Flow 关闭，才继续往下执行。

继续前面的例子，下面这个简单的 ViewModel 会消费 Repository 提供的数据：

class LatestNewsViewModel(
    private val newsRepository: NewsRepository
) : ViewModel() {

    init {
        viewModelScope.launch {
            // Trigger the flow and consume its elements using collect
            newsRepository.favoriteLatestNews.collect { favoriteNews ->
                // Update UI with the latest favorite news
            }
        }
    }
}
Flow.kt

一旦开始收集 Flow，生产者就会启动，按固定间隔获取新闻，再把网络结果发出来。这里的 while(true) 循环会让生产者一直运行，直到 ViewModel 被清理、viewModelScope 被取消，数据流才关闭。

下面两种情况会停止收集：

  • 负责收集的协程被取消，就像前面的例子。这也会停止底层生产者。
  • 生产者已经发完所有数据项。此时流会关闭，调用 collect 的协程继续执行。

除非用其他中间操作符改变了行为，否则 Flow 是冷的、惰性的：每调用一次终止操作符，生产者代码就会执行一次。前面的例子如果有多个收集者，数据源就会按多个不同的固定间隔，重复获取新闻。多个消费者需要同时收集时，可以用 shareIn 共享 Flow，减少重复工作。

捕获意外异常

生产者也可能由第三方库实现，因此可能抛出意料之外的异常。可以用 catch 中间操作符来处理。

class LatestNewsViewModel(
    private val newsRepository: NewsRepository
) : ViewModel() {

    init {
        viewModelScope.launch {
            newsRepository.favoriteLatestNews
                // Intermediate catch operator. If an exception is thrown,
                // catch and update the UI
                .catch { exception -> notifyError(exception) }
                .collect { favoriteNews ->
                    // Update UI with the latest favorite news
                }
        }
    }
}
Flow.kt

前面的例子发生异常时，collect 的 lambda 不会执行，因为它没有收到新的数据项。

catch 也能向 Flow 里 emit 数据。所以示例中的 Repository 可以在异常时，改为 emit 缓存的值：

class NewsRepository(
    // ...
) {
    val favoriteLatestNews: Flow<List<ArticleHeadline>> =
        newsRemoteDataSource.latestNews
            .map { news -> news.filter { userData.isFavoriteTopic(it) } }
            .onEach { news -> saveInCache(news) }
            // If an error happens, emit the last cached values
            .catch { exception -> emit(lastCachedNews()) }
}
Flow.kt

这次发生异常时，collect 的 lambda 就会执行，因为异常处理过程中向流里发出了一个新值。

在不同的 CoroutineContext 中执行

默认情况下，flow 构建器中的生产者，会在收集协程的 CoroutineContext 中运行。前面也提到，它不能切换到其他 CoroutineContext 去 emit 值。但这未必适合你的场景。比如本文的 Repository，就不应该在 viewModelScope 使用的 Dispatchers.Main 上执行这些操作。

想改变 Flow 的 CoroutineContext，可以用 flowOn。flowOn 只改变上游的 CoroutineContext，也就是生产者，以及写在 flowOn 之前（上方）的所有中间操作符。下游不受影响：位于 flowOn 之后的操作符和消费者，仍然使用收集 Flow 时的 CoroutineContext。如果有多个 flowOn，每一个都从自己所在的位置往上影响上游。

class NewsRepository(
    private val newsRemoteDataSource: NewsRemoteDataSource,
    private val userData: UserData,
    private val defaultDispatcher: CoroutineDispatcher
) {
    val favoriteLatestNews: Flow<List<ArticleHeadline>> =
        newsRemoteDataSource.latestNews
            .map { news -> // Executes on the default dispatcher
                news.filter { userData.isFavoriteTopic(it) }
            }
            .onEach { news -> // Executes on the default dispatcher
                saveInCache(news)
            }
            // flowOn affects the upstream flow ↑
            .flowOn(defaultDispatcher)
            // the downstream flow ↓ is not affected
            .catch { exception -> // Executes in the consumer's context
                emit(lastCachedNews())
            }
}
Flow.kt

在这段代码中，onEach 和 map 使用 defaultDispatcher；catch 与消费者则使用 viewModelScope 的 Dispatchers.Main。

数据源层做的是 I/O 工作，所以应选用针对 I/O 优化的 dispatcher：

class NewsRemoteDataSource(
    // ...
    private val ioDispatcher: CoroutineDispatcher
) {

    val latestNews: Flow<List<ArticleHeadline>> = flow {
        // Executes on the IO dispatcher
        // ...
    }
        .flowOn(ioDispatcher)
}

Jetpack 库中的 Flow

许多 Jetpack 库已经集成 Flow，Android 第三方库也广泛使用它。实时数据更新、持续不断的数据流，都很适合用 Flow。

你可以在 Room 中使用 Flow，接收数据库变化。在数据访问对象（DAO）中返回 Flow，就能取得实时更新。

@Dao
abstract class ExampleDao {
    @Query("SELECT * FROM Example")
    abstract fun getExamples(): Flow<List<Example>>
}
Flow.kt

Example 表每次发生变化，Flow 都会发出一个新列表，包含数据库中的新数据项。

将基于回调的 API 转换为 Flow

callbackFlow 能把基于回调的 API 转成 Flow。比如，Firebase Firestore 的 Android API 就使用回调。

注意：从 24.3.0 版本开始，firestore-ktx 已提供返回 Flow 的 snapshots() 扩展。所以，对于这个 API，不用再自己写转换代码。

下面的代码展示了怎样把这些 API 转成 Flow，并监听 Firestore 数据库的更新：

class FirestoreUserEventsDataSource(
    private val firestore: FirebaseFirestore
) {
    // Method to get user events from the Firestore database
    fun getUserEvents(): Flow<UserEvents> = callbackFlow {

        // Reference to use in Firestore
        var eventsCollection: CollectionReference? = null
        try {
            eventsCollection = FirebaseFirestore.getInstance()
                .collection("collection")
                .document("app")
        } catch (e: Throwable) {
            // If Firebase cannot be initialized, close the stream of data
            // flow consumers will stop collecting and the coroutine will resume
            close(e)
        }

        // Registers callback to firestore, which will be called on new events
        val subscription = eventsCollection?.addSnapshotListener { snapshot, _ ->
            if (snapshot == null) { return@addSnapshotListener }
            // Sends events to the flow! Consumers will get the new events
            try {
                trySend(snapshot.getEvents())
            } catch (e: Throwable) {
                // Event couldn't be sent to the flow
            }
        }

        // The callback inside awaitClose will be executed when the flow is
        // either closed or cancelled.
        // In this case, remove the callback from Firestore
        awaitClose { subscription?.remove() }
    }
}

flow 构建器有上下文限制，而 callbackFlow 允许你用 send 从不同的 CoroutineContext 发出值，也可以在协程外用 trySend 发出值。

callbackFlow 内部使用通道，概念上很像阻塞队列。channel 有一个容量，表示最多能缓存多少个元素；callbackFlow 创建的 channel 默认能放 64 个。当 channel 已满，你还想放入新元素时，send 会挂起生产者，等空出位置再继续；trySend 则不会放入元素，而是立即返回 false。

只有容量允许时，trySend 才会立即把指定元素放进 channel，然后返回成功结果。
