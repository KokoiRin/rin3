## 这一章真正讲的不是“怎么贴便签”

第一次看到 EventStorming 的十个步骤，很容易把注意力放到颜色上：

- 橙色是事件；
- 蓝色是命令；
- 紫色是策略；
- 绿色是读模型；
- 粉色是外部系统。

但颜色只是让多人协作更顺畅的视觉语法。本章真正解决的问题是：

> 怎样让拥有不同局部知识的人，围绕同一条业务故事说话，并逐步把事实、决策、因果、责任和边界讲清楚？

十个步骤并不是十套独立技术，而是同一张模型的十次聚焦：

1. 先收集已经发生的业务事实；
2. 把事实排成主线与分支；
3. 标出痛点和知识空白；
4. 找到流程发生阶段转换的位置；
5. 补上人主动发起的命令；
6. 补上系统自动继续的策略；
7. 补上人作决定前看到的信息；
8. 补上范围外系统的输入与输出；
9. 从命令、状态和事件中寻找一致性边界；
10. 再把相关聚合归入限界上下文候选。

这个顺序非常重要：**先有业务故事，后有边界，最后才谈实现。**

## 我最想保留的四个认识

### 领域事件是业务承认的事实，不是技术回调

事件要用过去式，是因为它描述已经发生的事实。

“应用模板”是一个意图；“模板已应用”才是事实。“请求成功回调”虽然也发生过，但它使用的是实现语言，不一定具有业务意义。

这条区分对 native-text 很重要。模板选择链路至少可能存在：

- 用户已选择模板；
- 平台写回已请求；
- 模板已应用；
- 模板应用已失败；
- 上次已提交模板已恢复。

如果把这些都压成一次 `selectedIndex` 修改，就会丢掉“用户当前想要什么”和“平台已经确认什么”之间的业务差异。EventStorming 不会自动修复设计，但它会让这些不同事实在墙上无法再假装成同一件事。

### 分支和痛点比幸福路径更接近真实规则

幸福路径适合建立共同起点，但真正暴露领域规则的通常是分支：

- 平台写回失败后恢复什么？
- 过期回调到达时，是否仍可改变当前会话？
- 二次编辑恢复的是模板 ID、展示位置，还是平台内容事实？
- Pack 或多页模式是否遵循相同规则？

当参与者对这些问题给出不同答案，不应立即用一个“合理实现”把图补完整。粉色痛点的意义，就是允许团队诚实地写下：**这里还没有共同知识。**

这也解释了为什么 EventStorming 的主要产物不是架构图，而是对齐后的认知，以及一张明确标出未知区域的业务地图。

### 聚合与限界上下文应该在故事之后出现

如果一开始就问“TemplateSession 是不是聚合”“Common 是不是一个限界上下文”，讨论很容易被当前类结构和目录带走。

EventStorming 反过来做：

- 哪些命令会改变状态？
- 改变成功后，业务承认了哪些新事实？
- 哪些规则必须共同保持一致？
- 失败时，哪些状态必须一起回滚？
- 哪些聚合共享一套语言和模型，又通过策略紧密协作？

这些答案才提供聚合和限界上下文的候选边界。

同时要注意，业务边界不直接等于代码边界：

| EventStorming 发现的问题 | 后续设计要回答的问题 |
| --- | --- |
| 哪些事实属于同一业务语境 | 哪些语义由 Common 拥有 |
| 哪些状态必须共同一致 | 一次事务或 Session 的最小边界是什么 |
| 哪些动作来自范围外部 | Android / 鸿蒙如何适配平台生命周期与副作用 |
| 哪些上下文用不同模型说话 | 跨边界传递命令、结果还是快照 |

先把业务语义说清，再决定 `commonMain`、Android 或 OHOS 的所有权，才不会把平台目录误当成领域边界。

### 事件模型不等于事件溯源

EventStorming 的结果是事件化的业务模型，但这不意味着：

- 每张事件便签都要成为代码里的 Event 类；
- 每个事件都要写入消息队列；
- 系统必须采用事件溯源；
- 每个限界上下文都要拆成独立服务。

工作坊首先是一种知识探索方法。实现时仍需判断某个事实是否需要持久化、发布或回放，以及事件溯源是否符合这个业务领域的复杂度和审计需要。

这是一个很容易跑偏的地方：我们刚刚通过“先不谈技术”获得了一张清晰业务图，不能在最后一步又机械地把便签逐张翻译成技术结构。

## 用 native-text 做一次小型 EventStorming

如果真要试一次，我会先把范围限定为：

> 用户从完成文字输入，到选择模板并完成平台写回；同时覆盖写回失败与二次编辑恢复。

第一轮只做全景步骤：

1. 让产品、测试、Common、Android、鸿蒙分别独立写事件；
2. 合并重复事件，先排成功主线；
3. 加入写回失败、过期请求、Pack、多页和二次编辑分支；
4. 用痛点标出各平台理解不一致的地方；
5. 标出“进入模板选择”“平台写回完成”“开始二次编辑”等阶段转折。

这轮的目标不是当天决定架构，而是得到一套共同业务词汇。第二轮再为模板选择流程补齐命令、策略、读模型、外部系统和聚合候选。

一个可能的局部片段是：

| 类型 | 例子 | 它帮助回答什么 |
| --- | --- | --- |
| 事件 | 模板应用已失败 | 业务已经承认了什么 |
| 策略 | 当应用失败时，恢复上次已提交模板 | 为什么流程自动继续 |
| 命令 | 恢复上次模板 | 系统接下来要做什么 |
| 读模型 | 模板列表、当前已提交模板、应用中状态 | 用户决定前需要看到什么 |
| 外部系统 | 平台 NLE / Pack 宿主 | 哪些事实或副作用在探索范围外 |
| 聚合候选 | 模板会话 | 哪些规则与状态需要共同保持一致 |

其中最值得讨论的不是“这些名字对不对”，而是每个人能否对每张便签给出同一个业务解释。

## 这章对我工作方式的提醒

我过去习惯从代码调查业务：追数据流、读写点、回调和平台差异，再反推规则。这个方式仍然重要，但它只能发现已经写进代码的知识。

EventStorming 补上了另一半：

- 产品脑中但没有写进需求的规则；
- 测试在回归中积累的边缘情况；
- 平台工程师各自默认但从未对齐的前提；
- 客服和线上问题里出现、代码结构却没有命名的业务痛点。

它和“先业务、后边界、再实现”的关系非常直接。代码分析可以验证真实实现，EventStorming 则帮助我们在改代码之前形成一张共同认可、包含未知点的业务图。两者结合，才比较不容易把迁移做成纯代码翻译。

## 一句话总结

第十二章让我把 EventStorming 理解成一种集体校准过程：**先沿时间线说清业务事实，再补上意图、因果和决策依据，最后才从一致性与语言中发现边界；墙上的模型会变化，但共同形成的理解才是最重要的产物。**
