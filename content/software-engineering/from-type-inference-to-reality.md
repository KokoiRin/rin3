:::slide {"kind":"code","chapter":"inference","eyebrow":"THE MISSING TYPE"}
## 那个没有写出的类型

```cpp
std::vector<User> users = getUsers();
```

```kotlin
val users = getUsers()
val activeUsers = users.filter { it.active }
```

看到 Kotlin 代码时，我突然想到：这些变量究竟被推断成了什么类型？

我不知道。但在完成眼前工作时，好像也不重要。

:::detail
在 C++ 的传统写法里，类型是代码中非常显眼的一部分。到了 Kotlin，编译器可以根据右侧表达式推断局部变量的类型。类型并没有消失，只是从“必须由我重复写出”，变成了“工具能够可靠推出，必要时我再去查看”。

这个体验让我立刻想到了 AI 编程。使用 AI 完成一个功能时，我也在把一部分实现细节交出去：我先表达目标、限制和验收条件，不一定亲手写出中间的每个辅助类型、API 调用和转换步骤。

两者当然不是同一种机制。类型推断遵循语言规则，结果可以由编译器确定和检查；AI 生成具有不确定性，仍然需要测试、审查和运行证据。它们真正相似的地方，是**人的注意力都被允许向上移动**：不再重复表达工具已经能处理的细节，而是更直接地表达意图。

这使一个小小的语法体验变成了更大的问题：软件工具的长期演化，是否一直在把“怎么做”下沉，把“为什么做、要做成什么样”留给人？
:::
:::

:::slide {"kind":"prose","chapter":"inference","eyebrow":"A LONG MOVEMENT"}
## 让细节逐层下沉

从高级语言、垃圾回收、类型推断、IDE、框架到 AI，工具不断接管可以推导、生成或机械验证的工作。

> 编程的抽象层级不断上升，人越来越接近意图，机器越来越负责展开细节。

:::detail
高级语言让程序员不必直接安排寄存器和跳转；垃圾回收接管了一部分内存生命周期；类型推断减少了重复的类型声明；框架封装网络、序列化和生命周期；AI 又开始生成更大范围的实现。

每次抽象上移，都不是让下面一层从此没有价值。抽象会泄漏，系统会失败，性能和边界问题仍会迫使我们向下理解。变化的是学习与工作的顺序：底层知识从“每一步都要亲自操作”，逐渐变成“建立判断、验证结果和处理异常时调用”。

因此，用“降低编程门槛”描述这条路线还不够完整。它真正改变的是**表达意图的成本**。以前我们必须把意图翻译成大量精确步骤，现在工具能替我们完成越来越长的一段翻译。

但翻译变便宜以后，原始意图是否正确、完整、彼此一致，就会变得更显眼。要理解这条分界，可以借用 Fred Brooks 在《No Silver Bullet》中提出的一组经典概念。
:::
:::

:::slide {"kind":"matrix","chapter":"complexity","eyebrow":"ESSENCE AND ACCIDENTS"}
## 两种复杂度

| 追问 | 偶然复杂度 | 本质复杂度 |
| --- | --- | --- |
| 它从哪里来？ | 当前表达和实现手段 | 要解决的问题本身 |
| 常见例子 | 样板代码、胶水转换、繁琐配置 | 业务规则、状态关系、利益冲突 |
| 工具能做什么？ | 大量自动化或隐藏 | 降低处理成本，未必消除问题 |

关键不是“代码复杂不复杂”，而是：**换一种更好的工具以后，这个困难还在不在？**

:::detail
“偶然复杂度”里的偶然，并不是偶尔发生的故障。它指问题本身没有要求、却被某种实现方式额外带进来的困难。手写能够推导的类型、重复的序列化转换、大量接口胶水和机械配置，都可能属于这一类。换一种语言、框架或生成工具，它们可以显著减少。

本质复杂度则来自问题所包含的概念和关系。以退款为例，解析 JSON 和转换 DTO 是实现工作；已发货后能否退款、怎样处理部分退款、怎样在消费者保护与商家风险之间取舍，才是系统必须回答的问题。即使存在一句 `buildRefundSystem()` 就能生成代码的语言，这些决定仍然没有自动获得答案。

Brooks 进一步用四个性质解释软件为什么难：组成部分存在大量非线性交互；软件必须顺应法律、平台和旧系统等不规则的外部约束；成功的软件总被要求继续改变；而软件又没有一种能同时展示全部结构的天然形状。它们通常被概括为复杂性、顺应性、可变性和不可见性。

这组区分不是给每项工作贴永久标签。同一项数据库一致性问题，对业务人员可能只是技术细节，对负责存储系统的人却可能是必须解决的问题。更实用的判断是：**在当前问题边界内，什么只是表达成本，什么是无论怎样实现都必须作出的决定？**

Brooks 的原始论述可见 [《No Silver Bullet: Essence and Accidents of Software Engineering》](https://www.cs.unc.edu/techreports/86-020.pdf)。他的结论并非“软件永远不可能进步十倍”，而是：如果困难主要来自概念结构本身，就不能期待单一的实现技术普遍消除它们。
:::

:::slide {"kind":"prose","chapter":"complexity","eyebrow":"WHAT REMAINS"}
## 被工具显露出来的工作

AI 迅速压低实现成本以后，眼下最关键的问题越来越集中在：

- 哪些状态应该放在一起？
- 哪些职责必须分开？
- 什么性质必须始终成立？
- 怎样让未来变化停留在局部？

这正是抽象、建模、模块边界与架构设计要处理的工作。

:::detail
这也解释了一个看似偶然的经历：在 AI 还没有今天这么强时，把“提高抽象和建模能力”设为目标；工具剧烈变化以后，这个目标却没有过期。

原因不是预言对了某项技术，而是目标靠近了较稳定的困难。代码生成得越便宜，“系统应该长成什么样”就越难躲在实现背后。一个模块应该拥有哪些状态，谁负责维护不变量，哪些变化可以被隔离，这些判断会直接决定 AI 生成的代码是在加深结构，还是更快地制造混乱。

不过，抽象和建模不是复杂度的来源，而是对抗复杂度的方法。它们也不是把一切包装得更高级。好的抽象删去与当前目的无关的细节，同时保留会影响行为的约束；好的边界让相关变化共同发生，让无关变化彼此隔离；好的架构则使这些判断在系统继续演化时仍然可以被看见和修正。

所以眼下值得训练的并非“设计更多层”，而是从现实规则中找出稳定概念、关系和不变量，再为它们选择最小而清楚的归属。
:::
:::

:::slide {"kind":"prose","chapter":"ai","eyebrow":"THE MOVING BOTTLENECK"}
## 如果 AI 也会设计

假如 AI 能稳定完成领域建模、模块划分、架构权衡与演化分析，软件工程确实可能出现数量级的生产率提升。

但 AI 降低的是**处理本质复杂度的成本**，不一定让复杂现实本身消失。

:::detail
大型支付系统中的法规、银行规则、异常状态、多方利益、历史兼容和持续变化，不会因为 AI 给出了优秀架构就不存在。AI 可能迅速建立多个候选模型、分析权衡、实现并验证它们，让过去需要数月的人类工作缩短到几天；但它处理的仍然是这些真实关系。

这说明“本质”也具有观察者和边界。某些今天受限于人类认知、因而极难处理的概念结构，未来可能被更强的 AI 轻松驾驭。对人而言近似不可消除的困难，未必对所有智能都同样困难。

可一旦建模成本也显著下降，瓶颈不会停止，只会继续上移。以前我们问“怎样写出来”，接着问“系统怎样设计”，再往后就会问：**我们究竟想要什么结果？**

退款策略更保护消费者，还是更防范对商家的欺诈？推荐系统优化点击、停留时间，还是长期满意度和内容生态？这些问题没有脱离目标的纯技术最优解。AI 可以帮助推演后果，却仍需要明确由谁承担代价、公司追求什么、哪些价值不应被指标牺牲。
:::
:::

:::slide {"kind":"flow","chapter":"reality","eyebrow":"BEYOND DELIVERY"}
## 功能不是终点

1. 观察现实中的行为与问题。
2. 建立对用户和业务的模型。
3. 提出一个可被证伪的假设。
4. 用产品、算法或流程实施干预。
5. 测量结果，修正原来的模型。

软件不是闭环的终点，而是改变现实并获得反馈的手段。

:::detail
传统的软件交付流程常在“上线”处结束：需求、设计、编码、测试、上线。但当实现越来越便宜，仅仅证明功能存在，已经不能说明它创造了价值。

真正面向业务的闭环从现实开始，也回到现实。我们先观察用户处境，建立一个暂时的解释，例如“用户离开是因为无法快速找到有价值的内容”；再据此设计搜索、推荐或信息架构；上线后测量行为变化；如果结果不符合预期，就不是继续堆功能，而是回头检查原来的模型。

这里发生了一次重要的能力扩张。过去我们主要为复杂软件系统建模：对象、状态、边界、协作。再往上一层，我们要为复杂现实系统建模：用户为什么行动，多方利益怎样相互影响，一次产品改动会触发什么短期和长期后果。软件成为对这个系统施加干预的工具。

这也改变了“完成”的含义。代码通过测试，只证明实现符合已表达的要求；线上系统稳定，只证明干预可以持续运行；只有现实反馈才能回答，最初的问题判断是否成立，目标是否真的更接近。
:::
:::

:::slide {"kind":"prose","chapter":"reality","eyebrow":"DATA IS EVIDENCE"}
## 数据不会替我们定义需要

数据首先告诉我们：在当前环境和产品机制下，用户做了什么。

它不会自动告诉我们：用户为什么这样做、真正需要什么，或者我们应该优化什么。

:::detail
一个用户连续观看三小时短视频，可能意味着内容提供了很高价值，也可能意味着机制让他难以停止。停留时长上升是一项观测，不是对长期满意度的自动证明。

因此，业务闭环不能简化成“收集数据，然后优化指标”。日志和行为数据帮助我们看见发生了什么；实验与因果推断帮助判断某项改变造成了什么；访谈、用户研究和领域知识帮助解释为什么；公司的使命、规则与伦理边界则决定哪些结果值得追求。

消费者、生产者、平台和监管者的目标经常冲突。过度偏向消费者，可能造成恶意退款和优质商家退出；过度偏向商家，又可能侵蚀信任。数据可以展示不同策略的后果，却不能在没有价值前提的情况下，替组织决定应该由谁承担成本。

所以更高层的工程判断，是把目标、假设、干预和证据连接起来：先说清希望现实发生什么变化，再选择能反映它的指标；既观察短期局部收益，也检查长期副作用；最后允许反馈推翻原来的判断。
:::
:::

:::slide {"kind":"prose","chapter":"reality","eyebrow":"A TRANSFERABLE FRAME"}
## 问题在不断向上移动

```text
机器细节 → 代码实现 → 软件模型 → 业务设计 → 现实反馈
```

每当下一层变得更便宜，上一层就更清楚地成为瓶颈。

:::detail
现在回看最初那个问题——“Kotlin 把变量推断成了什么类型？”——答案不是“类型从此无关紧要”，而是：当工具能可靠处理一项细节时，我们可以把主要注意力移到它所服务的目的上，并在验证或故障要求时再向下追踪。

AI 正把这个变化扩展到更大的实现范围。眼下，它让模块边界、领域模型、架构权衡和验证能力更加重要；如果未来连这些工作也被大幅自动化，注意力还会继续上移到问题定义、价值选择和现实反馈。

面对新的工具，可以用三个问题判断自己的工作正在发生什么变化：

1. 哪些困难只是当前表达方式带来的，已经可以安全地下沉？
2. 哪些概念、关系和取舍无论怎样实现都必须面对？
3. 如果这一层也被自动化，新的决定权会移动到哪里？

这套框架比预测某种语言、框架或 AI 会不会取代程序员更稳定。工具不断变化，但工程始终需要有人确认意图、约束和证据是否连成了一条真实的因果链。
:::

## 从表达意图，到验证现实

> 当写代码不再困难，真正的问题就会变成：我们希望什么发生，又凭什么相信它真的发生了？

INTENT → MODEL → INTERVENTION → EVIDENCE
