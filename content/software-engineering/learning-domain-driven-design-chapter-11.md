## 为什么第十一章紧接着第十章

第十章解决的是“面对当前业务复杂度，应该选择哪种足够简单的设计”。第十一章补上了一个更现实的问题：**即使当初选对了，环境变化以后，它也可能不再正确。**

这对 native-text 的 Common KMP 迁移尤其重要。我们现在看到的边界，并不一定是过去团队判断失误；它也可能是在 Android 单平台、较少业务规则和不同组织结构下曾经合理，只是在鸿蒙接入、跨平台一致性、失败恢复和二次编辑出现后逐渐过期。

因此，评价旧设计不能只问“它好不好”，还要问：

- 它当初解决了什么问题？
- 哪些外部条件已经变化？
- 现在的痛苦来自业务本身，还是来自过期的设计决策？

## 我真正理解的四件事

### 设计决策应该带有失效条件

本章把变化归纳为四种向量：

| 变化向量 | 可能出现的信号 | 需要重新检查什么 |
| --- | --- | --- |
| 业务领域 | 新盈利点、能力商品化、规则复杂度变化 | 子域类型与投入方式 |
| 组织结构 | 团队拆分、异地协作、发布节奏不同 | 限界上下文与集成关系 |
| 领域知识 | 新不变量、边缘情况、旧知识流失 | 模型、命名与边界 |
| 增长 | 聚合变大、上下文变得“话多” | 子域、上下文和一致性边界 |

过去我更容易把架构决策记录成“为什么这样做”。第十一章提醒我，还应该记录“**出现什么信号时要重新评估**”。否则 ADR 很容易变成历史说明书，而不是仍然参与设计的约束。

### 越来越难改，是领域信号，不只是代码质量问题

当一个支撑子域逐渐变成核心子域，原本适合简单逻辑的事务脚本或活动记录会开始吃力。规则、不变量和状态转换不断增加后，重复、分支和不一致也会变多。

这里最重要的不是“看到复杂代码就上领域模型”，而是把痛苦当作调查入口：

1. 业务真的增加了新的本质复杂度吗？
2. 如果没有，是不是旧边界制造了偶发复杂度？
3. 如果有，现有模型是否仍能让非法状态难以产生？

以模板选择为例，请求、展示和参数校验原本可以是简单流程。但加入平台异步写回、失败回滚、过期回调、二次编辑恢复后，只靠一个“当前选中项”和更多布尔值就会越来越危险。`selectedIndex` 与 `committedIndex` 的区分，不只是实现细节，而是在承认业务中存在“用户想要的状态”和“平台已经确认的事实”。

### 知识不成熟时，边界应该允许纠错

本章给出一个很实用的启发式：当领域知识还不清晰、逻辑又经常变化时，限界上下文可以先宽一些；等词义和规则稳定后，再拆成更窄的上下文。

这不是鼓励大泥球。区别在于：

- 宽边界仍然有清晰的内部概念和依赖方向；
- 团队承认边界暂时较粗，并知道未来根据什么信号拆分；
- 不会为了微服务数量提前固化尚未验证的跨服务契约。

对迁移工作也是一样。先把一条完整业务链的状态、事务和副作用看清楚，再决定 Common 与平台的边界，比逐文件判断“能不能放进 `commonMain`”更可逆。

### 迁移要显式承认我们不知道的历史

从普通领域模型迁移到事件溯源时，旧系统通常没有完整历史。本章提供两种方法：

- 根据当前状态尽力推测过去事件；
- 使用 `migrated-from-legacy` 事件，明确表示历史从这里开始才可信。

第二种方式让我印象更深。它表达了一条很重要的工程原则：

> 诚实的不完整，胜过精确的虚构。

这也适用于当前迁移：未指定模块继续走旧链路，Common 只接管已经明确授权的能力。与其把系统包装成“已经全量统一”，不如明确新旧事实从哪一条业务链、哪一个状态转换开始分界。

## 映射到 native-text 迁移

### Common 化是一种设计演进，不是代码翻译

真正的变化向量包括：

- 从单平台实现变成 Android、鸿蒙共享业务语义；
- 团队和宿主拥有不同的发布节奏与平台知识；
- 模板选择出现异步写回、失败恢复和过期请求；
- 首次输入、模板选择、二次编辑和最终 Pack/NLE 写回需要重新划分所有权。

因此，迁移后的设计不需要忠实复制旧类结构。它需要保护旧链路中仍然成立的业务事实，同时淘汰只适用于旧环境的偶发复杂度。

### 用“强一致的最小集合”检查 Session

一个 Session 不应该因为名字方便就持有整条编辑链路的所有状态。可以逐项询问：

1. 哪些状态必须与一次平台写回共同成功？
2. 哪些只是 UI 展示或缓存，可以稍后更新？
3. 失败时必须共同回滚的最小集合是什么？
4. 哪些事实只有平台知道，Common 不应该伪造？

这些答案才决定聚合或事务边界，而不是类文件当前放在哪个目录。

### 用“话多”识别错误边界

如果 Common 每一步都要询问平台当前状态，平台又不断读取 Common 才能决定下一步，问题可能不是接口太少，而是同一个业务事实被拆给了两个所有者。

更健康的形态通常是：

- Common 拥有业务会话、请求代次和可验证的状态转换；
- 平台完成 NLE/Pack 写回、页面生命周期和可见副作用；
- 跨边界传递的是明确命令、结果或错误语义，而不是彼此内部状态的连续镜像。

## 接下来可以怎么做

- 在重要 ADR 中增加“复查触发器”，而不只记录当时的理由。
- 对迁移链路标明哪些旧行为被保留、哪些事实从新实现开始可信。
- 发现复杂分支时，先区分本质复杂度与过期设计造成的偶发复杂度。
- 定期检查 Common 与平台是否变得过度“话多”，以及一个 Session 是否吸收了不需要强一致的状态。
- 当领域知识仍不稳定时，优先保持可逆边界；知识稳定以后，再做更细的提取和复用。

## 一句话总结

第十一章让我把架构理解成一组需要持续验证的假设：**设计不会因为当初正确就永久正确；真正健康的系统，会让过期边界能够被看见、解释并安全地演进。**
